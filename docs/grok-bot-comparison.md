# Grok Bot 功能、界面与运行机制：Jarvis 对比研究（2026-10-26）

> 更新：2026-10-27，Asia/Shanghai。先读结论、改进与预测，再查详细方案和研究依据。已实施部分按首节链接的限定实测判断；其余方案及收益预测仍为 proposed，不因文档和图表完善而视为能力已实现。

<a id="grok-research-recommendation"></a>
## 先读结论、改进与预测效果

**最新实现：**[工作闭环1.4.0结论与图表](evidence/workflow-closure-1.4.0/report.html)：保守返工分析、当前版结案和聊天一致性接通，316项回归、六条界面流程与原开销门在冻结候选中全部通过；保留每轮失败与修复。[实测范围](delivery-validation.md#workflow-closure-evidence)。真实业务质量、通用语义理解、长期学习收益、多Bot接管及生产部署仍待完成。

**验收后进一步深查：**[12 项离线观察](delivery-validation.md#real-work-diagnostic-evidence)确认，文本检查通过仍可能遗漏业务条件；固定措辞也可能误拒正确结果。优先补“要求覆盖 → 可靠入队 → 局部返工 → 默认负责人 → 条件化经验”，再扩大自主范围。[结论、预期效果与原设计相容性](decisions-review.md#real-work-deep-audit) · [可实施的源码切面](core-bootstrap.md#modernization-next-implementation)。本轮新增诊断和方案，未修改生产运行机制，未取得长期质量增益。

**验收入口已具体化并执行：**[一个命令复验本地闭环，再按真实任务与目标领域签收](delivery-validation.md#completion-acceptance-runbook)。新增固定答案核对及事务提交前/后真实测试进程退出；[首轮 170 项测试、界面及原开销门槛通过](delivery-validation.md#completion-acceptance-evidence)。技术通过、生产实际加载和长期收益分别判断。

**最新实际进展：本地文本的“约定验收 → 执行核对 → 迟到纠正 → 暂停错误方法及实际采用 → 新证据复核 → 再次采用”已接通，并补上模块恢复后原任务接续。** 158 项相关回归和实际界面流程通过。原任务账本、许可、执行锁、身份及发布机制继续复用；新方法处理新输入会建立原任务并排队，不复制旧答案。综合质量、长期学习收益、通用多 Bot 和自改造仍未签收。[使用与范围](core-bootstrap.md#completion-loop-runtime) · [实测及未验证项](delivery-validation.md#completion-loop-evidence)。早一阶段的只读观察器及 2.343 ms 局部开销保留为[历史版本证据](delivery-validation.md#outcome-observer-evidence)。

| 这次实际改了什么 | 可观察到的变化 | 不能据此宣称 |
|---|---|---|
| 原目标批准时冻结明确文本条件 | 工具成功但条件不符，不能结案；满足事先完整条件可自动核验 | 已自动理解全部自然语言目标 |
| 反馈、方法和实际采用共享来源引用 | 纠正可阻止错误继续传播；历史效果仍保留 | 任意知识自动归纳或已获得长期收益 |
| 方法暂停后允许带新证据复核 | 错误经验可修正，也不能靠一次认可自动复活 | 每次成长都会单调变好 |
| 既有调度增加有界持久接续 | 模块恢复可接回原工作，取消和撤权仍优先 | 所有故障都会自动修好 |

**闭环审查结论：文本领域已有局部运行闭环，完整自主助手仍未形成可签收的端到端闭环。** 通用目标结案、外部等待、业务补救、通用自愈、评价器校准、多循环协调和累计收益仍有缺口；陪伴、学习与机器人还需各自领域证据。[闭环审查摘要](#jarvis-closure-audit-summary) · [十个缺口及已有基础](decisions-review.md#closure-gap-register)。

**实施结论：改造应嵌入原“三位一体”——定向、协作、观察成长，共用连续身份、任务账本与控制底座。负责 Bot 增强协作，评价/知识增强观察成长，自愈与进化复用原研发及发布。源码有局部基础，但“运行上不破坏”仍需联合验收。** [具体实施与保留目标](#jarvis-implementation-preservation) · [源码改造表](core-bootstrap.md#modernization-code-map) · [逐项影响评估](delivery-validation.md#trinity-design-impact-assessment)。

| 已有基础与下一步 | 然后怎样扩展 | 如何确认没有牺牲原目标 |
|---|---|---|
| 已有事件评价与受限文本闭环；接着补要求覆盖和可靠入队 | 默认负责人、局部返工、报告经验、必要的多 Bot 委派 | 原任务/动作/身份和前台交互不变；评价故障不重做业务 |
| 故障证据接原恢复与研发 | 自愈复测、trial、已授权自动采用 | 自愈与进化不抢发布；候选不能修改自己的准入标准 |
| 一个领域、一条完整闭环 | 按 K0—K6 扩展到模块替换和多节点 | V-TRI、原回归及真实收益同时验证；不以文档完备代替实现 |

**本轮补充的核心判断：越用越聪明，来自“总结有证据的区别、在适用时复用、在不适用时重新判断”；不是记忆越多就必然越聪明。新结构当前分数下降时，可以继续研究，但不能只凭潜力替换稳定服务。** [深度分析与案例](#jarvis-learning-deepening) · [知识库策略](knowledge-learning.md#knowledge-compounding) · [低分改造处理](evolution-release.md#growth-regression-policy)。

| 本轮问题 | 策略结论 | 预期作用与边界 |
|---|---|---|
| 新结构好、当前分数更低怎么办？ | 分别看结构证据、实际交付和新能力；稳定通路继续工作，候选有界修复 | 保留创新空间；不会把暂时低分自动当进步，也不因一次失败永远放弃 |
| 怎样越用越聪明？ | 真实结果 → 纠正差异 → 条件化经验 → 后续检验 → 局部采用 | 少犯重复错；失败和反例同样参与成长，不能保证每次单调提升 |
| 知识库到底作用多大？ | 分层使用、控制变量做有/无及逐层对照 | 找出事实、方法和工具各自的条件性收益；现在没有可据实填写的占比 |
| 相似问题如何更快省 token？ | 小量方法卡、当前变量核对、必要时确定性技能，计入全部成本 | 避免反复从零规划；不以漏掉证据和检查换节省 |
| 怎样防混乱、防变笨？ | 来源谱系、增量总结、条件/反例、失效传播、知识与代码共同恢复 | 限制错误扩散；重复摘要不充当多份独立证据 |
| 怎样防固步自封？ | 先查关键差异，保留竞争方法、近似反例和有界探索 | 熟题可走快路径，条件改变或新题可推翻旧经验 |

**当前最明确的差距是日常交办的产品完整性。** Grok Bot 已公开提供多渠道交办、持续职责、跨应用、例行流程和执行可见性；Jarvis 虽有多个有实测的模块，但通用串联、完整语音、原生常驻入口和长期责任仍不完整。功能清单更长，不能抵消这些使用断点。

**Jarvis 的潜力在于把“长期个人伙伴”和“可核对的行动/记忆/成长”合成一套系统。** 本地优先、模型可替换、来源与用途、受限代码候选和原目标回接已有部分实现基础；它们也带来更高的集成与维护成本，效果仍需真实生活任务检验，不能只靠架构图领先。

建议保留既定产品定位，把 Grok Bot 的交办、接入、可见执行、方法沉淀和事件职责转译到现有 Host、任务、记忆与发布体系中。先让一项真实工作在授权范围内自然完成并可恢复，再扩大工作种类和并行规模。

完整外部来源登记在[本次来源索引](references.md#grok-bot-research-sources)，沿用产品页既有 S353，新增 S359—S379。阅读本工程当前状态，从[根入口](../README.md#start-here)、[运行与能力边界](tasks-agents.md#conversation-action-runtime)、[记忆缺口](knowledge-learning.md#memory-final-gap-register)、[验收记录](delivery-validation.md#conversation-evidence)进入；这些主题页仍是完整规则的唯一权威。

### 改了什么，预计会怎样

![改进到效果的路径：负责人、评价诊断、经验成长和自主委托](diagrams/assistant-improvement-effects.png)

[SVG 放大](diagrams/assistant-improvement-effects.svg) · [唯一图源](diagrams/assistant-improvement-effects.mmd)。以下是设计因果假设，不是完成状态；完整规则由链接指向的主题负责。

| 改进项 | 用户预计感受到的变化 | 成立前提与可能代价 | 后续观察 |
|---|---|---|---|
| [一个工作负责人](tasks-agents.md#task-owner-collaboration) | 少催办、少转述；任务有人跟到交付 | 委派清楚、接管唯一；过度分工会增加延迟 | 独立完成率、协调次数、重复动作 |
| [复用委托与重要性判断](security-sovereignty.md#autonomous-decision-boundary) | 普通事务自己办，需要决定时一次说清 | 授权覆盖具体效果；不能为了少问而漏掉必要决定 | 可避免询问、必要确认漏检 |
| [产物评分与检查](delivery-validation.md#task-outcome-scoring) | 在交付前发现缺项，减少用户返工 | 检查器能发现真实问题；需额外计算和时间 | 首次合格率、错误放行、评价成本 |
| [因果诊断](health-maintenance.md#task-causal-diagnostics) | 出错时看得懂原因，修复更有针对性 | 输入、版本、效果能关联；错误归因可能误导修复 | 定位耗时、未解决故障、复发 |
| [纠正进入经验](knowledge-learning.md#task-experience-learning) | 说过的改法在适用场景真正生效 | 经验正确且召回适当；错误泛化会制造新问题 | 同类错误复发、采用收益、误用率 |
| [Harness² 方法改进](evolution-release.md#harness-learning-loop) | 难任务有机会采用更有效的方法 | 可重复探测、独立验证、成本有界；不保证每次更好 | 任务质量变化、额外成本和回归 |
| [陪伴与学习](interaction-persona.md#task-companion-experience) | 后台办事时仍能交流；教学跟随真实掌握情况 | 前台资源、正确记忆和真实复测；不能只靠语气评价 | 打扰反馈、延迟复测、连续交流 |
| [多机器人协调](architecture.md#embodied-multi-agent-brain) | 一个目标可协调多个数字/实体执行者 | 先有设备能力和本地保护；增加通信与物理复杂度 | 模拟协作、冲突/断网/旧命令处理，实机另验 |

### 预测与实测对照看板：先登记预期，以后填入事实

**预测版本 r1，登记日 2026-10-26；全部新增效果待实测。** [r1 固定快照](evidence/assistant-forecast-r1-2026-10-26.json)保留本次原预测，后续另增版本。下表数值是本项目的低置信工程假设，用于决定值得验证的提升量级；不是既有测量推算、统计置信区间、性能承诺或发布门槛。当前缺少匹配基线，不给 Jarvis 编造一个当前总分。论文成绩也不能换算成这里的预测。

| 预测编号／改进 | 主要指标 | r1 预测增益或方向 | 匹配基线 → 改后实测 | 与预测的差距／结论 |
|---|---|---|---|---|
| <a id="jpf-01"></a>JPF-01 负责 Bot | 已授权普通任务独立完成率 | 增加 **3—10 个百分点** | 未测 → 未测 | 待验证 |
| <a id="jpf-02"></a>JPF-02 委托决策 | 每任务可避免询问次数 | 相对减少 **20%—40%** | 未测 → 未测 | 待验证 |
| <a id="jpf-03"></a>JPF-03 产物检查 | 首次交付合格率 | 增加 **3—8 个百分点** | 未测 → 未测 | 待验证 |
| <a id="jpf-04"></a>JPF-04 因果诊断 | 故障定位中位耗时 | 相对减少 **20%—40%** | 未测 → 未测 | 待验证 |
| <a id="jpf-05"></a>JPF-05 经验复用 | 适用机会中的同类错误复发率 | 相对减少 **15%—35%** | 未测 → 未测 | 待验证 |
| <a id="jpf-06"></a>JPF-06 Harness 方法改进 | 可重复困难文档任务的质量 Q | 增加 **2—6 分／100 分** | 未测 → 未测 | 待验证；另看探测成本 |
| <a id="jpf-07"></a>JPF-07 陪伴与学习 | 可选打扰反馈、延迟复测表现 | 方向：更少不合时宜打扰、学习保持改善；**暂不设数值** | 未测 → 未测 | 需个人长期观察 |
| <a id="jpf-08"></a>JPF-08 多机器人 | 联合任务及冲突/断网场景 | 方向：具备可验证协调；**暂不预测硬件成绩** | 未测 → 未测 | 先模拟，实机单独登记 |
| <a id="jpf-09"></a>JPF-09 JPF-01—05 联合接入 | 资料研究与文档交付的质量 Q | 增加 **4—8 分／100 分** | 未测 → 未测 | 待验证；不是单项收益相加 |

数值的适用边界：先限定任务域、工具能力和有效授权；JPF-04 仅针对可重现且可定位的故障集合，未解决故障另外计入；JPF-05 只比较确实有适用经验的再次出现机会；JPF-06 不含真实副作用重复执行。基线已经接近上限时，增益受上限约束；基线为零时，不能计算相对减少百分比。完整指标口径与成本约束归[预测实测协议](delivery-validation.md#forecast-validation-protocol)。

**读表例子：**若后来测得 JPF-09 同量表基线为 68 分，r1 对应的条件预测是 72—76 分，而不是“已经达到 76 分”。实际得分与样本不确定性都取得后，才能判断低于、符合或好于预测。各项预测存在交互和重叠，不可把百分比、百分点和质量分相加。

目前所有“改后实测”均留空；已有并发和短文本工作流证据保留在[当前基础](#jarvis-current-gaps-update)，不能挪作上述改造的效果证明。[实测登记入口](delivery-validation.md#forecast-actual-register)给每个预测编号保留记录位置。以后每次相关实现追加原始证据和评估，再更新本表的摘要与链接；原 r1 预测不能覆盖改写。

### 以后怎样判断低于、符合或好于预测

![预测、同条件实测、差距判定与复盘的闭环](diagrams/assistant-forecast-validation.png)

[SVG 放大](diagrams/assistant-forecast-validation.svg) · [唯一图源](diagrams/assistant-forecast-validation.mmd) · [完整判定规则](delivery-validation.md#forecast-gap-judgement)。

| 实测情况 | 文档应怎样写 | 接下来怎样处理 |
|---|---|---|
| 同条件、硬条件通过，实际增益明确低于预测范围 | 低于预期；列出差距和仍然取得的收益 | 区分机制无效、实现不完整、任务不适用与成本问题；修复或保持原版 |
| 实际增益与不确定性均落在预测容差范围 | 符合预期；限定任务域和版本 | 按已有发布条件采用，继续观察，不外推全部能力 |
| 实际增益明确超过预测上界 | 好于预期；解释来自哪项证据 | 用保留任务复测；排除样本偏差、评分泄漏和成本换质量 |
| 只有点估计较好，区间宽或样本不足 | 初步倾向，尚不能定论 | 补样本，不把“没证明有差”写成“已证明相同” |
| 量表/任务/预算不可比，或关键条件失败 | 不可比较／未通过；不计算一个漂亮增益 | 修复实验或回退，保留失败记录 |

本轮完成了文档重排、预测登记和图表，**没有运行这些改造的业务实验**。维护与渲染记录见[本轮回执](evidence/assistant-forecast-documentation-2026-10-26.json)。

## 深度审查：这些循环是否真的接上，还有什么遗漏

**答案是“局部链条有实现基础，完整闭环尚未证明”。** 三位一体、任务负责、评价、知识和发布的职责已经能对齐，但职责齐全与每次交接都可靠是两件事。完整审查及源码依据统一在[闭环审查页](decisions-review.md#closed-loop-audit)，这里先列结论。

![闭环不仅有正常交付，还要接回等待、失败、纠正与后续经验](diagrams/assistant-loop-closure.png)

[SVG](diagrams/assistant-loop-closure.svg) · [唯一图源](diagrams/assistant-loop-closure.mmd)。图示 proposed；每条回接都需当前目标/权限/版本与实际效果核对，不表示本轮启动了后台任务。

| 必须接住的交接 | 已有设计/基础 | 仍需落实的关键点 |
|---|---|---|
| 工具成功→用户目标达成 | 原 Task 回执、结果量表 | 逐条目标证据对账；执行完成、质量和交付分开 |
| 暂时做不了→以后可靠接续 | 等待/取消/资源规则 | 持久等待关联、事件水位、丢失唤醒竞态、到期与无进展处理 |
| 模块修好→原工作继续 | 包恢复与受限研发回接 | 恢复事件接原等待；取消、撤权、UNKNOWN 和版本变化时重新判断 |
| 交付完成→迟到纠正→经验修订 | 成果引用、原件失效和纠正 | 知道哪些后续步骤采用了该经验，修订评价并核对已交付影响 |
| 自动评价→值得相信的评价 | 独立测试、量表与审阅 | 误放行/误拒绝、争议和漂移校准；分数变高可能只是评委变了 |
| 单次改进→长期越来越好 | 有界试验、保留集和回退 | 固定参照、累计退化、组件组合及多循环互相干扰 |
| 文本工作→全功能个人助手 | 陪伴、学习与设备设计 | 长期掌握、体验反馈、真实触发和物理效果分别验证 |

已有的总预算、撤权、反例、回退与组合验收并未被忽略，本次细化其交接与共同失败场景。重要新增反例是：每次只比上版下降一点，长期却越来越差；或者代码恢复了，已经造成的业务后果仍未收尾。[累计退化](evolution-release.md#cumulative-evolution-guard) · [业务补救](tasks-agents.md#business-remediation-closure)。

后续仍按[原实施工作包](core-bootstrap.md#closure-stage-integration)推进。[本地文本场景](delivery-validation.md#completion-loop-evidence)已覆盖正常、失败、等待、取消、重启、纠正和恢复；[V-CLC-01—10](delivery-validation.md#closure-validation-cases)完整联合场景尚未整体运行，没有编造闭环百分比、业务评分或新的收益预测。

<a id="jarvis-trinity-integration"></a>
### 三位一体和新增能力是什么关系

![三位一体保留原身份与控制底座，新增责任、评价和学习接在原链上](diagrams/assistant-trinity-integration.png)

[SVG 放大](diagrams/assistant-trinity-integration.svg) · [唯一图源](diagrams/assistant-trinity-integration.mmd) · [核心不变量](architecture.md#trinity-change-invariants)。图表示拟接入职责和证据流，不证明当前隔离、自动成长或模块替换已实现。

定向面理解主人目标、优先级和取舍；协作面通过负责 Bot 推进工作并交流；观察成长面从真实结果中提出评价、故障、经验和改进。三者使用同一连续身份，既不要求三个常驻模型，也不让负责 Bot 成为新的最高权威。自检、自愈、进化是管理流程，不能替代三职能的产品分工。

| 原目标 | 此次改造怎样保持并增强 | 最容易破坏目标的错误接法 |
|---|---|---|
| 三位一体 | 定向→原 Goal/Plans；协作→负责人/原 TaskRuntime；观察成长→评价/知识/故障 | 另建总经理 Agent 同时拥有任务、权限、评分和发布 |
| 自评估 | 任务产物评价与包准入评价分开，均链接真实证据 | 执行者自述成功，或用代码测试分代替用户任务质量 |
| 自愈 | incident 去重，先恢复，再原故障复测；代码修复复用研发器 | 每次失败都改代码，恢复动作结束就关闭故障 |
| 自改造、自进化 | 现有候选→独立检查→发布→原目标回接，增量接自动策略 | 永久只能建议；或为自动化直接删除现有发布检查 |
| 模块独立 | 单一状态写入者、有界队列、可选模块可关闭、兼容替换 | 所有逻辑塞进 Core；学习服务宕机使所有工作停止 |
| 越用越聪明 | 经历和纠正变成可检验方法，适用检查、反例和失效传播 | 复制摘要、热门经验锁定、新知识未经验证直接控制动作 |

因此，原设计目标不需要推翻；真正需要改的是接线、状态关联、模块管理与可核对的行为。但“理念兼容”只能得出设计层结论，不能推出实现不会破坏原机制。[完整影响评估](delivery-validation.md#trinity-design-impact-assessment)。

<a id="jarvis-learning-deepening"></a>
## 深度补充：怎样越用越聪明，避免越改越差

**2026-10-26，设计 proposed；本节没有新增运行成绩。** 原 JPF/r1 预测保持不变。本轮补齐它们成立所需的学习、知识治理和退化处理机制，不把这些补充算成预测已兑现。

<a id="jarvis-learning-definition"></a>
### “聪明”应表现在哪里，而不是只看总结和记忆数量

对 Jarvis 而言，持续成长至少有四种不同结果：记得更准确；遇到熟悉问题能少走弯路；发现条件变化时不误用旧方法；在能力缺口出现时能生成并验证新方法。模型权重不变，也可以通过资料、上下文、工具和流程改善这四项；这不等于模型本身已完成训练或获得通用自主智慧。

Google 的 ReasoningBank 从成功与失败经历中提炼方法，说明失败经验也可以有用；其官方介绍同时说明用了模型自评和简单追加，不能据此认为经验正确性与整库治理已经解决。ACE 强调条目化增量，避免反复整体重写丢失细节。这些研究支持方向，Jarvis 仍需自己的适用条件、真实证据和独立检查。[ReasoningBank](https://www.research.google/blog/reasoningbank-enabling-agents-to-learn-from-experience/)、[ACE](https://arxiv.org/html/2510.04618v1)。

因此，成长不是“每次完成后总结一大段”，而是每次有新证据时更新正确的记录，再验证它是否改变后续行为。没有新信息可以不总结；没有后续适用机会，不能提前把经验标为有效。只增加反思 token、总结字数或知识条目，很可能只是更多开销。

<a id="jarvis-regression-analysis"></a>
### 结构很好但改后低分：研发可以继续，默认服务不必一起退步

![结构潜力与当前表现分开，稳定服务与有界候选研发共用发布底座](diagrams/assistant-growth-regression.png)

[SVG 放大](diagrams/assistant-growth-regression.svg) · [图源](diagrams/assistant-growth-regression.mmd) · [完整处理规则](evolution-release.md#growth-regression-policy)。

“结构很好”也需要证据：故障是否更容易定位、修改是否更局部、恢复是否更可靠、能否增加旧版做不到的能力。只有架构图漂亮，不能证明值得继续投入。另一方面，刚完成迁移的候选可能因少数实现缺陷拉低成绩，不能只凭一次平均分否定整个方向。

| 情况 | 合理决定 | 不应做的事 |
|---|---|---|
| 结构收益有证据，失败集中且可修复 | 在原研发预算内继续修复，保持稳定路径 | 用“新架构先进”直接替换日常交付 |
| 新能力成立，但旧能力退化 | 新能力单独验收，必要时限定路由 | 改评分权重，把旧问题藏进平均分 |
| 评分方法变化或基线虚高 | 按同一量表重新比较两者，保留原结果 | 直接比较不可比数字，或坚持使用错误旧分 |
| 反复修复仍无净收益 | 缩小范围、替换假设或停止候选 | 以已经投入很多为由无限追加预算 |
| 新版数据/经验污染旧行为 | 隔离受影响知识和检索，检查恢复组合 | 只回退代码，继续引用错误经验 |

可采用的增量路径是让一段新方法在原接口后验证，取得证据再扩大，最终退役被替代路径。稳定与候选只是同一系统的运行/实验状态，不是精灵一套、工作台一套或两个长期竞争的 Jarvis。影子任务不真实下单/发送，不让两个版本争抢同一动作所有权。

这也回答“不改可能永远不进步”的顾虑：保护日常服务，并不阻止有预算的实验失败。研发资格依据结构假设和学习价值，生产采用依据实际效果；两者不能互相替代。有限测试无法保证永不变差，但可以使退化更早暴露、影响更小，并保留继续尝试的能力。

<a id="jarvis-knowledge-contribution"></a>
### 知识库处在整条任务链的什么位置，当前基础到了哪里

知识库应在开始前提供相关证据和方法，在执行中补缺口，在失败后辅助定位，在完成后接收经过核对的经验。它既不只是聊天历史搜索，也不是能直接发布命令的权威。

本轮只读发现，现有实现已经有关键词/语义候选融合、来源引用候选、版本与目的地核对等基础。具体如 [retrieval.py](../modules/context_knowledge/retrieval.py) 中词项/近邻融合，[claims.py](../modules/context_knowledge/claims.py) 中原文引用验证和候选审阅，以及 [goal_context.py](../host/goal_context.py) 中目标绑定与失效检查。读取到的检索源码标为 1.1.0；部署及效果仍按对应实际证据，不能从类名或版本号推出完整学习闭环已经实现。

当前主要缺口是：把任务经历归纳为带条件和反例的方法、在下一任务判断是否适用、核对它到底省了多少成本或减少多少错误，以及错误经验影响后的系统性恢复。已有资料库和向量检索为此提供基础，不应全部重写成另一套“智能知识中心”。

| 任务瓶颈 | 知识库能帮助什么 | 单靠知识库不能解决什么 |
|---|---|---|
| 缺事实/资料 | 找到来源和已核对信息 | 资料本来没有、过期或无权读取 |
| 重复规划和重复错误 | 提供条件化方法、反例和检查清单 | 模型无法理解关键差异 |
| 重复计算/操作 | 支持提炼成确定性技能 | 没有工具、权限或真实执行能力 |
| 故障难定位 | 关联类似失败、版本和已知修复条件 | 外部服务不可用、真实效果未知而无法对账 |
| 长期适应主人 | 提供可纠正的情境偏好和共同经历 | 用历史偏好代替当前明确意图或无限推断人格 |

它的实际贡献可能很大，也可能为负。必须比较无长期经验、事实检索、原始经历、条件化方法、差异检查和已验证技能等配置；同时固定当前任务资料与其他能力。完整方案比不查库更差，可能是检索噪声、过期内容、错误总结、适用性错误或模型误读，需要逐层定位，而不是默认增加库容量。[分组对照与归因](delivery-validation.md#knowledge-value-ablation)。

<a id="jarvis-conditional-learning"></a>
### 从同类经验得到方法，但不把方法变成定式

![先检查当前条件，再复用或探索；只把有新证据的经验增量纳入知识](diagrams/assistant-knowledge-reuse.png)

[SVG 放大](diagrams/assistant-knowledge-reuse.svg) · [图源](diagrams/assistant-knowledge-reuse.mmd) · [条件化复用规则](knowledge-learning.md#conditional-experience-routing)。

好的总结应说明“为何有效、什么前提、怎样检查、什么情况下不能用”。它应更像条件分支和可证伪假设，而不是“以后碰到这个词就做同一个动作”。

**假设案例：网页采集返回空内容。**

| 经验写法 | 下次容易发生什么 | 应保留的区别 |
|---|---|---|
| “空内容就重试三次” | 登录过期、结构变化和权限问题都被当作网络抖动 | 结果一样不代表原因一样 |
| “先区分未加载、身份失效、目标结构变化；仅对允许且可重试的暂态失败有限重试” | 根据当前证据选择处理，避免重复无效动作 | 记录页面状态、工具版本、错误证据和不可重试条件 |
| “本次检查发现原因是结构变化，旧方法不适用；新解析候选经样本验证后采用” | 原经验被补充条件或分成新分支 | 新规则仍有验证范围，不升级成万能答案 |

同类经验的“共同点”用于提高效率，“关键不同点”用于避免犯错。聚类后要寻找反例；同义重述可以合并，版本或条件不同必须保留分支。多个 Bot 转述同一错误不增加可信度。知识的权威来自来源和验证，不来自它被检索了多少次。

快路径可以只读取短卡与必要证据，但要保留退出条件。遇到新版本、关键约束缺失、矛盾、反复纠正或明显新问题，就转入复核/研究。Self-RAG 的研究支持按需检索而非无条件拼接；原方法包含专门训练，Jarvis 这里只借鉴选择与检查思想，不能声称已经复现。[Self-RAG](https://arxiv.org/abs/2310.11511)。

<a id="jarvis-knowledge-cost-and-order"></a>
### 让知识成为资产：增量整理、按需读取、按真实收益付出成本

整库不应是一篇越来越长的总提示。先按来源和类型保存，再通过主题目录、条件化方法卡和必要原件提供上下文。长上下文的内容位置及无关材料可能影响模型使用证据，应在本模型和任务上验证；不能把“上下文放得下”当作“理解得好”。[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)。

| 策略 | 预期收益 | 代价与限制 |
|---|---|---|
| 只形成有价值的局部增量 | 减少重复总结和遗失旧限制 | 要识别是否真的有新信息，必要时回查来源 |
| 目录 → 方法卡 → 原件的渐进读取 | 降低无关上下文，保留深挖能力 | 索引、版本与引用必须可靠 |
| 把稳定重复步骤变成技能/检查器 | 少重复推理、结果更可复现 | 有构建、验证和维护成本 |
| 不同条件保留多个方法 | 兼顾速度、质量、离线或不同工具环境 | 需要清晰的适用性选择，不是所有方法一起塞入 |
| 保留负例与有界挑战试验 | 减少固步自封，发现替代方法 | 额外成本只用于明确不确定性，受预算限制 |
| 暂停/修订坏经验并修复派生视图 | 阻止错误持续扩散 | 恢复不能复活已遗忘内容，已外发效果另行处理 |

最终应算“每个合格交付的完整成本”，同时保留失败任务的花费。少了主回答 token，却多了昂贵的总结、查询和反复验证，可能并不更省；读得少而错误更多则更不划算。方法形成成本要由后续真正适用的任务摊销，短期不回本也要诚实记录。[成本与回本示例](knowledge-learning.md#knowledge-token-economics)。

<a id="jarvis-learning-implementation"></a>
### 怎样接到现有系统，怎样验证没有越学越差

| 既有位置 | 本轮细化的增量 | 先验证的结果 |
|---|---|---|
| 任务结果与 OutcomeAssessment | 关联实际采用的经验 ID/版本及纠正差异 | 能解释某条经验是否影响结果，避免假记功 |
| TaskEpisode／知识候选 | 归纳条件、原理、反例和来源谱系 | 同义重复不膨胀，错误归纳不自动进入默认视图 |
| 现有检索与目标上下文 | 先过滤，再检查关键差异；按需展开 | 熟悉题节省，近似反例拒用，新题能重新研究 |
| 原知识生命周期与发布 | 局部修订、失效、知识/索引版本与候选隔离 | 候选失败不污染稳定服务，恢复不复活撤销数据 |
| 既有评估与成长通路 | 分层对照、成本归因、非退化与有限探索 | 有益才扩大；失败有诊断价值但不伪装成升级 |

实施沿 K0—K6，不另建路线：K0 先冻结契约、反例和指标，K1/K2 接关联记录与有限复用，K3/K4 扩大归纳和已验证技能，K5 才替换自身检索/规划模块，K6 再扩展多节点。阶段归属仍以[原路线](core-bootstrap.md#task-learning-stage-placement)为准，不需要等完整知识系统成熟才验证一条真实闭环。

最小可交付闭环应同时证明三个场景：**该复用时更快、更省且质量合格；不该复用时能拒绝旧方法；经验错误时能纠正并停止传播。** 少任何一项，都不能宣称“越用越聪明”。新增 [V-KLG-01—10](delivery-validation.md#learning-validation-cases)及知识贡献实验均保持未运行。

本轮策略归纳是：保护已验证能力，让候选能失败；把总结写成可检验的方法，让方法能被推翻；让知识按需进入行动，并以真实收益决定保留和扩大。当前没有证据保证单调进步，也没有为知识库编造收益占比或 token 节省成绩。[研究来源](references.md#learning-compounding-sources) · [本轮文档证据](evidence/learning-knowledge-strategy-2026-10-26.json)。

<a id="jarvis-autonomy-deepening"></a>
## 设计深化：从交办工具走向长期个人助手与多机器人主脑

**日期：2026-10-26。产品方向来自主人本次明确要求，标记 accepted；下列新增机制及实验仍为 proposed。** 本轮完成研究与文档细化，不把设计文字、流程图或已有局部模块算作新增功能已经运行。总体结论是：Jarvis 在长期目标覆盖和可控制的成长方式上，有超出 Grok Bot 公开产品范围的设计；当前缺口主要在统一闭环和稳定体验，而非缺更多 Bot 名字。

<a id="jarvis-goal-advantage"></a>
### 哪些理念和目标有超越空间

“超越”应分别理解为目标范围、设计约束和实测能力。前两项可以比较，第三项需要相同任务、预算、工具权限和评价方法的对照。没有查到某项公开承诺，也不证明 Grok 内部绝对没有相关能力。

| 方向 | Jarvis 已有目标或基础 | 相对 Grok Bot 公开描述的区别 | 成为实际优势还缺什么 |
|---|---|---|---|
| 长期个人伙伴 | 跨模型延续身份、共同经历、偏好和承诺；工作与陪伴同等重要 | 产品重点从多个工作角色扩展到个人长期关系及生活/学习；Grok 也有记忆和持续职责，不能说它完全不理解用户 | 跨月体验、准确接续、隐私与遗忘、不中断交流的真实验证 |
| 数据和模型自主性 | 本地优先、可替换模型、资料用途/来源、离线退化 | 用户更能控制资料与依赖；Grok Bot 采用受管云端运行和模型路由 | 普通 PC 成本、稳定安装升级、离线可用性；本地不天然比云更安全 |
| 有证据的能力成长 | 能力缺口回到原目标，受限候选、检查、发布和回退 | 目标超出仅保存偏好或复用步骤，包含改方法和受控替换自身模块 | 通用评价、经验真正复用、多个任务域的收益与防退化 |
| 行动可信度 | 原任务账本、取消/恢复、未知结果不盲重放、权限与预算单独校验 | 强调“真实发生了什么、谁负责、怎样恢复”的可审查约束 | 长运行、跨服务/设备、故障注入和接管验证；文档严格不等于实测更可靠 |
| 多助手与多机器人 | 一个个人核心统筹专业角色和不同设备 | 比 Grok Bot 当前公开的数字工作协作目标更宽，包含具身任务与本地保护层 | 世界状态、设备协议、分布式所有权、硬件级安全与逐设备验收 |

上述是**面向长期使用的设计差异**，并不是证明 Jarvis 模型智力更高、办公成功率更好或机器人控制领先。Grok 的公开优势仍是交办入口、连接器、云端持续执行、跨应用成果和多渠道协作的整合；Jarvis 的这些链路目前更分散。来源依据见 [S359—S379](references.md#grok-bot-research-sources)，Jarvis 目标权威为[产品细化](product-requirements.md#autonomous-assistant-north-star)。

<a id="jarvis-current-gaps-update"></a>
### 先校正当前基础，避免把已有机制重做一遍

第一次报告之后，本轮读取到[有界并发 1.0.0 证据](delivery-validation.md#bounded-concurrency-evidence)：已有默认两槽调度、独立聊天通道、原任务排队/取消/恢复，以及限定负载的回归和浏览器检查。该记录还声明了主服务加载情况。因此不再把并发描述为仅发现源码；同时，正式持续性能结果在本轮读取时仍待登记，不能外推重 GPU、所有供应商、所有设备或任意任务都不影响聊天。

[英语学习与日志复盘](delivery-validation.md#personal-workflows-evidence)也已有短文本真实调用证据；这不是长期学习效果或情绪陪伴整体验收。现有[目标经验候选](knowledge-learning.md#goal-memory-runtime)已能从回执形成候选，但主要仍是待核对摘要，尚非“每次纠正后自动变成高质量可复用方法”。原报告提到的记忆质量缺口仍不能因新增 Bot 或 Harness 方案而视为解决。

当前最需要补齐的是四段连接：**有人负责到底、成果能被检查、纠正能进入下次行为、有效改进能安全采用。** 原调度、记忆和成长模块是这些连接的基础。

<a id="jarvis-multi-bot-design"></a>
### 多 Bot 应怎样协作：一个对外负责人，按需组织内部工作

建议保持一个主人认识的 Jarvis，设置少量清晰的专业职责入口，例如工作、研究、学习和生活；每项实际工作选定一个负责 Bot，内部按需要使用专业执行者和检查者。用户交办后，不需要自己挑选每一个执行者、复制上下文、催进度或合并答案。

| 设计选择 | 收益 | 代价与适用限制 |
|---|---|---|
| 单个负责 Bot＋少量执行者 | 责任、进度、返工和交付入口清楚 | 负责人可能成为瓶颈；用持久状态、可接管所有权和轻量计划控制 |
| 多个角色共享原任务底座 | 保留原恢复与预算，避免重复执行 | 需要任务任期、委派边界和资源冲突管理 |
| 独立检查角色 | 发现遗漏与偏差，减少“自己觉得做完了” | 增加成本；同模型相互赞同不是独立事实 |
| 简单任务单执行者 | 延迟和费用低，排错直接 | 复杂跨领域任务再增加协作，不强求每项任务组成团队 |

例如“研究一种机械结构并交付说明和模型”：研究执行者核对资料，建模执行者制作资产，检查者验证尺寸/引用/可打开性，负责 Bot 整理交付并接收后续修改；实际专业质量必须由对应验证证明。模型服务按任务选择和预算调用，一个 Bot 不必常驻占一份模型。

完整职责、接管、迟到结果、原任务修订与迁移规则只维护在[单负责人协作](tasks-agents.md#task-owner-collaboration)，数据归[增量契约](contracts.md#task-learning-records)。

<a id="jarvis-autonomy-and-diagnostics"></a>
### 更自动与更容易排错，需要同时推进

“不重要的事务不找主人决策”应落实为可复用委托和明确边界：系统知道哪些目标、对象、额度和效果已经获准，普通步骤自动完成；新承诺、越界或关键事实缺失才提出具体问题。缺少某个决定时，先完成能独立进行的部分。不能一方面声称全自动，另一方面每轮都要求用户批准分工、检查和保存经验。

也不能通过不询问来掩盖不确定性。允许自动发送某类例行消息与允许任意对外承诺是不同授权；一次性同意与长期委托也需区分。既有 Gmail 等通道的现行限制，在对应实现和验收完成前仍有效。详见[自主决策边界](security-sovereignty.md#autonomous-decision-boundary)。

排错要从产物缺陷回溯任务、子任务、动作、输入来源、能力版本和检查证据，区分理解、检索、分工、工具、环境、资源和代码问题。频繁失败不应自动等同于“需要改源码”。给用户展示当前影响和下一步，给开发视图保留可重现依据；详见[任务因果诊断](health-maintenance.md#task-causal-diagnostics)。

<a id="jarvis-scoring-and-memory"></a>
### 每次评价、修改后记住，怎样才会越用越好

应把“完成状态”“成果质量”“评价证据”“未来经验”分开保存。工具返回成功不证明文件可用；一项任务得到高分也不证明其方法能推广。每项工作有评价记录，但证据不足可以待评，不能让模型凭自信编一个 96 分。

[评分设计](delivery-validation.md#task-outcome-scoring)给出可配置维度、硬条件、示例计算及不同任务的口径。评分不是目标本身，作用是找到具体缺陷、选择返工与比较长期收益。必要确认不能扣成“自主性差”，用户改变要求不能全部算系统失败，取消也不能污染质量统计。

修改应形成三种不同结果：本次成果更正；下次相同情境的经验；经过跨任务验证后的稳定方法。并不是所有纠正都升级为全局规则。例如“这份报告不要图表”未必表示主人永远不喜欢图表。经验要带适用条件、反例和来源，能被纠正、撤回或遗忘。

真正的成长指标是后续同类任务的首次合格率提高、重复错误减少、少重复交代、成本合理，且原有能力没有退化。[经验闭环](knowledge-learning.md#task-experience-learning)负责怎样记录与使用，[联合验收](delivery-validation.md#task-score-learning-validation)负责怎样证明；不以数据库越来越大或每天改代码证明成长。

<a id="harness2-analysis"></a>
### Google Research Harness²：值得借鉴的具体内容

已核实为 Google Research 仓库 [harness2](https://github.com/google-research/harness2/tree/1cfe254e8d25b15f37048c3730134686abe60335)，不是泛指 agent harness，也不是现成机器人主脑。本轮固定提交 `1cfe254e8d25b15f37048c3730134686abe60335`，只读论文、说明和部分核心源码；没有安装或运行。

论文提出两层循环：当前任务中提出改法、执行探测并按行为差异组合；任务之间保留有证据的方法与经验，影响后续改进。模型权重保持不变；每个新任务从共同执行基线开始，按需吸收历史经验。作者明确指出行为对照不等于正确性证明，选中某个结果也不等于方法已经最优。[论文方法部分](https://arxiv.org/html/2610.14224v1#S2)。

| 借鉴点 | 对 Jarvis 的价值 | 接入与限制 |
|---|---|---|
| 通用方法候选＋领域候选 | 区分“工具使用/规划有问题”和“专业方法有问题” | 通过已有改进单提出；不把所有失败归因于提示词 |
| 先运行探测，再组合 | 从真实产物差异判断改法是否有用 | 仅在可重复、隔离的实验里比较；真实副作用不能重复试 |
| 保存被采用的方法及条件化经验 | 下次能重用有效组件，同时知道何时不适用 | 接现有分域记忆和版本化能力包，不复制第二套任务核心 |
| 保留稳定基线，选择性使用经验 | 避免上一任务特例污染所有后续任务 | 有条件检索、验证适用版本，错误经验可撤销 |
| 独立评价与可复现运行记录 | 区分“被选中”和“真的更好” | 冻结模型、环境、资料和保留集，记录额外成本 |

仓库说明与源码提供了重要实施细节：同领域任务按顺序读取先前经验，不跨用未来任务记录；经验条目要求线索、教训和证据，保存完整采用方法供按需检查。Jarvis 可以借鉴其证据关联，但不应把整个经验树默认塞进上下文。[实验说明](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/docs/EXPERIMENTS.md)、[经验库源码](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/library.py)。

成本需要正视：该版本递归实现说明一次预算 k 对应 4k 次任务执行和 3k 个改进阶段，重试、选择与外部评估还可能增加工作；不能把 k=1 理解为只多一次普通回答。并行降低部分等待时间，却不消除计算费用。[递归实现](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/recursion.py)。因此本项目建议低成本任务直接走稳定方法，重复失败或高价值任务再启用有界探测。

尤其不能照搬实验运行边界：仓库说明默认未限制网络，并提示公开评分材料可能被执行者取得；Codex 实验还关闭了沙箱。这不适合作为个人长期助手的默认配置。Jarvis 应保留既有隔离、权限、隐藏保留集与发布控制；论文中的 prompt guardrails 不等于本系统的确定性网关。[实验环境与泄漏说明](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/docs/EXPERIMENTS.md#web-access)。

**适合借鉴方法，不适合整包替换 Jarvis。** 研究针对有限专业基准的结果不能直接推导生活助手、情绪陪伴、长周期成长或机器人效果；其许可证及第三方依赖也须在真正引入代码时重新核查。具体接入规则归[双层方法改进](evolution-release.md#harness-learning-loop)。

<a id="jarvis-change-impact"></a>
### 哪些要改进，会不会影响现有机制

下表的“优先”是投入判断，实施仍按 K0—K6；不是另立开发时间线。**本轮仅改文档，没有改变运行机制；未来实现会改变接口和行为，必须逐项兼容，不能承诺零影响。**

| 改进 | 现有基础与缺口 | 影响与主要风险 | 兼容／退出方式 |
|---|---|---|---|
| 优先：负责 Bot 与委派 | 有任务/并发，缺通用负责到底与接管 | 双负责人、重复效果、预算重复计算 | 原任务加关联字段；新任务先用，任期隔离；在途任务不强迁 |
| 优先：任务评价与证据 | 有领域测试和回执，缺统一产物评价 | 自评失真、额外时延、分数掩盖失败 | 先只读投影；评价失败不重放已完成动作；保留明细 |
| 优先：因果诊断与问题卡 | 有日志/故障治理，缺贯通的用户可读问题定位 | 日志隐私、噪声、无据归因 | 关联 ID、脱敏引用、有限保留；故障结论可修订 |
| 优先：纠正进入经验检索 | 有分域记忆/经验候选，缺普遍自动采纳与效用测量 | 错误规则积累、跨域泄露、遗忘不彻底 | 候选/采用分离，明确条件与失效关系，保留失败反例 |
| 随上述接入：委托策略自动决策 | 已有授权和预算，缺一致的“何时自己做”体验 | 少问变成漏问，或保守到处打断 | 先影子判定，再限定任务域启用；沿用现行通道约束 |
| 在闭环成立后：Harness 方法改进 | 有受限研发和发布，缺通用对照、方法库与保留集 | 高费用、过拟合、污染评分、自我强化错误 | 固定评估边界、限定候选预算、独立检查和既有回退 |
| 核心体验持续补齐：陪伴与学习 | 有文本交互和两个短工作流，缺长期效果 | 关系记忆错乱、无效主动提醒、只会鼓励不会教 | 分开任务/情绪/学习记录，偏好可改，按真实使用验收 |
| K6 按能力扩展：多设备与机器人 | 有组合设计，缺实机与群体控制证据 | 双指挥者、陈旧感知、物理风险、网络中断 | 高层主脑＋本地控制；先模拟，再逐设备验证 |

不应被替换的基础包括：唯一任务与回执来源、G0 和权限网关、根预算、取消/恢复与 UNKNOWN 语义、记忆域和遗忘、单一发布/回退事务。新机制引用这些事实，不再维护一套 Bot 专属队列、自动化专属账本或“成长数据库”中的副本真相。

当检查与成长采用共享资源时，还要服从现有前台保留和后台并发限制；有 Bot 负责人不等于每个 Bot 永久占线程/显卡。没有收益就保持简单路径。具体阶段归[原路线中的落点](core-bootstrap.md#task-learning-stage-placement)。

<a id="jarvis-companion-robot-direction"></a>
### 陪伴、学习和机器人主脑怎样统一

统一的是主人、目标、经历、承诺和任务协调；不同能力各有证据和执行边界。陪伴需要稳定表达、理解偏好、记得共同经历并承认不确定；学习需要观察真实答题、安排适量练习和复测；办事需要交付物和效果回执。不能用一个“智能程度分数”替代这些目标。

未来主脑适合决定“谁在什么条件下做哪项任务、如何协调、是否真的完成”，本地机器人负责感知与动作执行，并保留实时避碰、联锁和停止。Google 官方 Robotics 文档将具身推理、任务编排和机器人 API 结合，亦明确集成方仍承担安全环境责任；这支持分层思路，不能证明把聊天模型连上电机就获得安全机器人。[Google Robotics ER 文档](https://ai.google.dev/gemini-api/docs/robotics-overview)。

例如“帮我准备学习空间”：数字助手整理学习材料，设备节点在已获准范围处理灯光/环境，机器人在具备能力和安全条件后执行整理；负责 Bot 核对各项结果，学习 Bot 按当日目标陪练。每个效果有自己的状态，任一设备不可用时交付其余有效部分，不虚报整个目标完成。这只是目标场景，当前并未实现该联动。

产品交互归[统一体验](interaction-persona.md#task-companion-experience)，机器人职责与断网/陈旧命令规则归[具身分层](architecture.md#embodied-multi-agent-brain)。近期最有价值的交付是让若干常用工作稳定跑通“交办—负责—执行—检查—修改—记住—下次用上”，同时维持自然交流；它也是扩大为多机器人主脑前必须成立的基础。

## 可以借鉴什么，怎样接回当前工程

<a id="grok-borrow-now"></a>
### 高优先级：先减少用户在现有模块之间搬运

以下是研究建议，不是新的授权、实施时间线或独立验收定义。K0—K6 的归属依照[唯一实施路线](core-bootstrap.md#bootstrap-5)；各项是否通过仍由原主题验收判断。

| 建议 | 具体改变 | 复用位置与路线归属 | 应观察的净收益 |
|---|---|---|---|
| 统一问题与交付入口 | 同一会话能看到目标、真实状态、阻塞原因、产物与下一动作 | 现有目标投影/原会话；K1/K2；[桌面状态](interaction-persona.md#desktop-presence-state) | 找到任务与成果更快，少问“现在怎样了” |
| 让新并行源码形成完整证据 | 验证调度、取消、恢复、压力与前台回答，并登记实际加载版本 | 原调度器；K1/K2；[V-DLG](delivery-validation.md#conversation-separation-validation) | 后台有进展且主人仍能交流和指挥 |
| 连接与恢复跟随任务出现 | 缺连接时显示具体服务、账号、原因与恢复入口；恢复后回原任务 | Gmail/MCP 与原任务；K2/K6；[Gmail 契约](contracts.md#gmail-contracts) | 少重复配置和重新描述目标 |
| 沉淀已成功的方法 | 先保存有适用条件和失败样例的技能候选，再测试、启用 | 原技能目录与研发链；K2/K3/K4；[目标研发](tasks-agents.md#goal-growth-runtime) | 重复工作更少指挥，失败不会污染稳定方法 |
| 把记忆管理做得更易用 | 聊天可发起查看/纠正/遗忘，并链接实际条目与影响范围 | 原候选/事实/来源 UI；K2；[记忆生命周期](knowledge-learning.md#memory-lifecycle-completion) | 不丢弃可审查性，也不迫使用户理解内部表结构 |
| 授权按作用域复用 | 已获授权且条件未变就继续，只把缺少判断的具体操作交给主人 | 原权限与动作记录；K1/K2/K4；[控制边界](security-sovereignty.md#continuity-control-boundary) | 减少重复确认，同时不增加越权或未知重放 |

这里最有价值的顺序是：让已有能力能够自然受理、持续推进、处理阻塞、核验并回到原会话。单纯增加一个“Bot 创建器”或新的设置页，通常无法补这些断点。

<a id="grok-borrow-later"></a>
### 条件成熟后再扩展

| 借鉴项 | 依赖条件 | 当前建议 |
|---|---|---|
| 角色间异步交接 | 任务归属、关联、预算、去重与取消传播 | 接入既有组合契约；不要让 Bot 互发消息绕开受理 |
| 时间/事件职责 | 用户明确委托、来源规则、失败回执、错过触发策略与预算 | 先选一项真实低风险工作；本文没有启用调度 |
| 示教成技能 | 可录制操作、秘密字段处理、步骤抽取与失败分支验证 | 在已有工具闭环上试验，生成候选而非即刻无人值守 |
| 手机接续 | 身份、受众、加密传输、问题修订、产物一致性 | 优先核对与查看；不能只做能发消息的壳 |
| 远端 Worker | 作用域、资料最小化、唯一动作权、断线对账与费用 | 作为原系统执行端评估，继续保留本地主权与停用能力 |
| 团队职责/共享页 | 明确主体与私有/共享知识边界 | 先覆盖个人/家庭真实需要，再扩展组织治理 |

这些扩展归既有 K6 的逐能力接入；其中任何能力依赖的 K0—K5 基础须先完成适用部分，不另起第二条“追赶 Grok Bot”路线。

<a id="grok-borrow-limits"></a>
### 不宜直接照搬的选择

- **账号级全部共享。** 可以共用适配器或工具进程，不能因此默认所有职责可读所有私密文件、浏览器登录和 Vault 条目。
- **不显示实际模型路径。** Jarvis 可以保留简单的默认自动模式，同时为需要核对时提供供应商、用途、用量和未知费用信息。
- **用自动记忆替代用途许可。** “记住了”不能自动允许在家庭群聊、外部工具或其他模型中使用。
- **用模型审批替代执行约束。** Auto Review 可作为辅助，真实状态、作用域、修订和未知效果仍须由宿主管理。
- **把云端常开当作所有人的默认。** 可选远端执行有价值，但不能据此要求上传本地全部资料，或对本机睡眠作虚假承诺。
- **为展示团队而堆积角色。** 角色要有清楚责任和复用收益；一次性任务不必永远占一个 Bot。

这不是断言 Grok Bot 的选择普遍错误；它们服务于不同产品取舍，Jarvis 不应为了外观相似而牺牲已经确定的目标。

<a id="grok-product-boundary"></a>
## 先分清 Grok、Grok Bot 与 Grok Build

| 名称 | 本文采用的边界 | 容易造成的误判 |
|---|---|---|
| Grok | 通用聊天与模型产品体系 | 模型能回答，不等于能持久执行一项现实工作 |
| Grok Bot | 有名字、职责、长期上下文、工具与执行环境的 AI 队友产品 | 不是在聊天窗口放一个机器人头像 |
| Grok Build | 编码产品与开发工作流 | 其公开源码、沙箱或 CLI 行为不能直接当作 Grok Bot 后端证据 |
| X 上的 @bot / Grok 入口 | Grok Bot 的部分任务入口或其他 Grok 功能 | 不应把公开回复机器人和完整 Bot 工作系统混为一谈 |

Grok Bot 于 **2026-08-11** 发布；本文检索到的官方更新日志最新列项为 **v0.75.5，2026-10-23**。发布初期的订阅资格已经变化，不能沿用首发文章的套餐范围。本文优先采用当前帮助页和对应版本更新。[发布介绍](https://x.ai/news/introducing-grok-bot)、[更新日志](https://x.ai/changelog/bot)。

还要纠正一个影响比较的认识：**Grok Bot 并非固定只用 Grok 模型**。官方模型说明称其在后台选择第一方或第三方模型，不提供逐请求型号展示，也不允许用户选择或屏蔽某一具体型号；Cursor 编辑器的团队模型允许清单不直接约束 Grok Bot。它的“自动选最合适模型”是产品策略，不能据此证明效果始终最优。[官方模型说明](https://cursor.com/help/grok-bot/models)。

## Grok Bot 的功能：从交办到交付

<a id="grok-capability-map"></a>
### 主要功能及其实际含义

| 能力 | 官方公开行为摘要 | 价值与限制 |
|---|---|---|
| 长期职责 Bot | 赋予名字、头像与职责，通过聊天持续修正偏好；可固定、分组、隐藏 | 职责有持续负责人；隐藏不代表停止工作 |
| 跨应用办事 | 连接器优先，必要时使用浏览器、文件系统与终端 | 能跨工具处理事务；网站变化、登录和真人验证仍会阻塞 |
| 后台工作 | 云端环境承载任务与例行流程 | 关闭本机客户端不终止云端工作；仍受服务、额度及上游可用性约束 |
| 多 Bot 协作 | 群聊、异步消息和交接 | 减少人工搬运上下文；仍需清楚的阶段负责人 |
| 实时交流 | 文字、听写、语音对话和语音留言 | 交互途径较完整；不因此证明中文嘈杂环境体验达标 |
| 产物交付 | 文件、图片、工具结果和可预览卡片 | 用户能检查成果；格式支持不等于复杂文档还原准确 |
| Pages | 可持续更新的报告、看板或追踪页 | 结果有固定阅读位置；公开/团队分享边界要单独判断 |
| Skill | 将稳定方法保存为可复用指引 | 减少重复描述；不等于确定性程序或独立验证过的能力 |
| 示教 | 在支持的界面演示工作流，生成待审查技能 | 降低描述操作的成本；一次演示不能覆盖全部分支 |
| Routine | 时间或事件触发工作，并提供运行记录 | 可承担例行责任；触发频率、失败和开销需要管理 |
| Team Bot | 团队共享职责、技能与资料，配合个人会话 | 适合组织工作；不等同于所有人共享一个无限权限账号 |
| 独立收件地址 | 支持用户申领 Bot 邮箱并由例行流程处理来信 | 便于收据、订阅与通知；地址属于账号层，不是每 Bot 一地址 |

上述能力分别依据[Bot 管理](https://docs.x.ai/grok-bot/bots)、[协作](https://docs.x.ai/grok-bot/chat-and-collaboration)、[文件与 Pages](https://docs.x.ai/grok-bot/files-and-results)、[移动端](https://docs.x.ai/grok-bot/mobile)、[Agent Email](https://cursor.com/help/grok-bot/agent-email)。详细运行与边界在下文展开，不能把表中功能名称当作成功率证明。

<a id="grok-memory-skills"></a>
### 记忆、技能与学习分别是什么

官方记忆帮助页说明：Bot 可自行保存偏好、规则、个人事实和工作日志；通常无需逐项确认，也不保证每次保存都显示在聊天中。个人 Bot 没有完整记忆清单界面，主要通过对话查看、纠正与遗忘。各 Bot 有自己的记忆，同时少数账号事实可以共享；在群聊中，Bot 可能使用你在私聊提供的内容。[记忆说明](https://cursor.com/help/grok-bot/memory)。

这说明它追求低摩擦的连续上下文；**不能由此推断其完成了事实真伪判定、跨时间冲突消解或所有派生副本的遗忘传播**。私聊输入能够参与群聊回答，也意味着“模型知道”与“可以向当前受众说出”必须分开治理。Jarvis 的对照见[记忆比较](#grok-memory-analysis)。

Skill 是方法，Routine 是何时调用方法，记忆是持续上下文。官方示教流程会把可见操作整理为技能草案，并要求补充验证、失败与权限边界；示教录制最长十分钟，不记录麦克风，且可能分批开放。它是工作方法的积累，公开材料没有证明每个 Bot 因使用而持续训练自己的模型权重。[技能与示教](https://docs.x.ai/grok-bot/skills-routines-and-automations)。

<a id="grok-interface"></a>
## 界面与显示：它怎样让“正在办事”可理解

<a id="grok-interface-layout"></a>
### 信息组织与主要操作面

以下是按官方文档重建的功能布局，不是截图，不保证某一平台或灰度账号具有完全相同的位置。

| 界面区域 | 显示/操作内容 | 用户得到的理解 |
|---|---|---|
| 侧边栏 | Bot、群聊、固定项、分区、隐藏项和连接应用入口 | “谁在负责什么”成为导航对象 |
| 会话标题与详情 | 名字、头像、通知；例行流程和团队配置等 | 找到这个职责的设置和持续工作 |
| 中间消息流 | 回答、工具活动、问题、产物、待处理操作 | 工作过程与讨论保持在同一条记录 |
| 输入区 | 附件、语音、`@` 对象、`/` 技能 | 从自然交办逐步补足需要的上下文 |
| 右侧电脑预览 | 云端操作画面；展开后查看或接管 | 能看见点击、输入和当前页面 |
| 结果卡与侧栏 | 文件预览、Pages、Library 等 | 产物有明确入口，可继续修改 |
| 问题/审批卡 | 等待输入、具体动作或接管要求 | 区分“需要判断”和“系统还在做” |
| 侧栏状态 | 工作中、需要关注、未读结果等 | 用户无需反复询问全部 Bot |

布局根据[协作与消息](https://docs.x.ai/grok-bot/chat-and-collaboration)、[电脑预览](https://docs.x.ai/grok-bot/computer-and-apps)、[结果显示](https://docs.x.ai/grok-bot/files-and-results)及[状态与通知](https://docs.x.ai/grok-bot/settings-and-notifications)归纳。外观支持随系统、浅色和深色，并提供包括简体中文在内的多种语言。没有依据声称它具有 Jarvis 设计中的透明桌面精灵。

**分析：真正值得借鉴的不是三栏布局，而是显示对象与工作对象一致。** 问题挂到原工作，结果留在原会话，电脑操作能够展开查看，状态指向“你需要处理什么”。如果只复制头像、聊天气泡和动效，却让任务、审批、文件分别落在无关面板，交办仍然会断。

<a id="grok-interface-cards"></a>
### 卡片为什么重要，以及它目前的限制

用户的关注点会随阶段变化：刚交办时关心目标是否正确；执行时关心是否推进；遇阻时关心要补什么；交付时关心成果与证据。把所有内部日志始终铺开会增加负担，只显示“正在思考”又无法判断真实工作。卡片的价值是把当前可操作内容放在用户面前，同时允许展开证据。

官方群聊存在明确限制：审批、密钥/登录请求及邮件或 Slack 草稿不会像普通消息一样完整出现在群里；Bot 向群的交接目前以文本为主。因此“同一会话看清所有工作”在不同渠道并非完全等价，不能据群聊宣传想象它已解决所有控制界面。[群聊行为说明](https://docs.x.ai/grok-bot/chat-and-collaboration)。

Jarvis 应将“回到正确的本人窗口完成核对”做成连续导航：保留任务编号、问题修订、发起来源和回返位置，避免用户换个窗口后不知道自己在批准哪项工作。完整交互规则仍归[桌面场景](interaction-persona.md#desktop-presence-scenarios)与[显示契约](contracts.md#desktop-presence-contract)。

<a id="grok-interface-jarvis"></a>
### 与 Jarvis 当前显示和已采纳设计的差别

Jarvis 当前可运行界面是网页工作台：项目/会话导航、聊天、模型/推理选择、任务与目标面板、右侧检查区和设置。输入区明确支持受限 UTF-8 文本附件，当前源码写明最多四个、合计 12,000 字；图片/音频聊天接入与语音按钮仍显示待接入。出图工作室或 3D 识图的存在，不能证明通用聊天已支持相同输入。依据[页面源码](../apps/workbench/index.html)和[前端入口](../apps/workbench/app.js)。

已采纳的下一形态是“透明 Logo 精灵 + 场景卡片 + 按需打开工作台”，原生实现仍 proposed。它在日常陪伴和低打扰方面更贴近 Jarvis 的定位；代价是空间小，必须精确处理焦点、窗口命中、通知排队和状态聚合。Grok Bot 的可展开执行界面可以成为补充工作台的参考，不必改变已确定的 Logo 与主体形态。

当前显示依据可查看[真实记忆检索面板](evidence/memory-retrieval-1.0.0/recall-ui-expanded.png)；后续形态查看[场景设计参考图](evidence/desktop-companion-2026-10-25/presence-events.jpg)。前者只代表相应模块验收时的真实页面，后者是设计图，两者都不能冒充本轮全系统实测截图。设计权威归[工程首页](../README.md#desktop-companion-overview)。

<a id="grok-operation"></a>
## 运作机制：公开事实与合理推断

<a id="grok-cloud-runtime"></a>
### 云端电脑、工具路径与并行边界

Grok Bot 的公开执行模型是：客户端发消息，服务端组织模型与工具调用，工作在持久云端电脑或连接器上完成。**同一账号的个人 Bots 共用文件、浏览器会话和命令行凭据，每个 Bot 有自己的操作屏幕；独立屏幕不构成独立安全边界。** 同一 Bot 的屏幕一次执行一项电脑操作任务，其他 Bot 可并行推进。[云端电脑说明](https://docs.x.ai/grok-bot/computer-and-apps)。

由此可推断，它减少了重复登录与交接文件的成本，却仍需处理共享文件冲突、登录副作用、连接器限流与结果所有权。公开文档未披露完整任务数据库、队列算法、文件锁实现和全局死锁处理，本文不假设它已做到数据库级 exactly-once 或任意规模并行。

连接器与电脑操作形成互补：前者提供结构化接口，后者覆盖缺少接口的视觉流程。**分析：接口能力相同且可用时，通常应先用接口，因为参数、结果和错误更容易检查；视觉操作适合填补缺口，但应验证页面目标与操作后状态。** Jarvis 可以借鉴这种选择方式，不需要引入第二个任务权威。

<a id="grok-work-cycle"></a>
### 一项工作的典型闭环

下表是依据公开功能作出的逻辑重建，不是 Grok Bot 内部架构或协议说明。

| 阶段 | 可见行为 | 工程上真正需要解决的问题 |
|---|---|---|
| 受理 | 通过聊天或触发器接收结果要求 | 谁发起、代表谁、作用域与完成条件是什么 |
| 补足上下文 | 读取历史、资料和相关系统 | 当前性、权限、受众与不可信内容如何区分 |
| 选择方法 | 调用技能、连接器或电脑操作 | 选择是否可解释，缺少能力时怎样停止或接管 |
| 执行/协作 | 跨工具推进或交接给另一 Bot | 单一负责人、冲突、重试、预算与中间文件 |
| 判断/回问 | 显示问题、草稿或审批卡 | 用户答复是否仍对应当前目标与准确动作 |
| 验证/交付 | 返回文件、链接和完成说明 | 结果是否真实存在，部分完成与未知效果是否明确 |
| 保留经验 | 保存偏好、方法或例行流程 | 哪些只是候选，何时失效，怎样纠错与停用 |

该闭环的公开体验依据[总览](https://docs.x.ai/grok-bot/overview)。对 Jarvis 的意义是减少人在阶段之间搬运信息，而非让模型对所有状态都说了算。

<a id="grok-routine-runtime"></a>
### 例行工作与事件驱动

Routine 不等于后台永不停歇地让模型思考。它定义特定 Bot 在时间或事件到来时运行；官方支持日程以及部分 Slack、GitHub、邮件或 webhook 等触发。webhook 返回 200 仅表示受理并开始运行，不表示任务完成。高频触发会消耗额度，部分限流失败不会自动重试。[Routine 帮助](https://cursor.com/help/grok-bot/routines)。

**分析：Jarvis 应借鉴“长期责任由事件唤醒，运行有回执”的方式。** 闲置时不需要额外付费轮询模型；来源变化、定时点与明确委托触发可追溯任务。先解决去重、错过触发的处理、过期输入和停用后不再运行，再增加自动化数量。完整规则仍归[任务与资源调度](tasks-agents.md#resource-scheduling-5)，本文没有创建任何计划或监听器。

<a id="grok-security-runtime"></a>
### 安全控制、Vault 与恢复

Auto Review 是基于模型的动作检查，可放行、要求本人判断或拒绝；Ask first 规则优先，允许规则不代表所有动作必然放行。它需要与最小权限、明确动作范围共同使用；不能充当不可绕过的权限证明。[审批说明](https://docs.x.ai/grok-bot/approvals-security-and-privacy)。

**版本更新必须单独看。** v0.75.5 的日志说明：用户主动要求发送的邮件/消息可以在 Auto Review 放行后发送，例行工作等自行生成的内容仍等待草稿审阅。当前邮件帮助页已采用这个区分，早先检索摘要仍写“每次都点 Send”。因此，不能笼统总结为“全部自动发送”或“每次手工确认”。[版本记录](https://x.ai/changelog/bot)、[当前邮箱规则](https://cursor.com/help/grok-bot/agent-email)。

Vault 自 0.75.2 起可保存登录、卡片与联系资料。官方称秘密值不展示给模型；但 Vault 是账号级，不能把某项仅分给一个个人 Bot，且保存的卡片不保证每次使用前单独批准。**秘密值不可见与动作可被授权是两件事。** 这类便利功能不能直接照搬为 Jarvis 的付款或账号策略。[Vault 说明](https://cursor.com/help/grok-bot/secrets)。

企业安全文档公开了网络限制、模型输入检查等控制，但多项能力仅 Enterprise 可用。禁用连接器并不会同时禁用对应网站；远端 MCP 也需对应策略覆盖。所谓“不用于训练/提供商零保留”与产品为持续工作保存资料是不同层面，不能概括成“数据不上云”或“完全不留存”。[官方安全文档](https://prod.cursor.com/docs/grok-bot/security)。

电脑恢复还要区别软件更新、环境重建与最后保存数据的恢复；更新可能移除手工安装包，无法预先保存时最近改动可能丢失，聊天存储与电脑磁盘也不是同一个对象。Jarvis 值得借鉴的是把恢复范围说清楚，而不是将“重启/重建成功”显示成所有业务都已恢复。[恢复排障](https://docs.x.ai/grok-bot/troubleshooting)。

<a id="jarvis-concurrency-snapshot"></a>
### 并发源码已变化，不能再只引用旧“单槽”基线

这是首轮研究核对发现的实质差异：当时权威文档的早先源码基线仍写通用执行单槽，而工作区已经出现以下实现。表内是首轮只读代码的观察范围；同日后到的部署与测试证据见本节末尾：

| 文件/机制 | 本次只读所见 | 判断边界 |
|---|---|---|
| [dialogue.py](../host/dialogue.py) | 前台回答池 2；独立后台回复池 1；分别存在有界排队信息 | 增加了交流/后台区分，仍不等于硬资源隔离 |
| [task_scheduler.py](../host/task_scheduler.py) | 线程池上限 4；以原任务 ID 排队，按策略与压力调度 | 这不是“所有业务最多四个任务”的总容量定义 |
| [scheduling.py](../modules/task_resource/scheduling.py) | 默认执行并发 2，可配置 1—4；默认队列 32、内存余量 2,048 MiB、CPU 阈值 80% | 都是当前代码默认值，未查询主实例实际配置，也不是实测承诺 |
| 同一调度器 | 结合优先级、重要性、截止点和等待时间排序；冲突类别串行；资源指标未知时暂缓 | 资源估计与类别锁较保守，尚不能证明所有文件/设备冲突都覆盖 |
| [execution.py](../control/execution.py) 与 [core.py](../host/core.py) | 执行 cohort/permit 连接原恢复锁与任务检查 | 体现对并发所有权的处理，不能仅凭存在类名宣称恢复已验收 |
| [background.py](../host/background.py) 等 | 规划/研发仍有共用后台槽；邮件、出图、3D 等有各自通道或锁 | 多条线程池容量不可简单相加 |

**首轮结论是已有有界并行与前后台分离源码，未核实部署与完整混合负载；同日后续已读取到限定范围的测试及主服务加载记录，见[当前基础更新](#jarvis-current-gaps-update)。** 当前准确口径以[有界并发运行范围](tasks-agents.md#bounded-concurrency-runtime)和[对应证据](delivery-validation.md#bounded-concurrency-evidence)为准。不能继续断言“当前代码只能单任务”，也不能外推为“任意任务并行且聊天零延迟”；完整 V-DLG 仍按其独立验收推进。

<a id="jarvis-quality-gap"></a>
### 长期质量与自主性仍有可量化缺口

记忆验收记录提供了比“会记住”更有价值的反例：六语留出探测的回答正确为 **79/90（87.8%）**，低于既定 90% 门槛；90 份回答来自 30 个问题各重复三次，不是 90 个独立问题。英文长对话开发探测另有低准确率及裁判未知/无效项，不能被六语检索表现掩盖。详见[原始口径](delivery-validation.md#memory-continuity-evidence)。

这意味着 Jarvis 当前在可追踪检索、修订和失效传播上已有工程基础，但“长期相处后准确理解主人”仍未被这些测试证明。同样，纯文本候选在公开/留出用例中通过，只证明规定输入输出，不能替代真实邮件、采购或设计任务的业务验收。

完整语音、原生桌面精灵、跨设备状态与身份连续、长期主动学习以及通用自主研发仍有未完成项。**Grok Bot 的对应公开功能说明也不能作为这些目标已经可靠达成的证据。** 双方应在相同任务与错误条件下比较，不能拿 Jarvis 的 proposed 全图去对 Grok Bot 的产品现状，也不能拿 Grok Bot 的宣传去对 Jarvis 的失败样本。

表中 Grok Bot 一栏为前文已引用的官方能力，Jarvis 一栏为上述本地证据摘要；优势判断为本文分析，不是同场实测排名。

<a id="grok-deep-analysis"></a>
## 深层分析：差别为什么会出现

<a id="grok-identity-analysis"></a>
### 一个伙伴与一组队友，可以怎样兼容

Grok Bot 把职责作为可见主体，有利于明确“研究员”“日程助理”“客户经理”的工作范围。代价是用户可能需要决定找谁、记忆会不会重复、某个 Bot 是否还在负责。Jarvis 的核心要求是同一伙伴持续理解主人、承诺和未结事项；如果把每个任务都变成一个独立人格，会增加用户协调负担。

更适合 Jarvis 的借鉴是：**入口保持 Jarvis，内部职责可以明确且长期存在，只有需要理解分工时才向用户显示角色。** 工作归属必须来自任务记录；人格名字不能创造权限，也不能代表它已经连接某项能力。现有[Bot/Agent 边界](architecture.md#composition-bot-agent-boundary)已经支持这个方向，没必要再建立一套平行框架。

跨角色的连续性也不是把所有历史装进一个提示词。可共用的是获准且当前有效的身份与偏好；任务输入、私密资料、临时假设和执行凭据仍有自己的作用域。否则“一个 Jarvis”会变成无边界共享，“很多 Bot”会变成没有共同经历的重复对话。

<a id="grok-memory-analysis"></a>
### 记住得顺手，与记得可核对，是不同优势

Grok Bot 的便利来自用户少做管理；Jarvis 的当前路径则更强调候选、事实、来源、修订和失效。前者减少交互阻力，后者便于定位错误和控制用途。两者都可能失败：自动记忆会保存误读，过多人工管理会让长期记忆根本没有被维护。

Jarvis 可以把低风险偏好、临时工作摘要与正式事实分级呈现：自动形成候选，在恰当时机汇总核对；已有授权覆盖的确定性更新直接受理，真正缺少判断才回问。**减少重复确认不应通过偷偷放宽事实与资料用途边界实现。** 当前流程与完整目标的差距仍以[记忆缺口表](knowledge-learning.md#memory-final-gap-register)为准。

另一项关键差别是纠错的影响范围。改掉一个偏好字段后，旧摘要、引用回答、任务背景或导出产物可能仍保留旧值。Jarvis 已有部分派生依赖清理，后续应继续补外部副本、研发产物和备份边界。对 Grok Bot，公开资料不足以证明同等传播机制；准确结论是“未得到该项证据”，不是“对方一定不会纠错”。

<a id="grok-concurrency-analysis"></a>
### 真并行取决于资源与冲突，不能按角色数计数

并行认知、并行网络请求、并行文件读写和并行桌面操作是四类不同问题。增加 Bot、线程或独立操作屏幕只能解决其中一部分。比如两个独立检索可以同时推进；两个任务修改同一表格需要冲突协调；两个角色通过同一浏览器退出账号会互相影响。

Jarvis 新调度器已经体现“独立任务并行、冲突资源串行、资源不足等待”的方向。但 CPU/内存门槛是准入近似值，不能保证 GPU、磁盘、网络或外部模型限额不会争用；检查发生在任务开始前，也不等于运行过程中能抢占所有后台步骤。保留聊天池只是基础，还要验证有内容的回复、控制指令和背景进展。

因此，借鉴 Grok Bot 的异步交接时，应坚持原任务 ID、单一阶段负责人、有限深度、共享预算和取消传播。不要为了显示“多 Agent”再造一套队列；同一网页、同一外部账号或同一文档的写入需要具体冲突键。收益应看成功交付、等待与用户干预，不能看创建了多少角色。

<a id="grok-trust-analysis"></a>
### 自动判断不能代替动作与数据控制

Grok Bot 的 Auto Review 体现了一种产品选择：把授权语义与当前动作一起判断，尽量减少无意义打断。Jarvis 值得借鉴“理解既有授权”的部分，不能把它简化成每一步都问，也不能把模型的允许结论当作执行许可本身。

Jarvis 已有部分宿主约束：精确账号/草稿修订绑定、幂等编号、UNKNOWN 先核对、候选代码不直接发布。它们的作用是让外部效果仍受程序事实控制。后续浏览器和新连接器应复用同一原则：页面文字、邮件内容、插件返回与其他 Bot 请求是输入，不能自行扩展主人的授权。

同时，本地部署也不自动可信。当前家庭库依赖 Windows 同一用户 DPAPI，普通资料库未全加密；取得同一 OS 账户权限的程序仍在现有信任边界内。LPAC Worker 的实测覆盖是受限候选执行，不能宣传所有宿主、模型程序和插件都被同等隔离。完整准入继续归[供应链规则](security-sovereignty.md#personal-life-supply-chain)。

<a id="grok-cloud-local-analysis"></a>
### 云端执行与本地主权存在真实交换条件

云端让电脑关闭后继续工作，也便于手机接续；代价是依赖远端服务、账号、网络和数据处理链。本机让资料位置、特定硬件和安装工具更可控；代价是睡眠中断、普通 PC 资源不足、恢复材料与更新都要自行管理。

“给 Jarvis 加云 Worker”可以补连续执行，但不是换一个机器地址这么简单。需要明确远端拿到哪些资料、谁能发动作、断网时结果如何对账、谁负责取消和费用，以及本地与远端不能同时重复写入。这个方向应作为既有[多设备与共同体](federation.md#unified-intent-memory)中的受控执行端讨论，不能以借鉴为由迁出全库或改变身份权威。

<a id="grok-learning-analysis"></a>
### 从示教学习到能力成长，中间还缺独立验证

示教记录“这次怎么成功”，难以自动说明“哪些条件变化后不能这样做”。例如一次报表导出路径，无法覆盖账号切换、空数据、按钮改名、重复提交和异常恢复。把演示保存成技能有价值，把它立即当成稳定自动能力则会扩大错误。

Jarvis 的候选代码、独立留出案例与灰度回退可为这一缺口提供基础。适合先做的是：把已完成任务的方法整理为可审查技能，列出输入、输出、依赖、失败条件与证据；稳定后才接已有执行器。需要新代码时走原研发通路，不能让“会写技能”绕开发布与恢复规则。方向归[自主成长](evolution-release.md#growth-release-runtime)，不是新增训练系统。

<a id="grok-scenario-comparison"></a>
## 用真实使用场景比较优劣

| 场景 | Grok Bot 更可能带来的便利 | Jarvis 当前能承担的部分与缺口 | 对 Jarvis 的具体启发 |
|---|---|---|---|
| 早晨整理邮箱、日程、待办 | 跨应用与例行职责的公开产品路径较完整 | Gmail 有限读信/草稿；周期拉取、综合日程与长期责任未完整接通 | 先打通“读当前来源→整理→核对具体写入→留回执”的小闭环 |
| 研究后交付一份报告 | 多 Bot 分工、云端浏览与文件结果减少人工转交 | 有文本目标与产物通路，联网研究和任意文件格式能力不能一概保证 | 一名任务负责人统一结论，分工是内部实现，引用必须落到产物 |
| 私密家庭资料问答 | 手机交流便利，但需评估云端与受众路径 | 本地私密资料/许可有界实现；跨机恢复与多人语音受众未验收 | 保留资料级接收范围，把受众检查前移，不能只靠角色名 |
| 用本机机械/3D 工具生成成果 | 云电脑能做通用应用任务，特定硬件/软件可用性需另验 | 已有专门模块；质量与工程有效性各有未通过项 | 优先建立领域输入输出和验收，不追求“通用电脑操作”替代所有专用模块 |
| 出门后继续长任务 | 手机加云端执行明显更便利 | 本机需保持运行；远程执行端与共同体尚待闭环 | 先明确状态、取消与产物接续，再讨论远程计算 |
| 渲染时仍聊天、改变优先级 | 官方支持运行中继续指挥；实际响应性能未实测 | 已有分离通道和限定负载验证；重 GPU 等统一压力验证待补 | 同机混合负载验证，显示哪项因资源/冲突排队及原因 |

这些是产品路径与约束推演，不是实际对测成绩。对接近工作秘书、跨 SaaS 和外出使用的需要，Grok Bot 的当前公开产品面更完整；对个人定制、本机工具、细粒度来源治理与能力演化实验，Jarvis 有更直接的可控空间，前提是补齐证据与使用闭环。

<a id="grok-cost-comparison"></a>
## 费用、资源与维护：不能只比较订阅价

截至本次查询，官方公开的新 X Subscription 月付标价如下，税费另计；额度是跨产品的共享池，倍率不是“可完成任务数量”的保证。

| 套餐 | 美元/月 | Grok Bot 是否包含 |
|---|---:|---|
| Plus | 8 | 不包含 |
| Premium | 30 | 包含 |
| Super | 100 | 包含，较高共享用量 |
| Ultra | 200 | 包含，更高共享用量 |

来源为[当前价格页](https://x.ai/pricing)及[订阅说明](https://docs.x.ai/x-subscription/pricing)。旧 Cursor / SuperGrok 等账号还存在不同接入与超额路径；新订阅的共享周额度和充值，不能与旧计划的 on-demand 名称混用。绑定旧订阅也不意味着额度简单相加。[计费帮助](https://prod.cursor.com/help/grok-bot/plans)。

Jarvis 的费用则包括模型调用、远端服务、本地设备折旧、电力、存储、维护和开发时间；本地模型不是免费算力，开源组件也不是零运维。当前没有覆盖双方相同任务的完整账单，因此无法负责任地给出“便宜几倍”。

更适合比较的是：

```text
单位合格交付成本 =
（调用/订阅分摊 + 执行环境 + 失败重试 + 人工核对与维护）
÷ 满足同一完成条件的交付数
```

同一任务还需并列报告用时、用户干预次数、错误外部动作、数据外发与恢复情况。若一方省钱但需要用户反复重做，它不一定更划算；若一方体验顺滑但无法满足资料范围，也不能用速度抵消该约束。Jarvis 的完整对比方法继续归[组合收益实验](delivery-validation.md#composition-benefit-experiment)及[PC 资源验收](delivery-validation.md#pc-footprint)。

<a id="grok-unknowns-validation"></a>
## 尚不能下结论的部分，以及怎样验证

<a id="grok-evidence-conflicts"></a>
### 资料冲突与未知项

| 问题 | 当前证据允许的结论 | 需要避免的说法 |
|---|---|---|
| 首发套餐与当前套餐不同 | 采用当前价格/计费矩阵，保留历史日期 | “必须购买首发最高档才能用” |
| 发送是否每次点击 Send | 需区分用户主动发送请求与后台自行生成，且看版本/规则 | “它总能自动发”或“它永远只能留草稿” |
| 旧说明只有四个设置面板，后来增加 Vault | 新功能应参照对应帮助页和版本 | 把旧截图当成当前全部界面 |
| 更新日志/帮助页的搜索摘要与正文不同步 | 以本次实际打开的正文和明确版本为依据 | 仅凭搜索摘要判断权限 |
| 每 Bot 有电脑，与账号共享电脑的表述 | 对个人账号采用明确的“共用环境、独立屏幕”说明 | 每 Bot 有独立 OS 权限或隔离磁盘 |
| Team Bot 的电脑与权限 | 取决于本人会话、同事会话或 Slack 共享场景 | 全部团队流量都使用创建者电脑与身份 |
| 长期记忆与学习 | 证实产品有持续记忆/技能机制，质量和底层细节未知 | “无限上下文”“永不遗忘”“自动训练出独立模型” |
| 生产安全与稳定性 | 本文未实测，不公开内部机制的部分保持未知 | 根据宣传或认证推断绝无注入、丢数据或越权 |
| Jarvis 版本与源码 | v0.1.0 发布号 + 本地增量快照 | HEAD 发布代码等于工作区所有能力 |
| Jarvis 并发 | 同日后续已核对局部测试与部署记录，完整压力范围仍有限 | 用旧单槽描述否认新进展，或用局部证据冒称全部验收；见[更新](#jarvis-current-gaps-update) |

Team Bot 还明确区分团队记忆与个人笔记；例行流程通常属于创建它的那位用户，而非天然代表整个团队。其授权和执行位置应按[团队 Bot 专页](https://docs.x.ai/grok-bot/team-bots)核对，不能把个人 Bot 的共享电脑规则不加区分地套到所有团队场景。

X 的 `@bot` 入口也有地区和账号条件，公开回复主要确认转交，成果留在 Bot 会话。它展示了“外部入口接回原工作”的方法，但不应据此假定任意地区、任意帖子格式都可用。[X 入口说明](https://docs.x.ai/grok-bot/tag-on-x)。

<a id="grok-future-comparison"></a>
### 后续真正有意义的同场比较

这是一份待执行的对比取样建议，复用现有验收体系，不新增第二套合格门槛。

| 对比样本 | 固定条件 | 要观察什么 | Jarvis 对应权威 |
|---|---|---|---|
| 跨工具报告 | 同一公开资料、交付格式、时间预算与可用账号 | 正确且有来源的结果、工具失败、人工接续、费用 | [收益实验](delivery-validation.md#composition-benefit-experiment) |
| 后台工作时聊天与取消 | 同一机器基线与确定后台负载 | 有内容回复、控制延迟、任务进展和资源峰值 | [V-DLG](delivery-validation.md#conversation-separation-validation) |
| 跨会话纠正/遗忘 | 合成事实、过期版本、明确接收范围 | 纠正后回答、旧结果复活、引用依赖与受众泄漏 | [记忆验收](delivery-validation.md#memory-context-acceptance) |
| 邮件与未知效果 | 模拟收件人、重复请求、发送后断线 | 准确账号/内容、重复外发、UNKNOWN 对账 | [邮件验收](delivery-validation.md#gmail-evidence) |
| 方法复用 | 先成功一次，再改变输入、页面或条件 | 技能是否识别失效，是否停在正确边界 | [成长发布](evolution-release.md#growth-release-runtime) |
| 恢复与接续 | 可控进程退出、过期登录、网络中断 | 原任务、产物和预算是否保留，是否误重放 | [恢复契约](contracts.md#composition-durability-contract) |

没有实际 Grok Bot 账号实测前，应把它的对应数值留为“未测”，不能用模型常识填分。Jarvis 也要把运行版本、输入、开始/结束状态及失败保留完整；不同模块的测试数量不能累加包装成同场胜率。
