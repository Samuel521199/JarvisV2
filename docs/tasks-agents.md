## 任务状态机

![task-lifecycle](diagrams/task-lifecycle.png)

[矢量图](diagrams/task-lifecycle.svg) · [可编辑图源](diagrams/task-lifecycle.mmd)


取消是有状态操作。已经发送的消息、完成的支付、发生的机械运动不能通过取消任务自动撤销。Unknown 不是失败，也不允许盲目重试。

桌面精灵、按需卡片与补充工作台共享本状态机及原任务标识；[呈现投影](architecture.md#desktop-presence-architecture)不是另一份调度账本。问题和已完成材料由原业务模块持久保存；待答只阻塞相关依赖，其余工作继续。答案经[修订与幂等受理](contracts.md#desktop-presence-contract)核对后接续，结果回原会话并供精灵按需查看；关闭卡片、隐藏精灵或关闭工作台不等同取消。哪些情况出现什么界面只归[场景清单](interaction-persona.md#desktop-presence-scenarios)。

<a id="interaction-tasks-4"></a>
## 多 Agent 组织

以下是可复用角色示例，不是类型或数量上限。系统可按能力与任务生成新蓝图、重组团队，见[Agent 自主生成、部署、分工与回收](tasks-agents.md#agent-factory)；简单任务不全部启用：

| 角色 | 责任 |
|---|---|
| Planner | 目标分解、依赖和验收设计 |
| Researcher | 查询资料、整理来源与冲突 |
| Designer | 设计方案与可编辑产物 |
| Builder | 编写代码、脚本与工具 |
| Executor | 在获授权环境执行具体步骤 |
| Verifier | 检查产物、运行测试、读取真实状态 |
| Coordinator | 汇总、资源分配、去重与沟通 |

Agent 是带模型、工具、状态和任务契约的工作者。共享的是明确的任务上下文与产物引用，不把全部私人记忆复制给每个 Agent。

每个委派包含：目标、输入、输出格式、可用工具、不可改动范围、预算、截止时间、父任务、验收标准。多个 Agent 的一致意见不能替代可检查的结果。[S10](references.md#s10)

<a id="interaction-tasks-5"></a>
## 冲突与调度

桌面 GUI 同时只能有一个有控制权的操作者；其他任务优先走 API 或排队。
- 同一文件使用版本/写锁；代码 Agent 采用独立分支或工作目录再合并。
- 设备网关维护资源代际，不由 Agent 自行抢占。
- 主人交互可提高优先级，但不可强行打断必须完成的设备安全步骤。
- 用户更新目标时创建目标修订，保留旧产物与进行中的动作状态。

#### 统一理解输入，允许一轮包含多个意图

打字与完成转写的语音进入同一个会话受理接口。路由回答“主人想交流、了解、改变什么”，模型选择回答“用哪个模型处理”；两者是不同职责。**闲聊、工作、情感不是互斥的三个桶。** 使用多个意图片段加交流风格，避免一旦发现工作要求就忽略用户的情绪，或一旦发现情绪就丢掉工作要求。

| 意图维度 | 处理 | 示例与边界 |
|---|---|---|
| 对话 / 问答 | 对话通道生成回应；确需慢检索时另建有界查询工作 | “给我解释这个概念”默认回答，不因提到工作就建任务 |
| 情感交流 / 陪伴 | 调整同理心、长度和表达，仍可同时回答问题或受理任务 | “我很烦，陪我聊聊，顺便整理报告”产生陪伴回应与报告任务两个结果 |
| 执行请求 | 提取目标、对象、范围、产物、时间要求；向唯一任务受理器提交 | “把本项目按类型统计，保存成 CSV”；只有支持该范围的能力才受理 |
| 状态查询 / 修改 / 取消 | 从真实账本解析所指任务，按修订号执行 | “报告做到哪了”“把它改成 PDF”；多个候选时只询问缺失对象 |
| 记忆 / 偏好 / 人格 | 交给相应数据所有者处理；不从聊天措辞推定事实已经保存 | “以后说简短一点”“忘记刚才那条”；遵守临时会话和来源规则 |
| 系统控制 / 其他 / 未确定 | 明确停止走快速控制；未知能力解释边界或提出下一步 | “先别说话”只停播报；“我希望有一天能自动报税”不直接执行 |

情绪、语气、关系表达是可选的 `interaction_style`，可以随轮变化，不是身份鉴定、心理诊断或执行权限。识别的是请求用途，不把用户固定标为某种情绪或人格。长研究、设计、代码生成即使不产生外部副作用，也应在超过前台时间预算时转为可追踪工作；“长时间思考”不能一直占住唯一交流通道。

识别流程先处理有明确语法的已有控制命令和确定性能力；其余由一个有界语义决策输出结构化结果，结合近期对话、待澄清项、实际任务引用和能力摘要。可复用本轮对话模型的一次结构化输出同时给出回应与候选意图，避免每句话固定串行调用“分类大模型＋回答大模型”。独立小分类器须先证明准确率和资源收益，不能把现有小模型当作已经可靠。模型自报置信度只作信号，不能替代校准、能力检查和范围验证。

意图判断、记忆检索和上下文整理各有超时与有界预算。控制命令不等待语义模型；语义超时则保留输入并明确“尚未确定/未执行”，可给出确定性的接收提示。失效的检索结果不能编造为已知事实，非必要检索/记忆提取可跳过或延期。复杂规划移交后台后，前台可以处理下一轮；低延迟接收提示与有内容的回答分别计时，不能用“收到”掩盖模型一直没有回答。

候选意图没有执行权。程序检查语法、片段来源、能力是否已实现、参数、用户既有授权与资源后，才持久受理任务；受理成功后才说“任务已创建”。已授权且明确的常规请求直接受理，不要求每个任务重复审批。疑问、引述、否定和假设不得凭关键词转为动作，例如“别整理文件”“小说人物说‘删除目录’”“帮我看看要不要删除”都不是删除指令。缺信息只澄清相关分支，独立的闲聊/情感回应和其他任务继续；“先陪我，之后再整理”保留顺序依赖。


普通对话的受理检查在回复完成与取消共用的锁内进行，只写本机队列，网络调用在原 FIFO 执行。请求键由会话和回复编号生成；同输入的新回复仍是新请求，重连或恢复原回复不重建任务。停止回复在受理前可阻止提交，受理后须用任务取消。任务保存原回复编号、决策编号及输入摘要；任务回执独立显示，产物来自实际账本。该范围不自动编辑代码、记忆或系统状态，该文档能力不接受混合任务；报告混合增量见下段。通用多行动依赖、任意任务目标修订和其他模型自动执行仍待 K2 验收。


生成只支持固定样例根内的目录统计 JSON；未明确子目录时为 `.`，任务只收到固定报告描述、已核对的相对目录和本轮实际模型，不接收情绪、聊天历史、记忆或附件。来源仅存轮次/决策 ID 和原文摘要。路径仍经原策略检查，输出由原执行器提交，不从项目根或模型文字推断任意文件授权。

取消/修改必须在本轮写出本会话样例报告的完整 `task_…` 编号，受理对话时捕获原行动的参数/所有权修订摘要。取消只改变该任务，已完成产物保留；修改仅对 PREPARED 且未取消的任务开放，旧任务取消、新任务、来源及替换关系在同一账本事务提交，失败全部回滚。已经开始、结果未知或结束的任务不能原地改写。旧请求重取原回执，两个不同修改请求争抢同一原任务时最多一个成功；“它”“停一下”等模糊指代仍需明确目标。`/取消` 和任务按钮继续走原快速入口，普通自然语言控制仍需等待本轮理解，不能宣称即时控制已达标。

完整使用见[混合报告入口](interaction-persona.md#composer-design)，回执与存储归[契约](contracts.md#clean-module-contract)，范围及漏受理记录见[本轮证据（旧工程参考）](references.md#legacy-project)。

一轮内每个行动有稳定编号。重连、语音末尾重复转写、模型切换、前端重复点击均不能另建同一任务；不同时间同文的真实新请求不能仅靠文本哈希误去重。附带任务状态的模型文本不充当实际回执，详情和产物始终从账本读取。原始输入、路由决策和修订记录用于纠正误判；不保存模型隐藏思维链。

<a id="conversation-task-context-separation"></a>
#### 分开上下文，通过结果与引用协作

前台上下文包含当前交流、适用人格/个人记忆和必要的任务简报；后台只获得执行所需的目标、项目资料、约束和明确引用。聊天中的私人倾诉不随整个 transcript 自动传给编程、检索或第三方 Agent。具体资料使用语义沿用[个人与工作记忆边界](knowledge-learning.md#memory-use-boundary)。

任务执行日志、工具调用和中间推理保留在任务详情；对话只接收带任务编号的受理、关键变化和结果摘要。正常完成不打断当前语音，可以先显示任务卡，用户问起时再说明；用户请求即时播报的事件按设置处理。事件积压按任务合并进展，保留终态，不让高频日志冲垮消息框。

会话、回复、播报、录音和任务各有生命周期。切换会话停止本页录音/播报但不取消已受理工作；停止回复不撤销已提交任务。要取消任务必须定位目标并记录取消请求。外部动作是否已完成按回执核对，不能因为听到“停”就声称已经撤销。

<a id="end-to-end-flows-3"></a>
### 未知外部动作结果

```text
请求发出 → 网络断开/进程崩溃 → 结果 UNKNOWN
    → 查询外部系统 / 读取设备状态 / 使用同一幂等标识查询
    → 已完成：登记回执并验证
    → 明确未执行且允许重试：重试原意图
    → 无法确认：保持等待，必要时由主人选择
```

不得在“无法确认”分支默认重试，更不能将日志重放解释为再次执行命令。

## Agent 自主生成、部署、分工与回收



<a id="agent-factory-1"></a>
### Agent 数量与类型不写死

Jarvis 根据任务、环境、已连接设备和资源状况，自主判断应该使用普通程序、单 Agent、固定工作流还是动态团队。角色名称与数量不是预置名单的上限；新领域可以产生新的蓝图。

**2026-10-22 收敛方案 proposed：**Bot 作为可选通道/持续职责绑定，角色蓝图与 Agent 实例使用同一执行底座；完整概念定义归[组合框架](architecture.md#composition-concepts)。通用引擎可以装配成开发者、研究者、生活伙伴或 NPC，具体任务仍受已接通能力及结果验证约束。

“可持续扩展”意味着接口和存储没有人为固定的角色数量上限，可以随资源增加扩容；每次部署仍有明确的资源、预算、委派深度、时间与终止条件。有限机器和预算不支持字面意义的无限活跃实例。

| 对象 | 含义 |
|---|---|
| AgentBlueprint | 可复用配方，定义见[概念表](architecture.md#composition-concepts)；由工厂解析依赖并选定版本 |
| AgentInstance | 本次工作身份，绑定 RunSpec、任务及上下文；运行状态不写回蓝图 |
| Worker / ModelDeployment | 实际执行与推理资源；由同一资源准入分配，逻辑角色可以共享 |
| TeamPlan | 一次任务的角色、依赖、分工、预算和部署方案；具体字段归[装配契约](contracts.md#composition-contracts) |

这些对象不是一一对应。许多逻辑角色可以休眠或共享少量 Worker；一个复杂任务也可以使用多个工作者。生成 Agent 通常先生成配置与工作流，只有确实缺少能力才研发新代码。

<a id="agent-factory-2"></a>
### 自主组队流程

![agent-team-lifecycle](diagrams/agent-team-lifecycle.png)

[矢量图](diagrams/agent-team-lifecycle.svg) · [可编辑图源](diagrams/agent-team-lifecycle.mmd)


新设备接入后先认证与能力探测，再在必要时生成对应 Agent；不因发现设备就自动取得控制权。设备离线后撤销对应可用能力，持有该设备任务的 Agent 保存状态并重新规划。

<a id="agent-factory-3"></a>
### 工厂和团队控制器

Agent Factory：寻找已有蓝图、生成候选蓝图、验证工具与契约，登记不可变版本。
- Team Controller：观察任务结果，决定重分工、拆分合并和扩缩，不自行增加总预算。
- Capability Observer：维护带时间戳的设备与模型能力快照；执行前重新验证关键能力。
- Deployment Scheduler：选择节点、申请资源、部署 Worker，并处理失败和迁移。
- Agent Registry：维护身份、版本、父任务、租约、状态和产物。
- Resource Governor：统一管理 Agent 与普通模块的配额，不按 Agent 名字分配特权。

这些是逻辑模块，初期可组合到现有工作者和 node-host 中。

<a id="agent-factory-4"></a>
### 委派不会扩大权限

子任务继承主人目标与 G0，权限是父任务可委派权限的子集。预算先从父额度预留，再授予子 Agent；不能所有子 Agent 都把父任务的剩余金额当作各自预算。

子 Agent 可以提出进一步分解，但必须经过工厂和准入。所有后代绑定 root_task_id、delegation_chain 和 security_epoch；不能通过生成新身份、调用外部 Agent 或请第三方做事脱离约束。

外部 Agent 和第三方服务必须有明确能力、数据范围、预算、超时与取消契约。不支持可靠取消或幂等的服务，不能被包装成“可完全控制”的本地工作者；出现停机时必须如实报告未确认部分。

<a id="agent-factory-5"></a>
### 生命周期

```text
proposed → validated → admitted → deployed → running
    → draining → checkpointed → sleeping / retired
    → failed / quarantined / terminated_by_security
```

退休时撤销能力凭据、停止模型订阅、释放资源和设备占用；需保存的经验经过知识晋升。security terminated 状态不能自动被“任务恢复”转换为 running。

<a id="agent-factory-6"></a>
### 关键契约

角色蓝图、一次装配、Agent 实例及调用上下文的完整字段统一维护于[组合运行契约](contracts.md#composition-contracts)；原 purpose/工具/输入输出/预算/父任务/节点/G0/安全代际均保留，不再在任务章维护第二份可漂移的 YAML。当前 schema 和实现不因文档字段新增自动迁移。

多 Agent 仍需结果证据，不能通过多数投票决定事实或放宽 G0。默认使用本机有界调度和共享模型端口，不为每个角色创建常驻服务。Ray 等框架只作为已有集群需求时的对照材料，逻辑资源声明不等于操作系统硬隔离。[S29](references.md#s29) 组件选择受[普通 PC 准入规则](stack-project-layout.md#technology-selection-4)约束。

<a id="composition-execution"></a>
### 从自然目标到可恢复运行的装配流程

**proposed。** 本节定义流程，状态枚举仍复用[既有任务状态机](#interaction-tasks-3)，不增加平行账本。

1. **理解目标。** 个人核心区分交流、当前行动、否定、引用及未来愿望；关联本轮原文和既有有效授权。普通聊天直接回复。行动缺信息时先做可独立部分，只有影响执行的歧义才请求补充。
2. **发现能力。** 读取 Registry 与 SelfModel 的有界快照；查询环境、设备、账号、权限、网络和验证范围。只登记了技能却没有执行器时明确能力缺口，不能返回“已经会做”。
3. **选择方法。** 比较确定性操作、固定工作流、单 Agent 多技能和团队；先复用蓝图。规划器可以提出新配方，Composer 验证依赖、契约、必要输入、工具范围、数据用途和评估要求。
4. **固定本次配置。** 将选定蓝图、技能、工具、模型策略、上下文来源修订、任务图和终止条件写成 RunSpec；Task Runtime 以稳定请求编号完成去重、预算预留和受理。权限仅引用已有许可，不来自技能文本。
5. **按步执行。** Worker 获取资源后运行确定性步骤或 Agent Runtime。模型提出的工具意图先通过原动作入口；能力/权限/取消/节点代际在执行前复核，领域连接器持有真实副作用。
6. **等待与恢复。** 等授权、网络、资源、定时器或外部结果时保存检查点，释放 Worker/模型槽。读请求按允许策略有限重试；写请求结果未知时先查询原 action_id/提供商回执，不因换模型、换角色或重启重发。
7. **动态调整。** 有证据表明路径不可用时重规划未执行部分；保留已完成动作与依赖，重新分配父任务剩余额度。新子任务仍受委派深度、总成本、截止时间和无进展次数约束。
8. **交付及学习。** 以产物/环境检查为完成证据；模型意见可补充解释，不能自行覆盖独立验收。结果摘要交回个人核心；经验按原候选/知识晋升规则处理。释放租约，长期职责休眠至下一事件。

同一请求的重送必须返回原受理结果；相同动作编号配不同参数拒绝。模型连续重复同类失败、没有新证据或达到预算时，暂停该任务并记录可接续条件，不停止其他正常任务。控制完整性违规仍服从 G0 的全局锁存规则，不能当普通业务失败处理。

组合例：主人要求“制作单词小游戏并帮我学习”。先创建一个共同目标，开发与教学子任务共享获准的词表引用；编码角色输出可运行候选，测试角色用独立案例核验，教学角色生成计划。只有主人授权长期跟进时才登记 BotBinding；游戏产物、个人错题和通用开发经验分别存入对应领域，模型和角色数量由实际工作决定。

<a id="composition-runtime-cycle"></a>
#### 一步认知循环与完整调用时序

![从自然请求到可验证结果的运行时序（目标）](diagrams/composition-execution.png)

[SVG 放大查看](diagrams/composition-execution.svg) · [唯一图源](diagrams/composition-execution.mmd)。此图为目标流程；不要求每个方框调用一次模型，也不要求每次请求创建 Agent。

| 步骤 | 输入由谁提供 | 负责组件 | 输出与继续条件 |
|---|---|---|---|
| 识别和关联目标 | 主人当前请求，或已授权的事件绑定；检索到的正文不充当命令 | 个人核心与原受理入口 | 普通回答、需要信息的请求或可执行目标；记录原轮次来源 |
| 查前提并装配 | 能力目录、环境观察、作用域和预算 | Planner 提候选，Composer 做确定性解析 | 有版本和摘要的 RunSpec；缺依赖应说明缺什么，不假造工具 |
| 受理并给出进度 | 固定规格与原 request_id | Task Runtime / 原领域任务所有者 | 原任务 ID、预算预留与依赖；相同请求返回同一回执 |
| 准备认知步骤 | 当前检查点、已确认动作结果及当下有效的资料引用 | Context Service + Agent Runtime | 有界上下文；技能按当前步骤加载，未选的技能与全部历史不入 prompt |
| 决定下一步 | 模型输出或确定性规则 | Agent Runtime 产候选，Task Runtime 核对 | 结构化响应、动作、子任务、等待或变更提案；格式错误不能执行自由文本 |
| 产生现实效果 | 核定工具参数、范围和原动作编号 | Action Gateway + 领域服务/Worker | 真实结果或明确的 UNKNOWN；秘密仅由需要它的执行器解析 |
| 固定可恢复进度 | 原动作回执和结果证据 | 原任务所有者 + 检查点存储端口 | 原子修订或有界跨域对账；不能先将“已完成”显示出来再补业务写入 |
| 验收、汇报与纳入经验 | 产物、规则检查及必要的独立评价 | 领域验证器、个人核心、记忆/知识域 | 结果、局限、未结事项；经验先成候选，不自动成为长期真相 |

Agent Runtime 的最小循环是“观察 → 提议 → 交还控制”。运行引擎不应在一次调用里私自无限执行工具；外层根据预算、取消和实际进展决定是否还有下一步。等待网络或 Google 授权时返回等待条件，不让模型反复分析同一页来保持活跃；纯查询或固定转换可沿确定性路径完成。

技能切换发生在步骤边界：先确认上一动作结果，再加载下一方法。未用到的资料不传给新角色；跨项目、账号或虚拟世界时采用新用途视图。新工具超出原规格、来源发生实质变化或需要新增效果时，提出规格修订，宿主核对已有授权是否覆盖；已经覆盖的可自动继续，不重复询问；不覆盖的才需要补充必要信息或权限。

<a id="composition-recovery-flow"></a>
#### 等待、有限重试、取消和重启接续

![恢复时先查原任务与动作，不盲目重放（目标）](diagrams/composition-recovery.png)

[SVG 放大查看](diagrams/composition-recovery.svg) · [唯一图源](diagrams/composition-recovery.mmd)。图中等待原因是既有任务状态的附加语义，不创建第二套可以独立决定执行的状态机。

| 情况 | 本任务怎样处理 | 自动继续的条件 | 对其他活动的影响 |
|---|---|---|---|
| 缺少必要输入 | 保存已完成步骤与精确缺项；可独立的步骤继续 | 补充内容到达，核对原计划修订 | 其他聊天/任务正常受理 |
| 资源不足 | 排队或保存检查点，释放未使用的预留 | 调度器实际发放所需资源并重新核对期限 | 保留前台优先通道，不能由后台忙等占满槽位 |
| 首选模型限流/不可用 | 按原用途和成本策略选备选，累计实际调用成本 | 备选允许接收本次资料且符合剩余额度 | 同提供商共享配额仍可能影响其他调用，需要按真实配额域退避 |
| 网络不可用 | 能离线完成的步骤使用已安装能力，其余登记等待 | 网络恢复事件或有界探测成功，仍须重新准入 | 不关停整个 Jarvis；无网络时不能承诺自动下载缺失模型 |
| 账号授权失效 | 复用原账号恢复流程；等待本人必须的官方步骤 | 回调确认实际账号、scope 与原任务仍匹配 | 邮箱等待不占聊天的模型槽，也不重复创建连接任务 |
| 可重试读取/无副作用计算失败 | 有总次数、总期限及退避；记录错误指纹和改变了什么 | 有新条件或允许的下一尝试；不得每次切模型都重置计数 | 只影响此依赖分支，其他无依赖步骤继续 |
| 写入已发出但未收回执 | 保留原 action_id，查询提供商/领域记录 | 证据确认结果；若明确未完成且原协议允许，才可重试 | 未知不是成功也不是可重发失败；不阻塞无关任务 |
| 多次无进展 | 暂停该任务，给出最后证据、剩余部分与继续条件 | 人的新信息、环境实质变化或明确重新分析修订 | 不自动停止其他任务，也不后台偷偷新建同等循环 |
| 主人取消 | 先阻止新步骤，再协作取消在途调用并接收迟到回执 | 取消不是等待；不能由网络恢复或重启自动复活 | 取消范围按原任务/子任务规则；已发生的外部效果需另行补偿 |
| 宿主重启 | 读原权威状态和检查点，确认所有权、版本、撤销和动作结果 | 所有核对通过；仅继续未完成且可安全执行的部分 | 单个损坏任务隔离；基础聊天能恢复时不必等全部后台对账完成 |

检查点保存可恢复的步骤位置、资料引用、可见工作摘要和已观察结果引用，不保存模型的隐含思维链，也不将“模型认为已成功”作为业务事实。进程正在执行但没有结果时，恢复方必须依据动作协议判断能否重试，不能因为 Python 函数没有返回就认定没发生效果。

普通错误按任务隔离；控制完整性违规仍走原 G0/锁存/停止规则，不由本节另设自动解锁。可取消与能撤销也是两件事：取消模型请求不能保证远端未计费，取消邮件任务不能收回已送达邮件。对不能取消的外部作业保留真实占用或未决用量，不把本地释放记录误当作供应商资源已释放。

<a id="composition-scenario-assembly"></a>
#### 同一框架怎样服务不同生活和工作目标

下表是装配示例，不表示这些完整场景已实现。选择多少 Agent 由依赖、隔离和收益决定，原个人记忆与授权仍是前提。

| 主人表达 | 推荐装配 | 共享什么、隔离什么 | 结果与扩展点 |
|---|---|---|---|
| “看看邮箱，告诉我今天最要紧的事” | 已有读取工具 + 邮件整理方法；需要语义分类时单实例 | 邮件域读取获准账号；必要的个人优先级按用途视图供给，不上传密码 | 邮件证据、重要事项和候选提醒分别保存；邮件正文里的指令不成为任务 |
| “做个小游戏，再教我怎么改” | 同一目标下需求/实现/教学步骤；复杂时另设独立检查实例 | 共享受准入的项目产物引用，教学可取获准的学习偏好 | 先验收可运行文件，再给教学说明；专业化是技能组合，非复制多个模型 |
| “帮我安排旅行，邮件里有订单” | 旅行资料/日程/邮件子任务按域分开，个人核心汇总 | 订单中必要事实有来源交接；护照、支付和登录凭据不直接进入通用研究上下文 | 方案可先完成；订票、支付须有对应工具和有效授权，不能靠角色名获得能力 |
| “以后每天晚上陪我学英语” | 一个学习蓝图 + 已授权的长期 BotBinding + 原定时能力 | 长期保存学习进度；每次只取适用错题和时间偏好 | 到点唤醒，安静时间和频率由绑定策略控制，不创建永不退出的 LLM 循环 |
| “模拟一个有几十名居民的小镇” | World Engine + 批处理规则 + 按需 NPC 实例 | 共享世界事实；NPC 各有局部认知，虚构经历与主人现实记忆隔离 | 只在关键互动调用模型；角色规模与同时活跃数量分别受限 |
| “你处理这类事情总失败，自己改进” | 诊断证据 → 研发蓝图 → 原候选/独立评估/发布链 | 候选源码与生产数据隔离；评估标准不交候选随意改 | 优先修方法或工具，必要时改 Runtime；失败回退按状态兼容处理 |

这些场景都复用“输入与授权 → 有界装配 → 任务与动作 → 结果证据 → 候选学习”，但不合并各领域事实和事务。邮件、个人偏好、项目结果、公共知识及模拟状态的保存位置继续按[记忆分域](knowledge-learning.md#memory-scope-model)执行。

<a id="resource-scheduling"></a>
## Agent、模型与模块的统一资源自调度



<a id="resource-scheduling-1"></a>
### 所有工作使用同一资源账本

CPU、内存、显存、模型请求槽、Token 额度、费用、存储、网络、电量、温度约束、设备独占权和用户等待目标都纳入调度。普通程序、索引重建、语音模型、NPC 和 Agent 不能各自绕过全局资源额度。

资源租约应包含 node_id、scope、reserved、limit、deadline、priority、reclaim_policy、parent_budget_ref 与 security_epoch。额度发放与回收需要去重，失联节点的额度不能在未确认或未到期前被重复发放。

<a id="resource-scheduling-2"></a>
### 优先级

1. 独立监督、告警、停止和实体设备安全控制：有专用保留，业务调度不能收回。
2. 主人实时交流、重要信息受理、新任务交办及已有任务的查询、纠正和控制：保有不可被后台工作占用的服务容量。
3. 正式工作在剩余可用资源内按主人指定顺序、期限、重要性与依赖协调；紧急任务也不能吃掉交流与控制的保留。
4. 自主学习、进化实验、知识重建和虚拟世界扩展。

主人可调整业务优先级和资源预算；不能把监督资源分配给模型。学习或模拟若是主人的当前主要任务，可提升其业务优先级，但仍不能覆盖 G0 或停止控制。

**2026-10-26 产品要求 accepted，调度实现 proposed。** 优先级不能只按先来先做、模型自评或“占用资源最多”排序；紧急与重要分别记录，使用可解释规则形成有效顺序：

| 判断项 | 来源与作用 | 不允许的推断 |
|---|---|---|
| 主人明确指令 | “先做 A”“B 暂缓”“今晚交付”绑定任务 ID、原消息和修订；在可行范围内优先遵守 | 不把资料中引用的命令当主人新指令，不顺带取消其他工作 |
| 紧急性与期限 | 明确截止时间、剩余工作估算及余量；估算不确定时显示区间或未知 | 不因“看起来很急”虚构截止时间，不承诺资源不足时仍按时交付 |
| 重要性与延误影响 | 主人偏好、目标价值、已有承诺、延期影响；区分明确事实与推断 | 模型不能自行把自己的研究升级为最重要任务 |
| 依赖与解除阻塞 | 优先推进能解除重要父任务阻塞的前置步骤，临时继承其业务优先级 | 继承优先级不扩大权限或突破交流保留；同一父任务拆成大量子任务不能多抢份额 |
| 等待、公平与成本 | 等待老化、有界轮转、已承诺的最低进展份额；考虑剩余时间、切换成本与资源适配 | 不让小任务永远插队饿死长任务，也不让低优先级锁持有者无限拖住高优先级工作 |

先校验有效授权、依赖、期限与资源是否可执行，再在同一业务层内排序；无依据时使用普通优先级和稳定的先后顺序。模型可以从话语提议上述字段，确定性调度器负责裁决与记录简短理由，不保存隐藏思维链。已有明确偏好直接沿用；只有多项承诺确实无法兼得或对象有歧义时，询问受影响的取舍。任务价值、完成期限和“是否现在打扰主人”分别判断；高优先级不等于持续弹窗。

<a id="resource-scheduling-3"></a>
### 自适应决策

每次新增 Agent 或扩大模型并发，比较预期收益、协调成本、资源代价和等待时间。无收益或资源不足时可以排队、批处理、减少上下文、换模型、降低世界刷新频率、迁移任务、休眠或缩小范围。

采用迟滞与冷却，避免资源稍有变化就频繁装卸模型和迁移 Agent。监测实际内存与 GPU 使用；仅在调度器里声明“使用 1 个 CPU”并不会强制物理隔离。[S29](references.md#s29)

个人设备版本的扩展优先采用有界 Worker、模型复用与已配对节点间的任务分配。Kubernetes 扩缩容资料 [S30](references.md#s30)仅供明确服务器集群需求时参考，不列为后续必经升级；增加 Agent、运行 NPC 小镇或连接第二台 PC 都不自动构成引入它的理由。具体组件准入统一归[技术栈规则](stack-project-layout.md#technology-selection-4)。

<a id="conversation-resource-isolation"></a>
#### 普通 PC 的并行、保留与公平调度

**2026-10-26：交流保障与多任务并行为核心产品要求 accepted，完整实现和混合负载验证仍 proposed。** 聊天承担重要信息、新任务和任务命令的入口，不能因研究、渲染、出图、索引或模型长请求而失去响应。目标包括输入可受理、有内容的回答保持正常响应、明确控制可及时处理；只让输入框能打字或立即显示“收到”不算达标。后台不得造成可感知的聊天变慢；量化门槛和适用负载只归[并行验收](delivery-validation.md#conversation-separation-validation)。外部供应商耗时、断网与本机耗尽需分别报告，不能把目标宣称为任何条件下绝对零延迟。

多个独立工作必须能实际推进，不能永久用一个全局串行执行槽代替多任务。相同文件写入、设备与桌面控制、同一扬声器仍按冲突规则串行；只有相关步骤等待。采用资源池隔离（Bulkhead）思路，保留本地有界队列、少量按需进程和同一任务账本，不因并行新增第二个助手核心。[依据](references.md#conversation-isolation-sources)

| 逻辑通道 | 初始实现建议 | 资源与失败边界 |
|---|---|---|
| 控制 | 停播、取消、健康查询独立受理 | 不等待模型槽、任务 FIFO 或长数据库写锁；保留小型队列与控制线程 |
| 语音输入/输出 | 一个活动采集会话、一个播放所有者；STT/TTS 独立有界工作 | 音频环形缓冲和短段限额；落后时报告缺帧/重录，不积累分钟级未处理音频 |
| 对话 | 输入与指令受理独立于回复生成池；按设备验证的活动回复数保留专用容量 | 当前实现有两个回复槽，但并非完整输入隔离；后续输入可受理，补充/纠正有独立代际，不取消后台任务；旧远端请求的槽和费用到真实结束才释放 |
| 正式工作 | 从现有单槽迁移到按资源类型准入的多个有界执行槽，共用原任务语义 | 长规划、工具和渲染按阶段分配；独立步骤并行，冲突步骤串行；通用并行不得借用对话槽 |
| 维护/学习 | 空闲时借用容量 | 压力时在安全点让出；不依赖先完成知识提取、索引重建或进化才能回答 |

统一预算是准入决策的权威，不是把所有工作塞进一个总队列。前台/后台分别预留推理并发、CPU 时间和内存空间；服务连接池、供应商请求并发与速率额度也按用途分配。**两套供应商配置或两个 API key 并不自动获得独立配额**；同账号/项目限制必须按实际配额域合并计数。供应商慢或限流时，只延期相关请求，状态与控制仍可响应；有可用且获准的备选才切换。

有界输入箱保存原会话、消息/命令 ID、接收顺序及目标修订；界面区分“输入已保存”“任务已受理”“动作已生效”。回复槽全忙时仍受理重要补充、新交办、问题答案和明确控制；语义未解析不能假称任务已执行。模糊指代仅阻塞对应命令，已明确的任务 ID 或按钮控制走独立确定性路径；长语义规划转后台，前台保留简短沟通。输入溢出或持久存储失败时保留可恢复草稿并明确未接收，不能丢消息或虚报成功。后台日志、通知和成果推送节流合并，不占用输入的保留容量。

后台执行器、知识提取、邮件 AI、3D 规划和研发均须经相应用途准入，不能绕道调用对话池。当前部分 3D 规划仍复用聊天槽，是待消除的资源竞争；来源独立的线程池也不证明整机资源已经隔离。后台云调用同时受并发与 RPM/TPM 的前台预留限制；不可回收的远端调用不能借走硬保留后声称可瞬间让出。请求重试、候补与未知费用仍计原任务预算。

现有 `foreground_reserve_mib=1024` 仅是后台内存准入阈值，不是已分配给语音的内存，也不是完整语音足够运行的证明。新准入须依据实测 STT、TTS、LLM 驻留峰值、系统余量和 UMA 重叠计数设计。首版 STT/VAD 优先 CPU，GPU 留给经验证的 TTS/本地 LLM；预热只在用户开启语音且预算允许时进行，空闲卸载使用迟滞，避免反复装卸。

GPU 长内核或不支持取消的本地推理不能靠 `async` 强行抢占。应在准入前禁止超额常驻，并把背景推理切成可取消/可检查点的小批；必要时减少背景并发、延期某个环节、使用经验证的较小组件或获准云端候补。线程池适合有界 I/O，重 CPU 推理放现有独立进程/原生运行时；不依赖 Python 线程数声称 CPU 隔离已经实现。

持续聊天也不能把已承诺工作永久饿死。采用加权公平调度、等待老化、截止时间和有界前台突发；在交流保留之外为已准入工作提供最低进展份额。机器不足以同时满足二者时，默认减少后台并发、推迟新重任务、释放闲置模型，显示具体瓶颈与延期任务；需要主人选择的是哪些工作先做、是否延期或采用已允许的其他途径，不能把关闭聊天保障作为日常取舍。不可抢占动作在准入前须有界并核对最坏资源占用，已提交后等到安全点，不为提速盲杀或重复执行。

锁仅保护短状态变化，数据库事务内不做模型/网络/音频/文件扫描。SQLite WAL 仍只有一个写入者，不能把 WAL 当作无限写并发。任务受理/状态事件同事务写入已有任务账本；跨会话存储用幂等引用和对账，订阅端断开不丢任务。优先级倒置、磁盘满、锁等待与线程池饱和均须进入[并行验收](delivery-validation.md#conversation-separation-validation)。

<a id="resource-admission-loop"></a>
#### 有限本机资源的准入、让出与回收

一次调度只为下一可执行步骤发放租约，不把一个等待用户或网络的长目标永远绑定到全部计算资源。事件触发重算，资源观测采用有界采样和冷却，不持续调用模型来决定是否空闲。

1. **采样与预留：**观察整棵进程树的 CPU、内存、显存、磁盘 I/O、网络、温度/电量以及模型额度；先扣除操作系统、恢复/控制与交流保留。模型驻留、KV 缓存和派生 Worker 均计入；未知占用按保守估算处理。
2. **选择可运行步骤：**检查依赖与[业务优先级](#resource-scheduling-2)，为 CPU、GPU、I/O、云模型及独占设备分别使用有界池。并发是资源向量同时满足的结果，不用一个线程数代表全部容量；硬限额、实测容量、交互延迟门槛三者取最严。
3. **原子认领并执行：**任务/动作所有权、预算预留和租约具备修订与幂等语义；多个 Worker 不能取到同一步。仅在短事务中认领，模型/工具在事务外执行；同文件/项目输出采用冲突锁及版本检查，不直接删除现有全局锁后扩大线程数。
4. **反馈与让出：**当聊天延迟接近门槛、可用资源下降或新重要任务到达，先停止追加后台工作，再在已验证检查点让出低优先级步骤；仅支持取消的模块不能伪称可暂停恢复。无法抢占的长 GPU 工作须提前限制批次或延期；在已允许且能力/费用满足时才选云端或其他节点。
5. **释放与接续：**等待主人/依赖时释放可释放的 CPU、GPU 和执行槽，保留已完成产物及恢复状态；在途远端请求与 UNKNOWN 费用不得提前回收。故障、超时、重启通过原账本核对，确认租约所有权和效果后再接续。

设备性能配置从本机测量建立；并发上限、前台保留、后台预算与可接受期限可在设置中查看，不能默认用满全部 CPU/显存。先以保守配置验证，再阶梯增加并发；延迟超标自动收缩到上一次已验证档位并给出原因，增加容量使用迟滞，避免抖动。未知 GPU 指标、过热/电池或磁盘压力时保留交流，限制受影响的后台阶段。统一状态呈现只归[工作状态](interaction-persona.md#desktop-presence-state)，字段只归[调度契约](contracts.md#scheduling-contract)。

<a id="resource-scheduling-4"></a>
### 能力快照与重新规划

快照包括设备能力、已安装模型、可用工具、协议版本、信任域、连接状态、资源和时间戳。调度计划使用快照；真正行动前再次校验关键资源。

摄像头失联时，对依赖视觉的任务暂停或降级；GPU 失效时减少后台推理并切到已验证 CPU 路径；共同体节点离线时，不擅自复制尚未对账的现实动作。

<a id="resource-scheduling-5"></a>
### 从小到大的实测扩展

**2026-10-26 改造前源码基线（历史对照，不是当前容量）：**[普通对话](../host/dialogue.py)两个回复槽；[通用执行](../host/core.py)一个按数据根独占执行槽；[规划/研发](../host/background.py)共用一个后台槽。[出图](../host/image_generation.py)、[3D 工作室](../host/studio3d.py)、[邮件](../host/mailbox.py)、[索引](../host/knowledge.py)与[知识提取](../host/knowledge_extraction.py)各有单通道约束，但 3D 的部分规划复用普通回复池，研发执行阶段也会争用通用锁。槽数不能直接相加为任意任务的整机并发数，接收/排队数不等于实际执行数；后台统一配额与聊天响应保障尚未全接通。

规模测试按阶梯增加身份数量与活跃任务，记录吞吐、互动延迟、事件积压、成本、内存、错误率和角色一致性。达到预算或质量门槛后停止扩容，不能只用“成功创建了很多 Agent 对象”证明可用规模。

<a id="bounded-concurrency-runtime"></a>
### 有界并发 1.0.0：当前实现与使用

**2026-10-26，implemented；验证范围见[本轮证据](delivery-validation.md#bounded-concurrency-evidence)。** 本节取代上方“改造前基线”作为此版本的容量说明；仍未实现完整的跨模块物理资源与供应商配额隔离。

| 通道 | 当前行为 | 边界 |
|---|---|---|
| 普通聊天 | 两个专用回复槽；至多 32 个未结束输入，先持久保存再受理；当前回复期间可继续发送 | 同一会话按顺序回复。新增消息不会自动修改正在执行的任务；明确任务停止与优先级可由工作状态直接操作 |
| 3D／机械场景模型规划 | 使用一个独立后台回复槽，至多 8 个未结束输入 | 不占聊天的两个执行槽；仍可能与聊天共用同一个供应商额度 |
| 通用任务 | 默认两个执行槽，可配置 1–4；实际不超过逻辑 CPU 数的一半，至少一个；未结束派发请求默认上限 32 | 本轮确认两路独立内置任务执行重叠。三／四路仅是候选档位；插件与 MCP 冲突类保守串行 |
| 目标规划、能力研发／成长 | 保留既有一个后台模型槽 | 尚未统一成持久优先级队列；繁忙时记录仍可查看与显式重试，不伪称已经排队 |
| 出图、3D 制作、邮件、索引与知识提取 | 保留各模块原有限流；工作状态读取近期原始记录 | 不把这些槽数简单相加为整机保证；私密对话、机械场景制作、本地模型操作尚未完整纳入统一视图 |

**操作入口：**工作台右上“工作状态与资源”图标，按需展开运行中、排队中、等待你回答，以及等待条件、未知、失败与完成记录。设置 → 技能与执行 → 后台任务提供同一视图和资源预算；原任务创建、回执与历史账本收在折叠区。顶栏与主题仍遵守既有交互规则。

**调度和资源准入：**优先级、重要性、期望完成时间、安排理由及修订号保存在原任务 ID 上。排序包含优先级、重要性、临近期限和等待老化；每等待一分钟加一个老化分，上限 24，使较早的普通任务有机会越过新来的高优先级任务。规则只影响尚未开始的派发，不承诺任意期限可达，也没有替代用户指令的自然语言优先级识别器。默认为系统和聊天保留 2048 MiB 可用内存；CPU 达到 80% 后暂停新准入，并保持至少两秒冷却。已有前台消息排队时同样暂缓新通用任务。内存指标未知时排队，原因可见；内存配置是准入余量，**不是 OS 硬内存预留或全进程树强制限额**。已开始的不可抢占步骤继续到原检查点。

**聊天检查路径：**已迁移的会话连接不申请迁移写锁；历史按会话／时间索引读取。每轮回复复用本线程连接，检查点仅读取会话头，在新的短读取快照中核对引用、作用域与撤回，避免反复解码整段历史；这不缓存授权判断或减少检查频率。

**同一账本与恢复：**`task_dispatch` 只附加调度意图，不复制任务正文或执行回执。单个派发宿主持有所有权，活跃任务共享一次 OS 执行租约；只有该组首个任务启动前进行全局恢复，避免把另一活跃线程误判为遗留动作。每个任务绑定不可重复使用的线程许可；管理／CLI 仍受原独占锁约束。未派发输入和任务排队意图重启后保留；已派发但结果未知的动作标记 UNKNOWN，先核对原回执，不自动重做。取消只作用于指定任务／回复，等待队列中的其他工作继续。

**状态真实性：**未点击启动的就绪任务显示“等待条件／尚未启动”；真正受理的任务才显示“排队中”，附资源、冲突或槽位原因。统一视图对目标、研发和实际任务关联去重，并优先保留活跃记录，避免较早运行的任务被新历史挤出；来源不可用或尚未接入时明确说明。快照每两秒按需刷新，页面隐藏后暂停刷新；服务失联提示数据可能过期，不能将未接入、过期和未知显示成没有任务。

**仍待完成：**所有模块共享的供应商／Key 额度保留与退避、GPU／显存／温度的统一准入、原生精灵订阅、强制进程资源限额，以及“重要信息＋新任务＋修改命令”的完整语义识别。当前 UI 可受理同会话后续消息，不代表模型已立刻理解或执行这些命令。后续继续归入 K2 和既有 V-DLG 验收，不另建开发路线。

<a id="critical-review-6"></a>
## 补足预算与委派协议

这些状态在首期由 Task Runtime 通过 control.db 维护；跨节点通过有身份、代际和幂等键的消息投影，不能多个数据库同时自称权威。

**预算预留：** `requested → reserved → consumed / released / uncertain`。

- 幂等键是 `parent_budget_id + allocation_id`，重复申请返回同一结果。
- 受理任务、为其预留额度、登记动作意图和 outbox 在同一事务提交；未提交不发出执行许可。
- Worker 启动失败且有证据未消耗时释放；费用或外部效果未知时转 uncertain，仍占额度，不因超时自动退款。
- 回执以唯一 receipt_id 去重，记录已消费和可证明未使用的余额；迁移只能转移剩余授权，不能在目标重领全额。
- 子预算总额不超过父预算。外部服务不能严格限制最终收费时，使用预留余量、上限接口或拒绝不符合硬上限要求的动作，不能声称本地账本能控制所有供应商计费。

**任务委派：** `proposed → granted → accepted → active → revoked / closed`。

- 协调者写入 granted 和 outbox，绑定 assignment_id、owner_epoch、目标节点、资源范围、预算和期限。
- 目标节点幂等接受并回执；ACK 丢失通过查询同一 assignment_id 恢复，不另创建重复委派。
- 只有有效授权、代际和租约均通过执行端检查才 active；accepted 本身不意味着外部动作已执行。
- 撤销时保存已知/未知效果并对账。重新分配遵循[离线自治与联网共同体](federation.md#offline-federation)唯一权威和 fencing；不能仅靠原节点心跳超时推断其没有执行。
- 委派结束不删除动作回执和预算证据，保留到重试、离线和审计窗口结束。

这些状态说明了最小语义；完整 schema、数据库约束和形式化模型仍列为 M0 交付，不能把本节当成已验证协议。

## 个人邮件管家：从收件到办事（方案，2026-10-21）

本节为完整产品目标 proposed；当前 Gmail 连接、读信、草稿与受审阅操作已独立实现，见[Gmail 当前运行能力](#gmail-runtime)；完整后台同步和主动提醒仍未实现。默认是否启用及允许动作由主人的有效配置决定。

<a id="mail-management-experience"></a>
### 面向主人的视图与自然交流

主入口展示“需要我处理”“重要通知”“等待对方”“账单与行程”“订阅与低优先级”“可疑与垃圾”六个可重叠视图；它们是同一邮件记录的分类和工作状态，不复制六份正文。账号、项目和联系人作为筛选条件；Gmail 原始目录、未读数与本地待办数分别显示，避免把“看过”误认为“办完”。顶栏仅保留符合[图标规则](interaction-persona.md#workbench-settings)的邮件入口和状态；展开右侧可关闭、可调整宽度的面板，不长期挤占聊天。

可说“今天什么邮件需要我管”“找上次酒店确认”“这类广告以后别提醒”“帮我回复并等他确认”。后端返回来源邮件、判断理由、拟执行动作及当前状态；信息不够时先做查找／草稿，只有收件人、日期或操作范围确实影响结果时才澄清。“整理一下邮箱”不能自动等同于删除全部低分邮件。连接请求、查询请求、规则修改、实际发送必须进入不同能力，避免现有 Gmail 配置词法入口吞掉后续邮件任务。

<a id="mail-management-triage"></a>
### 判断重要性：优先级、可信度与待办分开

| 场景 | 判断依据与展示 | 默认建议行为 |
|---|---|---|
| 安全、支付失败、行程变更、临近截止 | 结合内容、实际日期、已确认的订单／行程和联系人；发件人自称紧急只是信号，不能单独证实真实性 | 高优先级提醒，显示证据与核对入口，不自动点击支付／重置链接 |
| 需要回复、审批、交材料 | 区分“在征询我”与群发抄送，提取截止时间、依赖和会话线程 | 进入待处理，起草或生成可修改行动；未得到结果不标为完成 |
| 等待别人回复 | 主人已发送且有待确认事项；不是所有已发送信都需要追踪 | 到期提醒，允许暂停／取消；自动催办另按预授权范围执行 |
| 账单、快递、会员、旅行 | 区分通知、收据、失败、临近续费和变更 | 聚合为订单／行程卡，必要时建议加入日程；不自动付款或订票 |
| 新闻、促销、社区消息 | 明确的订阅信号、重复内容、主人已纠正的偏好 | 放入摘要或静音；保留检索和查看“为什么被归类” |
| 垃圾、钓鱼、伪冒 | 来源线索、正文矛盾、危险附件与链接等多信号 | 标为可疑，隔离展示；模型判断不能保证识别所有诈骗，也不等于远端已移入垃圾箱 |

记录至少分开四条轴：**紧急程度、来源可信度、是否需要行动、分类置信度**。陌生发件人可能很重要，VIP 也会发无须处理的内容，营销信也可能含退款或订阅扣费通知。低置信度、关键截止与安全类冲突进入复核集合，不直接归档。亲友、公司、订单等关联只能使用主人已允许用于邮件的有限资料；不会因共享个人记忆而获得查询所有项目或私密资料册的权限。

邮箱服务已有的垃圾、类别和重要性信号可作为可解释输入，并与个人规则结合；供应商标签是弱信号，不等于来源认证。订阅/营销、疑似诈骗和重要通知分别处理，新规则先在有来源样本上验证。

先运行确定规则和去重，只有新内容、歧义或明确请求才选择模型。用户纠正生成带出处、范围、有效期的规则候选；“这个发件人不要提醒”和“以后所有广告都删掉”不是同一授权。忽略一次、未读、只读不回不能直接训练成永久偏好。规则可预览影响数量、解释命中、撤销并恢复原视图，作用域可选账号／联系人／主题／项目，具有冲突优先级和版本。

<a id="mail-management-actions"></a>
### 动作闭环与少打扰授权

读取和本地判断在已授予范围内进行；通知频率、安静时间、模型费用及自动动作可一次配置后持续生效。初始建议读、分类、摘要及本地草稿，远端动作按需授权。邮件正文不能授予新的长期权限。

1. **发现 → 核对 → 决策。** 有界同步新信和线程，保存出处与版本，区分建议、已排队与已完成；摘要每条可回到原信。
2. **办事。** 一个线程可关联多个可修改行动，沿用原计划、日程、任务队列；单个邮箱授权失效或任务失败只暂停该账号相关行动，前台聊天及其他任务继续。
3. **回复。** 先本地草稿，按需存入 Gmail 草稿；保留线程、Reply-To、附件与收件人核对。发送前绑定账号、To/Cc/Bcc、正文、附件摘要和草稿修订；修改任何一项使旧确认失效。群发、陌生收件人、承诺／费用类默认审阅；自动回复仅限主人明确设置的对象与模板范围。
4. **收尾。** 以供应商回执及后续读取核对远端结果；发送超时记为 UNKNOWN，先查证再决定是否重发。客户端幂等键和 Message-ID 不能保证 Gmail 绝对只投递一次，不盲目重试。归档／移入垃圾箱记录原标签及可恢复信息，永久删除首期不提供。
5. **接续。** 授权恢复后复核原账号、邮件版本、许可、收件人和截止时间；已取消或过期行动不因重连重放。提醒收到、已读、已回复、任务完成分别记账。

退订不能盲点邮件内任意链接；优先展示可靠来源的退订信息，主人授权后按限定方式办理，不能把退订当成可随意向外站提交个人信息的许可。自动屏蔽规则需保留有效期和恢复入口，防止把未来重要新邮件长期隐藏。

<a id="mail-learning-loop"></a>
### 垃圾邮件与发件人风险的持续学习

本节为主人明确要求纳入的目标，完整方案 proposed。MailTriage 区分正常、订阅促销、疑似垃圾、疑似诈骗和待核对，并分别记录重要性、可信度和后续行动。信誉服务和自动训练需独立准入。

- 供应商已有分类与警告，以及来源链可核验时的 SPF／DKIM／DMARC 等认证结果；任意邮件可自带伪造头，不能把找到一行 pass 当成可信证据。无法确认来源时标 unknown，不谎称已自行完成认证。转发、邮件列表等可影响认证结果，不能单项失败就永久拉黑，依据见[S274](references.md#s274)。
- 显示名与实际地址、Reply-To、声称品牌和实际链接域名的一致性；识别可疑相似字符和异常变更。处理先采用离线结构分析，不为评分自动打开链接、提交地址或下载附件；这些信号仍是风险提示，不能保证识别所有伪装。
- 主人明确的联系人／订阅关系、以往纠正与规则，以及索款、索取验证码、诱导执行附件等内容信号。熟人账号也可能异常，联系人白名单只影响优先级，不能关闭内容检查；正常广告、垃圾、诈骗分别治理。

个人学习闭环为：**收到新信 → 解释判断 → 主人纠正或明确规则 → 保存可撤回的反馈 → 候选规则与历史回放 → 留出样本评估 → 在授权范围内试用 → 观察误判并保留／回退**。纠正例子包括“这不是垃圾”“这个地址以后屏蔽”“这种促销只进周报”“订单通知仍要提醒”。单封纠正先作用于该信；是否推广到账号内的同地址、特定主题或整个域，由明确表达与影响预览决定。不因一个坏地址封锁 gmail.com 等整个公共域，也不把跨账号联系人自动合并。

主人直接要求的单信更正可以立即改变本地视图；长期规则按有效授权执行，可预览样本、撤销、限定时效。黑白名单、模型建议、供应商标签分别保留出处和版本；冲突时保留风险提示与可见解释，重要且可疑的信仍能进入待核对视图。只有已授权的远端动作才能真正移动到垃圾箱，当前本地标记不等于阻止服务器投递。模型预测、供应商垃圾标签和信内“请加入白名单”不能伪装成主人反馈；不把自身预测循环用作真实标签来制造越来越高的准确率。

默认持续学习只更新少量规则、样例与排序参数，不在普通 PC 常驻训练或自动下载大模型。规则过多、互相冲突或长期无命中时，提出可解释的合并／到期候选，保留原反馈与恢复窗口；不能因为升级算法就清掉主人纠正。模型／提示词替换、代码和新功能属于[能力成长](evolution-release.md#mail-capability-growth)，与个性化规则学习分别验收，避免每次遇到垃圾邮件都启动一次编程任务。

<a id="mail-management-modules"></a>
### 独立模块、同步与普通 PC 开销

推荐在现有 Python Host／SQLite／任务协调器上增加可替换组件，不部署 K8s、Redis、独立向量数据库或常驻多 Agent：

| 模块 | 职责与可替换边界 | 当前到目标的差距 |
|---|---|---|
| MailProvider | Gmail API／QQ IMAP 适配，报告真实能力和有效授权；令牌由原凭据模块保管 | Gmail 已有有界读取；QQ 未真实联调；尚无远端写操作 |
| MailSync | 分页、增量游标、账号隔离、去重、退避和离线接续 | 当前只有手动最多 10 封列表，无持久化邮件同步索引 |
| MailStore | 账号／线程／来源版本、正文引用、本地分类和工作状态 | 当前为会话资料箱，不能充当完整邮箱；数据保护见[邮件分域](knowledge-learning.md#mail-management-data) |
| MailTriage | 本地规则、可选模型、证据与置信度、纠正回放 | 尚无可验收的个人重要性排序和垃圾分类器 |
| MailAction | 已授权动作、Outbox、修订绑定、不确定结果与恢复 | 当前仅本地草稿；不把模型输出直接作为网络请求 |
| MailBriefing | 合并提醒、安静时间、去重升级、日报与待处理面板 | 当前无自动邮件提醒／日报 |
| MailWorkflow | 邮件到日程、个人计划、项目与候选知识的有限投影 | 已有选定 ICS 的本地提醒和独立草稿基础，邮件自动行动仍待实现 |

各模块另登记功能版本、依赖和回退点，由既有成长中心管理；具体升级与恢复语义唯一归[邮件能力的自主成长](evolution-release.md#mail-capability-growth)。新增功能可从“以后替我识别伪装客服”“增加招聘邮件汇总”等自然需求形成候选；邮件来信本身不能发起功能安装。

Gmail 优先沿用官方 API：定位稳定、可核对结果；MCP 可作为相同能力契约的适配入口，不能代替授权、记忆分域和动作账本。网页／桌面保留为授权及 API 未覆盖操作的补充，不作为常驻刷收件箱的主通道。QQ 适配保留 UIDVALIDITY＋UID，不将 Gmail 的 historyId 语义强加给 IMAP。

本机推荐**按需刷新＋可选自适应轮询＋Gmail history 增量同步**。首次只同步本人选择的近期窗口；游标失效 404 后进入有界重建／补齐并显示未覆盖范围，不假装已扫描整个邮箱。翻页完成并持久化变更后才推进游标；消息／通知重复按账号和供应商编号去重，删除和标签变化保留墓碑。同步事务不直接发送邮件，动作另走 Outbox。断网、休眠、锁定、停止和低资源会暂停；恢复不短时间补发全部旧提醒。[Google 桌面设备建议轮询、history 与 Pub/Sub 的依据](references.md#mail-management-sources)。

可选轮询初始建议 15 分钟、空闲拉长至 60 分钟，手动刷新即时；重试使用带抖动退避和单轮上限。以上是可配置设计值，不是已开启频率或即时通知承诺。Gmail watch 依赖 Cloud Pub/Sub 并需续订，适合以后已有在线节点的配置，不强加给单 PC；watch 续订不是 Google OAuth 本人重授权，也不能混为“每七天登录”。

先取头字段和变更编号，按需展开正文，附件不自动下载。一个有界同步 worker 足够首版，暂停时不加载模型；模型处理按新内容摘要去重，重复刷新不重新花 token。线程摘要保留来源与覆盖范围，不能静默截断后假装读完。优先 SQLite 索引／全文检索，确有语义检索收益再按需嵌入；普通 PC 不因启用邮箱启动一整套多 Agent。批量、缓存、磁盘上限和并发先提供可见配置；128 MiB 任务准入是现有估算，不能作为测得的内存占用或未来保证。

<a id="mail-management-delivery"></a>
### 开发顺序与验收

本节仅细化既有 K0—K6 内的邮件工作，不另建开发阶段。推荐顺序：**补齐 HTML 邮件的安全文本提取及账户数据保护 → 增量收件、搜索、六类视图 → 重要提醒／个人纠正 → 远端草稿与受控发送 → 可恢复整理与预授权自动动作**。首步不需扩大 OAuth 权限；后续写能力必须实际实现并经本人 Google 授权，不能只更改菜单文案。[权限区别](references.md#s270)尤其需要注意：gmail.compose 也允许发送，gmail.modify 也包含发送，gmail.labels 不等于可给邮件打标签；因此供应商 scope 和 Jarvis 动作许可需同时满足。

验收至少覆盖：真实纯文本与 HTML-only 邮件可读；不加载追踪像素／执行脚本；重要信漏报、垃圾误判、混合线程和中文时区截止；VIP 促销与陌生重要来信；可撤销纠正；分页／history 404／重复通知／重启；授权失效不拖住其他账号和聊天；草稿修改使旧发送许可失效；发送超时不盲目重发；本地归档／远端标签语义清楚；来源撤回影响后续摘要和候选。以主人标注的留出邮件集统计重要信召回、误提醒数、待办提取准确性和每百封成本，不凭演示给“智能”高分。

持续学习另验：认证通过但内容恶意、转发导致认证失败但内容正常、同域不同发件人、伪装熟人／Reply-To、主人否定与撤销、诱导白名单和伪造反馈、规则冲突及过期、升级前后同一留出集对照。升级回退采用[邮件能力成长的故障验收](evolution-release.md#mail-capability-growth-validation)，不以分类演示替代模块／数据恢复验收。

资源验收在目标普通 PC 测空闲与单批峰值内存、CPU、同步延迟、聊天延迟变化、落盘增长和实际模型费用，再设置默认值；当前大内存开发机和一次读取不能代表 8 GiB PC。先做影子分类与本地建议，经过个人纠正样本再开少量可恢复动作，保留一键暂停与回退。

可用的个人验收指标是：每天主动提醒数量、关键邮件漏报、误归垃圾、待回复积压与平均处理耗时，以及每百封模型费用。首批真实样本应由主人标注重要性和可执行性，按时间划分开发／留出集，避免用同一批纠正过的邮件证明泛化；报告覆盖的日期、账号、类别和样本量。重要邮件召回应优先于自动清理覆盖率，未取得样本前不填“99% 准确”等目标达成数字。

## 连续身份下的一次交流、办事与成长循环

**完整流程 proposed。** 它展开[三职能分工](architecture.md#continuity-facets)，复用既有任务状态机和[组合调用时序](#composition-runtime-cycle)，不是另建一份持续运行的超级 Agent。

![连续身份下的交流、行动、回执与学习流程](diagrams/continuity-work-cycle.png)

[SVG 放大](diagrams/continuity-work-cycle.svg) · [唯一图源](diagrams/continuity-work-cycle.mmd)。实线是本次主要工作流，虚线是按需使用的上下文和后续改进；底部状态是分支结果，不是新增任务状态枚举。

| 环节 | 谁处理、交付什么 | 避免的重复与失真 |
|---|---|---|
| 接收与接续 | 协作面接收主人话语或已授权事件，读取当前用途视图与原任务关联 | 不把每条聊天都变成任务，不默认读取所有历史 |
| 判断需要什么 | 简单聊天直接回复；已有确定性能力直接匹配；复杂目标才由定向面提出计划与验收候选 | 三个职能不是每次必调的三次 LLM；模糊输入不等于无限授权 |
| 装配和受理 | Composer 固定蓝图/技能/工具及版本；原受理检查范围、依赖、预算，复用根任务与幂等身份 | Bot 层次不决定任务层次；同一需求不得被多个 Bot 重复派发 |
| 执行一步 | 固定流程直接运行；需要认知时 Agent Runtime 产生 StepProposal，经 Task Runtime 与网关执行 | 模型不能直接写成功回执；子 Agent 和外部编码器仍属于原任务 |
| 观察与继续 | 核对真实结果；在原范围内有界重试/重规划，缺授权或网络时等待并释放槽 | 未知效果先对账，不通过换角色、换节点或换模型盲目重复；其他聊天/任务继续 |
| 交付与纳入 | 协作面说明真实完成/部分完成/等待，领域写入者提交结果；适合长期使用的内容形成候选 | 发送邮件回执、项目成果、个人偏好各归其域；不能把整个任务轨迹写成主人画像 |
| 观察成长 | 观察成长面按事件、故障和已授权计划分析反馈，提出技能/工具/实现候选 | 通过原独立评估与发布后才生效；主任务结束不代表改进候选已通过 |

例如“明天出门前帮我看看航班通知并整理准备事项”：邮件与日程职责共享获准的行程引用，读取真实通知，形成可核对的待办。若邮箱授权失效，仅相关分支等待；若时间冲突，提供证据或请求必要决定；若发现重复解析失败，可以提出邮件解析技能改进，但不能为了完成行程自行扩大邮箱权限、购买机票或更改根规则。

中断后的“还是同一个 Jarvis”依赖原目标、承诺、动作编号及有效资料继续存在，不依赖模型记住上一轮内部推理。更换引擎先核验检查点兼容；不兼容时可基于已知事实重新分析未完成步骤，不能重做已完成副作用。

<a id="proactive-goal-cycle"></a>
### 从主人目标主动发现任务，自主执行并独立交付

**完整流程 proposed；dev.2 接通固定纯工具研发，dev.8 增加[显式目标的可修改计划](#goal-planning-runtime)。尚未实现从任意聊天自主发现目标或自由规划全部事务。** 本节落实[自主工作与独立完成任务](product-requirements.md#personal-life-autonomous-outcomes)的最终目标：定向面维护目标解释与优先级，协作面推进和交付，观察成长面发现知识/能力缺口；三者只读写各自端口，不新增一个拥有全部权限的总 Agent。任务以个人为主，并覆盖获授权的家庭和小团体事务；记录请求者、服务对象、关联主人目标、资料受众及有效许可，不能把成员请求直接等同于主人授权。最小对象见[目标与机会契约](contracts.md#goal-opportunity-contract)，当前运行范围见[研发实现](toolchains.md#growth-development-runtime)。

| 环节 | 自动做什么 | 进入下一环节的条件 |
|---|---|---|
| 接续目标 | 从明确委托、已确认约定、长期职责和有效维护许可取得目标及其当前修订 | 事实、愿望、第三方请求和真正委托分开；不明确的目标解释可先成为建议 |
| 发现机会 | 消费获准日程/邮件/任务事件、截止时间、能力故障和技术变化，找到能推进目标的下一步 | 必须能解释关联哪个目标、依据是什么、为何现在值得做；不额外扫描未授权资料 |
| 去重与选择 | 合并同一效果、淘汰过期或主人已拒绝的候选；比较影响、紧迫性、证据、工作量和费用 | 先检查硬约束，再排序；评分不能把越权抵消成高收益，无收益时安静等待 |
| 形成可执行计划 | 明确产物或实际效果、完成条件、预算和期限；复用已有技能/工具，必要时分析、拆分或生成候选，计划始终可查看和修改 | 在当前许可内直接进入受理，不逐步骤要求确认；无法推断且影响执行的缺项才等待相应决定 |
| 推进与接续 | 依赖就绪后执行、检查、有限重试；失败时换有依据的方法，等待时释放资源 | 原任务/动作 ID、成本、撤权及未知效果继续有效；换方法不重置已花预算和失败计数 |
| 解决能力缺口 | 先查已有能力和可替代路径；必要时在研发许可内使用模型、Codex 或组合方案生成候选，验证与准入后接续原任务 | 新能力仍经过原发布与回退通路；无研发许可、预算耗尽或无法验收时说明具体阻塞，不悄悄安装和放宽完成标准 |
| 核验实际结果 | 核对产物、工具回执与业务条件；失败则修正，不能仅以模型自述或“已调用工具”判定完成 | 验证通过才进入完成；结果未知先对账，已确认的成功步骤不重复产生外部效果 |
| 交付与闭合 | 交付可用成果和必要证据，说明完成范围及仍未解决的问题，更新目标进度与承诺；按安静时间/重要性通知正确受众 | 有限任务按预先完成条件结束；部分完成、等待、失败不能记作完成。持续职责每次事件有独立结果，不开无终点推理循环 |
| 留下经验与改进 | 分域提交事实、候选知识、习惯假设及改进依据，关联下一次可能受益的目标 | 不能把一次任务的结论直接当成主人的稳定偏好；知识晋升与代码发布各走原流程 |

**发现机会不等于立即执行。** 对目标范围内的只读准备、计算、已许可文件操作和既有维护，满足条件后自主推进；新权限、未批准支出或未确定的重大取舍才需要主人决定。后台办理过程中，前台聊天、其他无依赖任务继续；拒绝或取消一个候选不能被另一个 Bot 重新提起以绕过选择。

举例：主人已委托“本月学会基础 Python，每周帮我安排练习”，并允许读取学习记录、生成本地练习和在指定时段提醒。Jarvis 可发现尚未完成的练习，调整难度，准备下次练习，整理常错知识；发现解析工具重复失败，还可在维护许可内验证改进。它不能据此擅自购买课程、联系老师或把私密学习记录发送到新供应商。主人改为准备另一门考试时，未开始的旧练习降级或取消；已提交的外部效果仍保留真实记录。

家庭／小团体例：在已有共享日程、采购清单编辑和家庭提醒许可下，主人提出“安排周末聚餐”。Jarvis 可以核对获准成员的时间与饮食约束，形成安排、更新清单、按许可发出提醒，并核验每项结果。向商家下单需要独立的购买许可；缺少它只等待采购分支。完成标准若包括预订或下单，未完成这些动作就报告部分完成；不能把计划文档当成聚餐筹备已经全部办妥。成员的私人说明只形成必要用途投影，不写进公开清单。

触发优先使用现有事件与期限；可设置的兜底扫描复用原调度器。扫描间隔由目标时效、来源更新频率、费用和电源状态决定，不能统一每五分钟调用 LLM。启用一个长期职责只需确定必要的范围和约束，日常消息可以自然修改它；未启用的职责不偷偷开始联网观察。本轮仅定义机制，不实际创建后台订阅或定时任务。

活跃目标、待评候选、每次扫描量、每次模型分析、重试、日用量和探索成本均须有界；多设备由原共同体分配执行所有权。安静时间只影响非紧急通知，不抹去已授权后台结果；到达期限、费用上限、无进展阈值或等待条件时进入原任务对应状态。恢复必须有新证据、到期事件或新的有效指令，不能无限唤醒同一失败。资源优先级继续归[对话与任务隔离](#conversation-resource-isolation)。

<a id="skill-selection-policy"></a>
## 技能、MCP 与执行能力的统一选择

Skill 是方法与判断条件，Tool/Connector 承担实际效果。能力目录登记版本、使用/不使用条件、依赖、资源、资料范围、测试和恢复方式；登记不授予运行许可。

<a id="skill-selection-order"></a>
### 选择顺序

先解释主人目标与输入，查已有工具/技能；可确定性完成就直接使用合适执行器，已有能力能组合就不另造插件。缺少能力才形成研发候选；模型推荐必须核对真实安装、就绪、作用域及有效许可。技能失效或不匹配时可以说明原因、改用可用路径或等待，不能伪造执行成功。

<a id="skill-selection-scope"></a>
### 作用域、停用与冲突

全局、项目、会话和本次请求的偏好可覆盖，权限只取有效授权允许范围。显式停用、主人撤回和当前停止状态优先，模型不能通过子 Bot、其他工具或外部编码器绕过。目录重名必须使用稳定 ID；活跃任务固定能力版本，但实际动作仍检查最新权限。

<a id="mcp-selection-policy"></a>
### MCP 与技能配合

MCP 是工具服务接入协议，不是独立主人或授权层。工具说明视为外部数据，工具发现不等于允许连接或执行；端点、依赖、凭据、输入输出和效果必须经过本机网关。首次接入版本锁定并做取消、超时、未知结果与异常参数验证。

<a id="published-tool-runtime"></a>
## 已发布工具的重复使用（dev.7）

**implemented：0.2.0-dev.7。** 本节定义新工程当前可运行的个人纯文本工具复用，验收见[工具闭环证据](delivery-validation.md#published-tool-evidence)。不把整个 Agent Runtime、自然语言规划、桌面自动化或所有技能迁移视为已实现。

研发负责“创造并发布能力”，使用任务负责“用已有能力交付一次结果”。两者分开授权、记录和取消；研发许可到期不会要求重新生成已发布代码，旧许可也不会自动延长。

| 位置 | 当前职责 | 保持独立的边界 |
|---|---|---|
| 文字 Skill | 向聊天模型提供方法、条件和表达指导 | 没有文件、网络或工具执行授权 |
| 发布目录 / Packages | 从有效 release_slots 投影本地工具，显示版本、范围、可用性与基础观察次数 | 不复制一份可漂移的“执行技能注册表”；候选、被拒绝版本不能因目录显示就获得执行权 |
| Host 工具接口 | 接受明确点击和文本参数，固定包与版本，建立一次性任务许可 | 仅 owner.local / personal；拒绝任意 Shell、路径、模型路由或调用者自带的宽授权 |
| Task Ledger | 保存输入、固定版本、动作、成本次数和回执，受理幂等请求 | 同一请求标识和相同参数返回同一任务；修改参数必须新建请求，刷新页面不重跑 |
| 现有 TaskRunner | 在原有一个后台任务线程中执行指定任务 | 不为每个工具新增线程池或常驻服务，不因为“运行这个工具”顺带执行其他待办 |
| 受限 Worker | 只执行已发布纯文本包，执行前与过程中检查停止、期限和权限 | 沿用[隔离边界](security-sovereignty.md#growth-worker-boundary)，不在 Host 导入候选代码 |
| 产物适配器 | 将确认后的结果写入本机任务产物目录 | 工具代码没有写入用户任意目录的能力 |
| UI | 显示输入、结果、状态和记录，允许复制、导出、明确附入聊天 | 结果不会自动变成记忆，也不会自动发给聊天模型 |

**实际流程：**发布且通过审阅的能力进入目录 → 主人选择版本并输入文本 → 确认本次使用 → 冻结任务与有限许可 → 后台运行此任务 → Worker 返回结果 → 固定产物写入 → 显示交付回执。新的使用复用代码，不重新规划、生成或调用模型。

请求只接受能力 ID、不可变 package_id、目录 revision、request_id 和 text。文本上限为 50,000 字符且 UTF-8 不超过 100,000 字节；请求总包仍受 HTTP 上限约束。每次许可只覆盖所选能力与 artifact.write.v1，最多两个动作、每动作一次派发、600 秒有效期。输入和结果保存在本机普通任务账本与产物中；这是普通资料范围，不是已加密的隐私保险库。

**版本与生命周期。** 新任务提交时要求页面选择的包和当前 revision 一致；已提交任务绑定不可变包，即使发布了新版本也不会偷偷改用新代码。全局停用仍阻断后续执行，恢复须重跑固定探测。被拒绝/退役包不能接续；尚被未结任务、当前槽或恢复槽引用的包不能退役。回退代码不复活已经撤销的单次许可。灰度累计两次运行后的 STABLE 只表示当前基础观察条件通过，不能证明所有输入都正确或已具备普遍业务可靠性。

**取消与中断。** 取消先撤销本次许可，再标记任务；在途 Worker 的检查点会停止它。无法确定是否产生结果的动作保留 UNKNOWN；有已落盘、匹配输入和版本的回执时只核对，不重跑。无回执则保留未知，主人可取消后明确新建一次处理。任务失败不停止聊天或其他独立任务。达到期限或明确失败的任务不会自动无限重试；下一次使用是新任务。

**轻量运行。** 复用既有 Python 标准库、SQLite 任务表、发布槽和一个后台任务通道，没有新数据库、模型下载或第三方服务。目录读取不启动探测 Worker；停用恢复、实际执行才按需使用 Worker。页面可见时每三秒读本机状态，关闭或隐藏时不轮询，不调用 LLM；这不是资源压测结论。

当前仍要求主人选择具体工具。自然表达的目标识别、可编辑多步计划、模型选择现有能力以及可撤回的持续主动许可是后续独立工作，不能把这个复用入口称为任意任务全自主闭环。

## 自然目标、可修改计划与组合执行（dev.8）

**implemented：0.2.0-dev.8；验证范围归[本轮证据](delivery-validation.md#goal-planning-evidence)。** 在当前已发布个人纯文本工具之上，增加一个轻量规划入口。主人不必记住工具 ID，可以描述目标，由真实模型建议能力和顺序；计划必须可见、可修改。这里没有迁入旧系统的通用 Agent 执行器，也没有把任意聊天自动转为动作。

| 层次/文件 | 承担的职责 | 不承担的职责 |
|---|---|---|
| `apps/workbench/goals.js` | 工作台右侧与设置页共用目标、模型档位、编辑、执行和交付界面 | 不持有能力授权，不直接执行模型文本 |

| `modules/task_resource/plans.py` | 保存目标、目录快照、提案、修订、取消和原任务关联 | 不调用模型、发布模块或桌面适配器 |
| `modules/model_gateway/routed.py` | 已有真实模型协议、计量、主备与未知结果处理 | 不把模型回复变成许可；恢复只处理本次规划调用 |
| 发布目录与原 Task Ledger | 固定每个能力版本、验证个人范围、编排动作和保存回执 | 不将未发布候选临时放进执行目录 |

**当前流程：**描述目标与可选文本 → 冻结可用工具及模型线路 → 有限模型规划 → 核对/修改实际输入、行动和预期 → 确认计划 → 在同一事务中建立任务许可与原任务 → 后台逐步执行 → 写入最后结果 → 查看实际输出和回执。缺能力或待补充问题进入 NEEDS_INPUT，保留目标，不把缩减后的任务冒充全部完成。

当前最多选取 12 个已发布且可用的个人工具，每个计划最多 4 个纯文本行动，最后由可信适配器自动增加一个产物动作。第一步使用核对后的输入；后续每步只能选同一输入或上一步已经确认的纯文本输出。禁止向前引用、环、任意命令、模型自带授权和隐藏参数。dev.8 仅将目标、显式文本及工具说明发送给规划模型；dev.10 另按[目标背景规则](knowledge-learning.md#goal-memory-runtime)装配获准记忆，聊天关联由[组合层](#conversation-action-runtime)处理，仍不自动读取项目文件。显式文本被模型改写会阻止进入待执行状态；主人可以在编辑页面主动修正。

规划只有 `model.generate.v1` 许可，最多 2 次调用、10 分钟期限。自动路由沿用当前默认和首个已启用的其他提供方，明确选定模型时仅用该线路；已知拒绝/结构不合规可使用预算内备选。超时或远端结果未知不自动重发，需要明确选择重新规划，历史调用与费用不清零。当前限制是调用次数与 token 上限，不是精确人民币费用封顶。

确认执行时比较提案 revision 与每个发布槽版本，检查当前停止/停用状态和作用域；授权、任务与提案关联同事务提交。目录更新、保存失败或旧修订均不能留下半个有效任务。确认后任务固定、最多 5 个动作、每动作一次尝试、10 分钟期限；修改目标另建计划。模型生成的 `expected` 只是人工核对描述，**不是独立业务验收程序，也不能保证规划正确或目标已经全部实现**。

后台沿用一个 TaskRunner；规划与编码研发共用一个 `BackgroundLane`，没有为每个目标新增线程池、服务或环境。前台保留原两路聊天通道，等待后台槽时目标仍在本机，可稍后继续。列表轮询只查本机状态，不调用模型。当前不自动排队唤醒、定时提醒、主动发现新任务或后台学习。

取消规划撤销其模型许可；取消已确认计划同时撤销本次执行许可，通过原检查点停止，其他无关任务保持可用。重启后的在途模型调用记为未知；执行中断先核对落盘回执，再接续剩余动作。已确认输出、已消费预算和取消标记不会因刷新、恢复或重复确认而重置。能力停用阻断后续执行，恢复仍走原发布通路。

计划正文、真实输入、输出、调用计量与任务回执按当前数据根保存；它们不会自动变成个人偏好、长期知识或项目记忆。复制和导出由主人显式选择；dev.10 已关联目标的真实输出也会返回原会话卡片。dev.8 缺少新能力时仅指出缺口；dev.9 已增加[目标关联研发与发布后回接](#goal-growth-runtime)。dev.10 的外部 Codex 仅接候选端口，MCP 执行仍待独立实现。

## 缺少能力时的目标关联研发（dev.9）

**implemented：0.2.0-dev.9；验证范围归[成长接续证据](delivery-validation.md#goal-growth-evidence)。** 本节在[目标计划](#goal-planning-runtime)之上补齐“发现缺口 → 拟订规格 → 受限研发 → 审阅发布 → 返回原目标 → 交付”。它复用原研发、发布、任务、Worker 和模型通道，不另建一个拥有全部权限的总 Agent。

| 步骤 | 当前执行内容 | 继续条件 |
|---|---|---|
| 发现缺口 | 原目标进入 NEEDS_INPUT，保留原目标 ID、原文、输入和未完成原因 | 主人选择“为这个目标设计能力”，仅限未执行、尚未做过关联研发的目标 |
| 拟订规格 | 原目标的冻结模型线路生成行为、公开示例、隔离验收建议和待解决问题 | 只产生结构化提案，无代码执行或发布许可；不支持的目标不能悄悄缩减 |
| 核对标准 | 修改行为与两组用例，选择研发规划/编码主备模型、档位和预算 | 明确核对规格及期望值后开始；公开与隔离用例输入不能重复 |
| 受理研发 | 同一事务建立限定授权、既有 development_run、路线与原目标关联 | 新能力 ID 由 Host 为原目标分配，不能覆盖其他能力；陈旧修订和失败写入整体回滚 |
| 编码与检查 | 原研发循环生成候选、AST 配方检查、LPAC Worker 执行固定用例；失败在原限额内修复 | 后续规划/编码只接收公开示例，不接收隔离用例或期望；不能改验收来放行 |
| 审阅发布 | 原源码/报告界面审阅精确候选，发布并执行独立样本任务 | 未认可候选不能经模块页绕过；原目标取消会撤权并阻止尚未发布的候选 |
| 返回目标 | 样本交付成功后核对当前发布版本，原子更新原目标目录，再使用原模型线路重新规划 | 沿用同一个目标，不再造一个无关联目标；原请求与输入不改，旧计划与目录保留为来源 |
| 真正交付 | 新计划仍可修改和核对；确认后用原任务执行通路处理原输入、保存结果 | 研发样本成功不算原目标完成；以原目标实际任务与文件回执作为结果 |

**验收标准的来源必须讲清。** 规格模型可以建议隔离用例，操作者核对或修正后冻结；它们对后续代码模型保持不可见。独立执行这些用例能检查实现是否符合固定标准，不能证明标准一定正确，也不是不同提供方独立研究得出的语义保证。当前仍保留规格确认、精确候选发布审阅、原目标计划确认三个节点；在本轮授权测试中由 Codex 核对，产品没有假装跳过这些节点。

每个目标只允许一次关联研发。初次规划最多 2 次模型调用，规格设计另有 2 次/10 分钟；研发沿用所选 2—8 次模型调用、1—3 个候选轮次、30—1800 秒总期限；发布后返回规划最多再 2 次/10 分钟。全链最高 14 次模型调用，默认界面配置最高 10 次，实际可能更少；这些是次数预算，不是金额保证。各阶段历史次数、撤销与未知结果不会因刷新或换模型重置。研发失败/取消后不自动新建一轮；dev.10 增加同目标显式修订，其独立小额预算见[聊天运行规则](#conversation-action-runtime)；不清空旧调用账本。

规划、规格设计与编码共用原一个后台模型槽。结束样本任务后，同一槽内顺序返回原目标；不会新增常驻服务、后台订阅或轮询模型。关闭面板不会取消；UI 轮询只读本机。取消原目标原子撤销相关许可并标记子研发/任务取消，检查点阻断后续动作；独立聊天和无关联任务不一并停下。已发布的共享能力或已经确认的文件不会因取消而被删除。

恢复沿用原账本：模型未知结果需明确选择重试；Worker 回执未知先核对再接续。若服务在样本交付之后、返回原目标之前中断，目标面板保留“回到原目标继续规划”，不会重新创建研发或重复发布样本。发布版本被替换/停用时返回步骤等待，恢复可用版本后接续。返回规划使用独立的 `-return` 调用身份，避免误用旧目录的缓存，也避免重置最初规划的调用记录。

实际职责定位：`modules/task_resource/growth.py` 保存关联与规格修订；`host/goal_growth.py` 组合原模块；`host/development.py` 复用原子受理与完成回接；`apps/workbench/goal-growth.js` 复用原候选审阅界面。普通目标、研发样本、原目标交付各保留自己的动作回执，靠关联字段追溯，不混为同一效果。dev.10 成功成长交付产生待核对经验候选；确认前不成为有效记忆，也不扩大为家庭共享。

当前只能生成受限 Python 纯文本能力，不能通过此入口安装依赖、编写并运行任意 Shell、修改核心、访问邮箱/桌面、创建后台定时任务或接管外部 Codex 桌面。dev.10 只接通了外部 CLI 的候选生成端口。这些目标显示能力缺口，需要对应新模块独立准入。完整自主成长设计仍按[原研发与发布](toolchains.md#autonomous-development-providers)推进。

### 立体内部构造与流动视图（4.0.0）

新产物默认“结构3D”，所有基本体、叶片、空心管壁、气门、燃烧室粒子、半透明火焰体与水面网格共享三维坐标。Jarvis独立实现几何、光照、相机投影、多边形深度排序，再生成SVG；不是旧平面轮廓随视角缩放。拖动绕视、Ctrl+滚轮/缩放条与聚焦后的方向键改变相机；方向键旋转不推进仿真时间。也可切回原理简图。

外壳可完整、透明、按Y平面剖开或隐藏，剖切深度可调；剖切仅处理外壳层，边界以金色轮廓强调，不构造实体截面封盖。分组拆解移开壳体、缸盖、配气机构或泵盖等，以辨认零件；不是装配仿真，拆解后不据几何间距计算运动关系。运动件、固定件、流动层及标注可分别显示；下拉菜单或点击零件可高亮并阅读关键结构说明。自定义关节机构沿用给定基本体/运动树；不把自动生成的几何视为经过实体干涉或制造校核。

火焰由三维锥状半透明网格和空间粒子组成，受理想燃烧阶段或油门控制。气流沿进/排气通道、压气机—环形燃烧室—涡轮—喷口运动；泵水沿轴向入口—径向叶轮—蜗壳—切向出口运动，另可显示发动机水套流动。水槽用线性波位移形成三维表面和水体外观。以上为预设路径/体积教学示踪，没有求解CFD、温压、化学反应或反向流体负载。多边形排序没有逐像素深度缓冲，透明交叠和极端视角仍可能存在排序伪影，不据此声称光线追踪或真实透明流体。

动画流畅度可选省电10、平衡20、流畅30FPS目标，默认20；实际更新率依设备、零件数和可见场景而变。隐藏标签页不推进时间，屏外绘图按可见范围跳过；这些优化不等于低配PC或长时资源已验收。SVG保存当前三维视图，HTML与JSON保留可运行场景配置。既有链接是不可变产物，获得新版视图须重新制作。

模型与测试闭环：tools/eval_anatomy_structure.py显式经Jarvis自身配置、对话槽、取消/未知恢复及用量账本生成复杂场景，再由可信结构审计与浏览器检查提供证据给同一路线模型评分。结构技术评分和视觉评审分开：当前文字模型收到的是部件、模型边界和测试数据，visual_score必须为null，不声称看过截图。原始评审保留，宿主按固定权重汇总；模型的部件误述不能覆盖配置事实。真实案例、改进与评分归[三维结构验收](delivery-validation.md#anatomy-structure-evidence)。

场景最多8个组件、8条无环连接，每个目标最多一条输入。shaft把前级输出角度和转速乘连接比传至齿轮或水泵；flow把泵轴速幅值按600rpm归一后映射到波幅，限于0—100%。这是单向运动/教学激励传递，不反馈扭矩、能耗或液压负载；反转时泵流线也不代表真实反转泵性能。传递后的轴速用保守上界限制在24,000rpm以内。独立模块共享一条演示时间轴，支持0.01—1倍时间、暂停/步进/归零、当前时间拖动、分组参数、单项效果开关、剖视、明暗，以及SVG、JSON、可运行HTML下载。高转速可能出现显示采样混叠，可调低演示倍率观察。

自定义机构声明式parts由id/parent、shape、joint、axis、position/offset/size/rotation、amplitude/frequency/phase/color组成；完整可执行范围以 modules/skills/anatomy/scene-schema.json 为准。父子关系必须无环，形状和颜色均为枚举；不能嵌入脚本、任意SVG、URL、纹理、安装命令或外部资源。页面内JSON修改通过同一结构校验，失败保留原场景；只在当前页面生效，下载HTML/JSON可保存修改，不回写原产物回执。

自由描述仅在明确点击“生成并制作”时调用选定模型。复用现有两槽前台聊天执行器、取消、联网/停止控制及用量账本；新建的专用模型会话关闭记忆注入，原始需求和候选作为资料。一次请求最多一次模型调用，不走自动备选，不自动重试；未知费用/结果仍标未知。模型必须返回严格JSON；适配器可把合法ASCII标识符中的下划线改为连字符并同步引用，保留原回答、逐项记录normalizations；碰撞或其他结构/范围错误仍拒绝，不更改物理参数、不忽略字段。宿主完整验证后才能制作；返回合法JSON不代表满足全部需求，界面标组件类型、简化范围与unfulfilled。无法表达的要求应列明，不把近似机构称为任意机械CAD。

接口：POST /api/anatomy/compose接收id、prompt、provider、model；GET /api/anatomy/compositions及其/id查看历史和状态；POST /api/anatomy/finish把CANDIDATE制作成DELIVERED，重复取回已有产物；POST /api/anatomy/cancel取消未交付请求。composition状态与模型调用分开记录，模型SUCCEEDED并不自动等于交付成功，非法候选显示INVALID。相同id相同请求不重发，修改请求复用id会拒绝。重启后未结调用继承聊天恢复的UNKNOWN，不重放；可继续取回已完成候选。

POST /api/anatomy/render保留slider-crank、planetary，增加studio：只能给preset或scene之一。planetary仍限sun_teeth/planet_teeth/mode并检查装配条件：S18—48、P18—36、R=S+2P，S+R被3整除及相邻轮布局；三种固定件按Willis关系联动。20°离散齿廓有0.06mm绘图间隙，不是制造公差。检查技能启停、停止与上游摘要后调用可信Node构建器，单构建锁、15秒超时。回执保存初始配置、版本、上游许可与摘要、十二个绘图资源及三个宿主校验文件摘要、产物SHA-256；自由生成附实际模型回执。UUID取回重新核对摘要，产物在本工程user-data/artifacts/anatomy，组合记录在state/anatomy.sqlite3。

### 计算、碰撞与 CAD 的可行性评估（proposed）

2026-10-23 对适配器 4.0.0 的源码和一手工具文档进行评估。下表保留当时的候选范围；后续实际实现见 [5.0.0 组装运行规则](#anatomy-engineering-runtime)，不能把整张评估表当作全部完成。评估阶段没有运行新求解或安装依赖，其只读环境快照见 [评估记录](evidence/anatomy-feasibility-2026-10-23/research.json)。

**现有实现的约束。** 自由机构只有盒体/圆柱与给定正弦运动，未定义质量、转动惯量、接触材料或载荷；模块轴连接只传角度/转速，不能反馈扭矩。父子树和模块连接拒绝环，不能直接表达四杆闭链或双向机电能量交换。外观网格不是可靠闭合实体，缸孔等内部轮廓不等于从缸体实际布尔挖孔。动画拆解、剖视和竖向放大属于展示变换，不能进入物理几何。构建器单锁、15 秒期限适合生成 HTML，不能直接承担长时 CFD；HTTP 产物的 CSP 也未开放 WebAssembly 编译或外部取数。

**共同前置与技能组织。** 继续归一个 Anatomy 用户技能，内部按任务条件选用子能力。先定义带版本的统一参数模型：显式 SI 单位/显示单位、几何特征与零件 ID、装配坐标、关节/约束、材料、质量惯量，以及可选流体域/边界条件。渲染网格、碰撞代理、CAD 实体和流体网格由同一参数模型分别生成，不能把一种表示当作另一种的可信输入。保留旧场景可读与明确迁移；缺物性或边界条件时列出缺项，用户可以选择有记录的教学默认值，不能静默当成工程数据。

模型只负责选择已登记能力和生成有界参数 JSON，可信工厂与数值求解器执行计算；不直接运行模型生成的 Python、Shell 或求解器字典。设置中每个子能力分别显示依赖/版本、可用或待安装、适用范围、最近验证的模型版本与算例；父技能默认可用不等于尚未准入的求解器可执行。求解版本/参数/机理/网格/边界/时间步均进入回执与缓存键，修改后使对应验证过期。

短小数值计算可在经准入的适配器运行；长任务复用现有任务账本、停止/取消、期限和 UNKNOWN 恢复语义，设进程、内存、输出/磁盘配额及并发上限，不把现有纯文本 Worker 的 256 MiB/3 秒预算或构建器 15 秒直接放宽。可信第三方原生库的隔离与打包须另验，不能把普通子进程当作已隔离。WASM 若用于浏览器碰撞，须先验证当前 CSP，最小化调整并保留无网络/无同源访问；不得为了依赖运行而统一放开任意脚本或网络。

**必须补的验收。** 干涉检测用已知分离/接触/穿透、许可配合和高速穿透样例，注明离散检测或连续检测范围；动力学用单摆、落体/碰撞与能量/关节残差检查。CAD 检查 B-rep 有效性、闭合/正体积、尺寸/单位、孔和壁厚，再回读 STEP 核对；STL 网格有效不等于 CAD 特征有效。热力/化学检查元素、质量、能量守恒，理想解析关系、官方参考算例和求解收敛。CFD 至少对照 Poiseuille 解析通道流，检查质量守恒、散度、网格与时间步细化；浅水检查守恒与相应波速/溃坝基准。每类算例预先定义误差限和失败状态，不设置一个适用于全部物理模型的统一准确率。模型文字审查、截图视觉审查和这些数值证据分栏；既有 4.0.0 的测试与文字评分不覆盖新能力。

**建议实施顺序。** 在既有 K0—K6 流程内按依赖推进：①统一参数模型，增加受控几何和真实剖面；②干涉检查、基础刚体与机电/泵集总动态，交付“电机—传动—泵负载”可验证样例；③受控 CAD 零件/简单装配及回读检查；④发动机零维循环，再以独立可选依赖接 Cantera；⑤二维通道流与浅水算例；⑥有实际需求及设备证据后接离线高质渲染/限定 OpenFOAM。GPU 渲染可与前几项逐步适配，避免将渲染重写作为全部数值能力的前置。未定义材料、边界与验证基准的任意三维湍流燃烧/流固耦合保留为后续研究。

**工具依据与准入。** [Rapier 官方](https://rapier.rs/docs/)支持刚体、碰撞、关节、事件，Apache-2.0；这不证明已接入本工程，也不等于逐齿齿轮接触已经可靠。[CadQuery 导入导出](https://cadquery.readthedocs.io/en/latest/importexport.html)明确 STEP/网格/参数历史的区别；CAD 内核的 [OCCT 许可](https://occt3d.com/dev/doc/overview/html/occt_public_license.html)为 LGPL-2.1 加额外例外，须逐项核对选用版本与发布方式。[Cantera 内燃机算例](https://cantera.org/stable/examples/python/reactors/ic_engine.html)与[一维反应流](https://cantera.org/stable/examples/python/onedim/index.html)证明限定反应模型有成熟实现；其[社区说明](https://www.cantera.org/community.html)标明 BSD-3-Clause，具体反应机理数据仍单独核对。[Clawpack 浅水算例](https://www.clawpack.org/gallery/pyclaw/gallery/dam_break.html)给出守恒方程与溃坝基准。[OpenFOAM 官方分发](https://openfoam.org/download/)提供 Windows/WSL 路线；检测到 WSL/Docker 命令不等于求解环境就绪。全部外部组件仍执行[供应链准入](security-sovereignty.md#personal-life-supply-chain)，本次没有指定未验证的最终依赖版本。

### 参数化实体、复杂零件组装与计算（5.2.0）

5.0 基础与 5.1 子总成/车辆运转 implemented；源码、正式服务与独立测试进程的验证分别登记在[组装验收](delivery-validation.md#anatomy-engineering-evidence)。一个 Anatomy 技能卡片管理全部组件，保留 4.0 页面；新增“19 件轴系组装”“流动与化学计算”“CAD 起步装配”“四杆闭链与机械臂逆解”。示例/JSON 零模型调用，自由描述明确选择制作类型和模型，依赖不可用时在付费调用前拒绝。复用原前台对话槽、取消/停止、费用与 UNKNOWN 规则。

**5.1 子总成与装后运转。** 同一卡片新增“32 件电动车组装与运转”。五个子总成分别是承载车架、电驱后桥、左右前转向轮组和动力电池；支持整机逐件安装、预装子总成整体装入，以及独立工位内的分批同步（如左右轴承/半轴同时安装）。切换观察范围或方式会显示该范围的完成姿态，不保存训练成绩；这是可播放/拖动进度的装配教学查看器，尚无手动抓取吸附装配游戏。局部组装结束后选择“整机集成”，可观察各总成作为刚体装入整机。

可选 assembly_plan 按本节当前数量预算分组，零件必须恰好属于一组，跨组约束保持父组先于子组；可选 batches 将组内零件再严格划为有序非空批次，批内同步、批间顺序。各组整体按统一 direction/distance 平移，保持全部内部相对姿态；同步批次保留原零件路径。可信内核分别检查最终静态、逐件插入、整组插入、批内运动件两两及前序已装件，每个插入批次七姿态，报告与质量状态分开。已知任一干涉或名义配合不符不能标成功；启用子总成时不自动使用仅适合逐件路径的旧顺序搜索。

装后运转是受控 vehicle 类型，使用 X 向前/Y 向左/Z 向上的独立 CAD 刚体：四轮、前轮支点、前转向零件和后转子名单显式登记，检查尺寸、轴线、轮距/轴距及转角范围。Ackermann 理想转向满足左右轮共同瞬心；轮速按各轮中心至瞬心距离分别计算，后转子使用后轮平均速度代替理想差速内部齿轮。支持正转、倒转、转向、暂停和复位；各轮相位按仿真帧时间积累（单步上限 0.15 秒），修改速度/转角不直接跳换相位。驱动为显式世界空间刚体变换，不自动求解既有 mates 的运动闭合。车辆固定在架空台架，未模拟车身道路行驶、轮胎变形、牵引力、悬架载荷或真实差速/转向拉杆。

只有整机完成、分解为零、没有组装播放且静态/逐件/整组/同步及运转检查均满足已检查范围，才可启动。拆解、退步或切换局部工位会停止并复位。运行/暂停后的非零姿态使用完整实体世界刚体变换，不把已裁切网格旋转后冒称新的全局截面；复位后可看原 Y=0 布尔剖面。默认运转检查为 -max/0/+max 转角与同相车轮 0/45/90° 的九个 B-rep 姿态，不覆盖任意独立相位、全周期或连续碰撞；复杂赛车的 extended 覆盖另见下段；SVG 仍有遮挡排序与性能限制。32 件样例、反例和浏览器/模型实际证据归[当前验收](delivery-validation.md#anatomy-engineering-evidence)。可编辑参数不等于任意车型均可生成或运动学通解。

**5.2 赛车、齿轮传动与车壳。** 新增 72 件电动方程式教学赛车，九个子总成，含电机输入、两级直齿减速、分立半轴、制动盘简化实体、安装柱/短螺钉、五件车壳及可拆尾翼。既有电动车/轴系继续保留。car body group 使用 type=body，完整/透明/隐藏只改变观察；单独外壳拆解则停止并复位运转。座舱壳有真实开口、安装通孔与开底空腔，鼻锥为渐缩空腔；组装使用实体检查，不靠透明显示隐藏重叠。

传动 JSON 使用 output、最多四对 driver/driven 齿轮、最多五组 gear/parts 键接轴。齿轮模数/齿数、平行 Y 轴、中心距、轴向重叠、同轴件名单与可达一致传动比图均作结构检查；不接收表达式。每对外齿轮满足 z₁ω₁+z₂ω₂=0，同轴键接件等速（理想无滑动关系，未切键槽或独立键实体）；输出载体仍为左右后轮平均速度。样例 18→36、24→48，两级总减速 4∶1，中间轴反向。模型不能把不一致或断开的图自行标成有效。

gear 工厂采用 20° 渐开线采样点的样条插值齿面、圆弧齿顶/齿根和直线过渡；18—60 齿，避免将低齿数无变位根切遗漏伪称精确。尺寸/中心距参考 [KHK 齿轮尺寸计算](https://khkgears.net/gear-knowledge/gear-technical-reference/calculation-gear-dimensions/)，代码为第一方独立实现。未含刀具根切、根部真实圆角、接触变形、齿面应力/疲劳、效率或润滑；不作为制造齿轮标准符合性结论。差速内部锥齿轮、转向拉杆闭环、悬架受力仍未建模。

统一数量预算调整为最多 96 件、16 组，**不是任意 96 件复杂啮合机构的保证**。赛车使用 extended 验证：五个转向值 × 六组同相/异相轮位，共 30 组实际实体姿态；不覆盖连续全周期。完全相同的刚体变换对复用静态交集，同一对和完全相同的两组变换复用已算交集，保留实际计算数与复用数；不通过降低干涉阈值或移除检查让样例通过。原 30 秒 CPU、45 秒墙钟、1 GiB 作业内存和 64 MiB 文件配额保留。复杂请求触及配额会失败，不发成功产物；本地诊断保留有界原生退出状态/末尾日志和已测资源。

超过 32 件的视图优先使用第一方本地 WebGL：沿用已核对 CAD 三角面，GPU 深度测试、实体拾取、轨道旋转和静态真实截面，不引入外部脚本/纹理；不可用时回退兼容 SVG，复杂模型可能较慢。透明外壳按部件绘制，未承诺逐三角形透明排序或任意显卡性能。CAD 导出仍来自同一可信实体。可携带下载超过原始 8 MiB 时按文件 gzip，嵌入压缩字节仍最多 8 MiB、展开原文件总计最多 32 MiB、最终 HTML 仍最多 12 MiB；点击后在沙箱本地解压，逐文件长度校核，HTTP 原文件摘要继续保留。未改变输出原始 CAD 字节或开放网络/同源权限。

数量压力、复杂度失败、真实运转性能与模型评审分别登记在[当前验收](delivery-validation.md#anatomy-engineering-evidence)。96 个简单分离件通过不能推断完整赛车的所有拓扑、机构闭链或制造级组装均可用。

**统一参数与实体。** schema=anatomy.engineering.v1；长度 mm、角度 degree，结果质量 kg、惯量 kg·m²。最多 96 件零件、95 条无环父子约束、每件一个装配步骤和四项不同实验。支持带中心孔块体、轴、空心轴套、带中心孔及 3—8 个阵列通孔的法兰、简化滚动轴承、无牙型螺栓和六角通孔螺母；钢/铝/青铜/聚合物/橡胶/复合材料使用明确的教学密度。参数 JSON 是可编辑来源，STEP 不保留完整参数历史。

可信 Open CASCADE 工厂构造实体、布尔挖孔，检查 B-rep 有效性/正体积，计算质心、质量和惯量。全局 Y=0 实体裁切产生封闭截面，再生成完整/剖面网格。滚动轴承有内外环及八球，没有滚道接触/预载；紧固件没有真实螺纹。基础示例保留 SVG 软件投影，复杂组装使用前述 WebGL；透明/遮挡排序限制按实际绘图器判断。

**定位、配合和组装。** 根件使用三维坐标/Euler 角；子件 position/rotation 为零，以父/子端口、轴向 gap、绕轴 twist 定位。axis 是中心基准，front/back 是轴向端面；法兰 bolt-i 在孔轴中面；螺栓 axis 是头下肩面，头向 +Z、杆向 −Z。fixed/revolute/prismatic 在本版表达静态定位类别，不是通用装配动力学。部分轴—孔、螺栓—孔检查名义直径差，螺母另查杆上的轴向覆盖；其余显示未校核，不能用 clearance 声明豁免干涉。

steps 必须父先子后、每件一次。direction 指向**最终位置到起点**，起点=最终位置+direction×distance，插入运动与该向量相反。先检查完成姿态的实体体积交集，再按步骤对每件七个直线插入姿态与已安装件作实体交集。静态干涉、离散路径干涉和名义配合分栏；七点采样可能漏过采样间穿透，不能成为连续扫掠体证明。默认 19 件示例先装内轮毂/隔套，再装两端轴承、机壳/法兰、密封和紧固件；螺栓名义长度覆盖螺母位置。展示拆解不改变检查几何。

若静态姿态无干涉而插入采样发现障碍，可信工厂可在原方向及其反向、原距离内搜索候选顺序；父件先装、最多 128 个候选检查。找到建议后提供“采用实体采样建议重新制作”，只替换步骤，不改零件、配合或最终姿态，重新完整检查并交付新 UUID。无解/预算耗尽只表示本搜索未找到方案，不证明不存在装配路径；建议不静默取代原方案，也不成为连续碰撞证明。

## 受控 MCP 办事通路（dev.11）

**implemented；实际验证归[本轮验收](delivery-validation.md#mcp-evidence)。** 新工程现在可调用明确登记并启用的 HTTP MCP 工具，复用原 Registry、GrantStore、Ledger、TaskRunner、目标计划及会话交付。它是外部执行适配，不是另一个 Agent 核心；服务器可以单独升级或替换，旧任务不会悄悄绑定新版本。

运行顺序为：登记端点 → 主人选择连接并发现 → initialize / initialized / tools/list → 展示外部工具及输入结构 → 主人选择允许的工具 → 自然目标生成可修改计划，或直接填写参数 → 核对确切端点与参数 → 原账本创建限次任务 → 执行前重新核对工具摘要 → tools/call → 持久回执 → 本机产物 → 原目标/会话交付。

| 环节 | 当前行为 | 明确限制 |
|---|---|---|
| 登记与发现 | 设置 → 技能与工具 → MCP 接入；发现只发送协议握手和列表请求，不发送 tools/call | 发现会接触指定服务；不能保证第三方服务自身无副作用 |
| 启用 | 每连接最多选择 12 个支持的工具；变更、停用、重新发现均改变准入修订 | 不使用 readOnlyHint / idempotentHint 自动授权；默认不启用发现结果 |
| 自然目标 | 最多 12 个目录项发送规划模型；同时有纯工具/MCP 时各取前 6 项；MCP 可作为首步；原始文字可由模型组装为 JSON 参数，数据含义仍需核对 | 最多一个 MCP 调用，参数必须事先以 JSON 展示；不支持由上一工具输出临时决定外部参数 |
| 直接调用 | 填写严格 JSON 参数，明确调用一次；相同 request_id 与内容返回原任务 | 参数变化重用 request_id 被拒绝；重新建任务仍可能重复外部效果，需先核对旧结果 |
| 结果 | 文本/结构化 JSON 保存回执和 result.json，目标任务回到原会话 | 工具内容为外部数据，不作为新指令；不下载链接、图片、音频或附件，不自动成为长期记忆 |
| 错误 | isError=true 保存已确认的错误回执，任务 FAILED，不执行成功交付步骤 | HTTP/RPC 中断、格式变化或不支持的结果可能落为 UNKNOWN；不凭“只读”声明重放 |
| 接续 | 已确认动作不重跑；落盘回执可核对并继续保存产物；取消只影响对应任务 | 缺少持久回执时需要外部核对，当前没有服务专用的远端对账适配 |

本版仅接**无凭据的 Streamable HTTP**：HTTPS 服务或字面量 127.0.0.1 / ::1 的 HTTP 服务。stdio、OAuth、凭据代理、长期订阅、资源/提示词接口、sampling、elicitation、MCP 异步 tasks 仍未实现；登记这些方式不会启动程序或调用其他供应商的 Key。HTTP 模块只支持受限协议子集，不能据此声称兼容所有 MCP 服务器。协议核对依据见 [S321—S323](references.md#mcp-runtime-sources)。

### 静态烘焙与三档 LOD

在已交付产物的验收页明确点击“烘焙贴图与生成 LOD”，新建有来源关联的任务，零模型调用。契约允许512/1024/2048图集，查看器可显式选择。512叶轮和2048坦克已有原生执行；1024未单独验收。模型规划不得自行选择资产或启用烘焙。流程为：计算后网格复制 → 合并静态副本 → 微小退化面清理/三角化 → 独立图集UV → Cycles材质表面烘焙 → basecolor、切线normal与ORM（R=AO/G=roughness/B=metallic）→ 三档实际GLB → 官方glTF校验。另保留单独AO图片和可编辑.blend。

这是同一计算后表面的材质烘焙，能转存部分程序微细节，**没有高模向人工低模的笼罩投射**。静态副本合并零件层级，不能用于发动机/车辆关节运转；原产物不变，.blend中保留隐藏的原对象。清漆、透射、各向异性未保真。自动减面约为原三角面的50%和25%，记录实际面数和双向采样表面距离；它不等于人工重拓扑，也不证明所有视角轮廓无跳变。

机器检查包含有限值、退化面、开放/非流形边、UV存在与越界、确定面积超载、LOD减面、采样偏差与格式校验。UV面积和大于1可确定非堆叠图集存在问题，小于1仍可能局部重叠；本版没有精确重叠或纹素密度检查。奇异UV产生的零切线用正交基补全并记录数量/警告，只修复向量有效性，不修复UV质量。开放边可能来自薄片或清理产生的孔洞，不能一律当成功或失败，必须结合用途检查。

### 面向高质量游戏资产的制作与验收

**游戏高模的运动与合批。** 编辑母版允许保留细粒度对象，供继续改形；检视与游戏交付副本按“刚体运动归属 × 材质”合并。紧固件、盖板和焊接件随所属总成运动，车轮、俯仰、转向、滑块等有相对运动的总成保留独立枢轴与父子层级。禁止为了减少对象数把运动关节合死，也不把每颗螺钉当成独立动画件。合并后核对三角面、世界空间表面、法线、UV、材质、动画及实际绘制调用；网格数、材质数和 draw call 分开记录，阴影通道与目标引擎场景另报。当前 leFH18 提供指定总成的刚体游戏预览，不代表通用自动绑定或连续碰撞验收。[分项实测](delivery-validation.md#studio3d-production-evidence)。

带 `jarvis.game-high.v1` 标记的未加工导入资产保留原 GLB 字节，Blender 生成可编辑源与渲染；消费作业内的输入暂存副本，托管原资产仍保留。原有资源预算、几何往返和官方格式检查继续执行，不能靠再次导出破坏自定义法线、动画或材质。查看器显示固定／旋转／平移总成和动画选项；高模未确认时禁用低模制作入口。元数据及这项界面禁用不构成通用安全边界，也不能把模型声明当作用户批准。先取得高模认可，再进行低模、投射烘焙与 LOD。

**2026-10-24 主人明确的制作要求（accepted）。** 现有坦克是低模草稿，不能当高模。以同一车型、同一外观状态的实车照片建立参考，先修正比例、轮廓、零件结构和分件材质，再交付高模母版；检查后制作低模、UV与高低模投射，最后生成游戏LOD。生成参考图只能辅助构图，不能代替实车照片或证明准确性。可执行的中文制作规格与机械/车辆/硬表面道具规则集中在 modules/skills/studio3d/production.py 的 BRIEF/PROFILES，工作室可查看；本节管理制作要求与验收边界。

统一按**三角面**记录预算。高模50万至200万是按需参考，不靠平面无效细分凑数；当前Worker仍限制150万计算后三角面。坦克LOD0目标2万至4万，履带、轮子、炮管、工具柄、灯具优先减少不能改善目标镜头轮廓的周向细分；主要开孔、板材厚度、剪影和运动件原点保留。低模可以从高模做分件减面、解析曲面重建或重拓扑，不能将“全局Decimate后没有报错”当作完成。去掉几何的细节必须有所属低模表面接收烘焙，薄浮雕不能成为无承接面的孤立贴图。

油漆、橡胶、玻璃、木材、锈与裸钢分别定义，普通不透明漆层以非金属响应为基线；露钢蒙版才产生金属响应。BaseColor不固化灯光，Normal传递局部凹凸，Roughness表现不同材料和使用痕迹，Metallic区分材质，AO保留独立通道。Height/视差可作为支持它的目标着色器的补充；不能代替侧面轮廓、真开孔和深凹遮挡。本查看器尚未接高度视差。

**1.3.0候选实现范围。** 设置增加高模母版候选与制作规范入口；查看器增加车辆/机械/道具类别、2/3/4万三角面预算和“高模→游戏低模→投射烘焙”。按源部件减面，bake_target把高模附着细节配给前置可见基件；在分离的烘焙位置执行Cycles selected-to-active、自动外扩笼罩和有界射线，随后恢复原坐标、名称与刚性原点。输出三档LOD、法线/底色/ORM/AO和有限射线覆盖报告。没有保留父子骨架、动画、透射和清漆；不是解析圆柱自动重建或艺术家重拓扑。来源高模必须为未烘焙已交付产物，拒绝把已有烘焙低模再次当作源母版。服务加载、真实执行及失败记录见[生产流水线证据](delivery-validation.md#studio3d-production-evidence)。

按目标平台、镜头距离、运动方式及美术参考确定预算；不存在通用面数或“全四边面即3A”的判定。建议流程与本版边界如下，通用资产交付参考[官方指南](references.md#s328)：

<a id="studio3d-hard-surface-review"></a>
#### 硬表面多视图复核与原生表面检查

火炮类游戏资产的经验提炼、参考策略、固定工具、练习清单和实际调用统一见[实施手册](studio3d-learning.md#studio3d-learning-scope)。通用审查不再强制 leFH18 炮盾形状；当前用户要求由资产策略传入。

2026-10-26 增加协作者使用的命令行工具，**implemented / 局部分项验证**。`tools/studio3d_reference_review.py` 将同一实际候选的参考图与渲染成对发送到用户明确选择的 Jarvis 模型线路，逐视图保存图像与模型摘要、回复、用量和失败状态。`modules/skills/studio3d/review_evidence.py` 核对候选与五视图绑定；局部裁切仍保留原图摘要与裁切范围，不替代完整五视图。已有成功结果按同一候选复用，中断或未知结果先查询原调用，不以自动重发掩盖失败。此工具没有接成工作室界面的无限循环，模型意见也不能直接执行任意脚本。

修改前先区分相机、几何、材质和光照；被指出缺失的零件应以局部近景和实际网格核对。整套轮组变换要连同轮毂、垫片和紧固件，先确认露出的是内侧还是外侧轮面，再调整厚度。参考图之间的开孔、附件或投影矛盾必须记录；同一共享模型不应为迁就单张图反复删除或恢复部件。每轮修改保留失败与被拒绝版本，实际导出后重新导入渲染并在 Jarvis 查看器核对，不能把原生程序材质预览当作 GLB 已保真。

用户明确纠正参考图解读时，记录被否决部件和新的参考优先级；最新纠正必须放在有长度限制的通用场景清单之前，避免随着清单增长而被截断。资产检查配置可用 `forbidden_meshes` 指定不得恢复的对象，检查实际场景中的隐藏对象和 Blender 自动编号副本；仅隐藏错误部件不算删除。轮组等几何方向改变后，也要同步核对程序纹理坐标和最终材质混合结果。

材质烘焙必须保持坐标系一致：世界位置贴图不能依赖合并后活动对象的局部法线选择投射轴。原始材质、合并烘焙输入和重新载入的 GLB 要用同一近景相机检查；发现条纹时分别隔离颜色、粗糙度和法线通道定位原因。平面端盖的放射状小三角形不能仅因面积小而被当作磨损倒角。悬空套环等遗留件要追查原先依附的部件，不能根据外形臆造用途。

机械外观出现多轮叠加时，逐件登记原生成来源、所依附主体及当前实际接触位置；撤销主体时同时核查独立紧固件、套筒和端盖。历史复原优先采用博物馆说明与实物所有者的原始照片，并区分型号差异、缺件和修复状态。只有形状相似不能推断零件用途；缺乏证据时可按用户要求简化成明确连接的游戏外观，但必须标明简化范围，不把新增支座或操作柄称为精确历史机构。自动视觉复核建议补回复杂细节时，不得自动恢复用户已否决的部件。

用户要求可开合游戏部件时，分别保存静止姿态、刚性动画成员和运动范围。分组烘焙后恢复动画，并在实际导出、Jarvis 导入和查看器中验证关闭/打开姿态；原始 Blender 动画存在不等于交付 GLB 保留动画。可视内腔检查只证明游戏网格的遮挡和连通关系，不代表真实内部机构复原或制造依据。

重新导出导入资产时，选择范围应包含可见网格所属的动画空父级，保留法线贴图所需的切线数据；不得为保留动画顺带导出无关灯光、相机或隐藏对象。核对用户当前查看器地址、实际 GLB 摘要、面数与动画状态，避免把旧页面当成新版本验收。

`tools/studio3d_blender_surface_audit.py` 在 Blender 内核查指定封闭表面的边界、有限坐标、可见面材质，以及指定磨损属性是否非空且连接到材质节点；`tools/studio3d_blender_finish_geometry.py` 提供保守的微小端环封口与硬表面法线处理。它们不证明无自交、每条着色分支有效或视觉相似度。烘焙可移除确无面引用的空材质槽，实际有面缺少材质必须失败。资产自己的接触检查另行核对附着与接地，不能用接触检查代替拓扑检查。高模仍由用户确认后才能制作 LOD；费用和 token 只汇总有回执的部分，未知的编写、图片生成费用保留为空。

### 参考图识别、有机道具与贴图修正（1.6.0）

在3D工作室上传PNG后，明确勾选“让模型识图（Gemini）”，选择已配置的Gemini/Vertex线路并点击规划制作；此时才会把该图发送给指定供应商。未勾选仍为本地对照。API对应显式的vision_reference=true，必须同时提供prompt和已上传reference。模型输出受约束的scene JSON，经契约校验后调用本地Blender；没有执行模型生成的Python。调用沿用原会话和费用账本；失败不会自动重发，已成功生成的候选可以复用而不增加模型调用。

1.4.0加入有机旋转曲面的封口、轻微分瓣和不对称，以及果皮/木质纹理。初版果实主体仍受旋转曲面表达能力限制；果皮条纹、皮孔和梗洼颜色是依据图像观测的程序化材质，不是扫描或照片贴图。半径最小0.1毫米，支持小果柄末端。摄影棚按实际几何和画幅适配取景、近裁切和接地距离。模型决定形状与色彩参数，固定插件决定这些参数怎样转成网格和材质；不能将它宣称为任意图像的精确3D重建。

高模检查后，在查看器选择“高模→游戏低模→投射烘焙”、有机道具、1000三角面预算与2K贴图。苹果量级在1.6.0默认4毫米投射距离；查看器允许按实际尺寸显式调整1至100毫米，并检查所有LOD覆盖和渲染。低模保留果实和果柄，果皮微细节投射至法线、底色和ORM；继续保留独立AO与三档LOD。高模BLEND保留完整材质层；高模基础GLB不能完整保留程序层，以BLEND和渲染对照；游戏低模GLB含烘焙贴图。交付需区分这两类外观能力。

**1.5.0 对照修正。** 已交付的声明式高模卡片新增“参考图对照修正”入口，使用当前附加参考（未附加时使用该高模的原参考）与明确选择的Gemini/Vertex模型。点击即明确发送参考图及实际渲染：第一次调用按轮廓、果柄/附件、果皮/材质、高光四项返回问题、修改和完整受限候选；固定Blender执行一次；第二次调用仅复核新渲染，不能再改模型。每次最多两次调用、一次改模，失败不自动重试，也不自动连续迭代。原版保留，新版回执与review.json保存双图摘要、模型会话、修改依据、最终needs_revision/acceptable/uncertain判断及未验证区域；acceptable只是该模型对当前视角的意见，不能授予AAA认证。上传、原图识图与双图对照的授权分别以实际点击的操作为准。

API使用refine=<已交付高模ID>、reference、vision_reference=true、provider/model和可选focus；只支持本工程声明式高模，不支持外来GLB、冻结低模或模型自行选择资源。失败的比较调用若已成功生成回复，可显式指定reuse_review=<失败任务ID>复用；必须核对原参考与渲染摘要、供应商和模型，仍执行一次改模及最后一次新复核。只支持已完成compare候选，不复用最后verify意见。受限sweep的cap_material以对象字段为规范，也接收params内同名别名并归一化；同时提供两处会拒绝。

插件新增受限sweep：2至32个控制点与逐点半径，沿曲线渐细、椭圆截面、封口及独立断面材质；细分步数2至16、周向8至64，仍计入总输入顶点预算。果皮新增最多8个椭球色区、条纹缩放/扰动、皮孔大小/颜色/强度、微凹凸尺度、粗糙度变化和果窝控制；这些是参考引导的程序化层，尚未实现照片去光照、纹理投射或像素级颜色恢复。摄影棚开放受限相机方向/焦距、横向或正方形画幅、最多三盏面积灯和背景/环境颜色及亮度。扫掠端面可添加有界不规则起伏。完整数值契约由工作室数据契约提供，文档不另抄一份所有字段范围。

技能以通用制作顺序配合物体类别规则；车辆的既有细则独立保留，有机道具重点检查不规则轮廓、凹窝、果柄和多尺度表面。先复核高模，再制作低模；参考相似度未达标的减面结果只作技术比较。低模和额外LOD仍要分别看渲染、剪影和接缝，不用格式校验替代视觉验收。查看器增加“柔和单主光／多灯摄影棚”切换，有机道具默认前者；实时检视灯光与Blender静帧并非同一渲染环境，精确对照以同一静帧设置为准。额外LOD明确显示待视觉验收，自动流水线保留视觉检查警告。

苹果完整实测及质量缺口见[苹果验收](delivery-validation.md#studio3d-apple-evidence)；图像外发与资源边界归[查看器安全边界](security-sovereignty.md#studio3d-viewer-boundary)。单图看不到的背面和底部只能推断，面数、格式校验和成功烘焙都不自动证明AAA美术质量。


**1.6.0 底色贴图与独立LOD。** 有机高模卡片增加“应用果皮底色贴图”：上传带来源/使用权的PNG，明确选择fruit_skin材质和映射方式后，本机新建模型。沿旋转体母线弧长生成SurfaceUV，减少果肩平坦区域的高度投影拉伸；其他形状可用局部Z轴圆柱映射。仅使用一张宿主摘要核验的底色图，覆盖程序条纹与皮孔；果窝色区、微凹凸和粗糙度仍为独立材质层。贴图打包进BLEND；双图修正隐藏私有资源ID并由宿主保留原绑定。此能力不是从照片自动去光照、背面重建或扫描PBR；本次Codex用imagegen生成的参考启发底色同样只属近似。

project模式的每级LOD现在分别从冻结高模生成低模、重新展开UV、独立投射并嵌入自己的底色/切线法线/ORM；有机类别的封闭lathe（不含布尔或壳厚修改）采用沿母线弧长采样的规则环网格，再贴合计算后的高模表面，其余部件继续分件减面；另交付各级AO和PNG。surface旧模式仍复用图集，不继承此项改进。UV间距16像素、烘焙扩边8像素；每个抽样三角形使用中心、近边与近顶点共7条平滑笼罩射线，总计最多8192条，仍不等于逐纹素证明。超过既有5%漏射阈值拒绝烘焙，较少漏射仍警告并需视觉检查。额外LOD回执包含独立覆盖/贴图记录，检视器显示当前LOD检查。Blender导入GLB启用Merge Vertices，合并允许合并的重合顶点，法线/UV仍保留；本次多视角复查证明仅合并不能解决果窝暗缝，最终由规则环网格改善。外部软件需按各自导入设置核查。完整实测与未验证项见[苹果证据](delivery-validation.md#studio3d-apple-evidence)。

**高模人工确认与成本记录（2026-10-24补充）。** 每轮高模须先提供实际渲染、同一母版五视图和可查看模型，等主人明确确认后再减面或生成LOD。`asset_pipeline.generate_lods=false`支持只烘焙当前几何的底色、法线与ORM，默认仍保留原LOD行为；没有创建低模或LOD的高模材质预览不能标成减面验收。`weathered_paint`是受限的程序化涂层/磨损材质；纹理采用几何位置坐标，避免独立零件合并烘焙后按整体包围盒拉伸，并支持稀疏划痕与粗糙度变化。多张AI参考有冲突时须记录取舍，由同一几何输出五视图，不将互不标定的图像或增加面数当作外观验收通过。 平滑网格按40°转折保留硬边，避免套环和铸件台阶被平均法线抹平；final可编辑母版主渲染为1920×1280；烘焙任务为控制贴图与降噪的叠加内存，主渲染保留1280×854，模型几何与贴图分辨率不受影响；五个正交审阅视图为960×640。每个资产放在`3DModels/<EnglishAssetName>/`，其`costs.json`/`costs.csv`逐阶段保留成功、失败和被否决版本的模型调用、输入/输出/推理token、美元估算与实测耗时；未暴露的内置生图及Codex会话费用为未知，不填零。Blender报告记录各建模、烘焙、渲染与LOD阶段耗时和本地阶段零API用量，费率估算与供应商实扣分开。

## 图片与图形设计 · Nano Banana（1.1.0）

图片与图形设计合并为一个组合技能入口，内部规则不另占技能菜单。现有Jarvis目录没有独立的平面设计执行器，因此本轮实现第一方设计要求编译与验收配方，不宣称安装了外部设计插件。需要产品图、海报、信息图、材质底色参考或3D建模参考时使用；另有自由绘图，共六类。普通聊天仅加载指导，明确在工作室提交才产生图片调用。

界面分为“设计与生成”“模型与预算”“作品与费用”。前者填写主体、用途、受众、风格、必要文案和限制；选类别后本地补入构图、材质、准确文字或科学事实等规则，不增加规划模型调用。选择Google连接和模型，实时预览实际像素规格、图片输出估算与本地预留额。后台保存当前选择为默认、管理模型启停及阈值。费用口径和分辨率唯一归[模型目录](models-offline.md#nano-banana-models)。

生成流程为设计要求→出图/编辑→实际尺寸核对→人工清单验收→继续修改或交付。每种设计有不同清单：海报核对文字和阅读层级；科普核对事实与连线；机械产品核对轮廓和材质；底色检查光照及边缘；3D参考检查视图一致性。初始状态为待人工检查，尺寸匹配且清单全通过才允许记录人工验收，不以API成功替代美术通过。验收记录保留图像SHA、修订和人工来源，没有伪造模型评分。

“以此图继续修改”只适用于符合输入预算的PNG；明确登记此图为本次参考后填写修改说明，下一次提交独立计费并记录父任务。宿主核对父图SHA确实存在于输入参考，不能随意挂名修改关系。PNG也可转入3D参考流程；3D工作室负责网格、材质绑定与烘焙，Anatomy负责机械结构与运动展示，图形设计本身不提供这些能力。JPEG与超限高分辨率输出可以下载，尚不自动转换或缩图。

所有输入参考都是明确选择的最多两张PNG；本地登记不外发，生成时才发送到所选线路。单次一张，不自动重试、自动换模型或循环改图。取消保留已获取用量；超时采用独立看门狗回收HTTP子进程。中断任务标记UNKNOWN并同步修复该任务的调用账本，不自动补发。通用未知费用和失败产物都可手工登记账单金额与依据，估算和账单分列，不相加。

API沿用/api/image-studio：GET根为目录、参数和配置，GET /jobs与/jobs/<id>为状态；POST /settings保存默认与启停政策；POST /preview本地编译设计与预估、零模型调用；POST /references只登记本地PNG；POST /jobs提交；POST /cancel取消；GET /files/<id>/image.png或image.jpg经SHA核对读取；POST /reference送入3D；POST /annotation保存人工验收或账单修订；GET /billing为全历史图片汇总。界面显示最近40项作品；已有统一费用页仍可查看每条实际调用。

配置保存在config/image-settings.sqlite3，状态及追加式注释在state/image-generation.sqlite3，产物与不可变原始回执在artifacts/image-generation/<id>。生成、编辑、费用快照和用量使用同一调用记录，不把图片二进制塞入文字回复。效果与未验证范围见[验收](delivery-validation.md#nano-banana-evidence)。

| 类别 | 处理与呈现 | 权限与纠正 |
|---|---|---|

| 账单／旅行／附件／项目材料 | 提取候选日程、待办、资料引用 | 不自动付款、订票、运行附件；个人／家庭／项目数据按原分域规则保存 |

实施复用现有队列、费用与记忆体系：接收去重→本地规则优先→必要时有界模型分类→候选动作→有效权限→执行与核对→低打扰通知→主人纠正与方法回退。先影子运行比较误判、遗漏和干扰次数，再开放范围明确的可逆整理；不要一次性给予全邮箱所有动作。

**PC 同步选型。** 先采用有界按需读取；下一步接 Gmail `historyId` 增量，过期后有界重建。Google 对用户设备仍建议轮询同步；Pub/Sub 推送需要额外云端配置，不作为普通 PC 的必需依赖。两分钟界面可选检查尚未实现 history 增量，不能称为推送或实时全箱监控。[Google 同步](https://developers.google.com/workspace/gmail/api/guides/sync) · [推送与用户设备建议](https://developers.google.com/workspace/gmail/api/guides/push)。

<a id="weixin-integration-plan"></a>
## 微信接入与桌面协作评估（2026-10-30，proposed）

**结论：先把微信接为同一个 Jarvis 的消息入口，再按需求加入个人微信桌面适配。** 前者适合手机派任务、接续工作和接收结果；后者适合读取用户选定的好友／群聊、准备回复及操作客户端。两者不是同一种权限，不能因扫码连接机器人就声称可读取所有聊天。当前仅完成资料与本工程代码评估，没有安装微信组件、绑定账号、读取私人聊天、发送消息或建立后台监听。来源归[微信接入研究](references.md#weixin-integration-sources)。

Codex 官方 Computer Use 已支持 Windows／macOS 桌面操作，但 Windows 使用当前前台桌面；它不是自动授予 Jarvis 的接口或执行权限。[S390](references.md#s390) 本次官方文档检索 WeChat 无命中，可用插件目录检索 WeChat 也未找到专用连接器；这只是本次可见目录结果，不能证明所有账号或第三方市场都不存在微信集成。第三方 WeChat-MCP 明确提供 Codex 配置，但该项目的执行层是 macOS Accessibility，不能直接用于本机 Windows。[S395](references.md#s395)

<a id="weixin-capability-scope"></a>
### 能做什么：消息入口与个人微信操作分开

下表为拟实现能力；基础研究不代表功能已通过运行验收。具体动作取决于连接器声明与账号实测，不用一个“已连接”开关代替整张能力表。

| 场景 | 对主人的作用 | 所需通道与实际边界 |
|---|---|---|
| 手机随口派任务 | “看看今天重要邮件”“继续昨天那个项目”“整理这份资料” | 官方微信机器人入口；接回现有意图、目标和任务，不另建模型路由或人格 |
| 远程询问与接续 | 问进度、补充条件、取消某一项、回答 Jarvis 的问题 | 映射原任务及会话；取消一项不停止聊天或其他工作 |
| 发语音、截图与文件 | 将可用媒体交给已有语音、识图、资料或研发能力 | 按通道实际媒体类型、大小、期限与资料外发许可；媒体接收不等于本工程已有全部处理器 |
| 工作完成／重要事项通知 | 简短完成回执、需回答事项、邮件和日程候选提醒 | 同一通知事件；支持安静时间、去重、摘要和频率上限；服务端消息窗口不允许时留在精灵／工作台 |
| 查找好友／群聊信息 | 查用户选定会话中可访问的约定、地址、文件和待办 | 需要个人微信桌面适配或用户主动转交内容；ClawBot 连接本身没有验证为全聊天检索权限 |
| 待回复与群聊摘要 | 摘要选定群、提取待回复、会议／项目事项 | 有限会话、时间与页数；未读取部分明确标注，不把窗口可见内容称为全历史 |
| 协助回复、翻译和改写 | 为指定对象准备回复，核对后发送 | 草稿与发送分离；明确对象／内容且有效授权覆盖的低风险回复可以自动执行，不重复索要同一许可 |
| 家庭／项目协作 | 家庭日程、项目进展、向允许对象共享成果 | 每个发送者独立身份和资料范围；群聊不能获得主人的私人记忆或整个项目库 |
| 关系与个人记忆 | 从授权内容中提取称呼、约定和偏好候选 | 保存来源与适用对象，可纠正、撤回；转述不是事实认证，微信好友也不是已认证家庭成员 |
| 预约与其他外部办事 | 将微信指令交给日历、研究、采购等已准入工具 | 微信只负责入口；各领域原有权限与本人确认条件不因远程指令而扩大 |

不将红包、转账、批量加好友、群发、全量聊天导出或朋友圈自动发布作为首批目标。部分第三方库宣传具备这些接口，也不等于它们适用于本工程或当前账号。

### 接入路线与开源借鉴取舍

| 方案 | 适合的事 | 普通 PC 成本与缺点 | 本工程选择 |
|---|---|---|---|
| 微信官方 ClawBot／Weixin channel | 主人私聊助手、提交任务、文本及支持的媒体往返 | 主动出站消息连接，通常无需驱动微信桌面；账号资格、消息窗口与接口支持仍需实测 | 第一优先；先验证允许的最小连接路径，不承诺控制其他联系人 |

| wxauto／wxauto4／wxautox4 | 已有 Windows 微信 UI 适配经验 | 版本、解释器、激活和许可差异；不能把旧仓库的 3.9 客户端说明套给新 4.1 客户端 | 借鉴控件定位、目标核验、消息事件；审查具体发行版后再决定依赖 |
| macOS WeChat-MCP | 近期消息、回复、聊天定位等桌面能力 | macOS Accessibility 与截图；需系统授权，Windows 不可直接复用 | 借鉴工具粒度与适配分层，不把附带角色提示和自动发消息能力全部启用 |
| 企业微信智能机器人长连接 | 家庭／小团队未来的群内协作、@机器人、工作通知 | 需企业微信账号与可用机器人；与个人微信、微信客服不是同一个 API 范围 | 有实际群协作需求再加入，不作为个人 PC 初次接入的先决条件 |
| Wechaty 多 Puppet／协议型方案 | 多后端抽象、模拟传输、事件接口 | 真正能力与费用依赖 Puppet 提供者；老 Web 与模拟移动端路径并非统一稳定接口 | 参考端口和 mock 设计，不将协议模拟、Hook、密钥提取作为默认路线 |

腾讯官方产品文档已经验证“扫码后从微信向电脑助手发任务并回传”的产品形态。[S391](references.md#s391) `@tencent-weixin/openclaw-weixin` 在本次 npm 元数据核查中为 **2.4.10、MIT、Node >=22.13.0、peer OpenClaw >=2026.5.12**。[S392](references.md#s392) 这说明现有插件有宿主依赖，不能声称它是可直接导入 Jarvis Python 的独立 SDK。

优先核对官方允许的独立接入方式、稳定契约和账号资格；若可行，独立编写薄适配器。若仅有 OpenClaw 插件受支持，可先评估有界桥接，但必须验证能够关闭第二套 Agent、工具执行、人格、长期记忆和模型调用；做不到就不作为默认依赖。MIT 只描述代码许可，不能据此推断服务端允许任意客户端或永远兼容；不能把社区整理的内部接口说明当正式服务契约。

**本机兼容性重点：**当前核心使用 Python 3.13。wxauto 安装文档列免费 `wxauto4` 仅 Python 3.9–3.12，Plus `wxautox4` 为 3.9–3.13，免费版当次列出的微信客户端上限为 4.1.8.107。[S393](references.md#s393) 这些是文档兼容声明，尚未核对本机微信版本或实际行为。不得为了接入直接降级核心；确需不同解释器则使用独立可停用进程。旧公开仓库 README 与当前产品条款、发行版许可须分别复核，不根据 GitHub 星数或单一 license 字段批准生产。[S394](references.md#s394)

企业微信官方方案已经支持主动 WebSocket 长连接，无需把本机工作台暴露公网；其 @机器人／私聊作用域不等于读取个人微信全部会话。[S396](references.md#s396) Wechaty 值得参考多后端与 Mock 抽象，但业务能力必须逐个提供者核对。[S397](references.md#s397)

**两条试验路径分开。** 要从手机指挥 Jarvis，优先验证 iLink 消息桥接候选；要读取并操作本人的 Windows 微信，优先验证 RungePei 的 UIA 型 MCP，wxauto-mcp 为对照。通用 Windows MCP 按其他桌面需求择一验证，浏览器用 Playwright 候选；不为比较一次性安装全部项目。依赖不进入核心环境，也不默认启用群发、朋友圈发布、添加好友、全盘文件或任意 Shell。

**已经发现的适配点。** RungePei 提供 HTTP 并不代表当前 Jarvis 已可直接安全挂载；保持[核心接入边界](#weixin-core-integration)，核对 MCP 版本、schema 子集、认证和输出大小。stdio 候选需补本工程客户端或受控桥接。多步会话需保持适当的连接生命周期，不能因每次换会话丢失控件引用、动作依据或桌面互斥。依赖来自同一系统用户的独立进程不是沙箱证明。

RungePei 源码注册中同时存在查询、单发、群发和朋友圈等工具；客户端勾选少数工具不等于服务器剩余能力消失，需在受控执行边界限制。其 README 的 91 项测试主要用 fake_wechat，不能当作本机真实微信已经通过。界面读取也可能改变已读状态，需单独核对，不因工具名是 get／read 就宣称完全无副作用。

jimingyuan7 的 README 声明会保存 bot token、游标、context token 与下载媒体，默认目录不在本工程；本工程采用时必须接入本地资料与凭据规则。示例返回值含 context_token，接入层必须剔除后再交模型；存在令牌不证明送达。媒体支持本地路径和远程 URL，也需文件范围及网络许可，不暴露任意路径上传能力。README 的工具数有不同表述，最终以固定版本的实际 tools/list 和契约测试为准。

首轮采用范围为：固定源码与依赖检查 → Mock／协议验证 → 选定微信窗口的有限读取 → 文件传输助手草稿与授权内单发 → 故障、重复调用和用户接管。是否引入原组件、独立实现适配器或只借鉴局部代码，由上述结果决定；不能以“已有开源库”替代准入、恢复和真实效果验收。

<a id="weixin-model-neutral-routing"></a>
### Skill 不绑定模型：当前使用 Google 通过本机 MCP 执行

**主人于 2026-10-30 明确：不把 Terra 或其他具体模型指定在 Skill 中，此次使用 Google。** 全局规则只维护在[组合概念定义](architecture.md#composition-concepts)。下面 Terra 小节保留为可选技术研究，并非本轮默认或必要依赖。

执行链应为：主人请求＋所选 Skill → Runtime 解析所需能力 → 使用当前获准 Google 路由 → 产生工具请求 → 本机 Jarvis 核对权限、参数与预算 → MCP tools/call → 有界脱敏结果 → Google 判断下一步／交付。Skill 没有 provider/model ID；Google 连接和主选／备选在运行设置中决定。若所选型号不具备所需函数调用／图片能力、余额不足或服务拒绝，明确报告，不静默改用 Terra 或其他提供者。

Google 官方同时有函数调用和 Remote MCP 路径。[S410](references.md#s410)[S411](references.md#s411) 对个人 PC 采用本机桥接：Google 接收工具描述并提出函数调用，本机 Runtime 调用 MCP。不能把本机 127.0.0.1 地址当成 Google 云端可访问的远程地址；不为此对外开放微信控制端口。Gemini API Interactions 的远程 MCP 示例也不能直接当作现有 Vertex generateContent 的同接口配置。

**现版的能力边界：**现有目标规划可以用模型生成受审阅的 MCP 步骤，但限制最多一项、只能第一步、source=input；这是有限任务组合，不是任意多轮操作。Google 文字适配没有传入工具声明，并将 functionCall 视为非文字完成结果。要运行通用 Agent／MCP 闭环，需独立受限工具端口、调用与返回映射、API 所需回合数据、步数／费用／取消检查及出站结果核对；保留普通聊天的原文字通道约束。

**已验证的局部兼容性：**新增显式运行的 `tools/probe_google_mcp.py --live` 探针，从本机设置选择 Google 路由，不硬编码型号，不修改全局默认，不加载私人会话或 Skill。此次实际选择 Vertex／Gemini，进行了强制单次函数调用、真实本地 HTTP MCP echo 调用及函数结果回传；第二次模型请求正确报告工具之后生成的随机回执。2 次模型请求、1 次 MCP 调用，Google 返回 totalTokenCount 合计 412。此数仅是本次合成实验用量，不是未来微信任务成本预测。

探针结果为 verified，生产通用工具循环与真实微信仍 proposed；未安装候选微信 MCP、读取聊天、发送消息、启用监听或改变路由设置。证据及可重复命令见[Google／MCP 验证](delivery-validation.md#google-mcp-probe-evidence)。

<a id="weixin-terra-computer-use"></a>
### 没有现成插件时：Skill、GPT-6.1 Terra 与本机执行器怎样配合

**2026-10-30 官方资料核查与本工程差距分析，仍为 proposed。** GPT-6.1 Terra 并非只能聊天：官方模型页列出文本／图片输入、computer_use、function calling 等支持，模型 ID 为 `gpt-6.1-terra`，工具调用需要 Responses API。[S400](references.md#s400) 但是模型不会自行获得本机屏幕、键鼠、微信登录态或应用权限。Codex App 已配置的 Computer Use 服务也不会自动成为 Jarvis 的稳定产品接口。

| 组成 | 在这里负责什么 | 单独使用缺少什么 |
|---|---|---|
| 微信 Skill | 如何找会话、提取消息、整理摘要、起草及核对结果；适用版本与失败时怎么办 | 方法说明不提供屏幕读取或点击能力；不能因加载 Skill 就显示微信已接通 |
| 原生插件／MCP | 暴露状态、读取、草稿、发送等真实工具 | 仍需合适的平台执行器、身份和副作用控制；MCP 本身不创造微信权限 |
| GPT-6.1 Terra | 理解截图、判断下一步、产生电脑动作或调用受限函数 | 缺少本地 driver 就无法执行；账号 API 可用性与费用尚未实测 |
| 本地 Desktop Driver | 限定窗口截图、控件查询、点击、输入、滚动及状态核对 | 需上层任务、目标和恢复；不能单靠坐标脚本理解全部业务 |
| 原 Agent Runtime／动作网关 | 保持会话、执行次数、权限、资源租约、恢复与实际回执 | 继续复用，不另建微信专属 Agent 主服务 |

**官方已有可借用的循环实现。** 当前指南示例使用 Python OpenAI SDK `3.31.0` 的 `AsyncComputerToolset`，或 Node SDK `7.33.0` 的 `ComputerToolset`；应用提供 driver，并通过 before_action／beforeAction、max_steps／maxSteps 控制执行。也可直接处理 Responses 的 `computer_call.actions`，执行后回传匹配 call_id 的 `computer_call_output` 和截图。[S401](references.md#s401) SDK 示例的 Playwright 浏览器仅用于网页，不能据此声称已控制微信原生窗口；微信需要 Windows／macOS 对应 driver。上述版本是本次指南示例版本，不代表本工程已安装或准入。

首个实现建议选择**现有模型凭据与路由＋受限电脑动作回路＋平台 driver**。优先评估 SDK 工具循环能否完整接入原权限、网络、预算与取消检查；若能则包装复用，若不能则在独立适配器中实现小型 Responses 回路，不让外部 SDK 拥有任务账本和权限判断。不默认加载任意 `exec_py`／`exec_js` 作为真实桌面控制入口；官方示例的代码执行路线只是可选形式，不能因示例存在就扩大核心权限。

**本工程已定位的修改面：**

| 当前代码 | 实际已有能力 | 待补齐的内容 |
|---|---|---|
| `adapters/models/native_transport.py` | OpenAI 请求已走 `/v1/responses`，当前作为文字／JSON 通道；图片仅允许 Vertex／Gemini | 增加独立 computer-use 请求／回执适配；不将动作塞回纯文字完成接口，也不取消其原防线 |
| `adapters/models/native.py` | 凭据本地解析、网络开关、有界子进程和取消检查；参考图片同样限 Gemini | 新端口复用上述边界，增加 OpenAI 图像与工具会话契约；普通 complete 保持原职责 |
| `adapters/models/vision.py` | PNG 验证、图片数量／像素／大小上限 | 复用图像验证，并维护窗口来源、屏幕缩放、坐标与截图修订关联 |
| `adapters/desktop/` | 现有目录选择、位置与资源辅助 | 补真实应用 driver；先窗口发现与只读观察，再加入有限点击／输入 |
| 现有模型设置与任务控制 | 已有提供者、档位、任务事实与费用基础 | 增加视觉操作用途的主选／备选、真实能力探测、步骤与费用上限，不更换全局聊天默认 |

闭环为：取得指定应用与短时输入租约 → 读取当前控件／限定窗口截图 → Terra 产生动作候选 → 动作网关核对范围与当前界面 → driver 执行少量动作 → 新截图／控件状态回传 → 独立核对业务结果。发送作为独立受控动作；不能让通用点击、Enter 或其他快捷键绕过发送许可。状态过期、目标变化或无法辨认时重新观察，不对旧坐标盲目操作。

**调用与费用策略（建议，不是基准结果）：**固定会话和可靠控件可用时优先本地确定性动作；页面未知或改版才用 Terra 视觉。官方建议 reasoning 从 medium 起做代表性比较，再按收益调整。[S402](references.md#s402) 普通通知与消息搬运不调用视觉模型，不为了听到一句微信消息就截图整个桌面。主选失效只切到已明确批准且支持图片／工具契约的备选；发送结果未知时先核对原动作，不因切模型重新发送。当前没有验证本机 API key 对 Terra 的访问、截图发送许可、费用或实机成功率。

第一轮可独立开发和模拟：电脑动作契约、Mock Driver、截图坐标映射、拒绝越界、取消／租约、循环次数和未知发送状态。随后以用户启用的微信窗口验证只读定位，再在文件传输助手验证草稿及授权内发送；不先让模型自动遍历所有联系人。微信消息通道与桌面路线仍按[实施顺序](#weixin-delivery-stages)分开验收，基础 driver 将来也可复用于其他受准入的桌面应用。

<a id="weixin-core-integration"></a>
### 放进现有架构的位置与共享方式

遵守[一套系统、多种表现](architecture.md#unified-system-principle)：微信、精灵、工作台都进入同一身份、意图、任务、记忆、模型路由与交付链，不增加“微信专用大脑”。消息适配器只搬运经过范围检查的消息；Bot 继续负责工作，Agent 执行有界步骤，Skill 描述方法，Tool 执行动作，Runtime 保存任务事实。

| 位置（拟新增或扩展） | 单一职责 | 复用与不重复项 |
|---|---|---|
| `sdk/` 消息契约 | AccountRef、PeerRef、ConversationRef、MessageEnvelope、CapabilitySnapshot、DeliveryReceipt | 账户／发送者／会话／任务明确区分；契约不含明文凭据 |
| `modules/channels/` | 入站去重、出站状态、会话映射、游标、通知路由 | 领域规则；不绕开现有任务和权限，不再建一份邮件库 |
| `adapters/weixin/` | 扫码、连接、读取事件、支持的媒体传输、回执 | 只实现官方已核对的传输能力；网络与令牌操作留在边界 |
| `adapters/desktop/` 的平台端口 | Windows UIA、macOS Accessibility、未来 Linux 的实际可用操作 | 接同一消息／动作契约；不假设每个平台能力对等 |
| `host/` 协调服务 | 把微信请求接入现有聊天、Goal／Task、人员与项目范围 | 默认由原 Jarvis Bot 负责；必要时加载已有角色蓝图与 Skill |
| `control/` 现有动作／资源边界 | 许可、身份、预算、桌面租约、取消与恢复 | 适配器不能自发扩大权限；桌面设备与账号动作按冲突资源串行 |
| 工作台／精灵／微信呈现 | 绑定状态、能力列表、单项任务进度、问题与交付 | 同一状态投影；顶栏入口遵守[图标规则](interaction-persona.md#workbench-settings) |

入站顺序为：接收有限消息 → 校验账户／已绑定发送者 → 去重并定位原会话 → 识别目标或补充 → 当前权限内规划执行 → 核验结果 → 出站回执。普通对话直接走聊天；不为了收到一句话都创建复杂 Agent 群。

现有 `adapters/mcp/http.py` 是**有界 Streamable HTTP 子集**，没有本机 stdio 启动和通用认证头转发；`host/connectors.py` 可将批准的工具调用接回原任务账本。因此“仓库有 MCP”不等于能直接运行任何微信 MCP。需要协议版本、传输、认证、工具副作用和返回值契约测试。若使用本地桥接，应具备经本工程支持的认证／OS 访问控制，不能因为监听 127.0.0.1 就当作只有主人能访问；不为便捷关闭本机访问钥匙。

本次代码定位没有找到经过验收的通用桌面截图、控件查找及点击／输入执行器。现有 `adapters/desktop/` 的目录选择、资源采样等，以及[研发桌面通道设计](toolchains.md#development-desktop-protocol)，不能算微信桌面执行已经实现。

<a id="weixin-scope-and-private-data"></a>
### 身份、资料、发送与第三方输入

1. **绑定消息身份。** 保存 channel、account、peer 与主人／家庭成员的显式映射。昵称或头像不足以证明本人；扫码仅授予对应消息通道，不自动授予私人资料导出、桌面所有动作和家庭管理员权限。重要权限变化继续使用原本人核验路径。
2. **同一记忆，按视图提供。** 主人私聊可使用获准的个人记忆；项目任务只装载相关项目上下文；家庭共享使用明确许可；群聊仅获得该群可见资料。微信消息默认是对话来源，不将所有聊天自动并入知识库。纠正与遗忘继续影响后续检索。
3. **外部消息只是材料。** 好友转发、群文件、网页、图片 OCR、机器人输出都不能成为主人新授权，不能要求关闭检查、泄露令牌或改变规则。微信收到的执行指令也要核验发送者与原授权，而非只判断语气像主人。
4. **外发有固定对象与内容。** 发送记录绑定账户、会话、对象、正文／附件摘要和有效许可。对象不明确就先消歧；已明确授权且范围内的日常消息可自动发送，敏感披露、支付和权限变化沿原领域约束。微信作为出口仍意味着内容经过平台，不用“主人本人接收”推断任何私密资料都可回传。
5. **凭据不进模型。** 新连接单独放在本工程 `user-data/` 的私密命名空间，复用现有 Windows 加密边界；不复制 Gmail 令牌，不将密钥、验证码或密码回发微信。跨平台安全存储必须有对应实现与验收，不能把 Windows DPAPI 说成通用方案。
6. **可收回自动处理。** 主人可设置会话白名单、只读／草稿／有限发送级别、安静时间、频率与费用上限，并停用单一微信能力。自我升级候选不能修改上述许可或自动换成能力更广的提供者。

<a id="weixin-resource-and-recovery"></a>
### 普通 PC 的资源预算、故障与升级

官方消息入口优先使用一个按启用账户受控的长轮询或长连接通道；空闲不调用 LLM、不持续截图、不扫描整个硬盘或聊天数据库。仅在新消息、用户指令和已授权提醒触发时做有界处理；支持队列上限、正文／附件大小、缓存保留、批量摘要、指数退避与熔断。连接心跳不是模型思考。

桌面路径按需获取短时输入租约；用户正在使用鼠标键盘、锁屏、目标窗口／会话改变时暂停当前桌面步骤，其他聊天和后台任务继续。新版 Windows 微信可能存在控件树不完整问题，社区兼容层也记录了这一现象；这是需要本机探测验证的风险，不是对所有版本的实测结论。[S398](references.md#s398) 优先读可靠控件和限定窗口，视觉失败后交付不确定状态，不进行无界坐标点击。

资源目标是尽量不增加常驻模型、浏览器、容器、数据库和另一个 Agent 主服务；尚无微信真实运行的 RAM、CPU、网络或费用基准，不能给出“占用几乎为零”“不会封号”或稳定性评分。官方通道跨操作系统复用性更好；Windows 桌面端口的通过不代表 macOS／Linux 已通过。

游标和消息 ID 持久化，重启先去重再接续；发送出站项使用本地唯一 ID，区分已排队、已提交、已确认、失败和结果未知。超时不盲目再次发送；能按提供者回执或界面核对时先核对，无法证明时保留 UNKNOWN 并提示相关项，不能承诺端到端 exactly-once。平台限流或回复窗口到期时保留待交付结果，转为精灵／工作台提醒，不无限重试。

适配器升级遵守既有候选、检查、灰度和恢复规则；候选不可直接覆盖运行模块。恢复代码不回退已经发送的消息、不重复原动作、不复活旧授权或遗忘内容。依赖固定版本并核对包来源、许可、安装脚本和运行时网络行为；本次只读核查不等于完成病毒或完整供应链审计。[S399](references.md#s399)

### 建议实施顺序与关闭条件

以下是接入工作包，不是另建 K0—K6 开发时间线。

| 次序 | 可交付内容 | 必须验证的关闭条件 |
|---|---|---|
| 1. 可用性与契约探测 | 核对本人的 ClawBot 入口、官方允许路径、版本与许可；确定实际能力 | 只读研究后再做用户启用的连接；不擅自解绑现有其他助手；没有稳定契约则明确阻塞该路线 |
| 2. 同核消息最小闭环 | 扫码绑定 → 说话／给任务 → 原任务执行 → 微信回执 → 工作台同一记录 | 文本往返、重复入站、陌生发送者、跨账号、过期授权、取消与重启；采用 mock 先验，真实连通另验 |
| 3. 个人助理联动 | 邮件摘要、已有任务查询、补充条件与文件交付、低打扰通知 | 不泄露私人／项目资料，通知去重与费用有界；平台窗口限制下有可见的替代交付 |
| 4. 个人微信桌面闭环 | 限定会话只读 → 回复草稿 → 有效授权内发送 | 从“文件传输助手”开始；验证焦点、重复昵称、用户接管、锁屏、改版及未知发送状态，再开放选定联系人 |
| 5. 可选家庭与小团队 | 企业微信／家庭成员分权、限定群协作 | 群成员隔离、权限撤回、个人记忆不泄漏；平台与账号能力逐项记录，不把单机模拟当跨平台实测 |

每个关闭条件分开记录 implemented／verified；本节全部保持 proposed。该研究不触发消息监听、自动发送、安装依赖、修改安全设置或开启计划任务。

## 英语学习与日志复盘 1.0.0（2026-10-26）

**implemented；限定真实对话与界面检查见[验收](delivery-validation.md#personal-workflows-evidence)。** 在现有文字技能目录增加两个默认可用的组合工作流，复用聊天、模型选择、用量账本和会话专属文件夹。没有新建后台轮询或独立模型服务。

| 工作流 | 输入与过程 | 实际输出 |
|---|---|---|
| 英语学习与练习 | 根据已知用途与时间开始短课；一道或少量练习 → 等待作答 → 区分错误与风格建议 → 同类重试 | 文字讲解、纠错理由、含实际作答与未完成事项的学习卡 |
| 日志与行动复盘 | 用户提供生活、学习或研发记录 → 区分完成、待办与想法 → 更正替换 → 下一步 | 有来源的日志、1—3项下一步与完成条件、接续摘要 |

**使用方式：**在聊天技能选框选择“英语学习与练习”或“日志与行动复盘”，即可在同一会话继续回答、纠正和总结。自动选择仅匹配明确请求开头，例如“开始英语练习：……”或“整理研发日志：……”，不会因单纯引述、否定或假设这些请求就选中新增技能。持续练习建议显式选中技能；没有实现通用语义意图识别或跨轮自动继承。

设置中的两个卡片有彩色图标、悬停及键盘聚焦提示、类型、适用/不适用说明与开始示例。可停用；“不使用技能”不注入指导。只有当前启用的工作流进入请求，并保存当时的正文与版本。新增工作流在智能助手模式下将纯教学和文本复盘作为当前对话交付；实际保存文件、发邮件、设提醒等另走已有目标与执行器，不把文字答复当成执行回执。

英文练习不提前给答案（用户要求自学答案或已经作答除外），不凭几道题认证等级；日志中的用户自述须明确来自用户记录，不能写成工具或测试已证实的结果。日期、时长、情绪和完成率不凭空补齐。学习卡与日志回复保存在会话及其专属文件夹；需要成为长期记忆或资料时继续使用已有记忆/知识入口，不能声称已经建立跨会话词库或独立日记数据库。

当前不含语音识别、发音评分、间隔复习数据库、定时提醒、自动新闻抓取/订阅及行业报告执行闭环。Gmail 的连接、有限读信与审阅操作复用[Gmail 助手](#gmail-runtime)，不是本轮新增或本轮真实邮件验收。以上扩展仍沿既有 K0—K6，不能把长期职责登记视为能力验收。

<a id="task-owner-collaboration"></a>
## 一项工作一个负责 Bot，多执行者协作（proposed）

**2026-10-26 设计细化，尚非通用运行能力。** 复用[Bot／Agent 边界](architecture.md#composition-bot-agent-boundary)和原 TaskRuntime。每项用户可感知的实际工作，恰有一个有效负责 Bot；未选择专用 Bot 时由默认 Jarvis Bot 承接。普通闲聊、内部定时器和确定性维护步骤不强制创建 Bot 任务。一个 Bot 可负责多项工作；Bot 不是独占进程、独占模型或额外权限。

| 职责 | 必须完成的事 | 不拥有的权力 |
|---|---|---|
| 负责 Bot | 理解目标、查相关经验、定义完成标准、分工、追踪依赖、合并成果、处理返工并交付 | 不靠自述完成任务，不独占评分和发布权 |
| 执行 Bot／Agent | 接受有边界的子任务，产出结果、证据、状态和阻塞原因 | 不自行改总目标，不把子任务预算变成新增总预算 |
| 检查者 | 对照冻结要求检查产物、真实效果和回归，给出可解释评估 | 不因与执行者意见一致就声称独立证据；不修改验收答案 |
| TaskRuntime／网关 | 保存任务事实、控制派发和租约、验证权限与副作用、执行取消和恢复 | 不将模型输出直接当作授权或外部成功回执 |

工作顺序是“接单并固定成功条件 → 检索适用经验 → 按必要性拆分 → 有界并行 → 检查与有限返工 → 原入口交付 → 形成经验候选”。简单任务由负责 Bot 配合确定性检查完成，不为展示热闹额外拉群。需要独立研究、不同工具或可验证分工时才增加执行者；共享事实通过带修订的任务上下文和产物引用传递，不靠所有 Bot 相互广播完整聊天。

**限定实现更新：**[1.3.0 共享执行额度](core-bootstrap.md#workflow-budget-runtime)已覆盖明确关联的 Goal/Task 工具动作预留与原账本消费；下面的模型/研发等总费用、完整依赖 DAG、任期与委派规则仍需后续实现。 [1.4.0 影响分析与当前版结案](core-bootstrap.md#workflow-closure-runtime)继续复用这一负责人投影，聊天目标跟随当前版本；仍无 Bot 任期或接管执行权。

每个根任务只有一张依赖 DAG；子任务只有一个父任务和一个有效负责人，引用同一成果不等于重复执行。并行数、递归深度、总代价、截止时间和返工次数在准入时冻结；耗尽时交付已有有效成果并说明缺口，不能自动扩容。相同文件、账号或机器人资源的冲突沿用既有租约和串行规则。

负责人转交使用[所有权契约](contracts.md#task-learning-records)的版本比较和递增任期。超时只产生接管候选；宿主先阻断旧任期新的写入，再原子转交，并查清在途动作。旧执行者迟到回报可追加事实，不能再派新动作或覆盖新计划。无法证明旧动作已停止时保留 UNKNOWN 并对账，不为换负责人重做购买、发送或物理动作。重启从原任务恢复，不创建平行任务账本。

用户的补充要求属于原任务修订：记录改动及其影响，保留可复用成果，只失效受影响子任务；全新目标再建立关联任务。负责 Bot 失败时只暂停受影响分支，其他独立工作和陪伴对话仍可继续。需要主人时由负责人归并为一个具体决定，按照[自主边界](security-sovereignty.md#autonomous-decision-boundary)准备材料。

迁移先给新受理的工作附加默认负责人；已有运行任务继续原协议，在明确检查点才接入新版。当前有界并发只是这一机制的基础，不能把“两个任务同时执行”写成已完成 Bot 分工、所有权转交和学习闭环。

<a id="real-work-routine-decisions"></a>
### 日常委托怎样自主推进，什么时候才需要主人（proposed）

**局部实现更新：**[工作交接 1.1.0](core-bootstrap.md#workflow-handoff-runtime)已把明确“批准并执行”的意图与受理原子保存，容量等待由原 Runner 接续。本节的常设自主委托、问题依赖分支和负责人接管仍未实现；此次改动不取消必要的受理边界。

本节落实[自主决策边界](security-sovereignty.md#autonomous-decision-boundary)，不另设授权系统。当前 [assistant](../host/assistant.py) 的操作建议需接收，[目标批准](../host/goals.py)与[界面启动](../apps/workbench/goals.js)分开；常设委托、按问题依赖推进和负责人接管仍待实现。实际诊断见[WF-01/02/08](delivery-validation.md#real-work-diagnostic-evidence)。

目标是主人交办后，已覆盖的普通步骤由 Jarvis 自行选方法、安排执行和检查；重要取舍、必要缺失信息和超出授权的动作才集中询问。一次“帮我整理资料”可覆盖该任务内已声明的可逆处理，并不等于永久允许其他任务或外部副作用。常设委托引用当前有效策略、范围、预算、期限和可使用默认值；撤回后在动作边界立即重新核对。

| 当前遇到的问题 | 推进方式 | 留下的可解释记录 |
|---|---|---|
| 仅是布局、文件命名等已有默认值的小选择 | 采用默认值，允许后续修订 | 默认值来源、影响范围，不生成重复审批 |
| 部分资料缺失，但独立部分可做 | 先做不依赖缺失信息的分支，等待只绑定受影响步骤 | 问题引用、依赖步骤、下一次恢复条件和期限 |
| 缺少会改变正确性的关键约束 | 负责人合并问题，给出当前材料和选择后果 | 为什么无法推断、哪些成果已完成、何处等待 |
| 计划超出当前委托、预算或能力 | 保留已完成成果，按原边界处理扩展或降级 | 实际缺口与可行选项，不能自己扩大授权 |
| 执行已明确交办但进程中断 | 从持久执行意图接续入原队列 | 原幂等键、目标修订和当前权限；不重复建任务或发许可 |

问题应有必需性、可用默认值及依赖集合。旧版未分类问题继续按原保守语义处理；不能自动把所有旧问题降为可选。新协议只暂停真正依赖该回答的部分。记录用于解释决策的条件和来源，不保存或展示模型隐含思维链。

自主性按“在委托有效且信息足够的任务中，正确完成且不需额外人工介入的比例”衡量，同时单列必要询问、可避免询问、错误自动决定和停滞。少问问题但误做更多，不算改善；把必要询问算成失败，也会诱导系统猜测。

<a id="real-work-revision-repair"></a>
### 补充要求后的局部返工：保留历史，继续同一件工作（proposed）

当前 [goal_context.amend](../host/goal_context.py) 仍不允许修改已经关联 Task 的目标。[工作接续 1.2.0](core-bootstrap.md#workflow-rework-runtime)已实现默认负责人和纯文本串行计划的关联后续版本，由明确选择的起始步骤确定返工后段；原 Goal/Task 与回执保持。下面的通用自动影响分析、外部业务补救和完整多 Bot 仍为 proposed，不能借用这个子集的通过状态。

1. **区分补充与纠错。** 新增原来没有的交期要求属于范围修订，旧结果按原标准的成绩保留；原要求已有交期却漏掉，属于原交付缺陷，追加纠正评价。不能将所有错误包装成需求变化，也不能把所有新增需求都记为旧方案失败。
2. **计算最小影响集合。** 比较条件、输入、来源和工具绑定的变化，沿原步骤/产物依赖向下标记；没变且仍有效的成果可引用。影响不明时将相应部分标为待核对，不能为省 token 假定无影响。
3. **建立关联返工 Task。** 记录原 goal/revision、原产物摘要、新要求及返工原因，按原 Ledger、许可、预算和队列运行。新 Task 只包含需要重做或重新检查的步骤；根工作显示当前修订和关联结果。
4. **重新检查后交付。** 修过的内容和依赖它的条件必须重验，未变部分保留有效证据；原入口展示改动摘要和当前结论，迟到反馈始终绑定其针对的产物版本。
5. **总结差异，而非覆盖旧答案。** 将“原先为何遗漏、什么新条件改变选择、哪些成果可复用”交给[条件化经验](knowledge-learning.md#report-experience-boundaries)。取消、超时或预算耗尽时保留明确待办和有效产物，不无限返工。

外部已发生效果不在上述内容复用中自动重放。发信、购买、设备动作等只依据原动作回执和[业务补救协议](#business-remediation-closure)继续；不知道是否发生时先对账。并发纠正和负责人更换必须比较目标修订与任期，旧修订的迟到结果可留为事实，不能覆盖当前结案。

<a id="goal-outcome-closure"></a>
## 从任务执行到目标结案：补齐交接闭环（proposed）

本节补充[主动目标循环](#proactive-goal-cycle)与[恢复分支](#composition-recovery-flow)，不建立第二个 TaskRuntime。任务完成、目标达成、成果可交付和长期收益是不同事实；闭环可以以有依据的完成、部分完成、拒绝、取消或明确等待结束，不要求每项工作都强行成功。

<a id="goal-completion-reconciliation"></a>
### 目标逐项对账，而不是只看最后一个工具成功

受理时将 GoalMandate 的当前完成条件拆成稳定的条目引用，注明必需/可选、验证方式、证据出处、受影响产物/效果和无法自动判断的部分。确定性标准先用检查器；开放要求使用领域量表和必要反馈，不能自动把模型生成的期望答案当真值。缺少关键验收依据时，先说明可验证范围和缺口，不靠完成后临时降低标准结案。

| 事实层 | 说明什么 | 不推出什么 |
|---|---|---|
| 动作回执 | 本次工具/外部操作实际发生了什么 | 发生了操作不等于用户目标实现 |
| Task 执行状态 | 原步骤是否按运行契约结束 | SUCCEEDED 不自动表示业务质量合格 |
| 目标条件对账 | 每项必需条件有无证据、失败或未知；哪些条件因用户修订已失效 | 子任务全绿不抵销根目标遗漏；可选条件不能替代必需条件 |
| 交付状态 | 当前成果在获准入口可访问、说明准确、通知是否送达 | 弹窗出现不等于用户满意；关闭提示不等于批准或拒绝 |
| 后续使用结果 | 使用后是否发现错误、是否真正节省时间、学习是否保持 | 暂无投诉不证明有效；自动评分不冒充用户体验 |

根目标由原 Goal/任务领域对账，负责 Bot 组织证据；评价模块写评价，UI 只读投影。绑定 goal_revision、产物摘要和效果回执；目标修订后只失效受影响条件和待执行步骤，保留已发生事实。无需主人逐条签收普通任务；客观条件满足时可以按既有授权自动完成，对必须依赖主观反馈的维度保持未评。

交付后发现缺陷，追加纠正/返工修订和影响范围，不覆盖原评价、撤销原动作事实或把旧任务伪装成从未成功。后续反馈涉及已结束工作时，由原目标管理决定追加修订或建立关联补救任务；它不会凭一条消息重发已经发送的内容。

<a id="durable-wait-resumption"></a>
### 等待必须有人负责、有可核对的继续条件

原 WAITING 和队列状态保留；补持久等待关联，至少记录所属工作/修订、等待原因、所需事件或决定、负责消费者、下次可检查时间/期限、最近进展证据和资源预留情况。等待条件由实际执行域产生，模型可以提出原因，不能虚构网络已恢复或用户已同意。

| 等待原因 | 有效唤醒依据 | 唤醒后的必要动作 |
|---|---|---|
| 输入/重要决定缺失 | 对应问题的新修订答案，或明确修改原目标 | 核对问题仍有效、任务未取消和答案适用范围；沉默不算回答 |
| 网络、账号或模块暂不可用 | 对应来源的新状态/恢复事件，或策略允许的有界探测 | 重新核对目标、权限、版本和依赖；恢复事件只是候选继续条件 |
| 资源不足 | 原资源调度器发放真实许可 | 不靠收到事件自行创建槽位；旧预留未释放时不能双占 |
| 外部效果 UNKNOWN | 原请求/回执/对账结果的新证据 | 先对账，不能把超时当未执行后重发 |
| 无进展或预算耗尽 | 有实质改变的证据，或新的有效预算/目标修订 | 原花费、失败次数和历史仍有效；新请求名不能重置限制 |

等待登记与暂停交接必须可恢复：源事件水位和注册操作需解决“先恢复、后开始等待”的丢失唤醒竞态。注册时读取当前依赖状态并记录水位，消费时去重；重启核对未结等待与现状，不仅依赖进程内通知。没有订阅支持的来源使用已授权调度的有界核对，不能声称所有来源天然支持推送。

未过期但长期无进展的工作要显示责任、阻塞和退出条件；到期后按原目标策略交付部分结果、停止或请求一个具体决定。不得静默遗忘，也不能为了“永不放弃”无限后台重试。取消和撤权优先于所有迟到唤醒。循环依赖需报出等待链并停止自动扩张，不能让 A 等 B、B 等 A 却各自显示正常。

这里只补设计，不实际创建订阅、定时任务或后台守护进程。实施复用原调度、目标记录和事件消费者，关联格式归[闭环交接记录](contracts.md#closure-handoff-records)。

<a id="business-remediation-closure"></a>
### 部分效果、取消和修复之后怎样收尾

技术故障恢复与业务善后分开。模块恢复后，原工作仍须检查哪些效果已发生、哪些条件未满足、是否还需要向前修复或补偿；Health 关闭 incident 不能代替 Goal 完成对账。

每种有外部效果的能力应声明：怎样查询结果、是否支持幂等/取消、是否存在补偿、补偿所需授权与限制。无补偿能力可如实声明不可逆，再由现行任务策略决定是否允许原动作；不能自动编造“撤销工具”。补偿也是新动作，要有自己的真实回执，并引用原动作；失败或未知时继续保留未决项。

例如某任务已发通知、后续附件生成失败：恢复附件工具不能撤回通知。可在授权范围内生成正确附件、补交或发送更正；是否需要新外发动作由当前策略判断，不能重跑整个任务再发一遍原通知。取消后也需保留已发送事实，不能将取消显示为“从未执行”。

由恢复或新能力触发的继续请求，统一回到原等待/目标准入：当前目标仍需要、许可仍有效、结果已对清、依赖版本可用才继续。原目标已取消/过期时，新能力可以保留，但不得复活原工作。

<a id="module-wait-runtime"></a>
## 模块恢复后接续原任务的运行子集（1.0.0）

[Waiting](../modules/task_resource/waiting.py) 接在现有 TaskRunner，登记 task_waits：task_id、task_revision、source_watermark、state/reason、原 deadline、wake_count 和最近核对时间。它只接手**曾有持久执行申请、实际开始过、因 module_disabled 进入 WAITING 且没有未知动作**的任务。手工创建但未申请执行的工作不会被它偷偷启动。

注册同时重读原任务和当前模块条件，故恢复事件先于等待注册也能接上；重启后从原账本与调度申请对账。等待转 QUEUED 与原调度入队在同一事务中提交，后续仍由原执行锁和动作幂等机制运行。每轮最多登记 32 项有新修订的等待、检查四项，已处理的旧项不永久挤占新项。

重新排队前核对停止状态、当前来源、原绑定的全部剩余能力、范围和许可；真正产生效果时再走原预算与撤权检查。取消优先，期限不重置；UNKNOWN/DISPATCHING 不自动重放；绑定变化、撤权、来源变更等显示 BLOCKED；到期显示 EXPIRED。每个等待任务最多自动唤醒三次，模块反复开关也不能无限循环。

工作状态显示等待、已排队、需核对、到期、取消或被新任务状态替代。这个实现是“模块已经恢复 → 原工作继续”，**不负责自动修改模块代码或打开被关闭的模块**；它不能替代通用自愈诊断、外部副作用补偿、任意问题回答唤醒和多机器人重连。对应实测见[闭环运行证据](delivery-validation.md#completion-loop-evidence)。
