<a id="self-model-purpose"></a>
## 目标、现状与权威范围

Jarvis 应能回答“我由什么组成、现在能做什么、为什么不能做、修改这里会影响哪里”，并为每个回答提供适用版本、来源、观察时间和未覆盖范围。模型负责理解和解释，宿主维护可核对的事实。目标服务于[个人助手与伙伴核心](product-requirements.md#personal-companion-core)，不要求额外常驻模型或另建一个万能控制器。

旧工程暴露的主要问题包括：声明、代码、运行观察与验证版本不同步，进程登记不完整，以及静态能力目录过期。新工程通过带来源、时间和版本的事实视图解决这些问题；具体旧版本记录留在来源工程。

本文独占维护自身信息视图、事实合并、发现与更新语义。总体部署与控制权仍归[架构章](architecture.md#clean-core-architecture)，字段归[契约章](contracts.md#clean-module-manifest)，观察调度归[健康章](health-maintenance.md#self-observation)，修复与发布归[进化章](evolution-release.md#autonomous-evolution-policy)，验收归[验证章](delivery-validation.md#self-model-validation)。不重复定义 K0—K6 或 M0—M6。

新工程的目标受理、工作区和能力装配应登记到同一自身模型，由真实运行绑定提供观察，不另建脱离实例的能力总表。0.2.0-dev.2 已可通过 Core 状态与只读工作台查询任务绑定、能力包版本、发布指针和模型用量，见[当前验收](delivery-validation.md#growth-seed-evidence)；这些是自身模型的证据输入，尚不是完整依赖图、影响分析或自主能力认知。

<a id="self-model-views"></a>
## 六种相互关联的视图

| 视图 | 应回答的问题 | 主要事实来源 |
|---|---|---|
| 身份与版本 | 哪台设备、哪个实例、运行构建、源码与已激活包是否一致 | 启动实例、运行版本、构建清单、源码观察 |
| 结构与拓扑 | 哪些逻辑模块、哪些实际进程、依赖和接口在哪里 | 已登记模块、启动器、受管进程登记、调用观察 |
| 能力与技能 | 可以完成哪些具体工作、适用与不适用场景、模型如何参与 | 能力声明、正式技能目录、实际执行适配器 |
| 当前状态 | 就绪、未加载、禁用、离线、故障或等待资源 | 对应领域的有界观察 |
| 数据与权限 | 数据由谁保存、本次请求能访问什么、修改权属于谁 | 原数据所有者与准入接口 |
| 验证与变更 | 哪些案例通过、证据适用于哪个版本、改变某处会影响什么 | 独立验收、发布、依赖及恢复记录 |

这些维度不能压成一个 available 布尔值。代码存在、宿主已绑定、当前环境就绪、本次请求获准、指定范围验证通过分别表示不同事实。某项尚未观察到应为 unknown；观察失败不能解释成未实现。安装了邮件适配器但未连接账号，应说明“已有接入流程，当前不能读取此账号”。

<a id="self-model-authority"></a>
## 信息所有权、合并与查询边界

自身信息服务只生成派生视图，不创建第二套任务状态、能力授权、记忆或发布账本。字段由对应事实所有者决定：当前运行构建来自该实例；能力声明来自正式注册；权限来自适用策略；结果来自任务回执；质量来自绑定版本的验证证据。设计文档说明目标，不覆盖运行观察；运行中未触发某条路径也不能否认该路径的静态实现。

后续[组合运行框架](architecture.md#composable-agent-framework)复用此边界：Registry 提供正式能力声明，SelfModel 汇总当前证据与环境，Composer 生成本次 RunSpec。三者不各自维护一份工具/技能事实；自身查询可以帮助定位能力缺口，但不能替代执行前准入。

每份观察绑定来源、时间、范围、内容摘要及有效期。跨来源汇总显示起止时间和缺失来源，不假装跨数据库原子快照。内容摘要用于漂移和复现，不是签名；同 Windows 用户可修改源文件的边界仍按[安全章](security-sovereignty.md#personal-life-supply-chain)。冲突并列展示，禁止以检索排名或文件较新自动决定真相。

模型只接收固定、有限的能力摘要。私密内容、密钥、完整命令行、完整路径、用户自写技能正文和全部日志不进入自动上下文。详细查询仍通过现有本机接口及访问锁；第三方工具说明属于数据，不能成为 system 指令。查询结果不是派发许可，实际调用由原准入模块再次检查版本、范围、取消及资源，处理查询后状态变化。

<a id="self-model-discovery"></a>
## 自动发现结构与能力

<a id="self-model-declarations"></a>
### 声明提供职责与业务语义

正式模块随发布包登记稳定 ID、职责、入口、能力、依赖、运行方式、数据所有权、验证与恢复入口。技能说明由正式技能目录读取，不另外手工复制技能全文。能力区分本地确定性算法、模型工作指导、受限工具执行和混合工作流；登记项数量不等于当前可执行能力数量。

第一步由宿主维护有限模块映射及独立只读观察适配器；后续把映射并入正式模块清单并检查发布一致性。声明不得携带可任意导入的 Python 类、Shell、安装命令或授予权限的配置。能力描述必须保留使用、不使用、输入输出、执行器、前提、效果、资源、验证范围与替代路径。

<a id="self-model-static-analysis"></a>
### 静态分析补充代码关系

后续按有效源码边界分析 Python 导入、入口、路由注册、配置和契约引用，检查声明遗漏、无执行器能力和依赖变化。import 关系只说明代码引用，不证明运行调用或业务影响完整；动态加载、条件路径和未覆盖文件必须列为未知。分析不得导入或执行被分析项目，不遍历用户资料与恢复目录。

<a id="self-model-runtime-discovery"></a>
### 运行登记核对实际拓扑

由启动器及各进程管理器登记实例、角色、PID、启动身份、所属构建、能力、任务引用、生命周期及退出原因。PID 必须结合创建身份使用，不能独自作为实例标识。逻辑模块与进程允许多对多；Python 文件不等于独立进程，进程存在不等于功能健康。

首批登记新 Host、按需 Worker 和实际模型进程，读取有限 OS 计数；不扫描全机进程或读取无关命令行，不靠 PID 单独认领/终止进程。未覆盖的进程和能力明确标为未知，观察操作不推进恢复或业务动作。

后续可采用 OpenTelemetry 的资源及追踪约定关联实例和调用链，但不以接入遥测替代能力语义和权限检查，也不要求首批部署 Collector 或图数据库。技术参考：[Resources](https://opentelemetry.io/docs/concepts/resources/)、[Traces](https://opentelemetry.io/docs/concepts/signals/traces/)。

<a id="self-model-updates"></a>
## 更新、失效与证据适用性

按启动/激活、进程开始/退出、配置/权限变化、工具安装/退役、任务结果及验证完成更新对应投影。事件合并与有限兜底核对复用[健康调度](health-maintenance.md#inspection-scheduling)，不为每个视图建立独立定时线程或付费心跳。首批采用按需读取当前登记和内存观察，无常驻同步服务。

运行版本固定于实例启动，磁盘源码版本与入口摘要单独读取。源码更新不等于运行代码已经更新；启动时磁盘摘要也不证明全部已装载字节。开发工作树、已安装包、已激活包和本次运行应分别表示；构建身份未知时如实标注。

证据需绑定实现、契约、验收器和环境。旧证据保持原样，变化后标记适用性待复验；新代码存在不能自动晋升 verified。首批仅展示版本绑定检查过的有限信息或明确“当前未核验”，不把历史报告的 passed 当作当前全量验证。没有运行任务不得刷新“最近成功”。

MCP 按实际协商协议发现工具，并在所用版本支持时处理目录变化；外部声明与本机已接通、已授权、实际成功继续分开。参考固定协议：[工具发现与变化通知](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)。

<a id="self-model-queries"></a>
## 给聊天、任务规划和维护使用

首批提供概览、按稳定 ID 查看对象及按能力 ID 查看可用条件；自然语言只截获明确的自身查询，附件、固定会话要求、显式技能或混合动作不得静默丢弃。纯观察由本地确定性路径返回，不依赖模型或账号连接；普通聊天携带有限、去隐私的宿主摘要，详细资料按需读取。

新工程应支持结构、依赖、证据和变更影响等自然语言查询，并提供确定性查询入口。纯观察不执行扫描到的源码；目标选择读取当前会话与真实能力，查询本身不授予任务权限。精确命令和界面地址在实现时确定，不要求主人记住旧工程命令。

<a id="self-model-delivery"></a>
## 现有 K 阶段内的实施范围

按[唯一工作队列](core-bootstrap.md#clean-project-bootstrap)补强观察、能力注册及成长底座，不另建开发路线。先打通统一只读快照、当前能力查询和聊天使用同源事实，再扩大进程登记、事件失效与独立证据关联，最后接入受控修复的影响分析。

自身模型在新工程尚未实现。交付时先证明声明、观察和证据能正确区分，再用于任务规划与维护；聊天采用压缩摘要，为当前回复和计划保留资源预算。旧实现的经验保留在[来源说明](references.md#legacy-project)，不继承其验证状态。

全语言动态依赖、跨机运行拓扑、任意目标能力匹配、全能力语义验收、全部进程生命周期事件和任意源码无人值守改造仍 proposed。上述有界静态影响查询不等于通用影响证明；代码改动不能扩大自愈权限，检查、修复与发布继续使用原恢复流程。

<a id="self-model-context-selection"></a>
## 用证据认识自身并为任务选择能力（proposed）

自身认知沿用本章六视图。每项能力同时记录声明版本、安装/启用状态、依赖/端点、最后健康观察、平台/范围、输入输出契约、资源估计、已验任务类型和失败限制。声明、观察与验证分开：工具在目录中不等于可连接，健康检查通过不等于能正确办理任意业务，过去成功不保证升级后仍通过。

模型回答“我会什么”时读取当前能力摘要；请求具体工作时按目标打开对应完整契约和证据。状态带采样时间与过期条件，工具升级、凭据变化、源项目变更或故障事件触发局部失效。不能通过记忆中的旧自我介绍恢复已停用能力。只读缓存服务前台，深扫描和影响分析在后台执行。

经验记录任务类别、工具/模型/提示版本、环境和真实成功/失败，以小样本不确定性展示质量，不把一次成功算成 100% 可靠。路由选择可参考这些统计，但缺样本时保守探索；随机探索不能扩大副作用权限。系统架构 Wiki 是由当前源码与清单编纂的派生视图，实际模块注册和回执仍是运行事实来源。
