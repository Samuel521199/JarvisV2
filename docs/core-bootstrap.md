<a id="seed-foundations"></a>
## 种子核心与初始资产

<a id="bootstrap-1"></a>
### 核心从哪里开始

**产品核心是“能自然交流、记住适用信息、下次接续、自主工作，并自主学习和进化”的个人助手。** 以[个人为主、家庭与小团体为辅](product-requirements.md#personal-service-scope)，最终在有效授权内[独立完成任务并交付](product-requirements.md#personal-life-autonomous-outcomes)。相处、行动与成长一起构成类钢铁侠贾维斯的目标；原先仅把代码成长闭环当作起点，遗漏了[伙伴核心判据](product-requirements.md#personal-companion-core)，而把成长完全推到核心之后也不符合主人要求。K2 先贯通文本个人体验与一条受限成长闭环，后续扩大能力范围。

实现依赖仍需先打牢 K0/K1 的契约、持久状态与可恢复控制，但最小可用体验在 K2 同时接通个人会话、基础人格配置、可纠正记忆和少量可靠能力。纯聊天不创建任务；需要执行才进入任务/动作账本。第一段智能来自已有本地模型或获授权远端模型，不需要先训练基础模型，也不要求首版本机小模型已经拥有强编程能力。

建设关系：

**主人确定相处方式与需要 → 我们做出可交流、可记忆、可协助的种子版本 → Jarvis 从真实使用中识别能力缺口 → 已有技能或改进候选解决问题 → 独立验证 → 主人获得更好的协助体验。** 外部 Codex 是其中可选的编码协作者，不持有 Jarvis 的个人身份与关系记忆。

这里“自己进化”指 Jarvis 能发起、组织、验证和采用改进；复杂代码可以由外部开发 Agent 协助完成。谁写代码与谁掌握运行身份、任务、权限、评估记录和发布权是不同问题。

<a id="bootstrap-2"></a>
### 最小核心必须有哪些

以下是最小助手及其成长底座的职责，按 K0—K6 渐进接通，不要求每项成为大型服务或独立 Agent。人格和个人连续性从 K2 文本体验开始；通用成长不是首次聊天的前置条件。

| 核心职责 | 第一版具体做什么 | 为什么现在就需要 |
|---|---|---|
| 个人身份、表达与会话 | 稳定助手标识、主人设置的称呼/语气/关系配置；无需项目的文本交流 | 换模型、切换会话仍是同一个助手，不只有任务执行器 |
| 个人记忆与交流连续性 | 复用事实/归档接口，接通明确记住、纠正、忘记与有界相关召回 | 下次不必重复交代；个人偏好和项目资料各守作用域 |
| 初始知识、规则、技能与系统清单 | 随种子版本预装可信资料、有效规则、基本技能及版本/依赖信息 | 首次启动就知道自己的结构、边界与已有能力 |
| 主人控制与恢复底座 | 当前会话停止、任务取消、明确退出、最后可用版本与恢复 CLI；完整身份与锁存按新工程控制契约实现并验证 | 系统出错或升级失败时主人仍能控制它，由新工程独立测试证明控制有效 |
| 持久任务内核 | 接受任务、状态机、取消、预算预留、动作意图、回执与 UNKNOWN | 不能把进程中断当成任务从未发生 |
| 能力执行器 | 读限定文件、写候选产物、运行受限工具；权限和资源检查 | 模型可以建议行动，但不能直接获得整台电脑 |
| 模型与开发者端口 | 一个本地模型适配、一个可选外部编码适配 | 允许先借助强编码 Agent，再逐步提升本地能力 |
| 候选工作区与构建器 | 源码快照、固定工具链、隔离构建、产物摘要 | “写出代码”必须变成可检查、可运行的包 |
| 独立评估与发布器 | 保护基线、运行验收、灰度、回退、记录结果 | 自己说“改进了”不能自动等于允许上线 |
| 最薄进化循环 | 从失败或明确需求生成改进单，提交候选，读取评估结果 | 让已有核心能够发起下一次成长 |

三库种子与可信等级详见本页对应定义：知识保存带来源的事实，规则经受保护执行器生效，技能通过测试后注册。初期另保存任务记录、主人明确偏好、能力目录、改进记录和产物引用；无需先建立通用知识图谱。防止结构退化、代码/文档污染、误删旧版本与无限自愈的完整要求见[长期健康自愈](health-maintenance.md#system-health)。一个任务 Worker 和一个编码任务足以验证限定成长实验，却不足以证明个人伙伴核心已成立；语音、复杂化身、NPC 和大规模共同体再按需扩展。

所有正式效果仍受[G0 最高宗旨](security-sovereignty.md#product-definition-6) 约束。没有完整语义判断能力的早期版本，只开放能明确限制和验收的任务范围；不能把功能不完整解释为暂时取消监督。

<a id="system-health-1"></a>
### 第一版就要有三类基础库

**最小核心出生时就必须拥有知识库、规则库和技能库，同时具备自己的能力与版本清单。** “最小”指规模有限、来源清楚、可验证，不是只有一个模型加聊天窗口。它们是本页种子闭环的基础数据，不必各自部署大型服务。

| 基础资产 | 回答什么 | 第一版必须预装 | 初期实现 |
|---|---|---|---|
| 知识库 | 我知道什么，证据在哪里？ | 项目定义、系统结构、接口、安装与恢复说明、模型/设备能力、主人明确偏好、已验证操作经验 | 原始资料 + SQLite 元数据/全文检索；向量检索按需 |
| 规则库 | 我可以做什么，必须遵守什么？ | G0、主人身份与权限、文件/网络/设备范围、预算、停机、发布和数据外发规则 | 受保护版本化配置与确定性执行；不能只靠检索提示词 |
| 技能库 | 我如何可靠地完成一种工作？ | 查询状态、限定目录读取、产物生成、候选构建、验证、报告等基本技能 | 不可变技能清单 + 执行器 + 测试与依赖 |
| 系统清单 | 我现在由什么组成？ | 模块/接口版本、依赖关系、数据所有者、运行位置、权限、工具链、健康探针、当前/回退发布版本 | 发布清单与模块注册表；由实际安装/运行状态核对 |

模型训练中已有知识不是本项目的事实库；对话摘要不是规则；一段建议或代码也不是已可用技能。外部 Codex 可以协助编写候选内容，但没有把候选规则自动提升为根规则的权限。

主人身份、权限引用等敏感资产只保留必要元数据或密钥库引用；不因为叫“系统知识库”就把全部凭据集中进可检索文本。

<a id="system-health-2"></a>
### 种子资产与可信等级

建议随首个版本发布 SeedBundle，绑定代码/配置/文档/技能/测试摘要和版本：

- **事实与系统说明：**当前架构图、模块职责、接口契约、数据格式、安装与恢复手册、支持矩阵。
- **主人明确设置：**名称、可用设备、目标、偏好、预算、禁区、授权范围和适用期限。
- **基本技能：**查看能力和任务状态、读取获准样例目录、写入产物区、提交改进单、运行候选构建、查询评估报告。
- **基本维护：**只读健康检查、已验证组件重启/回退配方；停止与解锁属于受保护底座，不伪装成可随意重写的普通技能。
- **基线与已知限制：**初始真实任务、恢复测试、不能做什么、失败案例、待确认事项。

知识记录至少有 kind、source、version、evidence_ref、validity、scope、owner 和 privacy。区分“原始证据、已验证事实、主人偏好、待验证假设、外部未可信资料、模拟内容、已撤回记录”。互联网学习先进入待验证区；不能覆盖主人规则，也不能把 NPC 情节当成现实经验。

规则通过受保护加载路径生效，知识检索仅用于解释。知识库损坏或检索不到 G0 时，执行器仍必须执行已经验证加载的规则；规则状态无法验证则拒绝业务。技能使用前匹配当前契约、运行依赖和授权，技能描述中自称“可信”没有准入效力。

<a id="bootstrap-4"></a>
### 两个层次：哪些能长大，哪些不能自行放开

**受保护的根控制层：**主人身份、停止状态、权限执行、发布信任根、基线评估规则和恢复入口。Jarvis 可以提出这些实现的改进方案，但不能在自身业务权限下修改、批准并激活；由主人维护入口处理。G0 宗旨不属于可修改对象。

**可演进的工作层：**技能、工具、检索策略、人格配置、编码适配器、规划器、任务策略、模型组合，以及后期获准的运行模块。这些使用版本化包替换，不直接覆盖正在执行的生产目录。

评估器可以扩展测试；候选不能删除旧测试、降低阈值或查看受保护保留集。新评估规则也要独立审查，并保留历史结果的口径。否则系统很容易通过修改自己的评分标准获得“越来越高分”。

“底座小”是控制复杂度的目标，不是声称 OS、执行网关、授权代码和发布器不属于信任基础。

<a id="bootstrap-5"></a>
## 开发顺序与每一步的出口

| 顺序 | 我们与 Codex 先实现什么 | Jarvis 能自主做什么 | 进入下一步的证据 |
|---|---|---|---|
| K0：规范和夹具 | 初始知识/规则/技能包与系统清单；Task/Action/Capability/Artifact/Module/BuildProfile 六个契约；G0 执行边界；测试数据 | 暂无生产自主行为 | 相同输入、预期产物、失败条件已明确 |
| K1：确定性外壳 | 会话/任务取消、待命、故障恢复、SQLite 账本、受限文件能力、命令行入口 | 执行预定义本地任务、报告真实状态 | 崩溃恢复、重复请求、取消、未知结果和越权拒绝通过 |
| K2：最小个人助手与成长核心 | 个人文本会话、基础人格、可纠正记忆与接续；透明精灵、按需卡片和补充工作台接入同一 Host；本地模型端口、三库检索、有限工具循环；能力缺口与改进单接入既有受限候选/验证/发布通路 | 无项目或常开工作台也能交流、查状态、回答问题与接收成果；按需行动、断网使用已有能力；在约定范围完成一条需求驱动的生成、验证、启用与回退闭环 | [V-PAL](delivery-validation.md#personal-companion-validation)及[精灵细化场景](delivery-validation.md#desktop-presence-validation)、[K2 最小成长](core-bootstrap.md#clean-project-bootstrap)与既有 V-K2 通过；保持身份/记忆与既有能力，坏候选被拒 |
| K3：开发协作 | 候选工作区、一个离线工具链、Codex 适配器、构建任务 | 为不会做的事提交改进单，调用编码助手产出候选 | 无生产密钥泄露、失败限额、真实构建产物 |
| K4：可扩展自主成长闭环 | 将 K2 受限通路和 K3 开发协作推广为可复用外部评估、包目录、灰度/回退与改进账本 | 为不同真实需求自动生成、验证并启用低风险新工具，超出首个预定义配方 | 通过保留测试；坏版本被拒；生产不被原地改写；新增能力有真实调用与收益证据 |
| K5：首次真正修改自身模块 | 一个可替换的检索或规划模块、兼容与回退协议 | 提出并验证自己的模块改进 | 同一任务集净收益成立、旧能力未退化、可以回退 |
| K6：逐能力扩展 | 实时语音、复杂形态、多语言、第二节点、设备与 Agent 等按需接入；扩大个人、家庭和小团体的可靠办事范围 | 在更多场景和设备延续同一个助手，按需求组织能力，自主完成已授权任务并交付 | 各能力单独满足设计文档集验收；覆盖个人／成员／共享边界及独立完成任务的证据，扩展不破坏个人核心体验 |

K1 可以暂时用假模型/规则输入验证可靠性，但它还不能叫完整智能 Jarvis；K2 形成最小个人助手与受限成长核心，基础人格、交流连续性和自主成长都不能全部推迟到后期。K3/K4 扩大开发与发布通路，K5 才包含替换自己运行模块的证据，不能把 K2 的单工具闭环等同于任意自身重写。

自主工作从 K2 的有限任务闭环开始，经 K3/K4 的能力补齐与发布、K5 的自身改进持续增强，再由 K6 扩大场景；不等全部能力齐备才开始独立办事。家庭与小团体场景沿用相同任务链，先验证个人／成员／共享边界，再开放对应多人效果。每阶段交付都应声明哪些任务已能独立完成，哪些仍需必要人工步骤，证据归[增量验收](delivery-validation.md#personal-life-acceptance)。

这张表是唯一实施顺序；[M0—M6](delivery-validation.md#delivery-gates) 仅定义能力验收门：可以在语音、界面和共同体尚不完整时，先用纯文本和本地文件任务验证 K4。不能等待整个目标架构完工才开始进化，也不能在缺少评估与恢复时就开放自修改。

桌面入口在既有阶段内细化并遵守[统一系统准则](architecture.md#unified-system-principle)：K0 冻结[共享呈现契约](contracts.md#desktop-presence-contract)及正反例；K1 接真实来源、恢复校准和单项取消；K2 复用既有业务与设置服务，验证原生透明／命中、托盘找回及精灵与工作台间的输入、问题、配置和原任务交付接续。基础 Logo 精灵属于 K2 日常工作形式，不推迟到 K6 的复杂形态；完整可选语音及更多平台／设备执行按 K6 分项扩展，继续复用该基础。上述为待交付范围，不把已有网页或设计图计作桌面壳完成；阶段内部缺口与依赖按实际证据推进。

编码适配、凭据隔离和改进事务详见 [外部编码协作](toolchains.md#autonomous-development-providers)；净收益评估详见 [证据标准](delivery-validation.md#bootstrap-8)。

### 每个工作包具体交付什么，完成后怎样签收

| 原阶段／工作包 | 具体改动与依赖 | 完成证据／启用边界 |
|---|---|---|
| K0 · 固定不变量与样本 | 在[接入契约](contracts.md#modernization-integration-contracts)明确写入者、版本和失败返回；冻结原行为快照、目标量表及反例。为所有权/评价/经历建立新增 schema，不改变 task.v1 的严格校验 | 通过契约正反例、依赖规则和静态设计审查；没有运行成绩。冻结 V-TRI/V-TLC/V-KLG 所需夹具 |
| K1 · 结果事件和影子评价 | 从 Ledger 终态事件读取 task/goal/产物摘要；新增评价持久化、幂等消费和失效关联。仅写新关联记录，不让评价改 Task 状态 | 同一事件重放不重复消费；评价失败不重复执行。先 observe-only，无自动拒收/发布/学习效果 |
| K1/K2 · 三职能适配与默认负责人 | 用薄端口包装现有规划、交互和观察；新工作关联默认 Jarvis Bot。先展示责任，后补派发任期与 CAS 转交；所有效果路径通过任期测试才允许接管 | 同一身份、目标修订和 task/action 延续；旧任期不能派发；聊天不因背景评价等待 |
| K2 · 单领域结果检查和返工 | 给本地纯文本交付定义客观格式检查＋必要内容量表；记录修改前后产物。补受影响步骤返工，已确认外部动作不重放 | 真成功、格式通过但语义不合格、检查器不可用三个场景均有准确状态；原成果保留 |
| K2 · 条件化经验的最小闭环 | 从真实纠正形成一个带来源/条件/反例的模式；在现有检索中增加适用检查、选择记录和撤回传播 | 正确复用、不适用时拒用、错误时撤回三例都通过；先一个领域，不要求全库自动归纳完成 |
| K2 · 必要时再启用多 Bot 委派 | 复用原子任务与调度；保存一张 DAG、子额度预留和输入/产物引用；根预算计入执行、评价与归纳 | 单负责人、父取消、迟到回执、冲突资源、额度耗尽全部验证；简单任务不开额外 Agent |
| K3 · 自愈接原研发与发布 | 接 incident 去重与修复租约；已验证恢复配方优先，无配方才生成恢复原契约的候选；原故障复测独立于常规回归 | 故障定位→恢复→复测→观察闭环；环境故障不触发改代码；与进化竞争时仅一个发布者 |
| K4 · 自动采用与经验反馈 | 固定 trial 的基线、允许改动面、预算和保留集；加现有授权策略的自动准入。关联采用/拒绝/回退到知识收益记录 | 在既有授权内，一项合格低风险候选自动采用，一项坏候选被拒或恢复；均回到原目标；仍需人工的重要取舍集中呈现 |
| K5 · 模块及核心可替换 | 为一个明确模块做第二实现/兼容替身；完成排空、状态交接、版本栅栏与兼容恢复，逐模块扩展到核心 | 原身份、承诺、纠正与在途工作保持；观察成长模块停用不阻塞无关服务；不是一次替换全部核心 |
| K6 · 远端与机器人扩展 | 将已验证端口接设备适配器，先模拟分区、接管和撤权；物理动作另行取得真实证据 | 不改变三职能和任务权威；远端模型/节点无权自立主身份或抢同一动作 |

### 第一条具体贯通案例：一项文本工作、一次纠正、一次受控修复

选择**隔离测试目录中的文本整理/格式转换**作为首个贯通领域，使用合成资料和无外部副作用工具。此案例是待实施验收脚本，不会因写入文档而在当前电脑执行。

| 步骤 | 原系统上怎样接线 | 留下什么、怎样证明保持设计 |
|---|---|---|
| 1. 受理“整理这份材料，结论放前面” | assistant/Goal 建原目标；Direction 提议完成标准，宿主固定目标修订和授权；默认负责人挂到该工作 | 原会话/goal/身份不变；所需标准来自用户，不从历史偏好覆盖当前要求 |
| 2. 按需取经验并计划 | Context 返回有权限且条件适用的方法；Engagement 通过负责人请求原 TaskRuntime 执行 | 保存采用/拒用经验引用；只生成一份实际任务和动作链 |
| 3. 产物完成后检查 | 原工具回执保存成功事实；Reflection 触发独立 outcome 检查并给缺项 | Task 技术执行完成和目标质量是否合格分别展示；检查器无权伪造工具结果 |
| 4. 指出“遗漏一个重要限制” | 将纠正绑定目标/产物修订，仅返工受影响内容，再检查 | 新产物和评价引用新修订；已完成效果不以新 ID 盲目重放；未受影响成果继续复用 |
| 5. 形成经验并试近似反例 | 记录“限制条件必须随结论保留”的条件化方法；下一任务另设“只按原文顺序摘录”的要求 | 前者合理复用；后者按新要求拒绝旧版式，证明会用也会不用 |
| 6. 注入已发布纯文本工具错误 | 隔离测试包在特定输入失败；Health 合并 incident，先恢复可用包，必要时 Development 修复原契约 | 实际观察故障→恢复→原故障复测；候选不改验收答案，修复不新增业务目标 |
| 7. 再提出真正的新能力 | 另建关联 trial，经原候选、保留集和发布通路采用或拒绝 | 自愈与进化分开、原目标回接、预算总账可核对；发布失败不污染经验默认视图 |

首个交付应先完成第 1—5 步及对应关闭/恢复用例，再在 K3/K4 接第 6—7 步；这是一条逐步贯通的证据链，不要求首个改动就完成全自动自进化。

<a id="modernization-migration-switch"></a>
### 怎样接入、启用和退出，避免破坏旧任务与现有机制

1. **先冻结基线。** 记录实际源码/构建摘要、数据库 schema、有效包、任务/模型/量表版本和受影响用例。只在隔离测试数据上演练迁移，不能拿业务库试错。
2. **先扩展关联记录。** 按原适配器事务新增表/索引，不移动旧任务和事实。旧任务标记 legacy；缺少过去评分/负责人证据就保留未知，不倒造历史。新 schema 版本在实施时依据最新迁移编号确定，不在文档预占或硬写下一号。
3. **再旁路观察。** 新消费者仅读取事件、追加评价/候选；原调度、授权、发布不受评分控制。评价结果与人工/原检查对照后，才考虑作为决策输入。旁路不能重复执行工具。
4. **按能力逐项启用。** 所有权强制、委派、评分、经验读取、经验写入、自动归纳、自动修复、自动采用分别可控；开关是有效策略的投影，不能绕过权限。关闭经验不关闭原事实纠正，关闭进化不关闭已获准自愈，关闭评分不删除成绩。
5. **接入在途工作必须有检查点。** 旧任务可原协议完成；不得一半动作执行后补一个虚假任期。新任务启用任期后，所有派发路径必须核对；未覆盖的专用插件/连接器明确不在首批范围。接管先阻断旧写入、核对 UNKNOWN，再转交。
6. **先限制新入口，再排空退出。** 关闭新任务采用，保留在途版本、消费者水位和审计；可停可选学习消费者，但不能直接关闭新任务的任期栅栏。恢复旧宿主前必须证明它能理解当前任务/schema；否则留兼容适配器或暂停受影响工作，不回灌旧整库。

新配置的产品默认值应依据该能力验收与既有授权确定；`observe-only` 只是首次实施的验证状态，不是最终产品永远需要人工批准的机制。自动采用应由当前策略验证“允许域、影响、预算、包摘要、评价与恢复证据”，重要或未知取舍才交给主人。精灵和工作台共用这一策略和状态，不各做一个开关系统。

### 启动与完成第一项任务

在工程根目录运行，使用现有 Python 3.13 标准库即可；本版没有 pip 运行依赖。默认数据位于 `user-data/`，由首次 `init` 创建，未复制旧数据库。不同开发实例可在命令名称之前加 `--data-root user-data/another-instance`；不要让不可信人员操作这个本机管理 CLI。

```powershell
python -I -B apps/cli/main.py init
python -I -B apps/cli/main.py submit contracts/examples/text-report.task.json
python -I -B apps/cli/main.py run
python -I -B apps/cli/main.py tasks
python -I -B apps/cli/main.py status
```

`run` 每次最多处理 100 个已就绪任务后退出，不常驻后台。示例首次提交执行两步，并把报告放到 `user-data/artifacts/<task_id>/<action_id>/report.json`；`task <task_id>` 返回真实回执及相对路径。再次提交相同 request_id 与内容只返回原任务，换内容必须使用新 request_id。任务期限从受理时计时，排队与重启不重置；cost_units 是本地动作额度（每次尝试 1），不是实际模型 token 或货币计费。

初次 `init` 创建的 `local-default` 仅允许 `owner.local / personal` 下的文本分析与内部报告写入，总额度 1000 次尝试、有效期一年；重新初始化不会刷新额度或复活撤权。其他主体／范围必须由本机操作者通过 `grant-add <JSON文件>` 明确建立授权；`grant-revoke <grant_id>` 阻止后续动作。当前身份字段是本机可信操作者指定的上下文，尚无面向其他真实用户的登录认证。

<a id="core-seed-recovery"></a>
### 停止、接续与模块切换

```powershell
python -I -B apps/cli/main.py cancel <task_id>
python -I -B apps/cli/main.py stop
python -I -B apps/cli/main.py status
python -I -B apps/cli/main.py resume --token <status中的stop_token>
python -I -B apps/cli/main.py reconcile <task_id>
python -I -B apps/cli/main.py resume-task <task_id>
python -I -B apps/cli/main.py run
```

上述是按实际状态使用的独立命令，并非每次恢复都执行全部步骤。取消不会自动复活；等待的普通任务可在条件满足后接续。UNKNOWN 必须先核对，文件缺失、部分写入或内容不符时仍等待，不能据此盲目重写。`stop --latch` 用于明确锁存，普通 resume 无法解除；本版尚未实现受保护的锁存解除流程，不应把锁存当普通暂停试用。

```powershell
python -I -B apps/cli/main.py modules
python -I -B apps/cli/main.py module probe text-analyzer
python -I -B apps/cli/main.py module activate text-analyzer --implementation text.scan.v1 --revision <当前revision>
python -I -B apps/cli/main.py module rollback text-analyzer --revision <新的revision>
```

模块管理从 `modules` 读取当前 revision 后执行；旧修订拒绝。任务固定已受理的实现版本，普通停用仍立即阻止该模块的新动作。当前替换仅覆盖可信、无状态的两个内置文本实现；不是任意插件下载、核心数据库迁移或进程热替换。

### 原生入口与开发检查

原生控制程序只依赖 Rust 标准库，Cargo.lock 无第三方 crate。当前机器已构建 release 可执行文件；其他机器开发构建使用现有兼容 Rust 工具链，实际测试版本见[运行锁定记录](../packaging/runtime-lock.json)。

```powershell
cargo build --release --offline --locked --manifest-path control/bootstrap/Cargo.toml
.\control\bootstrap\target\release\jarvis-control.exe status --data-root .\user-data
.\control\bootstrap\target\release\jarvis-control.exe stop --data-root .\user-data
```

原生 `run --data-root <目录> --project-root <工程> --python <解释器完整路径>` 可启动同一任务 Host，停止标记出现后结束其直接子进程；不自动重新启动。它不依赖 Python 框架或云端来执行 stop/status，但目前只监督直接子进程，尚非任意进程树或恶意同账户程序的安全隔离。

开发验证命令：


### 准备环境、授权和启动

Windows + CPython 3.13，使用已有本机解释器，不安装 pip 包、容器或服务器中间件。Worker 准备命令把该解释器的标准运行文件放入本工程数据目录并登记摘要；不会引用旧工程运行包或修改原 Python 安装 ACL。

```powershell
python -I -B apps/cli/main.py init
python -I -B apps/cli/main.py worker-prepare
python -I -B apps/cli/main.py worker-status
python -I -B apps/cli/main.py grant-add <本机维护许可JSON>

python -I -B apps/cli/main.py development-runs

```

维护许可沿用 `jarvis.grant.v1`，必须覆盖同一个 principal/scope 下的 `model.generate.v1`、`development.build.v1`、`release.activate.v1`、目标 `plugin.*.v1` 和 `artifact.write.v1`，并有有效期限、共享额度。原 `local-default` 不扩大权限。本次真实验收已在本机创建仅覆盖清单工具的短期 `development-demo`；这不是新安装的默认授权。许可过期或撤销后不因重启、换模型、回滚代码而复活。

dev.2 的种子模型线路在 `config/model-routes.json`（dev.3 导入后以[本地设置](models-offline.md#portable-model-settings)为准）：配置模型 ID、明确 HTTPS 端点、环境变量名、输出 token 上限、超时以及主备顺序。密钥只从当前进程环境读取，不写入该 JSON、不复制旧工程配置；环境凭据可用不等于调用成功。默认离线，`--network` 只允许本次研发使用已配置线路，没有开启常驻自主联网服务。当前实现为兼容 Chat Completions 的 JSON 通道；其他提供者必须验证其接口，不能只换名称就声称兼容。

示例规格已固定输出契约、公开样例、宿主独立用例、交付输入和预算。模型看到目标、方法与公开样例，**不看到独立用例的期望值、控制库、身份库或凭据**。重复相同 request_id 与内容返回原研发编号；修改请求必须换编号。生成的程序只能使用当前纯文本配方，通过后先灰度，再用它完成同一个目标并保存交付。

<a id="growth-seed-control"></a>
### 中断、费用未知与版本恢复

```powershell
python -I -B apps/cli/main.py dev-cancel <dev编号>
python -I -B apps/cli/main.py dev-resume <dev编号> --network
python -I -B apps/cli/main.py releases
python -I -B apps/cli/main.py release probe <pkg编号>
python -I -B apps/cli/main.py release rollback <plugin能力编号> --revision <当前修订>
python -I -B apps/cli/main.py release disable <plugin能力编号> --revision <当前修订>
python -I -B apps/cli/main.py release activate <pkg编号> --revision <当前修订>
python -I -B apps/cli/main.py release retire <pkg编号>
```

模型超时、网络中断或宿主死亡后，远端可能已计费；标记 UNKNOWN，不自动换供应商再发。确实决定再试时，由本机操作者运行 `dev-resume <编号> --network --retry-unknown`，保留已用调用次数和未知回执，不清零额度。明确 HTTP 拒绝或已知无效结果才在原预算内尝试已配置备选。

Worker 与包操作遵守停止/取消检查；任务、授权、研发状态和调用预算持久保存。模型等待使用独立研发锁，不占据普通任务执行锁；检查、发布和实际动作仍在有界执行段内串行。当前只支持一个研发流程占用研发通道，不是无限并发 Agent。

插件计算成功后由宿主先保存绑定原 action_id 的结果回执，再确认任务。崩溃后有回执可用原 `reconcile → resume-task` 接续；缺少回执则仍 UNKNOWN，不能把重新计算冒充已收到原结果。恢复研发流程不会自动清除未知任务动作或取消状态。

代码包恢复的完整规则归[当前发布实现](evolution-release.md#growth-release-runtime)。dev.2 工作台仅提供只读观察；dev.3 增加下节的文字对话与模型设置。研发与维护操作仍通过本机 CLI，尚未接通自然聊天自动派发研发或桌面 Codex 通道。

## 从能力缺口回到原目标完成交付（dev.9）

1. 在“目标与计划”描述任务。现有能力不足时，原目标会显示缺口；点 **为这个目标设计能力**。
2. Jarvis 拟订可复用行为、公开示例和隔离验收建议。点“查看 / 修改规格与用例”核对；目标涉及尚未接入的邮箱、桌面等能力时，先处理缺口，不把纯文本结果当作全部完成。
3. 点 **核对规格并开始研发**，设置规划/编码模型、档位、备选与预算。确认已核对期望值后，开始受限编程；不会让你手动填写能力 ID 或复制研发 JSON。

6. 服务中断时，可在此目标接续规格设计、原研发或“回到原目标继续规划”；取消目标会同时撤销关联研发权限。失败不会偷偷生成无数新研发任务。

| 原会话、目标详情与工作状态显示同一份评价 | 共用 [Outcomes](../modules/evaluation/outcomes.py)；执行状态继续来自 Ledger，综合质量证据不足时显示待验证 |
| 历史终态事件和中断后的评价补齐 | 已有 TaskRunner 循环消费原 events；同事务保存评价或失败记录与消费水位，不建立新的定时服务 |
| 评价失败时原任务仍可交付 | 记录可见失败，最多三次有界尝试；冷却后由已有消费者续评，手动“重新核对结果”只重试评价，不执行工具 |
| 文件、目标或引用依据发生变化 | 再次打开原任务或刷新近期状态时重新核对，追加新评价与 supersedes；历史证据不改写，也不宣称文件被持续监控 |

使用入口是**设置 → 技能与执行 → 工作状态**，也可在聊天的目标卡片和目标详情展开“结果核对”。“查看评价依据”显示分项及引用；产生新版本后可“查看评价变化”。共享的“结果核对开关”持久保存，关闭后保留原账本、文件、历史评价及所有原有控制。重新启用仅补评，不补做业务动作。

这是三位一体中 Reflection 的一个确定性实现：Direction 的目标/计划解释、Engagement 的任务执行和 Continuity 的身份仍走原通路。没有赋予评价模块取消任务、修改授权、发布代码或自动提升知识的端口。现有发布检查继续生效；该可选观察器不是新的强制发布准入器，不能拿它的 PARTIAL 结果当作放行依据。

具体运行契约、限额及失败语义唯一维护在[结果评价运行子集](contracts.md#outcome-observer-contract)。源码版本与功能/性能/界面结果唯一维护在[本次验收](delivery-validation.md#outcome-observer-evidence)。完整 GoalMandate、任务负责人任期、条件经验与自愈回接继续按[原实施次序](#modernization-work-packages)推进；本次没有改变 K0—K6 顺序。

## 本地文本任务的验收、反馈、方法复用与恢复闭环（1.0.0）

**限定领域已形成可执行链路：事先约定条件 → 原任务执行 → 当前证据核对 → 按约定结案 → 迟到纠正 → 暂停相关方法及采用 → 新证据复核 → 新任务再次采用。** 这次增加了实际入口、持久记录和失败出口，不把整个助手或多机器人能力标成完成。范围与证据见[本次验收](delivery-validation.md#completion-loop-evidence)。

| 入口／触发 | 当前实际行为 |
|---|---|
| 本地“文本统计 → 保存报告”任务 | 自动登记配方级检查；成功后显示约定检查通过率。配方检查不等于自动理解任意自然语言目标 |
| 目标计划的“约定验收条件并执行” | 在批准原任务的同一事务内保存文本等于／包含等条件；可声明只覆盖配方，或足以验收本次完整目标；开始执行后不能降门槛 |
| 原会话、目标详情、工作状态 | 共用结案状态，允许记录认可、指出需要修改、撤回纠正和查看反馈历史；无需每次交付都填反馈才能运行 |
| “用这个方法处理新文本” | 首版仅支持个人文本统计配方；记录实际采用，创建原 Ledger 任务并持久排队，原 TaskRunner 自动执行，新输入重新计算 |
| 后续发现反例或依据失效 | 相关方法暂停；尚未执行的采用在动作边界停止，已执行任务保留真实回执、评价失效；不把事实改成未发生 |
| “复核方法的新证据” | 方法暂停或到期后，核对未决反例、当前版本和暂停／到期后的不同输入证据，通过后产生新方法修订；旧采用记录不会自动获得新资格 |
| 已申请执行的任务因模块停用而等待 | 模块恢复后通过[原调度恢复接续](tasks-agents.md#module-wait-runtime)继续；取消、期限、未知效果和当前许可仍优先 |

保留三位一体的分工：目标条件归原目标/任务域；执行继续使用 Ledger、Gateway、许可和执行锁；结果核对与经验只保存证据及有条件的方法。没有新建独立 Bot 账本，也没有给评价器发布代码或外发信息的权限。

需要补复核证据时，在“设置 → 技能与执行 → 工作状态 → 任务创建与历史账本”中用“新建后台任务”建立两个不同输入的文本统计任务，再“执行已就绪任务”。它们要在方法暂停／到期之后创建，并保持同一工具绑定；处理未决反馈后回到原来源点击“复核方法的新证据”。任务目标改变、失败检查未解决或证据过旧时仍不会放行。

完整使用与约束分属[运行契约](contracts.md#completion-loop-contract)、[方法及反例治理](knowledge-learning.md#conditional-method-runtime)和[恢复接续](tasks-agents.md#module-wait-runtime)。首版新增记录在原数据库中增量创建，旧任务和用户事实不重建。新增逻辑已通过测试；本轮没有重启或部署正在运行的生产服务。

## 工作交接 1.1.0：可靠执行意图与明确要求覆盖

**2026-10-26，implemented；限定验证见[本轮证据](delivery-validation.md#workflow-handoff-evidence)。** 落实上一轮[首个实现包](#modernization-next-implementation)中的两个切面，复用原 Goal、Ledger、授权、Scheduling 和 Completion。通用语义评价、负责人任期、局部返工和多 Bot 不在本版实现范围。

| 入口／行为 | 当前实现 | 保持的边界 |
|---|---|---|
| 计划中的“确认此计划并执行”或“约定验收条件并执行” | 一个 `approve_and_run` 请求在同一事务保存目标受理、任务、许可、验收条件及执行意图；原调度自动消费 | 不需第二次 UI 启动调用；原 `approve` 仍只批准。旧已批准任务继续使用原开始入口 |
| 就绪队列已满 | 执行意图留在原 dispatch 表，标明等待容量；原 Runner 有空间时再入队 | 不突破原就绪队列上限；新受理的执行意图总量达到 100 时整笔受理失败，计划仍待核对 |
| 请求已提交但响应丢失 | 同目标、原修订重试返回原 Task/意图；完成后也不重放 | 已取消、变版或改变验收条件仍拒绝；直接批准的旧请求不能在重试时偷偷改成执行 |
| 检查通过而要求未列全或验证器不适用 | 保留检查通过率，结案为 SATISFIED，覆盖显示未证实／待核对 | 不再仅凭 `coverage=complete` 给出 VERIFIED；保留原动作成功事实 |
| 明确列出的原样文本／统计要求都有对应支持的证据 | 在全部原结果检查合格且声明完整范围时为 VERIFIED | 只证明明确列出的受支持要求；不证明自然语言目标没有遗漏，`semantic_goal_verified` 仍为 false |
| 业务含义、事实、预算、交期等要求 | 可逐项列出并冻结，但本版显示待核对 | 不用关键词包含或统计检查冒充业务验证；下一步仍需领域验证器及真实任务校准 |
| 升级后重新核对、迟到反馈 | 旧结论进入核对历史；新结论、反馈和原执行记录分开 | 旧“认可”绑定旧证据，不自动认可新版评价；拒绝反馈仍继续阻止无效来源 |

工作台新增必需要求、要求类型与历次核对入口，精灵及其他入口仍通过同一任务投影读取结果。普通目标记忆候选改为“执行观察”，注明覆盖是否证实；旧候选接收时依据来源摘要重新核对。这里没有自动把业务结论写入知识库，也未扩大报告方法复用范围。

存储的 `completion_schema` 从 1 增量迁至 2，保留旧 Task、Action、验收规则和反馈；新增 `completion_history`。旧运行代码不理解新版评价 schema，应使用兼容版本恢复，不手工将版本号改回 1。迁移和探针仅在临时数据上验证，当前生产服务未重启、未部署；实际生产加载与原数据迁移须另行核对。

## 工作接续 1.2.0：默认负责人、版本关联与局部返工

**结论：本地纯文本工作可以保留已完成前段、建立关联的新版本，再沿原任务系统执行。** 这是 K1/K2 的限定实现，使用原身份、Task、许可、Scheduling、Completion 和回执；没有另建执行器，也没有启用多 Bot 接管。[实测与限制](delivery-validation.md#workflow-rework-evidence) · [实际接口](contracts.md#workflow-rework-contract)。生产未部署。

| 改进 | 实际行为 | 原设计如何保留 |
|---|---|---|
| 默认负责人 | 新受理目标登记当前 assistant_id 下的 default Bot；旧任务首次接续时明确记为补登记 | 不创建第二个助手身份；负责人只是责任投影，不能颁发权限，不含租约/接管 |
| 一件工作有多个版本 | 原 Goal/Task 不变，新 Goal 关联原根工作、父版本、原因和起始返工步骤；旧入口可打开当前版 | 单一当前版本、修订比较与事务提交；重复请求不产生分叉 |
| 复用已完成部分 | 支持成功的本地纯文本串行计划；显式选最早重做步，固定此前最后输出，后续按原链重新执行 | 旧动作、交付文件和原标准不覆盖；MCP、未知效果和运行中任务不自动重放 |
| 区分补充与纠错 | 新增要求保留原评价；纠错原子追加原任务 reject 反馈，子版本自己约定验收 | 负反馈进入原 Completion/知识来源检查，不把错误自动升级成成功经验 |
| 依据变化与恢复 | 草稿、受理和每次效果检查核对来源/背景/工具；迟到反馈会阻止继续。未受理草稿可说明理由后重新核对依据 | 不删除旧反馈；已受理任务不可改写；撤回资料或损坏回执不能靠认可复活 |
| 整件工作停止 | 原入口停止当前版、撤销其许可，保留已经完成的版本；重试旧请求不能复活 | 原 cancel/UNKNOWN 和执行检查继续生效；停止不承诺撤销已发生效果 |

操作路径：**完成原纯文本计划 → 关联返工 / 追加要求 → 选择变更类型及最早重做步骤 → 调整新计划 → 重新约定验收并执行 → 查看版本结果与累计已用成本。** 文字要求只进入新目标与审阅说明，本版不会自动把新要求编成工具逻辑，自然对话也尚未自动选择当前返工版本和起始步骤；选步也不是自动语义影响分析。复用前段时编辑器将实际输入设为只读；从第一步重做时可以改输入。每件工作最多 3 次接续，所有新执行仍经过原受理与有界授权。

闭环终态包括完成、需要改进、明确等待和停止。迟到反馈后，尚未受理的当前草稿可用“重新核对已变化的复用依据”保存核对理由并提升修订；重新受理必须使用新修订。已经受理的版本、源文件被改写/撤回、祖先依据失效等情形，保留阻塞原因，停止该工作后制定新的受审计划；当前还没有自动重建这类任务或重选有效祖先的机制。

新增存储为 [work_schema](../adapters/storage/work_schema.py) 和 [Works](../modules/task_resource/works.py)，跨领域接线集中于 [work_revisions](../host/work_revisions.py)。三位一体保持原分工：决策/交接由 Host 装配，执行事实和授权由原机制保存，评价/学习读取事实并能反证；新责任表没有执行能力。1.2.0 时根预算仅汇总实际成本并限制修订次数；后续 [1.3.0](#workflow-budget-runtime)已补工具动作共享额度，完整费用范围仍未实现。因此任期接管、多 Bot、常设自动授权及自主修码发布仍不能据此启用。

恢复旧代码前必须先停止新受理并处理关联在途任务；旧代码未必理解新来源检查，不能把“增量表未删除旧记录”当作运行降级安全证明。迁移没有回填旧负责人，也没有修改身份、原任务、原许可和旧回执。

## 工作额度 1.3.0：跨版本预留、计费与明确止损

**2026-10-27，implemented；限定验证见[本轮验收](delivery-validation.md#workflow-budget-evidence)。结论：同一件工作的关联版本开始共享工具执行额度，原任务账本继续保存唯一消费事实。** 额度不足会在受理事务内拒绝新执行，不能靠增加一个返工版本绕过；这没有扩大原任务许可，也未启用多 Bot 接管。[实际契约](contracts.md#workflow-budget-contract)。生产未部署。

| 改进 | 用户能看到的变化 | 原机制与未覆盖范围 |
|---|---|---|
| 一件工作的执行总额 | 初版计划可填写总额；默认是本版工具动作数（含保存）×4。后续所有明确关联版本共用 | 每个版本仍需原受理；总额不是新许可，不是人民币/token/模型/研发费用 |
| 新计划先预留 | 原 Task、许可、验收和整版预留一起提交；不足则一起回滚，计划保持可修改 | 保留原 approve-only 与 approve_and_run；不留“获批但没有额度”的新任务 |
| 原账本扣费 | 原 Ledger 每次派发扣费；同事务检查根额度和预留，原效果检查再核对 | 不新建另一套花费账本；重试/对账不重复记账，原 grant 仍独立生效 |
| 确定后才释放未用额度 | 已用、预留和可用分别显示；普通终态释放确定未用部分 | WAITING/RUNNING 继续占用；UNKNOWN/DISPATCHING 即使任务取消也保留尚未核清的预留 |
| 明确调整与停止 | 负责人卡片可调整总额并填写原因；不能低于已用+预留，也不会因此自动运行 | 根工作取消后禁止新额度变更；旧请求重试只返回原回执，不复活工作 |
| 旧记录逐步接入 | 升级只加预算表；旧已受理任务仍按原限制运行；旧工作的新增返工须先设置共享额度 | 不补造过去的许可或预算；正式接入时计入已有消耗和仍占用的额度 |

操作路径：初版 REVIEW 计划填写“整件工作执行总额”后按原方式受理；负责人卡片显示“已用 + 预留 / 总额 · 可用”。不足时先调整计划；确需增加总额可明确填写调整原因，随后再受理原草稿。调额本身不会创建执行许可、Task、排队请求或恢复取消任务。

计算只有一个口径：**已用 = 原关联 tasks.spent 之和；占用 = 已用 + 未用预留；可用 = max(0, 总额 − 占用)。** 每版预留按原任务 max_cost_units 固定，派发时原账本已用增加而剩余预留相应减少；预留释放是原状态和回执的投影，不把失败、已消费或未知效果返还成可重复使用的额度。

[WorkBudgets](../modules/task_resource/work_budgets.py)归原任务资源模块；[Ledger](../modules/task_resource/ledger.py)在原派发事务检查它，[Core](../host/core.py)在原效果检查再核对。Host 负责将预算约束接入 Goals/Works，Completion 和知识继续读取原结果。无第二调度器、第二身份或自行授予权限的预算服务；本轮为 K1/K2 的进一步接线，不能据此签收完整三位一体、通用自愈或自主改造。

这是明确关联 Goal/Task 的工具动作额度，尚未合并规划模型、研发试验、时间、token、实际货币账单，也不自动识别被拆成多个独立根工作的同一业务目的；后续多 Bot 和常设自主委托必须补齐这些范围。本轮六组合成资料对照用于检查已有返工机制，不是生产业务效果或自动判断返工范围的实现。

## 工作闭环 1.4.0：保守影响分析、当前版结案与会话一致性

**结论：补齐“改什么 → 从哪里重做 → 用同一额度执行 → 核验当前版 → 迟到纠正重新打开”的本地纯文本链。** 运行实现已完成；验证范围见[本轮证据](delivery-validation.md#workflow-closure-evidence)，字段见[契约](contracts.md#workflow-closure-contract)。生产未部署，通用语义理解和全功能助手仍不能据此签收。

| 改进 | 使用后的变化 | 保留原机制 |
|---|---|---|
| 自动计算最早受影响步 | 完成计划后选择“修改计划并自动分析返工范围”；输入、目标、步骤或工具版本变化都有解释 | 只分析完整的纯文本串行计划；目标或输入变化保守从头重做，不猜测语义 |
| 复用前段前再核对 | 只保留逐项相同、当前工具有效且回执仍可核查的前段；提交时再分析，依据变化拒绝 | 沿用原来源摘要、版本 CAS、许可、取消和 UNKNOWN；分析不会批准或执行 |
| 一件工作只有一个当前结案结果 | 从旧入口、当前版和聊天查看都指向相同结案投影；旧版本自己的结果与分数继续保留 | 不新建第二份完成事实或替换 Completion；等待、停止、缺证据均不是完成 |
| 聊天看到当前工作 | 模型上下文使用当前版目标 ID；原会话可接续/取消当前版，过期或跨会话建议拒绝 | 历史消息仍保留原结果；语义修改仍通过原计划/返工编辑入口，不自动授予执行权限 |
| 可重复的一次总验收 | 原验收入口收集全部不同用例一次，并串联交接、返工、额度、结案、方法回用和性能检查 | 保留全部验收条件、冻结 ID 和源码；缺测、跳过、失败或源码变化不放行 |

操作路径：完成的纯文本计划 → 修改整份计划与说明 → 分析修改影响 → 查看保留/重做步和预计动作单位 → 生成关联草稿 → 按原入口约定验收并执行。当前 UI 可改输入、目标及已有步骤的能力/预期；完整 API 还接受合法的步骤增减。改完分析后的任一字段，界面清除旧分析；服务端独立再验。 若之前版本已复用更早的前段，改变完整目标/输入时会拒绝局部自动返工，要求重新核对完整计划，避免漏掉最初步骤。不能把预期描述当作新的工具实现或自动验收程序。

结案条件是**当前版本**已有完成执行，原 Completion 在明确支持的要求范围内 VERIFIED/ACCEPTED 且覆盖完整，同时工作未停止、预算依据完整、没有未知效果或超额占用。100% 条件检查但要求未覆盖仍是待核验；完整业务 Q 继续为空。来源撤回、迟到反馈或评价不可用会使结案重新打开。自然语言目标是否列全并未自动证明。

三位一体仍以原分工运行：Host 的[影响分析](../host/rework_impact.py)与[结案投影](../host/work_closure.py)装配现有模块，原 Ledger/Scheduling 执行，原 Completion/知识来源提供反证。没有增加总 Agent、第二执行器、常设授权或第二知识库；自愈继续是原模块恢复接续，经验成长继续是已有文本统计条件方法与来源失效机制。自动写代码、自主发布、通用报告方法归纳、长期成长、多 Bot 租约和机器人控制仍是单独的未完成目标。

本版没有新增数据库 schema；自动分析结果、完整候选与目标的摘要写入既有审计事件，与关联草稿同事务，不复制正文到日志。旧任务/历史回执不改写；在途关联任务仍依赖新版检查，不能把“没有新表”当成可以安全热降级。

## 领域核验 1.5.0：结构化报价从执行成功到可核验交付

**本轮补齐一种有限领域的独立验收：预算、交期、完整合格集合、最低价和所选来源引用。** [契约](contracts.md#workflow-domain-contract) · [验证与预测差距](delivery-validation.md#workflow-domain-evidence)。这是“真实委托到可核验交付”的首个技术切面；自然语言需求提取、真实报价可信性、常设委托、完整费用和长期收益仍待后续证据。

| 改进 | 使用后的效果 | 保留机制 |
|---|---|---|
| 执行前冻结输入摘要 | 不能在生成结果时偷偷替换预算、交期或候选集合 | 原 Goal 受理事务与验收冻结；不匹配时整次受理回滚 |
| 独立计算合格方案与最低价 | 工具成功但选择错误仍需纠正；并列最低价均可接受，无符合项也有明确结论 | 原 Completion、产物一致性检查与当前工作结案 |
| 原始输入贯穿多步文字处理 | 不根据工具自行删减的候选名单验收 | 只允许受支持的本地纯文本串行链；交付必须来自被核验的最终步骤 |
| 固定含义的领域要求 | 不允许把“信誉良好、保修十年”挂在同一核验器下冒充已核对 | 通用 semantic 要求保持待核对；semantic_goal_verified 始终 false |
| 可读失败原因与核验版本 | 能区分集合遗漏、选错最低价、来源不符和格式错误；核验器变更会更新证据指纹 | 保留原反馈与评价历史；迟到纠正继续重新打开工作 |

使用前提：已通过原研发/发布入口的纯文本报价能力，以及符合[输入契约](contracts.md#workflow-domain-contract)的结构化报价文本。本轮工具仅在临时验收实例中发布，未向真实用户数据目录安装报价能力。工作台打开待核对目标 → “约定验收条件并执行” → “结构化报价核验” → 核对预算、交期和范围 → 保存条件并执行。默认只检查部分要求；只有本次全部要求确实局限于该固定范围时，才选择全部必需要求。保修、资质、税费、报价日期等不能靠这一选项自动过关；源输入出现未知字段会拒绝，避免静默丢弃约束。

核验代码在原任务资源模块 [quote_checks](../modules/task_resource/quote_checks.py)，由原 Completion 调用；Host、Ledger、Scheduling、Goals、许可和共享预算沿用既有服务。工作台只增加验收方式与原因呈现，聊天与工作状态继续读取同一结案投影。未增加第二执行器、授权入口、知识库或数据库 schema；三位一体的现有分工没有被替换。原文本统计条件方法仍保留，报价验收通过不自动创建可复用报价经验。

兼容界限：旧字面检查与历史回执保留，新的核验器版本、输入摘要和原因进入现有证据指纹，不额外复制报价正文到核验审计。旧二进制不认识 quote_selection，不能据此推断可热降级；本轮验证候选代码上的旧用例，未演练生产迁移/旧代码回滚。更大任务需要更多独立核验器和覆盖分析，不应放宽此核验器来吞下未支持条件。

## 目标要求 1.6.0：逐句提取、输入对照与未覆盖内容

**本轮为1.5的独立报价核验增加前置要求审阅：从当前目标的明确中文表达提取预算、交期和最低价选择要求，逐段保留未覆盖内容。** [契约](contracts.md#workflow-requirements-contract) · [实测与预测差距](delivery-validation.md#workflow-requirements-evidence)。这是有限语法的确定性处理，不是通用自然语言理解；报价数据仍需结构化输入，未自动生成或改写预算/交期字段。

| 改进 | 执行与结案效果 | 仍需补齐 |
|---|---|---|
| 对照目标原文及引用位置 | 能查看每个识别片段、提取值和未覆盖片段；只读审阅不创建Task、执行许可或模型调用 | 当前保存的Goal不等于聊天全文；聊天改写、附件和跨轮上下文的漏项尚未核验 |
| 对照报价输入 | 预算、交期或币种不一致，重复条件不能自动取最后一个，受理前拒绝 | 不根据猜测覆盖输入；需修订原目标或计划后重新核对 |
| 未支持要求保留 | 保修、税费等未覆盖内容令完整覆盖不成立；可明确执行已约定的本地文字部分，仍等待核验 | 不把未支持要求改成“可选”，不自动把部分结果宣布完成 |
| 未支持控制表达阻止受理 | 未覆盖片段含“不要、或者、除非、如果、忽略、例外”等控制词时不继续执行 | 是有限词表的保守拦截，不是所有否定/条件表达的语义识别 |
| 目标、输入、解析版本绑定 | 改动或过期审阅不能沿用；目标过长不得只核验截断后的前半段 | 多来源材料与长期上下文仍需独立对账 |

使用路径：待核对目标 → “约定验收条件并执行” → “对照目标原文核验” → 查看原文、提取值与冲突。默认只检查部分要求。明确表达全部识别且与输入一致时，可沿原入口声明这些就是本次全部必需要求；仍不等于自动证明全部聊天意图。未覆盖附加要求时，界面固定部分范围；即使API强行提交complete，服务端也不能自动结案。存在冲突或未支持的控制表达则禁用执行，并由服务端再次拒绝受理。

例：`预算不超过100元，交期不超过5天，选择最低价报价，保留来源引用，保存结果` 可提取并对照；添加`必须保修三年`会保持待核对，添加`不要执行`会阻止受理。正确原文片段可换顺序或采用支持的等价表达；未支持的汉字数词、工作日、绝对日期、近似值和自由表达不会被静默当成已理解。

实现复用原Task资源模块的 [quote_request](../modules/task_resource/quote_request.py)、Completion、覆盖映射、Goal受理与工作结案；没有新增数据库、第二执行器、常设授权或知识库。工作台展现审阅结果，聊天和工作状态继续消费同一结案投影。已有1.5结构化核验与字面核验保留原含义；新方式才增加目标原文对照。未覆盖条件下的成功执行最多作为带限定的“执行观察”候选，不能自动形成可复用报价方法，不能由一次反馈认可消除未核验内容。

## 聊天来源 1.7.0：原话对账、来源绑定与失效重开

**新增“对照聊天来源核验”：把已关联用户原话、会话要求和当前Goal一起核对；模型写入Goal时遗漏的条件不能因Goal自身通过而消失。** [契约](contracts.md#workflow-sources-contract) · [实测与预测差距](delivery-validation.md#workflow-sources-evidence)。沿用1.5独立报价核验及1.6有限表达语法；这不是通用附件理解或多轮语义合并。

| 改进 | 改进后会怎样 | 当前边界 |
|---|---|---|
| 对账原话、会话要求和Goal | 原话中的“必须保修三年”即使未进入Goal，也保持待核验；不能用complete或认可反馈跳过 | 只解释受支持的明确报价表达；其他原文保留 |
| 对账明确冲突 | 原话预算90元而Goal/输入100元、会话交期4天而输入5天，受理事务拒绝 | 不擅自选择较新或较宽条件；未支持控制表达阻止受理 |
| 附件分清资料与权限 | 只有附件正文与本次结构化输入逐字一致，才显示“与本次输入逐字一致”；其余保留未核对 | 一致仅证明传入内容相同，不证明报价、供应商或附件叙述真实；附件指令不能授予权限 |
| 明示前文和修订缺口 | 前轮上下文、图片、记忆/技能背景、修订或返工链未解释部分均阻止完整结案 | 现有记录未保存所有上下文的精确逐轮依赖；本轮不猜测哪些旧要求已撤销 |
| 来源贯穿执行与评价 | 受理后来源改变，原执行检查点拒绝继续；完成后重新评价使旧通过证据失效 | 不回写历史动作，不撤销已发生副作用；跨数据库检查不构成全局原子锁 |

使用路径：已有聊天目标 → 核对纯文本计划 → “约定验收条件并执行” → “对照聊天来源核验”。展开“用户原话”“会话要求”或附件可看实际来源文本。来源齐全、有限语法已覆盖且输入一致时，可沿原入口声明全部要求；独立结果核验和其他原结案前提仍需通过。未核对内容固定为部分范围；明确冲突禁用执行并由服务端再次拦截。直接填写的Goal显示“仅核对直接填写的目标”，不能伪称已经对照聊天。

处理顺序为：`原话/会话要求 → 与完整Goal及输入对账 → 冻结来源摘要 → 原Task与许可执行 → 每个原检查点复核 → 独立结果核验 → 当前工作结案`。任一来源变化进入重新核对；尚有未核验内容则保留待证据。模型的摘要只是待验证表示，不再是这项检查的唯一输入。

实现复用原模块边界：Host的[来源组合器](../host/quote_sources.py)通过原Dialogues、Goals与Work记录读取来源；Task资源模块的[纯核验规则](../modules/task_resource/source_checks.py)只处理传入资料，由Completion端口取得审阅结果，不反向访问聊天模块。核心检查点仍控制实际动作，状态和知识候选仍消费原Completion投影。没有新增数据库、第二任务执行器或授权路径；三位一体的既有职责不变。

对照[三职能权威定义](architecture.md#continuity-facets)，本轮接入关系如下，不能据此将完整三位一体设计签收为已实现：

| 原职能 | 本轮增加的证据或守卫 | 保留的边界 |
|---|---|---|
| Direction 定向 | 将模型生成的Goal回查已关联原话和会话要求 | 未知条件留待核验，不自行改写主人的预算与要求 |
| Engagement 协作 | 界面显示原话及资料范围；原任务检查点复核来源 | 动作仍经原许可与账本；部分结果不承诺完整交付 |
| Reflection 观察成长 | 来源失效可以反证旧通过结论，保留未核验原因 | 核验器不执行修码/发布，不把不完整证据升级成方法 |

三职能仍共享原连续身份、Goal、Task与事实，不增加最高权限角色。模块独立由Host端口组合和架构检查约束；自评估不取得执行权，恢复代码也不能使变化的来源摘要重新有效。

自评估获得可追溯的来源范围和失效原因；自愈仍需沿原修订/返工流程，不能把来源错误自动修成宽松要求。自改造/自进化可将失败用作候选改进证据，但必须再验证，不得改写本轮冻结预测或给未知收益补分。部分任务仍只能成为带覆盖限定的执行观察；本轮没有把报价成功自动归纳为可采用方法。后续评价“越用越聪明”须同时测错误交付、不必要拒绝、人工介入、完整费用和经验负迁移。

兼容范围：旧字面、1.5和1.6验收方式保持原范围，新方式显式选择；不能把老验收结果追认为已对账来源。旧代码不认识新check，热降级、真实数据迁移与生产加载另行验收。本轮只增加来源正确性的有限守卫，没有实现常设委托、任意任务多Bot接管或通用机器人控制。

## 明确变更 1.8.0：新增、替换、撤销与有效要求重放

**新增“对照明确要求变更核验”，让尚未执行的同一聊天Goal可以按已接受原话明确修改条件，同时保留旧条件及其去向。** 原1.7核验方式及版本不改写。[契约](contracts.md#workflow-changes-contract) · [实测与预测](delivery-validation.md#workflow-changes-evidence)。适用范围为有限报价表达、原始Goal、最多3次已接受聊天amend；手工改写、执行后Work返工、自由语言和混杂前文仍需另行核对。

| 明确原话示例 | 本轮处理 | 产生什么效果 |
|---|---|---|
| `新增要求「必须保修三年」` | 增加有效条件；保修仍不属于报价核验器支持范围 | 可以明确执行部分本地结果，但不能自动结案 |
| `将要求「预算不超过100元」替换为「预算不超过90元」` | 逐字定位唯一有效旧条件，记录替换关系；其余条件保留 | 输入与当前Goal也一致时，可核验90元预算；不能顺便改报价资料 |
| `撤销要求「必须保修三年」` | 标记旧条件已撤销，保留原话和操作来源 | 其他条件仍有效；只有全部剩余要求可核验时才可能结案 |
| `把预算改低一点`、引用已撤销或不唯一条件 | 不猜测目标、值或优先级 | 阻止新方式受理，要求先形成明确变更 |

流程：`初始原话与会话要求 → 按已接受generation顺序重放明确操作 → 得到当前有效要求及历史去向 → 对照完整Goal和输入 → 原许可执行 → 原检查点复核来源 → 独立结果核验`。界面可展开要求变更记录，查看有效、已替换、已撤销的条件。接受修订仍走原聊天卡片；核验入口只读，既不接受卡片，也不触发规划或执行。

本轮没有把“最新一句”当作覆盖规则：撤销/替换必须逐字引用唯一有效旧条件；未被点名的用户原话和初始会话要求继续生效。最终模型Goal新增或遗漏实质条件会阻止受理。历史Goal可能曾表达不完整，本轮依据原话重放并核对最终完整Goal；不声称每个历史模型摘要都正确，也不回写它们。

仅允许输入的预算/交期上限随有效要求一致变化；所有报价项、金额、来源和币种须与最初输入一致。历史附件与当轮输入逐字一致时可以显示这一事实，但不证明其内容真实；其他附件仍保持未核验。后续会话要求出现不同的非空文本，不能自动替换最初会话要求。未知前文、图片、背景记忆/技能依赖继续限制完整结案。

新增规则在任务资源模块的[change_checks](../modules/task_resource/change_checks.py)内，通过原Host来源端口接入Completion、Goal受理和执行检查点；不新建数据库、身份、任务执行器或授权入口。对照[三职能定义](architecture.md#continuity-facets)：Direction获得更准确的有效要求，Engagement呈现范围并沿原许可执行，Reflection保存可反证的变更摘要与结果；核验不会发布代码或自动采用经验。

这一步减少的是某些明确变更造成的保守待核验，不是已经测出真实误拒率下降。未知要求仍只是限定观察，不能自动形成报价经验。执行后全量返工的逐项继承见[1.9](#workflow-inheritance-runtime)；后续先建立独立真实请求样本，再接完整费用和有限常设委托；真实错误交付、无谓拒绝、人工介入与完整成本必须一起测。

## 返工继承 1.9.0：旧要求接续，新结果独立核验

**新增“对照返工继承要求核验”：执行后的Work版本可逐条继承旧要求、明确变更，并重新验收本次结果。** 实现状态 implemented/verified（以下有限范围）；最终冻结证据见[验收记录](delivery-validation.md#workflow-inheritance-evidence)。[接口与边界](contracts.md#workflow-inheritance-contract)。原1.8仅核对执行前聊天修订，本能力独立使用新规则，不改变旧任务的冻结含义。

| 改进 | 实际处理 | 预测效果及边界 |
|---|---|---|
| 继承全部有效条件 | 从已冻结来源核验重建要求历史；未被点名的条件继续有效 | 减少返工遗漏条件；真实漏项率尚未测 |
| 纠错保持标准 | 选择“纠错”，变更原因填写 `保持全部要求` | 修工具或结果时不能顺便降低标准；原版本仍保留纠正记录 |
| 明确改变标准 | 选择“新增要求”，填写1.8严格引用式新增、替换、撤销指令 | 预算改变可重做；最终完整目标仍须包含其他条件 |
| 独立验收新结果 | 每版单独冻结验收、核对结果；保留原回执和交付 | 工具返回成功但选错最低价，仍判需要纠正 |
| 来源变化回接 | 复核祖先回执、文件、反馈及条件绑定 | 变化后暂停后续效果；未受理草案可显式重审，已受理版本不就地改签 |

流程图：`旧版已执行 → 读取旧版冻结条件＋来源回执 → 保留／明确增删改 → 对照新版完整目标与输入 → 原预算与授权受理 → 每个效果前复核 → 独立结果验收 → 当前Work结案或保留缺口`。旧版通过不能让新版自动结案；旧版有未知要求，也不能在新版悄悄消失。

操作顺序：打开已执行版本，选择“关联返工 / 追加要求”；填写完整新要求和明确变更原因，从第1步重做；生成后调整实际输入，选择“约定验收条件并执行”中的新核验方式。界面展示返工继承链，以及每项要求的有效、已替换、已撤销状态。纠错说明只有上述明确保留表达可签收；更自由的解释仍可用原返工机制，但不会因此获得新核验的完整通过。

当前只支持原始版本已冻结quote_changes、后续版本已冻结quote_rework的有限报价工作，最多3次接续、全部从第1步重做。原有部分前缀复用仍可用，但本轮没有证明它在需求变化后语义正确。报价资料、金额、来源、币种保持一致；仅预算与交期上限可与有效要求同步变化。未知保修、混杂前文、背景记忆及其他资料的不确定性继续保留。

实现复用[原Work版本服务](../host/work_revisions.py)、[来源接线](../host/quote_rework.py)及[任务资源核验策略](../modules/task_resource/inheritance_checks.py)，不增加数据库、执行器或最高权限身份。Direction管理条件及版本；Engagement沿原授权、共享成本和回执执行；Reflection独立检查本次结果并允许迟到反证。旧工作状态汇总、原取消机制与经验准入保持原义。

联合验收还发现并修复了详情读取竞态：任务、动作、预算和评价现在共享同一核心账本事务，避免把旧的待确认动作与新的完成状态拼在同一响应。动作执行规则不变，原预算门保留。

这形成有限返工的“要求—执行—评价—再修订”闭环，尚非全自动自改造。发现错误后如何诊断、产出候选、证明更好并自动采用，仍需后续工作。研发与生产采用的分离仍按[退化处理规则（proposed）](evolution-release.md#growth-regression-policy)验收。报价成功不会自动成为可复用知识；先取得真实对照数据，再做带适用范围、反例、到期复核和退化暂停的经验候选，避免把一次成功固化为通用经验。

## 来源恢复 1.10.0：保留旧事实，用新版本重新验收

**已受理的有限报价返工版本，仅因祖先反馈变化失效时，可以显式建立恢复草案。** 本轮 implemented/verified（以下有限范围），510项不同用例、12条浏览器流程及30道验收门全部通过；证据集中在[验收页](delivery-validation.md#workflow-recovery-evidence)。[实际契约](contracts.md#workflow-recovery-contract)。此能力接回1.9已受理后不能就地重签的断点。

| 改进 | 恢复时发生什么 | 预期效果与实测边界 |
|---|---|---|
| 证明失效原因 | 用旧反馈摘要替换当前快照中的反馈后，必须与旧绑定完全一致 | 限定“只有反馈变了”；真实诊断覆盖率仍未测 |
| 新版本接续 | 当前Work负责人新增恢复草案；原版和原验收不重签 | 不必丢掉版本链重建工作；仍需显式复核后重新受理 |
| 保留事实和成本 | 旧任务已完成则保持完成；未完成只在没有未知动作时停止；已用成本不退还 | 旧动作不重放，未用预留才释放；新的全量重做仍计费 |
| 保留全部要求 | 完整Goal、实际输入、未知要求全部继承；反馈说明不擅自改变要求 | 防止通过恢复降低验收标准；报价错误仍需纠正 |
| 多轮有界接续 | 后续反馈再次变化时旧恢复失效，可再分析；仍最多4个版本 | 不能靠恢复重置版本或预算上限；并非无限自愈 |

流程：`祖先反馈变化 → 原版停止继续引用旧依据 → 只读证明反馈是唯一变化 → 明确保留要求 → 原锁与事务停止旧待办／记录旧完成事实 → 同Work恢复草案 → 重新核验、受理与授权 → 原执行器全量重做 → 独立验收 → 结案或继续保留缺口`。

在当前版本选择“分析来源失效与恢复”，查看反馈变化、已用成本、可用额度和完整重做所需额度；勾选“保持全部当前要求”并填写说明，生成草案。再选择“约定验收条件并执行—对照来源恢复依据核验”。草案创建不派发任务、不授予新执行权；带恢复边界的版本禁止绕过该核验方式直接受理。新要求必须另行明确变更，恢复说明不能隐含新增或撤销。

只覆盖根quote_changes、后续quote_rework／quote_recovery的完整纯文本报价串行计划。目标须为READY、来源变化导致的WAITING或SUCCEEDED；所有已发生动作必须已确认且回执/文件可核对。RUNNING、未知动作、独立取消、原始资料撤回、上下文失效、交付损坏、过期或撤销许可、预算不足均不自动恢复。附加自定义验收条件也拒绝自动继承，以免丢失约束。

三位一体分工保持：Direction由[恢复服务](../host/work_recovery.py)和原Work管理新版本；Engagement沿原锁、任务账本、预算、权限与派发执行；Reflection由[恢复核验策略](../modules/task_resource/recovery_checks.py)和独立报价检查核验新结果。新增同一数据库中的不可变恢复记录，不增加最高权限主体、执行器或知识库。原[模块自愈](#completion-loop-runtime)、[退化处理设计](evolution-release.md#growth-regression-policy)仍各守原边界。

这补齐“反馈失效—有限恢复—重新验收”的连接。自动找根因、改代码、选优发布、知识自动晋升、完整费用及长期越用越好仍未签收。恢复成功只形成带范围的事实；方法收益必须通过真实任务、反例和延迟复测后再判断，不能把该轮条件通过率写成业务质量提升。

**implemented；本地技术verified，实际业务质量未签收。** 538项不同用例、12条浏览器流程及30道门通过。三领域真实模型试跑与修复复测已完成；修复后48轮中47轮硬条件通过、1轮超时待测，正文补审仍有事实扩写与计划保留缺口。完整结果归[权威验收](delivery-validation.md#workflow-trials-evidence)，不能用字段检查替代Q或全功能优秀。[实际契约](contracts.md#workflow-trials-contract)。

| 新能力 | 实际用途 | 预期效果及限制 |
|---|---|---|
| 运行前冻结 | 保存请求、隐藏于模型输入之外的检查参考、源码摘要、模型参数、顺序与限额 | 不根据答案事后改题或降低条件；同一末轮问题仍按所属会话上下文核验 |
| 工作流开关对照 | 同一当前运行代码、同一模型与预算，按AB/BA顺序比较none与选定文字工作流 | 检查技能引导是否减少错误路由；不是旧1.10与新模型版本的净收益比较 |

流程：`选定三领域样本 → 冻结要求/参考/模型/源码/预算 → 按AB/BA逐次执行 → 原会话文件回读 → 分领域检查 → 汇总每个不同任务的配对结果 → 明确失败环节与未测项 → 修复后新建一轮，旧证据保留`。

[对照器](../tools/work_trials.py)默认只预览；加--run才发起最多由冻结样本决定的调用。在临时数据根通过原DialogueHost、Skills、会话文件和真实NativeModel运行；凭据由现有保险库只读提供，不复制密钥、旧聊天或记忆。测试实例始终关闭记忆、固定模型、没有自动回退；不重启生产服务、不修改用户默认模型设置，不接受或执行模型提出的新Goal。原控制停止与网络开关仍生效。

可复用入口：`python -m tools.work_trials --suite tests/fixtures/work_trials_v1.json --output docs/evidence/自行指定新目录 --run --reasoning low --max-output-tokens 4096`。目录必须尚不存在，已有试验不重跑或覆盖。这个命令会实际调用已配置模型；模型、推理和上限应在新一轮前固定，不把跨配置变化都归因于工作流。

首批为每领域2个不同合成任务，共6个任务、每配置1次，包含24个对话轮次。它是问题筛查，低于[真实工作协议](delivery-validation.md#completion-real-work-acceptance)建议的小规模样本起点；不能签收“全功能都优秀”。学习测的是助手是否正确出题、纠错和保留未完成状态，不能替用户证明独立掌握或延迟保持。Markdown派生文档只是模型document字段的原样提取，另保留原会话文件；Word/PDF质量仍未测。

三位一体保持原职责：定向面提供原会话路由，协作面使用原对话与产物通路，观察面在[独立纯检查模块](../modules/task_resource/trial_checks.py)按冻结参考生成试验结果。定向提示补充“外层助手协议与reply内用户格式分开”，并让明确仅要回复且排除后台/外部动作的请求使用chat；原解析器、Goal受理和权限规则不放宽。没有新执行器、授权主体、正式评分存储或知识晋升路径。自改造之前先取得可靠失败归因；方法积累与采用仍须真实后续任务、反例及净收益证据。

**implemented；本地技术verified，真实业务质量未签收。** 561项不同用例、12条浏览器流程、30道门通过；候选36轮v2检查36通过、0失败、0待测。旧Markdown回放仍复现日志工作流中的扩写与计划遗漏，通用提示修复未达预期；[实际验收](delivery-validation.md#workflow-fidelity-evidence)保留反证。 在原三领域试验器扩展可选v2来源摘录格式；v1契约不变。事实与已确认计划逐条保留来源编号及原文，建议明确未采纳；正文必须与这些字段生成的Markdown一致。自由改写或额外正文不能借正确字段通过。原三位一体职责、Goal受理、解析器、预算、停止与正式知识存储不变。

| 修改面 | 作用 | 边界 |
|---|---|---|

| 原work_trials的v2分支 | 冻结并执行新场景、记录同样的模型/文件/费用证据 | 不增加生产API或并行执行器；不写回正式评分和知识 |

流程：`冻结原始材料与有效事实/计划 → 原助手生成字段及正文 → 逐字来源核对 → 当前版本与计划覆盖 → 正文一致性 → 分域结果/未知费用 → 修复后新试验`。不匹配即FAIL，试验器不悄悄重写模型回答；建议的质量、任意自由文本语义保持未测。

操作复用`python -m tools.work_trials --suite tests/fixtures/work_fidelity_v2.json --output docs/evidence/新的试验目录 --run --reasoning low --max-output-tokens 4096`，完整运行边界见[原对照器](#workflow-trials-runtime)。本轮6个新合成任务及3个程序性保留题均先冻结；这不是独立用户样本或人工金标准。[契约](contracts.md#workflow-fidelity-contract) · [本轮验收](delivery-validation.md#workflow-fidelity-evidence)。

## 交付影子核对 1.13.0：同一会话的事实、计划与回复

**implemented；2026-10-27最终冻结候选591项回归、13条浏览器流程、32道门通过；仅本节数据链范围verified，生产未部署。** 原对话发送、持久化、上下文、回复交付与工作台共用同一套核对依据，不新增执行器或授权通道。正常聊天无需提供依据；需要校准时，可在输入区展开“资料与计划核对”，逐行填写事实和已确认计划，勾选随本次消息更新。它们会进入可见原消息；后续回复沿用该会话的当前依据，不需要每次重新填。

| 交接 | 本轮实现 | 效果和限制 |
|---|---|---|
| 用户声明→依据版本 | 完整快照与预期修订号；来源逐字绑定本次消息位置；与新消息同一事务提交 | 防止旧编辑覆盖新版本；没有自动可信事实提取 |
| 当前依据→本轮上下文 | 受理时冻结，后续修改不改变已排队轮次；保存来源UTC时间 | 相对时间仍未核定，不将逐字保留当绝对日期正确 |
| 回复→影子核对 | 原Host交付时记录来源/正文结果，异常标不可用 | 不额外调用模型，不阻断、不自动改写，不写正式评分 |
| 观察→工作台 | 每条回复显示核对详情、原文与计划；旧依据或回复变化标历史 | 原文未找到可能只是改写；原文全找到也不代表额外内容正确 |
| 更正/改期/撤销 | 显式更新两组当前内容；清空并更新停止后续核对 | 原版本保留在历史轮次；事实声明不是执行许可 |

流程：`填写或沿用明确依据 → 原发送事务冻结版本 → 原模型回答 → 影子核对与回复一并保存 → 原工作台查看结果 → 明确修订或清空 → 新版本继续`。资料只作用于同一会话，不作为正式知识或跨会话长期记忆自动晋升。工作台与未来精灵使用同一请求/投影，不另建助手服务。

摘录格式复用[1.12核验](#workflow-fidelity-runtime)；自由正文只作原文出现检查，不能作通用语义判官或自动结案门。无依据时不推测，用户明确建立依据后再观察。长期事实有效性、自动提取、语义遗忘联动与相对日期解析仍须后续专门验证。[契约](contracts.md#workflow-shadow-contract) · [本轮实测](delivery-validation.md#workflow-shadow-evidence)。
