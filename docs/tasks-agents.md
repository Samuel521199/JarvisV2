<a id="interaction-tasks-4"></a>
## 多 Agent 组织

以下是可复用角色示例，不是类型或数量上限。系统可按能力与任务生成新蓝图、重组团队，见[Agent 自主生成、部署、分工与回收](tasks-agents.md#agent-factory)；简单任务不全部启用：

| 角色 | 责任 |
|---|---|
| Planner | 目标分解、依赖和验收设计 |
| Researcher | 查询资料、整理来源与冲突 |
| Designer | 设计方案与可编辑产物 |
| Builder | 编写代码、脚本与工具 |
| Executor | 在获授权环境执行具体步骤 |
| Verifier | 检查产物、运行测试、读取真实状态 |
| Coordinator | 汇总、资源分配、去重与沟通 |

Agent 是带模型、工具、状态和任务契约的工作者。共享的是明确的任务上下文与产物引用，不把全部私人记忆复制给每个 Agent。

每个委派包含：目标、输入、输出格式、可用工具、不可改动范围、预算、截止时间、父任务、验收标准。多个 Agent 的一致意见不能替代可检查的结果。[S10](references.md#s10)

<a id="interaction-tasks-5"></a>
## 冲突与调度

桌面 GUI 同时只能有一个有控制权的操作者；其他任务优先走 API 或排队。
- 同一文件使用版本/写锁；代码 Agent 采用独立分支或工作目录再合并。
- 设备网关维护资源代际，不由 Agent 自行抢占。
- 主人交互可提高优先级，但不可强行打断必须完成的设备安全步骤。
- 用户更新目标时创建目标修订，保留旧产物与进行中的动作状态。

<a id="conversation-intent-routing"></a>
#### 统一理解输入，允许一轮包含多个意图

打字与完成转写的语音进入同一个会话受理接口。路由回答“主人想交流、了解、改变什么”，模型选择回答“用哪个模型处理”；两者是不同职责。**闲聊、工作、情感不是互斥的三个桶。** 使用多个意图片段加交流风格，避免一旦发现工作要求就忽略用户的情绪，或一旦发现情绪就丢掉工作要求。

| 意图维度 | 处理 | 示例与边界 |
|---|---|---|
| 对话 / 问答 | 对话通道生成回应；确需慢检索时另建有界查询工作 | “给我解释这个概念”默认回答，不因提到工作就建任务 |
| 情感交流 / 陪伴 | 调整同理心、长度和表达，仍可同时回答问题或受理任务 | “我很烦，陪我聊聊，顺便整理报告”产生陪伴回应与报告任务两个结果 |
| 执行请求 | 提取目标、对象、范围、产物、时间要求；向唯一任务受理器提交 | “把本项目按类型统计，保存成 CSV”；只有支持该范围的能力才受理 |
| 状态查询 / 修改 / 取消 | 从真实账本解析所指任务，按修订号执行 | “报告做到哪了”“把它改成 PDF”；多个候选时只询问缺失对象 |
| 记忆 / 偏好 / 人格 | 交给相应数据所有者处理；不从聊天措辞推定事实已经保存 | “以后说简短一点”“忘记刚才那条”；遵守临时会话和来源规则 |
| 系统控制 / 其他 / 未确定 | 明确停止走快速控制；未知能力解释边界或提出下一步 | “先别说话”只停播报；“我希望有一天能自动报税”不直接执行 |

情绪、语气、关系表达是可选的 `interaction_style`，可以随轮变化，不是身份鉴定、心理诊断或执行权限。识别的是请求用途，不把用户固定标为某种情绪或人格。长研究、设计、代码生成即使不产生外部副作用，也应在超过前台时间预算时转为可追踪工作；“长时间思考”不能一直占住唯一交流通道。

识别流程先处理有明确语法的已有控制命令和确定性能力；其余由一个有界语义决策输出结构化结果，结合近期对话、待澄清项、实际任务引用和能力摘要。可复用本轮对话模型的一次结构化输出同时给出回应与候选意图，避免每句话固定串行调用“分类大模型＋回答大模型”。独立小分类器须先证明准确率和资源收益，不能把现有小模型当作已经可靠。模型自报置信度只作信号，不能替代校准、能力检查和范围验证。

意图判断、记忆检索和上下文整理各有超时与有界预算。控制命令不等待语义模型；语义超时则保留输入并明确“尚未确定/未执行”，可给出确定性的接收提示。失效的检索结果不能编造为已知事实，非必要检索/记忆提取可跳过或延期。复杂规划移交后台后，前台可以处理下一轮；低延迟接收提示与有内容的回答分别计时，不能用“收到”掩盖模型一直没有回答。

候选意图没有执行权。程序检查语法、片段来源、能力是否已实现、参数、用户既有授权与资源后，才持久受理任务；受理成功后才说“任务已创建”。已授权且明确的常规请求直接受理，不要求每个任务重复审批。疑问、引述、否定和假设不得凭关键词转为动作，例如“别整理文件”“小说人物说‘删除目录’”“帮我看看要不要删除”都不是删除指令。缺信息只澄清相关分支，独立的闲聊/情感回应和其他任务继续；“先陪我，之后再整理”保留顺序依赖。


普通对话的受理检查在回复完成与取消共用的锁内进行，只写本机队列，网络调用在原 FIFO 执行。请求键由会话和回复编号生成；同输入的新回复仍是新请求，重连或恢复原回复不重建任务。停止回复在受理前可阻止提交，受理后须用任务取消。任务保存原回复编号、决策编号及输入摘要；任务回执独立显示，产物来自实际账本。该范围不自动编辑代码、记忆或系统状态，该文档能力不接受混合任务；报告混合增量见下段。通用多行动依赖、任意任务目标修订和其他模型自动执行仍待 K2 验收。


生成只支持固定样例根内的目录统计 JSON；未明确子目录时为 `.`，任务只收到固定报告描述、已核对的相对目录和本轮实际模型，不接收情绪、聊天历史、记忆或附件。来源仅存轮次/决策 ID 和原文摘要。路径仍经原策略检查，输出由原执行器提交，不从项目根或模型文字推断任意文件授权。

取消/修改必须在本轮写出本会话样例报告的完整 `task_…` 编号，受理对话时捕获原行动的参数/所有权修订摘要。取消只改变该任务，已完成产物保留；修改仅对 PREPARED 且未取消的任务开放，旧任务取消、新任务、来源及替换关系在同一账本事务提交，失败全部回滚。已经开始、结果未知或结束的任务不能原地改写。旧请求重取原回执，两个不同修改请求争抢同一原任务时最多一个成功；“它”“停一下”等模糊指代仍需明确目标。`/取消` 和任务按钮继续走原快速入口，普通自然语言控制仍需等待本轮理解，不能宣称即时控制已达标。

完整使用见[混合报告入口](interaction-persona.md#composer-design)，回执与存储归[契约](contracts.md#clean-module-contract)，范围及漏受理记录见[本轮证据（旧工程参考）](references.md#legacy-project)。

一轮内每个行动有稳定编号。重连、语音末尾重复转写、模型切换、前端重复点击均不能另建同一任务；不同时间同文的真实新请求不能仅靠文本哈希误去重。附带任务状态的模型文本不充当实际回执，详情和产物始终从账本读取。原始输入、路由决策和修订记录用于纠正误判；不保存模型隐藏思维链。

<a id="conversation-task-context-separation"></a>
#### 分开上下文，通过结果与引用协作

前台上下文包含当前交流、适用人格/个人记忆和必要的任务简报；后台只获得执行所需的目标、项目资料、约束和明确引用。聊天中的私人倾诉不随整个 transcript 自动传给编程、检索或第三方 Agent。具体资料使用语义沿用[个人与工作记忆边界](knowledge-learning.md#memory-use-boundary)。

任务执行日志、工具调用和中间推理保留在任务详情；对话只接收带任务编号的受理、关键变化和结果摘要。正常完成不打断当前语音，可以先显示任务卡，用户问起时再说明；用户请求即时播报的事件按设置处理。事件积压按任务合并进展，保留终态，不让高频日志冲垮消息框。

会话、回复、播报、录音和任务各有生命周期。切换会话停止本页录音/播报但不取消已受理工作；停止回复不撤销已提交任务。要取消任务必须定位目标并记录取消请求。外部动作是否已完成按回执核对，不能因为听到“停”就声称已经撤销。

<a id="end-to-end-flows-3"></a>
### 未知外部动作结果

```text
请求发出 → 网络断开/进程崩溃 → 结果 UNKNOWN
    → 查询外部系统 / 读取设备状态 / 使用同一幂等标识查询
    → 已完成：登记回执并验证
    → 明确未执行且允许重试：重试原意图
    → 无法确认：保持等待，必要时由主人选择
```

不得在“无法确认”分支默认重试，更不能将日志重放解释为再次执行命令。

## Agent 自主生成、部署、分工与回收



<a id="agent-factory-1"></a>
### Agent 数量与类型不写死

Jarvis 根据任务、环境、已连接设备和资源状况，自主判断应该使用普通程序、单 Agent、固定工作流还是动态团队。角色名称与数量不是预置名单的上限；新领域可以产生新的蓝图。

**2026-10-22 收敛方案 proposed：**Bot 作为可选通道/持续职责绑定，角色蓝图与 Agent 实例使用同一执行底座；完整概念定义归[组合框架](architecture.md#composition-concepts)。通用引擎可以装配成开发者、研究者、生活伙伴或 NPC，具体任务仍受已接通能力及结果验证约束。

“可持续扩展”意味着接口和存储没有人为固定的角色数量上限，可以随资源增加扩容；每次部署仍有明确的资源、预算、委派深度、时间与终止条件。有限机器和预算不支持字面意义的无限活跃实例。

| 对象 | 含义 |
|---|---|
| AgentBlueprint | 可复用配方，定义见[概念表](architecture.md#composition-concepts)；由工厂解析依赖并选定版本 |
| AgentInstance | 本次工作身份，绑定 RunSpec、任务及上下文；运行状态不写回蓝图 |
| Worker / ModelDeployment | 实际执行与推理资源；由同一资源准入分配，逻辑角色可以共享 |
| TeamPlan | 一次任务的角色、依赖、分工、预算和部署方案；具体字段归[装配契约](contracts.md#composition-contracts) |

这些对象不是一一对应。许多逻辑角色可以休眠或共享少量 Worker；一个复杂任务也可以使用多个工作者。生成 Agent 通常先生成配置与工作流，只有确实缺少能力才研发新代码。

### 自主组队流程

[矢量图](diagrams/agent-team-lifecycle.svg) · [可编辑图源](diagrams/agent-team-lifecycle.mmd)


新设备接入后先认证与能力探测，再在必要时生成对应 Agent；不因发现设备就自动取得控制权。设备离线后撤销对应可用能力，持有该设备任务的 Agent 保存状态并重新规划。

<a id="agent-factory-3"></a>
### 工厂和团队控制器

Agent Factory：寻找已有蓝图、生成候选蓝图、验证工具与契约，登记不可变版本。
- Team Controller：观察任务结果，决定重分工、拆分合并和扩缩，不自行增加总预算。
- Capability Observer：维护带时间戳的设备与模型能力快照；执行前重新验证关键能力。
- Deployment Scheduler：选择节点、申请资源、部署 Worker，并处理失败和迁移。
- Agent Registry：维护身份、版本、父任务、租约、状态和产物。
- Resource Governor：统一管理 Agent 与普通模块的配额，不按 Agent 名字分配特权。

这些是逻辑模块，初期可组合到现有工作者和 node-host 中。

<a id="agent-factory-4"></a>
### 委派不会扩大权限

子任务继承主人目标与 G0，权限是父任务可委派权限的子集。预算先从父额度预留，再授予子 Agent；不能所有子 Agent 都把父任务的剩余金额当作各自预算。

子 Agent 可以提出进一步分解，但必须经过工厂和准入。所有后代绑定 root_task_id、delegation_chain 和 security_epoch；不能通过生成新身份、调用外部 Agent 或请第三方做事脱离约束。

外部 Agent 和第三方服务必须有明确能力、数据范围、预算、超时与取消契约。不支持可靠取消或幂等的服务，不能被包装成“可完全控制”的本地工作者；出现停机时必须如实报告未确认部分。

<a id="agent-factory-5"></a>
### 生命周期

```text
proposed → validated → admitted → deployed → running
    → draining → checkpointed → sleeping / retired
    → failed / quarantined / terminated_by_security
```

退休时撤销能力凭据、停止模型订阅、释放资源和设备占用；需保存的经验经过知识晋升。security terminated 状态不能自动被“任务恢复”转换为 running。

<a id="agent-factory-6"></a>
### 关键契约

角色蓝图、一次装配、Agent 实例及调用上下文的完整字段统一维护于[组合运行契约](contracts.md#composition-contracts)；原 purpose/工具/输入输出/预算/父任务/节点/G0/安全代际均保留，不再在任务章维护第二份可漂移的 YAML。当前 schema 和实现不因文档字段新增自动迁移。

多 Agent 仍需结果证据，不能通过多数投票决定事实或放宽 G0。默认使用本机有界调度和共享模型端口，不为每个角色创建常驻服务。Ray 等框架只作为已有集群需求时的对照材料，逻辑资源声明不等于操作系统硬隔离。[S29](references.md#s29) 组件选择受[普通 PC 准入规则](stack-project-layout.md#technology-selection-4)约束。

<a id="composition-execution"></a>
### 从自然目标到可恢复运行的装配流程

**proposed。** 本节定义流程，状态枚举仍复用[既有任务状态机](#interaction-tasks-3)，不增加平行账本。

1. **理解目标。** 个人核心区分交流、当前行动、否定、引用及未来愿望；关联本轮原文和既有有效授权。普通聊天直接回复。行动缺信息时先做可独立部分，只有影响执行的歧义才请求补充。
2. **发现能力。** 读取 Registry 与 SelfModel 的有界快照；查询环境、设备、账号、权限、网络和验证范围。只登记了技能却没有执行器时明确能力缺口，不能返回“已经会做”。
3. **选择方法。** 比较确定性操作、固定工作流、单 Agent 多技能和团队；先复用蓝图。规划器可以提出新配方，Composer 验证依赖、契约、必要输入、工具范围、数据用途和评估要求。
4. **固定本次配置。** 将选定蓝图、技能、工具、模型策略、上下文来源修订、任务图和终止条件写成 RunSpec；Task Runtime 以稳定请求编号完成去重、预算预留和受理。权限仅引用已有许可，不来自技能文本。
5. **按步执行。** Worker 获取资源后运行确定性步骤或 Agent Runtime。模型提出的工具意图先通过原动作入口；能力/权限/取消/节点代际在执行前复核，领域连接器持有真实副作用。
6. **等待与恢复。** 等授权、网络、资源、定时器或外部结果时保存检查点，释放 Worker/模型槽。读请求按允许策略有限重试；写请求结果未知时先查询原 action_id/提供商回执，不因换模型、换角色或重启重发。
7. **动态调整。** 有证据表明路径不可用时重规划未执行部分；保留已完成动作与依赖，重新分配父任务剩余额度。新子任务仍受委派深度、总成本、截止时间和无进展次数约束。
8. **交付及学习。** 以产物/环境检查为完成证据；模型意见可补充解释，不能自行覆盖独立验收。结果摘要交回个人核心；经验按原候选/知识晋升规则处理。释放租约，长期职责休眠至下一事件。

同一请求的重送必须返回原受理结果；相同动作编号配不同参数拒绝。模型连续重复同类失败、没有新证据或达到预算时，暂停该任务并记录可接续条件，不停止其他正常任务。控制完整性违规仍服从 G0 的全局锁存规则，不能当普通业务失败处理。

组合例：主人要求“制作单词小游戏并帮我学习”。先创建一个共同目标，开发与教学子任务共享获准的词表引用；编码角色输出可运行候选，测试角色用独立案例核验，教学角色生成计划。只有主人授权长期跟进时才登记 BotBinding；游戏产物、个人错题和通用开发经验分别存入对应领域，模型和角色数量由实际工作决定。

<a id="composition-runtime-cycle"></a>
#### 一步认知循环与完整调用时序

![从自然请求到可验证结果的运行时序（目标）](diagrams/composition-execution.png)

[SVG 放大查看](diagrams/composition-execution.svg) · [唯一图源](diagrams/composition-execution.mmd)。此图为目标流程；不要求每个方框调用一次模型，也不要求每次请求创建 Agent。

| 步骤 | 输入由谁提供 | 负责组件 | 输出与继续条件 |
|---|---|---|---|
| 识别和关联目标 | 主人当前请求，或已授权的事件绑定；检索到的正文不充当命令 | 个人核心与原受理入口 | 普通回答、需要信息的请求或可执行目标；记录原轮次来源 |
| 查前提并装配 | 能力目录、环境观察、作用域和预算 | Planner 提候选，Composer 做确定性解析 | 有版本和摘要的 RunSpec；缺依赖应说明缺什么，不假造工具 |
| 受理并给出进度 | 固定规格与原 request_id | Task Runtime / 原领域任务所有者 | 原任务 ID、预算预留与依赖；相同请求返回同一回执 |
| 准备认知步骤 | 当前检查点、已确认动作结果及当下有效的资料引用 | Context Service + Agent Runtime | 有界上下文；技能按当前步骤加载，未选的技能与全部历史不入 prompt |
| 决定下一步 | 模型输出或确定性规则 | Agent Runtime 产候选，Task Runtime 核对 | 结构化响应、动作、子任务、等待或变更提案；格式错误不能执行自由文本 |
| 产生现实效果 | 核定工具参数、范围和原动作编号 | Action Gateway + 领域服务/Worker | 真实结果或明确的 UNKNOWN；秘密仅由需要它的执行器解析 |
| 固定可恢复进度 | 原动作回执和结果证据 | 原任务所有者 + 检查点存储端口 | 原子修订或有界跨域对账；不能先将“已完成”显示出来再补业务写入 |
| 验收、汇报与纳入经验 | 产物、规则检查及必要的独立评价 | 领域验证器、个人核心、记忆/知识域 | 结果、局限、未结事项；经验先成候选，不自动成为长期真相 |

Agent Runtime 的最小循环是“观察 → 提议 → 交还控制”。运行引擎不应在一次调用里私自无限执行工具；外层根据预算、取消和实际进展决定是否还有下一步。等待网络或 Google 授权时返回等待条件，不让模型反复分析同一页来保持活跃；纯查询或固定转换可沿确定性路径完成。

技能切换发生在步骤边界：先确认上一动作结果，再加载下一方法。未用到的资料不传给新角色；跨项目、账号或虚拟世界时采用新用途视图。新工具超出原规格、来源发生实质变化或需要新增效果时，提出规格修订，宿主核对已有授权是否覆盖；已经覆盖的可自动继续，不重复询问；不覆盖的才需要补充必要信息或权限。

<a id="composition-recovery-flow"></a>
#### 等待、有限重试、取消和重启接续

![恢复时先查原任务与动作，不盲目重放（目标）](diagrams/composition-recovery.png)

[SVG 放大查看](diagrams/composition-recovery.svg) · [唯一图源](diagrams/composition-recovery.mmd)。图中等待原因是既有任务状态的附加语义，不创建第二套可以独立决定执行的状态机。

| 情况 | 本任务怎样处理 | 自动继续的条件 | 对其他活动的影响 |
|---|---|---|---|
| 缺少必要输入 | 保存已完成步骤与精确缺项；可独立的步骤继续 | 补充内容到达，核对原计划修订 | 其他聊天/任务正常受理 |
| 资源不足 | 排队或保存检查点，释放未使用的预留 | 调度器实际发放所需资源并重新核对期限 | 保留前台优先通道，不能由后台忙等占满槽位 |
| 首选模型限流/不可用 | 按原用途和成本策略选备选，累计实际调用成本 | 备选允许接收本次资料且符合剩余额度 | 同提供商共享配额仍可能影响其他调用，需要按真实配额域退避 |
| 网络不可用 | 能离线完成的步骤使用已安装能力，其余登记等待 | 网络恢复事件或有界探测成功，仍须重新准入 | 不关停整个 Jarvis；无网络时不能承诺自动下载缺失模型 |
| 账号授权失效 | 复用原账号恢复流程；等待本人必须的官方步骤 | 回调确认实际账号、scope 与原任务仍匹配 | 邮箱等待不占聊天的模型槽，也不重复创建连接任务 |
| 可重试读取/无副作用计算失败 | 有总次数、总期限及退避；记录错误指纹和改变了什么 | 有新条件或允许的下一尝试；不得每次切模型都重置计数 | 只影响此依赖分支，其他无依赖步骤继续 |
| 写入已发出但未收回执 | 保留原 action_id，查询提供商/领域记录 | 证据确认结果；若明确未完成且原协议允许，才可重试 | 未知不是成功也不是可重发失败；不阻塞无关任务 |
| 多次无进展 | 暂停该任务，给出最后证据、剩余部分与继续条件 | 人的新信息、环境实质变化或明确重新分析修订 | 不自动停止其他任务，也不后台偷偷新建同等循环 |
| 主人取消 | 先阻止新步骤，再协作取消在途调用并接收迟到回执 | 取消不是等待；不能由网络恢复或重启自动复活 | 取消范围按原任务/子任务规则；已发生的外部效果需另行补偿 |
| 宿主重启 | 读原权威状态和检查点，确认所有权、版本、撤销和动作结果 | 所有核对通过；仅继续未完成且可安全执行的部分 | 单个损坏任务隔离；基础聊天能恢复时不必等全部后台对账完成 |

检查点保存可恢复的步骤位置、资料引用、可见工作摘要和已观察结果引用，不保存模型的隐含思维链，也不将“模型认为已成功”作为业务事实。进程正在执行但没有结果时，恢复方必须依据动作协议判断能否重试，不能因为 Python 函数没有返回就认定没发生效果。

普通错误按任务隔离；控制完整性违规仍走原 G0/锁存/停止规则，不由本节另设自动解锁。可取消与能撤销也是两件事：取消模型请求不能保证远端未计费，取消邮件任务不能收回已送达邮件。对不能取消的外部作业保留真实占用或未决用量，不把本地释放记录误当作供应商资源已释放。

<a id="composition-scenario-assembly"></a>
#### 同一框架怎样服务不同生活和工作目标

下表是装配示例，不表示这些完整场景已实现。选择多少 Agent 由依赖、隔离和收益决定，原个人记忆与授权仍是前提。

| 主人表达 | 推荐装配 | 共享什么、隔离什么 | 结果与扩展点 |
|---|---|---|---|
| “看看邮箱，告诉我今天最要紧的事” | 已有读取工具 + 邮件整理方法；需要语义分类时单实例 | 邮件域读取获准账号；必要的个人优先级按用途视图供给，不上传密码 | 邮件证据、重要事项和候选提醒分别保存；邮件正文里的指令不成为任务 |
| “做个小游戏，再教我怎么改” | 同一目标下需求/实现/教学步骤；复杂时另设独立检查实例 | 共享受准入的项目产物引用，教学可取获准的学习偏好 | 先验收可运行文件，再给教学说明；专业化是技能组合，非复制多个模型 |
| “帮我安排旅行，邮件里有订单” | 旅行资料/日程/邮件子任务按域分开，个人核心汇总 | 订单中必要事实有来源交接；护照、支付和登录凭据不直接进入通用研究上下文 | 方案可先完成；订票、支付须有对应工具和有效授权，不能靠角色名获得能力 |
| “以后每天晚上陪我学英语” | 一个学习蓝图 + 已授权的长期 BotBinding + 原定时能力 | 长期保存学习进度；每次只取适用错题和时间偏好 | 到点唤醒，安静时间和频率由绑定策略控制，不创建永不退出的 LLM 循环 |
| “模拟一个有几十名居民的小镇” | World Engine + 批处理规则 + 按需 NPC 实例 | 共享世界事实；NPC 各有局部认知，虚构经历与主人现实记忆隔离 | 只在关键互动调用模型；角色规模与同时活跃数量分别受限 |
| “你处理这类事情总失败，自己改进” | 诊断证据 → 研发蓝图 → 原候选/独立评估/发布链 | 候选源码与生产数据隔离；评估标准不交候选随意改 | 优先修方法或工具，必要时改 Runtime；失败回退按状态兼容处理 |

这些场景都复用“输入与授权 → 有界装配 → 任务与动作 → 结果证据 → 候选学习”，但不合并各领域事实和事务。邮件、个人偏好、项目结果、公共知识及模拟状态的保存位置继续按[记忆分域](knowledge-learning.md#memory-scope-model)执行。

<a id="resource-scheduling"></a>
## Agent、模型与模块的统一资源自调度



<a id="resource-scheduling-1"></a>
### 所有工作使用同一资源账本

CPU、内存、显存、模型请求槽、Token 额度、费用、存储、网络、电量、温度约束、设备独占权和用户等待目标都纳入调度。普通程序、索引重建、语音模型、NPC 和 Agent 不能各自绕过全局资源额度。

资源租约应包含 node_id、scope、reserved、limit、deadline、priority、reclaim_policy、parent_budget_ref 与 security_epoch。额度发放与回收需要去重，失联节点的额度不能在未确认或未到期前被重复发放。

<a id="resource-scheduling-2"></a>
### 优先级

1. 独立监督、告警、停止和实体设备安全控制：有专用保留，业务调度不能收回。
2. 主人实时交流和明确优先任务。
3. 正式后台任务与已承诺的截止任务。
4. 自主学习、进化实验、知识重建和虚拟世界扩展。

主人可调整业务优先级和资源预算；不能把监督资源分配给模型。学习或模拟若是主人的当前主要任务，可提升其业务优先级，但仍不能覆盖 G0 或停止控制。

<a id="resource-scheduling-3"></a>
### 自适应决策

每次新增 Agent 或扩大模型并发，比较预期收益、协调成本、资源代价和等待时间。无收益或资源不足时可以排队、批处理、减少上下文、换模型、降低世界刷新频率、迁移任务、休眠或缩小范围。

采用迟滞与冷却，避免资源稍有变化就频繁装卸模型和迁移 Agent。监测实际内存与 GPU 使用；仅在调度器里声明“使用 1 个 CPU”并不会强制物理隔离。[S29](references.md#s29)

个人设备版本的扩展优先采用有界 Worker、模型复用与已配对节点间的任务分配。Kubernetes 扩缩容资料 [S30](references.md#s30)仅供明确服务器集群需求时参考，不列为后续必经升级；增加 Agent、运行 NPC 小镇或连接第二台 PC 都不自动构成引入它的理由。具体组件准入统一归[技术栈规则](stack-project-layout.md#technology-selection-4)。

<a id="conversation-resource-isolation"></a>
#### 普通 PC 的并行、保留与公平调度

**proposed；“互不阻塞”指不等待其他通道完成才能受理和处理本通道，不代表有限硬件可以无限并行，也不代表所有响应始终一样快。** 同一扬声器保持一条可理解的播报，同一文件写入和同一桌面控制权仍按冲突规则串行；排队应当局部可见，不能卡住整个助手。采用资源池隔离（Bulkhead）思路，但实现仍为本地有界队列与少量按需进程。[依据](references.md#conversation-isolation-sources)

| 逻辑通道 | 初始实现建议 | 资源与失败边界 |
|---|---|---|
| 控制 | 停播、取消、健康查询独立受理 | 不等待模型槽、任务 FIFO 或长数据库写锁；保留小型队列与控制线程 |
| 语音输入/输出 | 一个活动采集会话、一个播放所有者；STT/TTS 独立有界工作 | 音频环形缓冲和短段限额；落后时报告缺帧/重录，不积累分钟级未处理音频 |
| 对话 | 一个活动用户回复生成，另有有界输入箱 | 后续输入仍能受理；补充/纠正使旧回复代际失效，不因此取消后台任务；旧远端请求的实际槽和费用到真实结束才释放 |
| 正式工作 | 起步一个执行槽，保留现有持久任务语义 | CPU/I/O/模型各有预算，逐步验证更多槽；长规划放后台，不占对话专用槽 |
| 维护/学习 | 空闲时借用容量 | 压力时在安全点让出；不依赖先完成知识提取、索引重建或进化才能回答 |

统一预算是准入决策的权威，不是把所有工作塞进一个总队列。前台/后台分别预留推理并发、CPU 时间和内存空间；服务连接池、供应商请求并发与速率额度也按用途分配。**两套供应商配置或两个 API key 并不自动获得独立配额**；同账号/项目限制必须按实际配额域合并计数。供应商慢或限流时，只延期相关请求，状态与控制仍可响应；有可用且获准的备选才切换。

现有 `foreground_reserve_mib=1024` 仅是后台内存准入阈值，不是已分配给语音的内存，也不是完整语音足够运行的证明。新准入须依据实测 STT、TTS、LLM 驻留峰值、系统余量和 UMA 重叠计数设计。首版 STT/VAD 优先 CPU，GPU 留给经验证的 TTS/本地 LLM；预热只在用户开启语音且预算允许时进行，空闲卸载使用迟滞，避免反复装卸。

GPU 长内核或不支持取消的本地推理不能靠 `async` 强行抢占。应在准入前禁止超额常驻，并把背景推理切成可取消/可检查点的小批；必要时减少背景并发、延期某个环节、使用经验证的较小组件或获准云端候补。线程池适合有界 I/O，重 CPU 推理放现有独立进程/原生运行时；不依赖 Python 线程数声称 CPU 隔离已经实现。

持续聊天也不能把已承诺工作永久饿死。采用加权公平调度、等待老化、截止时间和有界前台突发；在资源许可时保留后台最低进展份额。机器不足以同时满足二者时，显示具体瓶颈与延期任务，让用户选择工作优先或交流优先，不虚报“全部实时”。不可抢占的已提交动作等到安全点；不得杀死它来换取更低聊天延迟。

锁仅保护短状态变化，数据库事务内不做模型/网络/音频/文件扫描。SQLite WAL 仍只有一个写入者，不能把 WAL 当作无限写并发。任务受理/状态事件同事务写入已有任务账本；跨会话存储用幂等引用和对账，订阅端断开不丢任务。优先级倒置、磁盘满、锁等待与线程池饱和均须进入[并行验收](delivery-validation.md#conversation-separation-validation)。

<a id="resource-scheduling-4"></a>
### 能力快照与重新规划

快照包括设备能力、已安装模型、可用工具、协议版本、信任域、连接状态、资源和时间戳。调度计划使用快照；真正行动前再次校验关键资源。

摄像头失联时，对依赖视觉的任务暂停或降级；GPU 失效时减少后台推理并切到已验证 CPU 路径；共同体节点离线时，不擅自复制尚未对账的现实动作。

<a id="resource-scheduling-5"></a>
### 从小到大的实测扩展

规模测试按阶梯增加身份数量与活跃任务，记录吞吐、互动延迟、事件积压、成本、内存、错误率和角色一致性。达到预算或质量门槛后停止扩容，不能只用“成功创建了很多 Agent 对象”证明可用规模。

<a id="critical-review-6"></a>
## 补足预算与委派协议

这些状态在首期由 Task Runtime 通过 control.db 维护；跨节点通过有身份、代际和幂等键的消息投影，不能多个数据库同时自称权威。

**预算预留：** `requested → reserved → consumed / released / uncertain`。

- 幂等键是 `parent_budget_id + allocation_id`，重复申请返回同一结果。
- 受理任务、为其预留额度、登记动作意图和 outbox 在同一事务提交；未提交不发出执行许可。
- Worker 启动失败且有证据未消耗时释放；费用或外部效果未知时转 uncertain，仍占额度，不因超时自动退款。
- 回执以唯一 receipt_id 去重，记录已消费和可证明未使用的余额；迁移只能转移剩余授权，不能在目标重领全额。
- 子预算总额不超过父预算。外部服务不能严格限制最终收费时，使用预留余量、上限接口或拒绝不符合硬上限要求的动作，不能声称本地账本能控制所有供应商计费。

**任务委派：** `proposed → granted → accepted → active → revoked / closed`。

- 协调者写入 granted 和 outbox，绑定 assignment_id、owner_epoch、目标节点、资源范围、预算和期限。
- 目标节点幂等接受并回执；ACK 丢失通过查询同一 assignment_id 恢复，不另创建重复委派。
- 只有有效授权、代际和租约均通过执行端检查才 active；accepted 本身不意味着外部动作已执行。
- 撤销时保存已知/未知效果并对账。重新分配遵循[离线自治与联网共同体](federation.md#offline-federation)唯一权威和 fencing；不能仅靠原节点心跳超时推断其没有执行。
- 委派结束不删除动作回执和预算证据，保留到重试、离线和审计窗口结束。

这些状态说明了最小语义；完整 schema、数据库约束和形式化模型仍列为 M0 交付，不能把本节当成已验证协议。

<a id="mail-management-plan"></a>
## 个人邮件管家：从收件到办事（方案，2026-10-21）

本节为完整产品目标 proposed；新工程尚无邮箱连接、后台同步或模型分类实现。默认是否启用及允许动作由主人的有效配置决定。

<a id="mail-management-experience"></a>
### 面向主人的视图与自然交流

主入口展示“需要我处理”“重要通知”“等待对方”“账单与行程”“订阅与低优先级”“可疑与垃圾”六个可重叠视图；它们是同一邮件记录的分类和工作状态，不复制六份正文。账号、项目和联系人作为筛选条件；Gmail 原始目录、未读数与本地待办数分别显示，避免把“看过”误认为“办完”。顶栏仅保留符合[图标规则](interaction-persona.md#workbench-settings)的邮件入口和状态；展开右侧可关闭、可调整宽度的面板，不长期挤占聊天。

可说“今天什么邮件需要我管”“找上次酒店确认”“这类广告以后别提醒”“帮我回复并等他确认”。后端返回来源邮件、判断理由、拟执行动作及当前状态；信息不够时先做查找／草稿，只有收件人、日期或操作范围确实影响结果时才澄清。“整理一下邮箱”不能自动等同于删除全部低分邮件。连接请求、查询请求、规则修改、实际发送必须进入不同能力，避免现有 Gmail 配置词法入口吞掉后续邮件任务。

<a id="mail-management-triage"></a>
### 判断重要性：优先级、可信度与待办分开

| 场景 | 判断依据与展示 | 默认建议行为 |
|---|---|---|
| 安全、支付失败、行程变更、临近截止 | 结合内容、实际日期、已确认的订单／行程和联系人；发件人自称紧急只是信号，不能单独证实真实性 | 高优先级提醒，显示证据与核对入口，不自动点击支付／重置链接 |
| 需要回复、审批、交材料 | 区分“在征询我”与群发抄送，提取截止时间、依赖和会话线程 | 进入待处理，起草或生成可修改行动；未得到结果不标为完成 |
| 等待别人回复 | 主人已发送且有待确认事项；不是所有已发送信都需要追踪 | 到期提醒，允许暂停／取消；自动催办另按预授权范围执行 |
| 账单、快递、会员、旅行 | 区分通知、收据、失败、临近续费和变更 | 聚合为订单／行程卡，必要时建议加入日程；不自动付款或订票 |
| 新闻、促销、社区消息 | 明确的订阅信号、重复内容、主人已纠正的偏好 | 放入摘要或静音；保留检索和查看“为什么被归类” |
| 垃圾、钓鱼、伪冒 | 来源线索、正文矛盾、危险附件与链接等多信号 | 标为可疑，隔离展示；模型判断不能保证识别所有诈骗，也不等于远端已移入垃圾箱 |

记录至少分开四条轴：**紧急程度、来源可信度、是否需要行动、分类置信度**。陌生发件人可能很重要，VIP 也会发无须处理的内容，营销信也可能含退款或订阅扣费通知。低置信度、关键截止与安全类冲突进入复核集合，不直接归档。亲友、公司、订单等关联只能使用主人已允许用于邮件的有限资料；不会因共享个人记忆而获得查询所有项目或私密资料册的权限。

邮箱服务已有的垃圾、类别和重要性信号可作为可解释输入，并与个人规则结合；供应商标签是弱信号，不等于来源认证。订阅/营销、疑似诈骗和重要通知分别处理，新规则先在有来源样本上验证。

先运行确定规则和去重，只有新内容、歧义或明确请求才选择模型。用户纠正生成带出处、范围、有效期的规则候选；“这个发件人不要提醒”和“以后所有广告都删掉”不是同一授权。忽略一次、未读、只读不回不能直接训练成永久偏好。规则可预览影响数量、解释命中、撤销并恢复原视图，作用域可选账号／联系人／主题／项目，具有冲突优先级和版本。

<a id="mail-management-actions"></a>
### 动作闭环与少打扰授权

读取和本地判断在已授予范围内进行；通知频率、安静时间、模型费用及自动动作可一次配置后持续生效。初始建议读、分类、摘要及本地草稿，远端动作按需授权。邮件正文不能授予新的长期权限。

1. **发现 → 核对 → 决策。** 有界同步新信和线程，保存出处与版本，区分建议、已排队与已完成；摘要每条可回到原信。
2. **办事。** 一个线程可关联多个可修改行动，沿用原计划、日程、任务队列；单个邮箱授权失效或任务失败只暂停该账号相关行动，前台聊天及其他任务继续。
3. **回复。** 先本地草稿，按需存入 Gmail 草稿；保留线程、Reply-To、附件与收件人核对。发送前绑定账号、To/Cc/Bcc、正文、附件摘要和草稿修订；修改任何一项使旧确认失效。群发、陌生收件人、承诺／费用类默认审阅；自动回复仅限主人明确设置的对象与模板范围。
4. **收尾。** 以供应商回执及后续读取核对远端结果；发送超时记为 UNKNOWN，先查证再决定是否重发。客户端幂等键和 Message-ID 不能保证 Gmail 绝对只投递一次，不盲目重试。归档／移入垃圾箱记录原标签及可恢复信息，永久删除首期不提供。
5. **接续。** 授权恢复后复核原账号、邮件版本、许可、收件人和截止时间；已取消或过期行动不因重连重放。提醒收到、已读、已回复、任务完成分别记账。

退订不能盲点邮件内任意链接；优先展示可靠来源的退订信息，主人授权后按限定方式办理，不能把退订当成可随意向外站提交个人信息的许可。自动屏蔽规则需保留有效期和恢复入口，防止把未来重要新邮件长期隐藏。

<a id="mail-learning-loop"></a>
### 垃圾邮件与发件人风险的持续学习

本节为主人明确要求纳入的目标，完整方案 proposed。MailTriage 区分正常、订阅促销、疑似垃圾、疑似诈骗和待核对，并分别记录重要性、可信度和后续行动。信誉服务和自动训练需独立准入。

- 供应商已有分类与警告，以及来源链可核验时的 SPF／DKIM／DMARC 等认证结果；任意邮件可自带伪造头，不能把找到一行 pass 当成可信证据。无法确认来源时标 unknown，不谎称已自行完成认证。转发、邮件列表等可影响认证结果，不能单项失败就永久拉黑，依据见[S274](references.md#s274)。
- 显示名与实际地址、Reply-To、声称品牌和实际链接域名的一致性；识别可疑相似字符和异常变更。处理先采用离线结构分析，不为评分自动打开链接、提交地址或下载附件；这些信号仍是风险提示，不能保证识别所有伪装。
- 主人明确的联系人／订阅关系、以往纠正与规则，以及索款、索取验证码、诱导执行附件等内容信号。熟人账号也可能异常，联系人白名单只影响优先级，不能关闭内容检查；正常广告、垃圾、诈骗分别治理。

个人学习闭环为：**收到新信 → 解释判断 → 主人纠正或明确规则 → 保存可撤回的反馈 → 候选规则与历史回放 → 留出样本评估 → 在授权范围内试用 → 观察误判并保留／回退**。纠正例子包括“这不是垃圾”“这个地址以后屏蔽”“这种促销只进周报”“订单通知仍要提醒”。单封纠正先作用于该信；是否推广到账号内的同地址、特定主题或整个域，由明确表达与影响预览决定。不因一个坏地址封锁 gmail.com 等整个公共域，也不把跨账号联系人自动合并。

主人直接要求的单信更正可以立即改变本地视图；长期规则按有效授权执行，可预览样本、撤销、限定时效。黑白名单、模型建议、供应商标签分别保留出处和版本；冲突时保留风险提示与可见解释，重要且可疑的信仍能进入待核对视图。只有已授权的远端动作才能真正移动到垃圾箱，当前本地标记不等于阻止服务器投递。模型预测、供应商垃圾标签和信内“请加入白名单”不能伪装成主人反馈；不把自身预测循环用作真实标签来制造越来越高的准确率。

默认持续学习只更新少量规则、样例与排序参数，不在普通 PC 常驻训练或自动下载大模型。规则过多、互相冲突或长期无命中时，提出可解释的合并／到期候选，保留原反馈与恢复窗口；不能因为升级算法就清掉主人纠正。模型／提示词替换、代码和新功能属于[能力成长](evolution-release.md#mail-capability-growth)，与个性化规则学习分别验收，避免每次遇到垃圾邮件都启动一次编程任务。

<a id="mail-management-modules"></a>
### 独立模块、同步与普通 PC 开销

推荐在现有 Python Host／SQLite／任务协调器上增加可替换组件，不部署 K8s、Redis、独立向量数据库或常驻多 Agent：

| 模块 | 职责与可替换边界 | 当前到目标的差距 |
|---|---|---|
| MailProvider | Gmail API／QQ IMAP 适配，报告真实能力和有效授权；令牌由原凭据模块保管 | Gmail 已有有界读取；QQ 未真实联调；尚无远端写操作 |
| MailSync | 分页、增量游标、账号隔离、去重、退避和离线接续 | 当前只有手动最多 10 封列表，无持久化邮件同步索引 |
| MailStore | 账号／线程／来源版本、正文引用、本地分类和工作状态 | 当前为会话资料箱，不能充当完整邮箱；数据保护见[邮件分域](knowledge-learning.md#mail-management-data) |
| MailTriage | 本地规则、可选模型、证据与置信度、纠正回放 | 尚无可验收的个人重要性排序和垃圾分类器 |
| MailAction | 已授权动作、Outbox、修订绑定、不确定结果与恢复 | 当前仅本地草稿；不把模型输出直接作为网络请求 |
| MailBriefing | 合并提醒、安静时间、去重升级、日报与待处理面板 | 当前无自动邮件提醒／日报 |
| MailWorkflow | 邮件到日程、个人计划、项目与候选知识的有限投影 | 已有选定 ICS 的本地提醒和独立草稿基础，邮件自动行动仍待实现 |

各模块另登记功能版本、依赖和回退点，由既有成长中心管理；具体升级与恢复语义唯一归[邮件能力的自主成长](evolution-release.md#mail-capability-growth)。新增功能可从“以后替我识别伪装客服”“增加招聘邮件汇总”等自然需求形成候选；邮件来信本身不能发起功能安装。

Gmail 优先沿用官方 API：定位稳定、可核对结果；MCP 可作为相同能力契约的适配入口，不能代替授权、记忆分域和动作账本。网页／桌面保留为授权及 API 未覆盖操作的补充，不作为常驻刷收件箱的主通道。QQ 适配保留 UIDVALIDITY＋UID，不将 Gmail 的 historyId 语义强加给 IMAP。

本机推荐**按需刷新＋可选自适应轮询＋Gmail history 增量同步**。首次只同步本人选择的近期窗口；游标失效 404 后进入有界重建／补齐并显示未覆盖范围，不假装已扫描整个邮箱。翻页完成并持久化变更后才推进游标；消息／通知重复按账号和供应商编号去重，删除和标签变化保留墓碑。同步事务不直接发送邮件，动作另走 Outbox。断网、休眠、锁定、停止和低资源会暂停；恢复不短时间补发全部旧提醒。[Google 桌面设备建议轮询、history 与 Pub/Sub 的依据](references.md#mail-management-sources)。

可选轮询初始建议 15 分钟、空闲拉长至 60 分钟，手动刷新即时；重试使用带抖动退避和单轮上限。以上是可配置设计值，不是已开启频率或即时通知承诺。Gmail watch 依赖 Cloud Pub/Sub 并需续订，适合以后已有在线节点的配置，不强加给单 PC；watch 续订不是 Google OAuth 本人重授权，也不能混为“每七天登录”。

先取头字段和变更编号，按需展开正文，附件不自动下载。一个有界同步 worker 足够首版，暂停时不加载模型；模型处理按新内容摘要去重，重复刷新不重新花 token。线程摘要保留来源与覆盖范围，不能静默截断后假装读完。优先 SQLite 索引／全文检索，确有语义检索收益再按需嵌入；普通 PC 不因启用邮箱启动一整套多 Agent。批量、缓存、磁盘上限和并发先提供可见配置；128 MiB 任务准入是现有估算，不能作为测得的内存占用或未来保证。

<a id="mail-management-delivery"></a>
### 开发顺序与验收

本节仅细化既有 K0—K6 内的邮件工作，不另建开发阶段。推荐顺序：**补齐 HTML 邮件的安全文本提取及账户数据保护 → 增量收件、搜索、六类视图 → 重要提醒／个人纠正 → 远端草稿与受控发送 → 可恢复整理与预授权自动动作**。首步不需扩大 OAuth 权限；后续写能力必须实际实现并经本人 Google 授权，不能只更改菜单文案。[权限区别](references.md#s270)尤其需要注意：gmail.compose 也允许发送，gmail.modify 也包含发送，gmail.labels 不等于可给邮件打标签；因此供应商 scope 和 Jarvis 动作许可需同时满足。

验收至少覆盖：真实纯文本与 HTML-only 邮件可读；不加载追踪像素／执行脚本；重要信漏报、垃圾误判、混合线程和中文时区截止；VIP 促销与陌生重要来信；可撤销纠正；分页／history 404／重复通知／重启；授权失效不拖住其他账号和聊天；草稿修改使旧发送许可失效；发送超时不盲目重发；本地归档／远端标签语义清楚；来源撤回影响后续摘要和候选。以主人标注的留出邮件集统计重要信召回、误提醒数、待办提取准确性和每百封成本，不凭演示给“智能”高分。

持续学习另验：认证通过但内容恶意、转发导致认证失败但内容正常、同域不同发件人、伪装熟人／Reply-To、主人否定与撤销、诱导白名单和伪造反馈、规则冲突及过期、升级前后同一留出集对照。升级回退采用[邮件能力成长的故障验收](evolution-release.md#mail-capability-growth-validation)，不以分类演示替代模块／数据恢复验收。

资源验收在目标普通 PC 测空闲与单批峰值内存、CPU、同步延迟、聊天延迟变化、落盘增长和实际模型费用，再设置默认值；当前大内存开发机和一次读取不能代表 8 GiB PC。先做影子分类与本地建议，经过个人纠正样本再开少量可恢复动作，保留一键暂停与回退。

可用的个人验收指标是：每天主动提醒数量、关键邮件漏报、误归垃圾、待回复积压与平均处理耗时，以及每百封模型费用。首批真实样本应由主人标注重要性和可执行性，按时间划分开发／留出集，避免用同一批纠正过的邮件证明泛化；报告覆盖的日期、账号、类别和样本量。重要邮件召回应优先于自动清理覆盖率，未取得样本前不填“99% 准确”等目标达成数字。

## 连续身份下的一次交流、办事与成长循环

**完整流程 proposed。** 它展开[三职能分工](architecture.md#continuity-facets)，复用既有任务状态机和[组合调用时序](#composition-runtime-cycle)，不是另建一份持续运行的超级 Agent。

![连续身份下的交流、行动、回执与学习流程](diagrams/continuity-work-cycle.png)

[SVG 放大](diagrams/continuity-work-cycle.svg) · [唯一图源](diagrams/continuity-work-cycle.mmd)。实线是本次主要工作流，虚线是按需使用的上下文和后续改进；底部状态是分支结果，不是新增任务状态枚举。

| 环节 | 谁处理、交付什么 | 避免的重复与失真 |
|---|---|---|
| 接收与接续 | 协作面接收主人话语或已授权事件，读取当前用途视图与原任务关联 | 不把每条聊天都变成任务，不默认读取所有历史 |
| 判断需要什么 | 简单聊天直接回复；已有确定性能力直接匹配；复杂目标才由定向面提出计划与验收候选 | 三个职能不是每次必调的三次 LLM；模糊输入不等于无限授权 |
| 装配和受理 | Composer 固定蓝图/技能/工具及版本；原受理检查范围、依赖、预算，复用根任务与幂等身份 | Bot 层次不决定任务层次；同一需求不得被多个 Bot 重复派发 |
| 执行一步 | 固定流程直接运行；需要认知时 Agent Runtime 产生 StepProposal，经 Task Runtime 与网关执行 | 模型不能直接写成功回执；子 Agent 和外部编码器仍属于原任务 |
| 观察与继续 | 核对真实结果；在原范围内有界重试/重规划，缺授权或网络时等待并释放槽 | 未知效果先对账，不通过换角色、换节点或换模型盲目重复；其他聊天/任务继续 |
| 交付与纳入 | 协作面说明真实完成/部分完成/等待，领域写入者提交结果；适合长期使用的内容形成候选 | 发送邮件回执、项目成果、个人偏好各归其域；不能把整个任务轨迹写成主人画像 |
| 观察成长 | 观察成长面按事件、故障和已授权计划分析反馈，提出技能/工具/实现候选 | 通过原独立评估与发布后才生效；主任务结束不代表改进候选已通过 |

例如“明天出门前帮我看看航班通知并整理准备事项”：邮件与日程职责共享获准的行程引用，读取真实通知，形成可核对的待办。若邮箱授权失效，仅相关分支等待；若时间冲突，提供证据或请求必要决定；若发现重复解析失败，可以提出邮件解析技能改进，但不能为了完成行程自行扩大邮箱权限、购买机票或更改根规则。

中断后的“还是同一个 Jarvis”依赖原目标、承诺、动作编号及有效资料继续存在，不依赖模型记住上一轮内部推理。更换引擎先核验检查点兼容；不兼容时可基于已知事实重新分析未完成步骤，不能重做已完成副作用。

<a id="proactive-goal-cycle"></a>
### 从主人目标主动发现任务，自主执行并独立交付

**完整流程 proposed；dev.2 接通固定纯工具研发，dev.8 增加[显式目标的可修改计划](#goal-planning-runtime)。尚未实现从任意聊天自主发现目标或自由规划全部事务。** 本节落实[自主工作与独立完成任务](product-requirements.md#personal-life-autonomous-outcomes)的最终目标：定向面维护目标解释与优先级，协作面推进和交付，观察成长面发现知识/能力缺口；三者只读写各自端口，不新增一个拥有全部权限的总 Agent。任务以个人为主，并覆盖获授权的家庭和小团体事务；记录请求者、服务对象、关联主人目标、资料受众及有效许可，不能把成员请求直接等同于主人授权。最小对象见[目标与机会契约](contracts.md#goal-opportunity-contract)，当前运行范围见[研发实现](toolchains.md#growth-development-runtime)。

| 环节 | 自动做什么 | 进入下一环节的条件 |
|---|---|---|
| 接续目标 | 从明确委托、已确认约定、长期职责和有效维护许可取得目标及其当前修订 | 事实、愿望、第三方请求和真正委托分开；不明确的目标解释可先成为建议 |
| 发现机会 | 消费获准日程/邮件/任务事件、截止时间、能力故障和技术变化，找到能推进目标的下一步 | 必须能解释关联哪个目标、依据是什么、为何现在值得做；不额外扫描未授权资料 |
| 去重与选择 | 合并同一效果、淘汰过期或主人已拒绝的候选；比较影响、紧迫性、证据、工作量和费用 | 先检查硬约束，再排序；评分不能把越权抵消成高收益，无收益时安静等待 |
| 形成可执行计划 | 明确产物或实际效果、完成条件、预算和期限；复用已有技能/工具，必要时分析、拆分或生成候选，计划始终可查看和修改 | 在当前许可内直接进入受理，不逐步骤要求确认；无法推断且影响执行的缺项才等待相应决定 |
| 推进与接续 | 依赖就绪后执行、检查、有限重试；失败时换有依据的方法，等待时释放资源 | 原任务/动作 ID、成本、撤权及未知效果继续有效；换方法不重置已花预算和失败计数 |
| 解决能力缺口 | 先查已有能力和可替代路径；必要时在研发许可内使用模型、Codex 或组合方案生成候选，验证与准入后接续原任务 | 新能力仍经过原发布与回退通路；无研发许可、预算耗尽或无法验收时说明具体阻塞，不悄悄安装和放宽完成标准 |
| 核验实际结果 | 核对产物、工具回执与业务条件；失败则修正，不能仅以模型自述或“已调用工具”判定完成 | 验证通过才进入完成；结果未知先对账，已确认的成功步骤不重复产生外部效果 |
| 交付与闭合 | 交付可用成果和必要证据，说明完成范围及仍未解决的问题，更新目标进度与承诺；按安静时间/重要性通知正确受众 | 有限任务按预先完成条件结束；部分完成、等待、失败不能记作完成。持续职责每次事件有独立结果，不开无终点推理循环 |
| 留下经验与改进 | 分域提交事实、候选知识、习惯假设及改进依据，关联下一次可能受益的目标 | 不能把一次任务的结论直接当成主人的稳定偏好；知识晋升与代码发布各走原流程 |

**发现机会不等于立即执行。** 对目标范围内的只读准备、计算、已许可文件操作和既有维护，满足条件后自主推进；新权限、未批准支出或未确定的重大取舍才需要主人决定。后台办理过程中，前台聊天、其他无依赖任务继续；拒绝或取消一个候选不能被另一个 Bot 重新提起以绕过选择。

举例：主人已委托“本月学会基础 Python，每周帮我安排练习”，并允许读取学习记录、生成本地练习和在指定时段提醒。Jarvis 可发现尚未完成的练习，调整难度，准备下次练习，整理常错知识；发现解析工具重复失败，还可在维护许可内验证改进。它不能据此擅自购买课程、联系老师或把私密学习记录发送到新供应商。主人改为准备另一门考试时，未开始的旧练习降级或取消；已提交的外部效果仍保留真实记录。

家庭／小团体例：在已有共享日程、采购清单编辑和家庭提醒许可下，主人提出“安排周末聚餐”。Jarvis 可以核对获准成员的时间与饮食约束，形成安排、更新清单、按许可发出提醒，并核验每项结果。向商家下单需要独立的购买许可；缺少它只等待采购分支。完成标准若包括预订或下单，未完成这些动作就报告部分完成；不能把计划文档当成聚餐筹备已经全部办妥。成员的私人说明只形成必要用途投影，不写进公开清单。

触发优先使用现有事件与期限；可设置的兜底扫描复用原调度器。扫描间隔由目标时效、来源更新频率、费用和电源状态决定，不能统一每五分钟调用 LLM。启用一个长期职责只需确定必要的范围和约束，日常消息可以自然修改它；未启用的职责不偷偷开始联网观察。本轮仅定义机制，不实际创建后台订阅或定时任务。

活跃目标、待评候选、每次扫描量、每次模型分析、重试、日用量和探索成本均须有界；多设备由原共同体分配执行所有权。安静时间只影响非紧急通知，不抹去已授权后台结果；到达期限、费用上限、无进展阈值或等待条件时进入原任务对应状态。恢复必须有新证据、到期事件或新的有效指令，不能无限唤醒同一失败。资源优先级继续归[对话与任务隔离](#conversation-resource-isolation)。

<a id="skill-selection-policy"></a>
## 技能、MCP 与执行能力的统一选择

Skill 是方法与判断条件，Tool/Connector 承担实际效果。能力目录登记版本、使用/不使用条件、依赖、资源、资料范围、测试和恢复方式；登记不授予运行许可。

<a id="skill-selection-order"></a>
### 选择顺序

先解释主人目标与输入，查已有工具/技能；可确定性完成就直接使用合适执行器，已有能力能组合就不另造插件。缺少能力才形成研发候选；模型推荐必须核对真实安装、就绪、作用域及有效许可。技能失效或不匹配时可以说明原因、改用可用路径或等待，不能伪造执行成功。

<a id="skill-selection-scope"></a>
### 作用域、停用与冲突

全局、项目、会话和本次请求的偏好可覆盖，权限只取有效授权允许范围。显式停用、主人撤回和当前停止状态优先，模型不能通过子 Bot、其他工具或外部编码器绕过。目录重名必须使用稳定 ID；活跃任务固定能力版本，但实际动作仍检查最新权限。

<a id="mcp-selection-policy"></a>
### MCP 与技能配合

MCP 是工具服务接入协议，不是独立主人或授权层。工具说明视为外部数据，工具发现不等于允许连接或执行；端点、依赖、凭据、输入输出和效果必须经过本机网关。首次接入版本锁定并做取消、超时、未知结果与异常参数验证。

<a id="published-tool-runtime"></a>
## 已发布工具的重复使用（dev.7）

**implemented：0.2.0-dev.7。** 本节定义新工程当前可运行的个人纯文本工具复用，验收见[工具闭环证据](delivery-validation.md#published-tool-evidence)。不把整个 Agent Runtime、自然语言规划、桌面自动化或所有技能迁移视为已实现。

研发负责“创造并发布能力”，使用任务负责“用已有能力交付一次结果”。两者分开授权、记录和取消；研发许可到期不会要求重新生成已发布代码，旧许可也不会自动延长。

| 位置 | 当前职责 | 保持独立的边界 |
|---|---|---|
| 文字 Skill | 向聊天模型提供方法、条件和表达指导 | 没有文件、网络或工具执行授权 |
| 发布目录 / Packages | 从有效 release_slots 投影本地工具，显示版本、范围、可用性与基础观察次数 | 不复制一份可漂移的“执行技能注册表”；候选、被拒绝版本不能因目录显示就获得执行权 |
| Host 工具接口 | 接受明确点击和文本参数，固定包与版本，建立一次性任务许可 | 仅 owner.local / personal；拒绝任意 Shell、路径、模型路由或调用者自带的宽授权 |
| Task Ledger | 保存输入、固定版本、动作、成本次数和回执，受理幂等请求 | 同一请求标识和相同参数返回同一任务；修改参数必须新建请求，刷新页面不重跑 |
| 现有 TaskRunner | 在原有一个后台任务线程中执行指定任务 | 不为每个工具新增线程池或常驻服务，不因为“运行这个工具”顺带执行其他待办 |
| 受限 Worker | 只执行已发布纯文本包，执行前与过程中检查停止、期限和权限 | 沿用[隔离边界](security-sovereignty.md#growth-worker-boundary)，不在 Host 导入候选代码 |
| 产物适配器 | 将确认后的结果写入本机任务产物目录 | 工具代码没有写入用户任意目录的能力 |
| UI | 显示输入、结果、状态和记录，允许复制、导出、明确附入聊天 | 结果不会自动变成记忆，也不会自动发给聊天模型 |

**实际流程：**发布且通过审阅的能力进入目录 → 主人选择版本并输入文本 → 确认本次使用 → 冻结任务与有限许可 → 后台运行此任务 → Worker 返回结果 → 固定产物写入 → 显示交付回执。新的使用复用代码，不重新规划、生成或调用模型。

请求只接受能力 ID、不可变 package_id、目录 revision、request_id 和 text。文本上限为 50,000 字符且 UTF-8 不超过 100,000 字节；请求总包仍受 HTTP 上限约束。每次许可只覆盖所选能力与 artifact.write.v1，最多两个动作、每动作一次派发、600 秒有效期。输入和结果保存在本机普通任务账本与产物中；这是普通资料范围，不是已加密的隐私保险库。

**版本与生命周期。** 新任务提交时要求页面选择的包和当前 revision 一致；已提交任务绑定不可变包，即使发布了新版本也不会偷偷改用新代码。全局停用仍阻断后续执行，恢复须重跑固定探测。被拒绝/退役包不能接续；尚被未结任务、当前槽或恢复槽引用的包不能退役。回退代码不复活已经撤销的单次许可。灰度累计两次运行后的 STABLE 只表示当前基础观察条件通过，不能证明所有输入都正确或已具备普遍业务可靠性。

**取消与中断。** 取消先撤销本次许可，再标记任务；在途 Worker 的检查点会停止它。无法确定是否产生结果的动作保留 UNKNOWN；有已落盘、匹配输入和版本的回执时只核对，不重跑。无回执则保留未知，主人可取消后明确新建一次处理。任务失败不停止聊天或其他独立任务。达到期限或明确失败的任务不会自动无限重试；下一次使用是新任务。

**轻量运行。** 复用既有 Python 标准库、SQLite 任务表、发布槽和一个后台任务通道，没有新数据库、模型下载或第三方服务。目录读取不启动探测 Worker；停用恢复、实际执行才按需使用 Worker。页面可见时每三秒读本机状态，关闭或隐藏时不轮询，不调用 LLM；这不是资源压测结论。

当前仍要求主人选择具体工具。自然表达的目标识别、可编辑多步计划、模型选择现有能力以及可撤回的持续主动许可是后续独立工作，不能把这个复用入口称为任意任务全自主闭环。

| 原受限 Worker / 产物写入 | 处理纯文本，串接已确认输出，保存实际结果文件 | 不拥有桌面、邮箱、网络或用户任意路径的写入权 |

**当前流程：**描述目标与可选文本 → 冻结可用工具及模型线路 → 有限模型规划 → 核对/修改实际输入、行动和预期 → 确认计划 → 在同一事务中建立任务许可与原任务 → 后台逐步执行 → 写入最后结果 → 查看实际输出和回执。缺能力或待补充问题进入 NEEDS_INPUT，保留目标，不把缩减后的任务冒充全部完成。

当前最多选取 12 个已发布且可用的个人工具，每个计划最多 4 个纯文本行动，最后由可信适配器自动增加一个产物动作。第一步使用核对后的输入；后续每步只能选同一输入或上一步已经确认的纯文本输出。禁止向前引用、环、任意命令、模型自带授权和隐藏参数。dev.8 仅将目标、显式文本及工具说明发送给规划模型；dev.10 另按[目标背景规则](knowledge-learning.md#goal-memory-runtime)装配获准记忆，聊天关联由[组合层](#conversation-action-runtime)处理，仍不自动读取项目文件。显式文本被模型改写会阻止进入待执行状态；主人可以在编辑页面主动修正。

规划只有 `model.generate.v1` 许可，最多 2 次调用、10 分钟期限。自动路由沿用当前默认和首个已启用的其他提供方，明确选定模型时仅用该线路；已知拒绝/结构不合规可使用预算内备选。超时或远端结果未知不自动重发，需要明确选择重新规划，历史调用与费用不清零。当前限制是调用次数与 token 上限，不是精确人民币费用封顶。

确认执行时比较提案 revision 与每个发布槽版本，检查当前停止/停用状态和作用域；授权、任务与提案关联同事务提交。目录更新、保存失败或旧修订均不能留下半个有效任务。确认后任务固定、最多 5 个动作、每动作一次尝试、10 分钟期限；修改目标另建计划。模型生成的 `expected` 只是人工核对描述，**不是独立业务验收程序，也不能保证规划正确或目标已经全部实现**。

后台沿用一个 TaskRunner；规划与编码研发共用一个 `BackgroundLane`，没有为每个目标新增线程池、服务或环境。前台保留原两路聊天通道，等待后台槽时目标仍在本机，可稍后继续。列表轮询只查本机状态，不调用模型。当前不自动排队唤醒、定时提醒、主动发现新任务或后台学习。

取消规划撤销其模型许可；取消已确认计划同时撤销本次执行许可，通过原检查点停止，其他无关任务保持可用。重启后的在途模型调用记为未知；执行中断先核对落盘回执，再接续剩余动作。已确认输出、已消费预算和取消标记不会因刷新、恢复或重复确认而重置。能力停用阻断后续执行，恢复仍走原发布通路。

计划正文、真实输入、输出、调用计量与任务回执按当前数据根保存；它们不会自动变成个人偏好、长期知识或项目记忆。复制和导出由主人显式选择；dev.10 已关联目标的真实输出也会返回原会话卡片。dev.8 缺少新能力时仅指出缺口；dev.9 已增加[目标关联研发与发布后回接](#goal-growth-runtime)。dev.10 的外部 Codex 仅接候选端口，MCP 执行仍待独立实现。

## 缺少能力时的目标关联研发（dev.9）

**implemented：0.2.0-dev.9；验证范围归[成长接续证据](delivery-validation.md#goal-growth-evidence)。** 本节在[目标计划](#goal-planning-runtime)之上补齐“发现缺口 → 拟订规格 → 受限研发 → 审阅发布 → 返回原目标 → 交付”。它复用原研发、发布、任务、Worker 和模型通道，不另建一个拥有全部权限的总 Agent。

| 步骤 | 当前执行内容 | 继续条件 |
|---|---|---|
| 发现缺口 | 原目标进入 NEEDS_INPUT，保留原目标 ID、原文、输入和未完成原因 | 主人选择“为这个目标设计能力”，仅限未执行、尚未做过关联研发的目标 |
| 拟订规格 | 原目标的冻结模型线路生成行为、公开示例、隔离验收建议和待解决问题 | 只产生结构化提案，无代码执行或发布许可；不支持的目标不能悄悄缩减 |
| 核对标准 | 修改行为与两组用例，选择研发规划/编码主备模型、档位和预算 | 明确核对规格及期望值后开始；公开与隔离用例输入不能重复 |
| 受理研发 | 同一事务建立限定授权、既有 development_run、路线与原目标关联 | 新能力 ID 由 Host 为原目标分配，不能覆盖其他能力；陈旧修订和失败写入整体回滚 |
| 编码与检查 | 原研发循环生成候选、AST 配方检查、LPAC Worker 执行固定用例；失败在原限额内修复 | 后续规划/编码只接收公开示例，不接收隔离用例或期望；不能改验收来放行 |
| 审阅发布 | 原源码/报告界面审阅精确候选，发布并执行独立样本任务 | 未认可候选不能经模块页绕过；原目标取消会撤权并阻止尚未发布的候选 |
| 返回目标 | 样本交付成功后核对当前发布版本，原子更新原目标目录，再使用原模型线路重新规划 | 沿用同一个目标，不再造一个无关联目标；原请求与输入不改，旧计划与目录保留为来源 |
| 真正交付 | 新计划仍可修改和核对；确认后用原任务执行通路处理原输入、保存结果 | 研发样本成功不算原目标完成；以原目标实际任务与文件回执作为结果 |

**验收标准的来源必须讲清。** 规格模型可以建议隔离用例，操作者核对或修正后冻结；它们对后续代码模型保持不可见。独立执行这些用例能检查实现是否符合固定标准，不能证明标准一定正确，也不是不同提供方独立研究得出的语义保证。当前仍保留规格确认、精确候选发布审阅、原目标计划确认三个节点；在本轮授权测试中由 Codex 核对，产品没有假装跳过这些节点。

每个目标只允许一次关联研发。初次规划最多 2 次模型调用，规格设计另有 2 次/10 分钟；研发沿用所选 2—8 次模型调用、1—3 个候选轮次、30—1800 秒总期限；发布后返回规划最多再 2 次/10 分钟。全链最高 14 次模型调用，默认界面配置最高 10 次，实际可能更少；这些是次数预算，不是金额保证。各阶段历史次数、撤销与未知结果不会因刷新或换模型重置。研发失败/取消后不自动新建一轮；dev.10 增加同目标显式修订，其独立小额预算见[聊天运行规则](#conversation-action-runtime)；不清空旧调用账本。

规划、规格设计与编码共用原一个后台模型槽。结束样本任务后，同一槽内顺序返回原目标；不会新增常驻服务、后台订阅或轮询模型。关闭面板不会取消；UI 轮询只读本机。取消原目标原子撤销相关许可并标记子研发/任务取消，检查点阻断后续动作；独立聊天和无关联任务不一并停下。已发布的共享能力或已经确认的文件不会因取消而被删除。

恢复沿用原账本：模型未知结果需明确选择重试；Worker 回执未知先核对再接续。若服务在样本交付之后、返回原目标之前中断，目标面板保留“回到原目标继续规划”，不会重新创建研发或重复发布样本。发布版本被替换/停用时返回步骤等待，恢复可用版本后接续。返回规划使用独立的 `-return` 调用身份，避免误用旧目录的缓存，也避免重置最初规划的调用记录。

实际职责定位：`modules/task_resource/growth.py` 保存关联与规格修订；`host/goal_growth.py` 组合原模块；`host/development.py` 复用原子受理与完成回接；`apps/workbench/goal-growth.js` 复用原候选审阅界面。普通目标、研发样本、原目标交付各保留自己的动作回执，靠关联字段追溯，不混为同一效果。dev.10 成功成长交付产生待核对经验候选；确认前不成为有效记忆，也不扩大为家庭共享。

当前只能生成受限 Python 纯文本能力，不能通过此入口安装依赖、编写并运行任意 Shell、修改核心、访问邮箱/桌面、创建后台定时任务或接管外部 Codex 桌面。dev.10 只接通了外部 CLI 的候选生成端口。这些目标显示能力缺口，需要对应新模块独立准入。完整自主成长设计仍按[原研发与发布](toolchains.md#autonomous-development-providers)推进。

自由描述仅在明确点击“生成并制作”时调用选定模型。复用现有两槽前台聊天执行器、取消、联网/停止控制及用量账本；新建的专用模型会话关闭记忆注入，原始需求和候选作为资料。一次请求最多一次模型调用，不走自动备选，不自动重试；未知费用/结果仍标未知。模型必须返回严格JSON；适配器可把合法ASCII标识符中的下划线改为连字符并同步引用，保留原回答、逐项记录normalizations；碰撞或其他结构/范围错误仍拒绝，不更改物理参数、不忽略字段。宿主完整验证后才能制作；返回合法JSON不代表满足全部需求，界面标组件类型、简化范围与unfulfilled。无法表达的要求应列明，不把近似机构称为任意机械CAD。

接口：POST /api/anatomy/compose接收id、prompt、provider、model；GET /api/anatomy/compositions及其/id查看历史和状态；POST /api/anatomy/finish把CANDIDATE制作成DELIVERED，重复取回已有产物；POST /api/anatomy/cancel取消未交付请求。composition状态与模型调用分开记录，模型SUCCEEDED并不自动等于交付成功，非法候选显示INVALID。相同id相同请求不重发，修改请求复用id会拒绝。重启后未结调用继承聊天恢复的UNKNOWN，不重放；可继续取回已完成候选。

POST /api/anatomy/render保留slider-crank、planetary，增加studio：只能给preset或scene之一。planetary仍限sun_teeth/planet_teeth/mode并检查装配条件：S18—48、P18—36、R=S+2P，S+R被3整除及相邻轮布局；三种固定件按Willis关系联动。20°离散齿廓有0.06mm绘图间隙，不是制造公差。检查技能启停、停止与上游摘要后调用可信Node构建器，单构建锁、15秒超时。回执保存初始配置、版本、上游许可与摘要、十个绘图资源及三个宿主校验文件摘要、产物SHA-256；自由生成附实际模型回执。UUID取回重新核对摘要，产物在本工程user-data/artifacts/anatomy，组合记录在state/anatomy.sqlite3。

模型依据：[NASA四冲程循环](https://www.grc.nasa.gov/www/k-12/airplane/otto.html)、[IIT Kharagpur直流电机](https://vlabs.iitkgp.ac.in/ctrl/Exp3/theory.html)、[TU Delft线性水波](https://coastal.citg.tudelft.nl/book/2a_pre_knowledge_waves.html)、[行星机构Willis关系](https://mechanics.ju.se/MachineElements/planetary-gears.html)。源码中的公式和简化须与这些理论适用范围区分。HTTP沙箱与下载边界归[机械产物边界](security-sovereignty.md#anatomy-output-boundary)，真实测试与模型覆盖归[验收](delivery-validation.md#anatomy-evidence)。任意拓扑机械、工程CAD/制造图、CFD/热燃烧/应力分析、流固耦合、通用电路和视频输出仍未实现。

<a id="conversation-action-runtime"></a>
## 自然聊天到目标与行动（dev.10）

**implemented：0.2.0-dev.10。** `host/assistant.py` 是聊天和既有目标模块之间的组合层；不新建任务执行器。普通聊天使用同一次前台模型请求返回 `assistant-turn.v1`，没有额外常驻意图模型。闲聊正常回答；明确办事请求形成目标计划；含糊请求先澄清。

| 入口或事件 | 当前行为 | 控制与回执 |
|---|---|---|
| 智能助手默认模式 | 识别 chat / goal / amend / cancel / resume | 可切为“只聊天”；不要求记住固定口令 |
| 明确新目标 | 回复落盘后关联一个目标，再尝试占用原后台槽规划 | 一个消息稳定映射一个目标；槽忙时保存建议，可从卡片继续，不自动执行工具 |
| 补充条件 | 显示合并后的完整目标与输入，确认后修改同一未执行目标并重新规划 | 修订 CAS；原授权撤销、原规划留证；最多 3 次手动修订，每次最多 2 次规划调用 |
| 取消 | 建议只能指向本会话目标，确认后调用既有取消事务 | 操作回执与取消同事务；完成的交付不会被误报为取消 |
| 接续 | 打开原目标，核对等待、未知回执或待审阅状态 | 不因一句“继续”重放未知外部效果或已完成动作 |
| 结果返回 | 原消息卡片显示目标状态和真实执行输出 | 只有已确认成功的工具回执可成为“已交付”；模型文字不能冒充执行结果 |

模型负责语义建议，宿主负责实际状态。非闲聊的接收、补充、取消、接续确认语由宿主生成，避免模型在建议阶段声称“已经更新/执行”。目标完整保留规则和输出要求，`input_text` 仅含待处理数据；模型仍可能提取错误，所以计划和研发规格保留可编辑核对入口。验收发现过规则与数据混放，已补提取约束并验证同目标补充；不据一次成功宣称所有模糊指令准确。

前台沿用两个回答槽，规划/规格/编码沿用一个后台槽，Worker 沿用既有执行槽；没有新增常驻服务。页面轮询只读本机。后台槽忙时不会无限排队或自动加预算，卡片负责接续。首次规划、规格、编码、返回规划的原预算不变，另加最多 3×2 次显式修订规划：默认上限 16 次、配置最大上限 20 次；自然聊天自身的模型调用另计，不混成“免费识别”。模型成本与已发生调用不会因重启、取消或修订清零。

身份、长期主动选题、定时职责、多人共享和任意设备执行仍遵守各自未完成的验收边界。本节只交付已有受限纯文本任务域的聊天入口与接续。记忆约束归[目标背景](knowledge-learning.md#goal-memory-runtime)，外部编码归[Codex 候选端口](toolchains.md#codex-candidate-runtime)。

<a id="mcp-runtime"></a>
## 受控 MCP 办事通路（dev.11）

**implemented；实际验证归[本轮验收](delivery-validation.md#mcp-evidence)。** 新工程现在可调用明确登记并启用的 HTTP MCP 工具，复用原 Registry、GrantStore、Ledger、TaskRunner、目标计划及会话交付。它是外部执行适配，不是另一个 Agent 核心；服务器可以单独升级或替换，旧任务不会悄悄绑定新版本。

运行顺序为：登记端点 → 主人选择连接并发现 → initialize / initialized / tools/list → 展示外部工具及输入结构 → 主人选择允许的工具 → 自然目标生成可修改计划，或直接填写参数 → 核对确切端点与参数 → 原账本创建限次任务 → 执行前重新核对工具摘要 → tools/call → 持久回执 → 本机产物 → 原目标/会话交付。

| 环节 | 当前行为 | 明确限制 |
|---|---|---|
| 登记与发现 | 设置 → 技能与工具 → MCP 接入；发现只发送协议握手和列表请求，不发送 tools/call | 发现会接触指定服务；不能保证第三方服务自身无副作用 |
| 启用 | 每连接最多选择 12 个支持的工具；变更、停用、重新发现均改变准入修订 | 不使用 readOnlyHint / idempotentHint 自动授权；默认不启用发现结果 |
| 自然目标 | 最多 12 个目录项发送规划模型；同时有纯工具/MCP 时各取前 6 项；MCP 可作为首步；原始文字可由模型组装为 JSON 参数，数据含义仍需核对 | 最多一个 MCP 调用，参数必须事先以 JSON 展示；不支持由上一工具输出临时决定外部参数 |
| 直接调用 | 填写严格 JSON 参数，明确调用一次；相同 request_id 与内容返回原任务 | 参数变化重用 request_id 被拒绝；重新建任务仍可能重复外部效果，需先核对旧结果 |
| 结果 | 文本/结构化 JSON 保存回执和 result.json，目标任务回到原会话 | 工具内容为外部数据，不作为新指令；不下载链接、图片、音频或附件，不自动成为长期记忆 |
| 错误 | isError=true 保存已确认的错误回执，任务 FAILED，不执行成功交付步骤 | HTTP/RPC 中断、格式变化或不支持的结果可能落为 UNKNOWN；不凭“只读”声明重放 |
| 接续 | 已确认动作不重跑；落盘回执可核对并继续保存产物；取消只影响对应任务 | 缺少持久回执时需要外部核对，当前没有服务专用的远端对账适配 |

本版仅接**无凭据的 Streamable HTTP**：HTTPS 服务或字面量 127.0.0.1 / ::1 的 HTTP 服务。stdio、OAuth、凭据代理、长期订阅、资源/提示词接口、sampling、elicitation、MCP 异步 tasks 仍未实现；登记这些方式不会启动程序或调用其他供应商的 Key。HTTP 模块只支持受限协议子集，不能据此声称兼容所有 MCP 服务器。协议核对依据见 [S321—S323](references.md#mcp-runtime-sources)。

个人 MCP 目录只供个人目标；项目目标不获得这些连接器。共享或家庭授权仍需后续独立分域设计。已交付外部结果可随同一会话的后续上下文发送到该目标既定模型（最多 1,500 字）；工作台说明这条数据路径，不把连接器输出直接提炼为记忆。

普通 PC 无新依赖、数据库服务器或常驻轮询：发现复用后台模型通道，调用复用单任务通道，前台聊天保留原独立槽位；传输最多两个在途线程，连接操作总等待 25 秒、socket 超时 5 秒、响应上限 128 KiB、目录最多 64 工具/8 页/64 KiB、入参最多 12,000 UTF-8 字节、最终回执最多 45,000 UTF-8 字节。额度单位是账本调用次数，不是第三方收费估算；发现不调用 LLM，目标规划仍按原预算计量。

<a id="context-aware-task-selection"></a>
## 结合记忆选择能力与前后台协作（proposed）

复用[统一选择](#skill-selection-policy)与[资源调度](#resource-scheduling)，不建立第二套 Agent 主循环。一个输入先产生可修改的多意图视图：闲聊、情感、知识问答、任务、记忆操作与澄清可以并存。任务状态由账本提供，聊天检索不靠模型猜测任务是否成功。

能力选择先用确定条件过滤：平台、在线状态、版本、已安装依赖、授权范围、任务输入/输出契约和资源上限；再在合格集合中按任务证据、质量、预计延迟/费用和近期失败情况排序。已有可用工具优先复用，Skill 提供流程与约束，Agent 负责确有必要的规划/执行；简单检索无需组建多 Agent。语义匹配只推荐候选，不能覆盖硬条件。工具目录来自[自身模型](self-model.md#self-model-context-selection)，不从网页宣传直接生成“已具备”能力。

缺能力时分别选择等网络/资源、查已授权连接器、请求必要信息、受限研发候选或明确无法完成。只有任务可分解、可独立验证且资源足够才创建多个 Agent；每个 Agent 得到最小必要视图、截止时间、费用和结果契约。共享写入通过事实/任务 API，不给全部 Agent 整库写权限。任务和分支记忆见[隔离规则](knowledge-learning.md#memory-branch-context)。

调度采用前台预留、可抢占后台和队列背压：聊天与语音优先，记忆提取/索引/学习低优先；数据库用短事务和有界写入队列，模型推理不持有数据库写锁。逻辑独立不代表硬件无限并行，同一 GPU/CPU 争用必须排队或降级。取消回复、停止播报、暂停学习、取消任务各有独立信号。索引落后可用事实/词项回答，不能让后台编纂锁住所有交流。

任务完成后验证效果，再把结果投递回原会话并产生经验候选；失败留条件与回执，不能把重试次数当作学习进步。主动提问与通知沿[伙伴互动](interaction-persona.md#companion-context-policy)，所有新增主动职责在明确启用前只作为设计。
