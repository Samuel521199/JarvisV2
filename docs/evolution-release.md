<a id="growth-governance"></a>
## 成长中心：三种能力、一个可追溯的成长过程

本节定义自检、自愈和进化的目标职责。新工程尚未实现这些运行能力，接口和界面分别按本工程契约及交互章交付。

| 能力 | 回答的问题 | 产物与成功条件 | 明确边界 |
|---|---|---|---|
| **自检 Inspect** | 现在是否正常，有什么证据？ | 有时间、范围、版本、覆盖度与新鲜度的检查报告；异常形成事件 | 检查完成不等于全系统健康；不改代码、不发布、不自动转为升级 |
| **自愈 Heal** | 怎样恢复原本承诺的能力？ | 恢复到既有契约，实际复测后关闭故障；必要时产生修复候选 | 不趁修复增加功能、换架构或放宽验收；修好必须有原故障复测证据 |
| **进化 Evolve** | 为主人的目标增加什么能力，改进是否值得？ | 带基线和验收的改进单，新能力/质量/成本收益经验证并发布 | 健康的旧版本低于期望新版本属于能力差距，不是故障；不能为持续动画或成长分数而制造任务 |

例如：v1 的 CSV 输出损坏属于自愈；v1 正常但主人希望增加 TSV 属于进化；检查 v1 是否正常属于自检。首次安装缺少一个可选新工具属于进化，已承诺启用的工具丢失才属于自愈。软件“有更新”只是进化候选，不自动证明应升级。修复可能写代码，进化也可能仅修改技能、配置或知识索引；分类依据目标，不依据是否调用编码模型。

三者分别有开关、模型策略、记录与成功定义。自检只写观察账本；是否自动消费异常由自愈策略决定，能力差距由进化策略决定。关闭自愈不会关闭自检，关闭进化不妨碍恢复旧能力。修复途中发现的新机会另建提案，不偷偷扩张本次故障范围。

<a id="growth-learning-ledger"></a>
### 成长记住什么，怎样避免越改越乱

共用一条可查询的因果链：**主人目标 → 观察/纠错 → 故障或能力提案 → 实验 → 独立验收 → 发布 → 实际收益 → 保留或退役**。界面展示这条链的证据摘要，不要求模型透露内部思考全文。每项记录绑定项目/个人/设备作用域、基线、来源、真实用量、成功或失败原因；失败和拒绝也形成可检索的经验，不能只记“成功故事”。

进化优先级先比较主人明确目标、对日常交流和协助的影响、重复发生的证据，再比较收益、耗时、费用、资源和可恢复性。改进可以是更准确地使用偏好、减少重复询问、避免不合时宜的提醒、改善离线回应，也可以是研发新工具；不以代码量、Agent 数量或更新频次定义成长。没有观察样本时显示“待评估”，不用模型给自己的高分替代事实。候选改善需在同一基准上满足冻结的最低要求，并说明旧能力是否退化；简单问题优先采用规则或已有技能，新增模型调用和依赖必须有可验证用途。

人格调整、事实纠正和程序发布分别走各自既有接口与验证，不把每次偏好更新变成一次代码发布。可执行能力的更新必须保留身份、适用记忆和未结事项；基础伙伴体验按[V-PAL](delivery-validation.md#personal-companion-validation)回归。相处是否更合意需要主人反馈，不用在线时长、聊天频率或让主人依赖系统作为收益指标。

个人偏好、技能经验和工程事实分别通过既有 Memory / Knowledge / Capability API 写入，不把运行日志全部变成长久记忆。用户纠正可撤销；旧结论绑定适用版本和失效条件；项目私有内容不因成长而自动跨项目或跨设备共享。身份和约定属于 Jarvis 的受控状态，模型替换不创建“另一个主人”或重置关系。共同体后续复制已验证事件与包引用，仍遵守[节点与作用域规则](federation.md#offline-federation)。

自愈与进化共用已有候选构建、验收、发布和回退流程，不复制两套发布器。独立验收器由宿主控制，模型评审只能提出风险，不能替代契约、兼容、隔离、迁移和真实结果测试。旧代码、文档、模型和调试产物的退役必须有去向与恢复窗口，完整规则沿用[长期健康与结构治理](health-maintenance.md#system-health)。所有自主行为遵守当前主人范围与[安全主题页](security-sovereignty.md#identity-authorization)，此设计不恢复已延期的认证工程，也不新设逐步人工审批。

## 自主进化与自我重构



<a id="self-evolution-1"></a>
### 六级进化对象

| 层次 | 可改变内容 | 典型验收 |
|---|---|---|
| E1 经验 | 纠正、偏好、失败原因与案例 | 检索正确、来源可追溯、不错误泛化 |
| E2 技能 | 操作流程、工具组合、例外处理 | 固定与保留测试场景通过 |
| E3 工具 | 脚本、插件、API 适配、小程序 | 契约、运行、权限、依赖和回归通过 |
| E4 策略 | 路由、检索、拆分、Agent 配置 | 在同等预算下比较真实任务表现 |
| E5 系统与形态 | 模块实现、UI、人格呈现、服务拓扑 | 兼容、迁移、连续性与恢复演练 |
| E6 模型 | 微调、蒸馏、训练本地模型 | 数据许可、训练资源、独立评估与部署 |

前五层可通过调用模型和软件工程实现，不要求直接修改模型权重。Voyager 的可执行技能积累与 Reflexion 的反馈记忆提供了研究参考，但都不证明任意现实任务可以稳定自进化。[S07](references.md#s07)[S08](references.md#s08)

<a id="self-evolution-2"></a>
### 进化触发条件

主人明确提出新能力或改造要求。
- 重复劳动超过预设频率。
- 已有技能成功率下降、耗时或成本异常。
- 工具接口变化、依赖停用、设备能力改变。
- 在获授权的维护预算内发现明确可验证的改善机会。

没有任务时不无限寻找改造目标。每项进化提案记录预期收益、影响范围、预算、验收标准、最大尝试次数、退出条件和恢复方案。

<a id="self-evolution-4"></a>
### 研发、验证与发布分权

编写候选代码的 Agent 可以改候选实现和相关普通测试，但不能自行改动独立验收基线、提高自己的权限上限或取得发布签名密钥。发布控制器根据预先设定的范围自动放行普通改进；超出已有授权时才形成具体变更提案。

候选构建在没有生产凭据、文件和网络权限受限的独立环境运行；验收启动器、基线和阈值不位于候选可写路径。测试结果由外部评估器采集，再交给发布控制器核对。独立进程、目录或代码分支本身不能替代权限隔离。

这允许在授权范围内自动完成研发、测试和部署，无需每一步都询问主人。关键在于权限可继承但不可自行扩张。

SWE-agent 说明工具界面设计与软件修复能力有关；实际发布仍必须验证运行结果。[S09](references.md#s09)

<a id="skill-admission-release"></a>
### 技能包的准入、升级与退役

2026-10-17 accepted：所有内置、导入及自主生成的技能发布前，须具备[选择契约](contracts.md#composition-package-contract)中的适用/排除规则、正反例、完整包摘要、依赖与执行边界，并通过[V-SKL](delivery-validation.md#skill-selection-validation)。技能包中的每项分别准入；缺规则或反例的候选保留待评估，不能通过扩大 description 自动启用。Anatomy 与编程包沿用同一发布控制器，不建立例外通路。

新增/更新时同时比较正文、脚本、依赖、使用范围和默认模式；禁止以新版本覆盖用户禁用项、提高预算或扩张外发范围。扩大自动匹配范围必须重新通过相关正反例与保留样本，不把误触发记录删除后宣称进步。回退保留可兼容策略修订、旧包及在途任务证据；停用/卸载不删除用户产物、原始资料和回执。选择顺序及作用域只维护于[任务章](tasks-agents.md#skill-selection-scope)，不在发布器复制另一套规则。

技能和组件按完整产出准入，验证前声明预期并保留失败；修订后仍不能满足用途的候选移出活跃目录，记录原因。无执行器、模型失败、UNKNOWN 或缺少关键素材时如实标记，不能签收成功。

<a id="self-evolution-5"></a>
### 修改自己的“形态和结构”

支持以下改造：

- **表现形态：**桌面悬浮窗、语音界面、移动端界面、虚拟形象和不同交互密度。
- **人格呈现：**称呼、语言、声音、角色、主动程度；身份和历史保持连续。
- **能力组成：**安装新技能、替换插件、增加或退役专业 Agent。
- **运行拓扑：**把重任务迁移到服务器、拆分进程、合并轻量服务、改模型部署。
- **内部实现：**替换检索引擎、规划框架、存储适配器、同步实现和部分语言实现。
- **基础底座：**通过外部引导与双槽机制替换 supervisor；恢复入口不能和被替换版本同时失去可用性。

拓扑使用声明式配置描述“哪些模块、版本、资源、依赖和路由”，先验证强制启动依赖可排序且无环，以及容量、契约、状态迁移与恢复可行性，再逐步应用。运行时调用和事件反馈可以形成循环，但必须有超时、去重、迭代上限和背压。禁止仅因为生成了代码就直接覆盖正在服务的目录。

<a id="self-evolution-6"></a>
### 评估防退化

评估包括主人真实任务样本、独立保留样本、异常输入、资源受限、离线环境和升级演练。模型评分只作为部分信号，不能替代文件检查、程序测试或设备反馈。

记录成功率、人工介入、耗时、成本和失败分布。候选版本可以失败，正式升级应满足声明的验收目标；不能承诺每次实验都变强。

<a id="service-continuity"></a>
## 持续服务、升级与迁移



<a id="service-continuity-1"></a>
### 连续性分级

本章只适用于安全状态有效且未锁存的普通升级。每次启动、迁移、回退和接管均重新检查 G0 门禁；安全关停优先于可用性目标。

| 等级 | 目标 | 适用场景 |
|---|---|---|
| C0 无感切换 | 新请求进入新版本，旧请求继续 | 无状态工具、提示词、部分配置 |
| C1 安全点接续 | 局部短暂停顿，任务状态保留 | 长任务迁移、单实例有状态模块 |
| C2 跨节点接续 | 其他完整节点接收可迁移功能 | 主机维护、服务器更新 |
| C3 维护窗口 | 明确暂停部分能力并保留恢复信息 | 无冗余 OS/驱动/固件更新、破坏性迁移 |

所有软件结构可升级，不等于所有升级都能在单机零中断；G0 规范不允许被自我改造削弱。服务等级应由组件、资源和实际演练决定。

<a id="service-continuity-2"></a>
### 新旧版本并行

1. 下载或构建新版本 B，验证来源、哈希和依赖。
2. A 继续服务，B 在独立端口/进程/环境启动。
3. 检查协议与状态兼容；执行准备和只读验证。
4. 将少量新任务交给 B；有副作用动作不进行双重影子执行。
5. 通过后扩大新流量，A 继续完成原有任务。
6. A 排空后退出，保留包、配置和恢复数据。
7. B 退化时停止新流量并回到 A；对 B 已发生的动作单独对账。

**有状态 node-host 的额外规则：**A/B 不能同时作为本机活动调度器和动作控制者。候选 B 先只读预热；A 停止领取新任务，排空或登记未决动作。supervisor 在唯一仲裁记录的持久事务中授予新的 host_instance_id / host_epoch，随后要求各执行端确认新代际，再激活 B。数据库提交和独立执行器均检查活动宿主代际，不能只依靠旧进程自觉退出。存量 Worker 经稳定入口重新连接；已发出动作仍需完成或对账。无法完成排空、状态交接或执行端确认时，使用 C1/C3，不套用普通无状态模块灰度方式。

流量切换不负责自动撤销数据库变更或外部动作。Kubernetes 的滚动机制可以作为后期部署参考，但不会自动替本项目完成业务回退；部署卡住也需要发布控制器处理。[S14](references.md#s14)

<a id="service-continuity-3"></a>
### 长任务与会话

任务固定 workflow_version、skill_version、planning_policy_version 和 checkpoint_schema，以便复现。每次动作仍由网关使用当前可验证的 enforcement_policy_version、撤销状态、授权有效期和离线规则检查；固定旧代码不意味着旧权限永久有效。新任务采用新版本，旧任务优先在原版本完成；必须迁移时在安全点导出状态，经迁移函数验证后再接管。

长期目标按阶段拆成可结束的工作流片段。旧版本设支持窗口和迁移检查点，到期前完成、迁移或明确暂停，不能直接终止仍持有动作的工作者。供应商模型退役也视为依赖迁移，不能假定固定模型名称可以永久调用。

Temporal 的版本化工作者是可选参考实现；不具备任意 Python 内存快照迁移能力。[S12](references.md#s12)

语音流绑定现有会话；声音或模型更新在轮次/会话边界切换。若硬件只能独占一个设备句柄或显存无法同时加载双模型，必须采用接续、另一节点承接或明确短暂加载等待。

<a id="service-continuity-4"></a>
### 状态迁移

新工程必须验证安装、独立健康检查、事务化版本选择、启动与回退。代码槽位切换不自动复制或回滚业务数据，数据 schema 兼容和新事实保留另验。

维护可以在前台继续交流时准备候选；真正切换需要核对受影响任务、槽位与状态兼容，不把“准备候选”声称为已完成热替换。

采用：扩展新格式 → 新旧兼容读写 → 回填 → 验证 → 切换读路径 → 等待回退窗口 → 清理旧格式。

跨版本协议遵循兼容规则，例如 Protobuf 不复用已删除字段编号；业务语义兼容还需要测试。[S13](references.md#s13)

数据库恢复快照可能丢失升级后新数据，所以“恢复旧快照”不等于无损回退。不可逆迁移应声明影响、备份点、前向修复方案和维护窗口。

<a id="service-continuity-5"></a>
### 恢复底座自身升级

引导器与运行中的 supervisor 是两个边界；两者每次启动都先验证独立停机锁，锁存、状态损坏或回退时禁止业务启动。
- supervisor A/B 槽由引导器选择，新版需在期限内写入健康确认。
- 未确认则回到旧槽；本地 CLI/安装修复入口仍可用。
- 引导器自身升级需要外部安装器或离线恢复入口，不能承诺无条件自救。
- 单次更新不能同时覆盖当前版本、备用版本、唯一恢复入口和全部恢复数据。

<a id="service-continuity-6"></a>
### 必须显式测试的底层条件

单机断电、硬盘损坏、OS 重启、唯一 GPU 驱动重置、唯一麦克风切换，都可能中断对应能力。跨设备接续也只能接续另一节点具备的能力；另一台机器不能凭网络连接接管已经断电的实体执行器。

<a id="end-to-end-flows-4"></a>
## 自主改进实际例子

主人要求“每周整理设计素材”。系统发现导出环节反复失败：

1. 从失败记录创建改进提案，目标是提高导出成功率，限定开发预算。
2. Researcher 查阅软件官方接口资料。
3. Builder 在隔离工作区开发导出适配器。
4. Verifier 使用正常、空文件、大文件、断连样本和独立保留样本验证。
5. 发布控制器核对既有授权，启动候选版本。
6. 对少量新任务使用新工具；旧任务仍使用旧版本。
7. 达标后扩大发布，记录改善证据；退化则回退。
8. 日后软件接口改变时重新进入这一流程，而不是覆盖生产代码后再尝试修复。

<a id="critical-review-7"></a>
## 发布单元矩阵

| 发布单元 | 首期实际承载 | 状态与权限 | 更新方式 | 连续性条件 |
|---|---|---|---|---|
| safety-host | G0 锁存、撤权、固定告警 | 独立受保护状态 | 主人维护入口；外部引导与已验证槽位 | 必要时 C3；不得普通自升级 |
| recovery-host | 普通进程恢复与版本启动 | 只读安全状态、获准拓扑 | 外部引导双槽切换 | 无可信监督时不启动业务 |
| node-host 包 | 任务、授权、预算、动作、记忆 API、包目录等 | 自有数据库；受信服务身份 | 排空或安全点检查点后独占接管 | 首期 C1；经验证才承诺更低暂停 |
| worker 包 | 对话、规划和任务执行 | 检查点引用、短期限定能力 | 新任务切新包；旧任务固定旧版本 | 资源足够可 C0；语音在轮次边界 |
| 工具/模型包 | 一个能力或一个模型组合 | 各自清单与兼容要求 | 版本并存、能力测试、灰度 | 显存不足时允许排队或短暂停顿 |
| desktop-helper | 用户会话内桌面操作 | 窗口/会话与资源租约 | 停止接受新动作，交接独占资源 | C1；不能两版本同时控制同一桌面 |
| builder/工具链包 | SDK、编译器、构建环境 | 只读输入与候选目录 | 新构建用新包，旧构建继续 | 不应中断生产；构建本身可重试 |
| memory 索引 | 可重建检索结构 | 来源数据不变 | 影子重建、双读对比、切换 | 数据量和存储余量允许时 C0 |

表中的同包模块具有源码与契约边界，但不会因为单独建目录就独立热更新。要提取成单独发布单元，必须同时解决数据所有权、IPC、生命周期和兼容测试。

检查点使用项目定义的版本化结构与产物引用；禁止把 Python pickle、框架闭包或供应商 SDK 私有对象当作长期跨语言格式。不可迁移的内部状态保留旧 Worker 运行，或显式结束后重新规划，不能假称自动迁移。

<a id="mail-capability-growth"></a>
## 邮件能力的自主成长与回退（方案，2026-10-21）

主人要求邮件能力持续学习、补充新功能并在失败时回退。完整邮件成长在本工程为 proposed；学习规则、更新代码和新增账号权限分别处理，生成者不能自动授予远端动作。

<a id="mail-capability-growth-levels"></a>
### 学习、修复、新功能与权限分别处理

| 变化类型 | 例子 | 成长与恢复单元 |
|---|---|---|
| 个性化学习 | 更正垃圾分类、对某联系人降低提醒频率 | 规则集／参数修订和启用指针；[学习闭环](tasks-agents.md#mail-learning-loop)不必生成代码 |
| 模型与提示词改进 | 更换邮件分类小模型、摘要模板或分档路由 | 固定模型标识／来源摘要、提示词及兼容配置；与原版本对照质量、费用、延迟，失败恢复旧选择 |
| 修复 | HTML 提取错误、已登记 API 字段变化、模块崩溃 | 同契约候选包，独立边界测试与恢复；网络、认证、资源、配额问题先按原因处理，不伪装成需要改代码 |
| 新功能 | 客户催办、招聘邮件汇总、发票归集 | 新能力契约、数据用途、样例／留出案例、预算、发布范围与依赖；缺少可判定验收标准时保留候选，不能自行宣布任意需求正确 |
| 权限或外部连接变化 | 增加发送、第三方信誉服务、导出联系人 | 单独核对主人授权和供应商要求，不由其他升级附带开通；只读域的自动升级许可不包括新增发送／外发数据 |

主人可预先规定允许自动改进的模块、读写能力上限、模型／费用／资源预算、试用范围与回退策略；范围内满足验收的候选自动推进，不逐步重复审批。没有有效预授权、依赖或独立验收器时保持稳定版本，反馈明确缺口。外部资料、来信、模型评审与候选程序不能扩大该范围、替换自己的验收器或关闭权限检查。反馈样本和候选数据保护见[记忆章](knowledge-learning.md#mail-learning-data)，代码准入沿用[供应链规则](security-sovereignty.md#personal-life-supply-chain)。

<a id="mail-capability-growth-release"></a>
### 候选、影子运行、灰度与实际收益

从主人自然需求或有证据的模块故障形成带范围的改进单，优先复用已有功能和规则；确有代码缺口才交给 CodingProvider／可选外部 Codex。冻结基线、接口和独立验收标准，先离线构建和隔离复验，再采用既有灰度与启用事务。编码器只得到必要的脱敏／合成样例，不默认把整个邮箱、凭据或留出答案发给编码模型。任意新 Python／npm 包或外部脚本仍执行原准入，不能因主人允许自我升级就运行未知安装程序。

邮件分类的影子运行只比较本地建议，不移动邮件、不发送、不触发重复提醒；初始灰度选择一个账号和有限来源／时间窗口。新功能与旧功能并存比较关键邮件漏报、垃圾误杀、截止提取、解释、实际用量及资源，不把“分类更多”当净收益。加入正文／资料外发、换模型供应商等需要满足当前数据用途许可。样本不足或用户质量反馈缺失时明确等待，不能靠同一批生成样例或模型互评晋升。

新增功能首次无旧版本时，恢复点是“禁用新功能并保留原能力”。纯分类／规则组件目标可按请求固定版本切换；读取、同步、写动作和宿主升级须分别使用兼容检查／排空或安全停止机制，不能宣称所有模块都可无中断热更新。排空不自动重放旧任务，切换代际阻止迟到候选继续派发动作；发送已经进入远端的不确定状态先核对回执。一个邮件组件退化优先隔离该组件，其他邮件基础能力、聊天和其他任务按其安全依赖继续运行；这是待验证目标，不是当前性能保证。

<a id="mail-capability-growth-rollback"></a>
### 所有受管升级都必须声明恢复方式

任何拟纳入自动升级的功能，发布清单必须包含：能力 id、当前／基线版本和摘要、接口／数据 schema、依赖版本、权限与用途要求、迁移与回退方法、健康／质量判据、观察窗口、可恢复材料和保留策略。不具备可验证恢复路径的变更不得进入自动发布。稳定版本和恢复材料放在受控发布存储，不在源码树复制旧全文；退役时检查引用、兼容与容量，不能为清理旧代码删掉唯一可用恢复点。

| 层次 | 必须支持的恢复 | 不能许诺的效果 |
|---|---|---|
| 规则、提示词、分类参数和模型选择 | 原子恢复旧修订，刷新派生缓存；保留主人原始纠正 | 回退算法不应删掉升级后新来的邮件、纠正或已核对日程 |
| 新增／修改模块与技能 | 验证最后健康版本与依赖后切回；首次新增则禁用；失败候选隔离 | 不恢复已撤销权限、不加载已知不安全版本；恢复包缺损时安全停用并显示原因 |
| schema／索引 | 首选向前兼容或可重建索引；迁移前保存受保护的恢复材料并实际演练恢复，保留迁移后新增记录的去向 | 不能直接用整库旧备份覆盖当前库，造成新邮件／任务／反馈丢失；不可逆且无保留新数据方案的迁移不自动发布 |
| 多模块依赖 | 按兼容依赖集合恢复并核对活动指针；账本保存切换中断点 | 不保证任意版本组合可用，也不通过放松 schema 检查启动旧程序 |
| 已执行的远端动作 | 代码回退后另查动作回执；支持的标签／垃圾箱操作可按原状态、当前权限和未被后续修改条件补偿 | 已发送邮件、已外发内容和永久删除不能靠回退代码撤销；没有可核对结果时不重复发送或覆盖主人手动修改 |

崩溃、输出契约错误、明确权限违规、关键留出案例失败触发停止候选与恢复；资源／费用或质量退化按发布前冻结的门槛和最小观察证据处理，门槛不能在失败后由候选改低。人工“恢复上一版”同时暂停该候选自动晋升，避免立刻重新升级回来。自动故障回退后隔离同一摘要的坏版本，带回原因再形成有次数／预算限制的修复单；不无限循环。恢复材料损坏、旧版已不兼容或旧版存在已知风险时，停止受影响能力并保留其待办，不拖垮其他无依赖能力。

<a id="mail-capability-growth-validation"></a>
### 邮件成长与回退的专用验收

需新增并通过：分类准确性退化／误杀重要信后的回退；提示词与路由恢复且不扩大数据用途；新功能崩溃后原收件和聊天可用；灰度不产生远端副作用；切换／迁移中进程中断后的恢复；有新增邮件和主人纠正时恢复旧模块仍保留新数据；旧 schema／依赖不兼容的拒绝；损坏恢复包与不安全旧版的停用；手动回退不被自动升级覆盖；发送 UNKNOWN 不重放；失败候选不能污染独立留出集或信任样本。

本节维护完整方案与验收定义。新工程尚未运行邮件插件升级、配置恢复或远端动作测试；每个受管升级必须有适用范围和恢复证据。

<a id="composition-evolution"></a>
## 组合能力的成长、兼容与退役

**proposed，2026-10-22。** 将角色蓝图、Skill、Tool、Runtime 适配器、模型策略和上下文选择器纳入原 E1—E6 与发布控制；不新增另一个“Bot 自升级”控制器。对象定义归[组合契约](contracts.md#composition-contracts)。

| 变更对象 | 关键检查及激活方式 |
|---|---|
| 蓝图/技能/任务图 | 测试触发正反例、依赖组合、输入输出、终止与成本；新任务固定新版本，在途任务保留旧配置 |
| 工具/连接器 | 除契约外测试真实效果、权限、取消、未知结果与补偿；影子模式仅比较计划或只读结果，不双发邮件、订单、桌面操作 |
| 模型/上下文策略 | 在固定资料与预算下比较结果；候选不得扩大供应商或资料用途；留出集与原始来源由独立评估方维护 |
| Agent Runtime / 状态结构 | 测旧检查点、活动任务、失败恢复与往返迁移；不兼容时排空或明确维护窗口，不承诺任意内存热替换 |
| 控制/停止/恢复底座 | 独立维护流程与既有受保护控制规则；业务 Agent 可提交候选，不可直接改门禁、签发权限或清除锁存 |

候选先说明当前缺口、相同任务的基线、预期收益、影响域、依赖与回退；优先组合已有能力，其次更新技能，再开发工具，最后才改变 Runtime/底座。此顺序是降低变更成本的选择原则，不是禁止有证据的结构重构。

组件单测通过还需组合检查：技能要求的参数、工具 schema、运行引擎、模型能力和产物验证必须兼容。激活使用 ReleaseManifest 与原子版本指针；必要的状态迁移提供明确可逆范围或向前恢复方案。回退旧代码不回退主人后来作出的授权撤销、事实纠正、已发送邮件或真实订单。

自动升级仅在已授权的改进域、预算和独立标准内进行。缺少可信验收标准的开放需求先形成可审阅候选；不能让生成者修改标准后宣布成功。成功指标按[组合验收](delivery-validation.md#composition-validation)衡量，不以生成包数、Agent 数或内部自评分当收益。

包引用关系记录在现有注册/发布信息中：运行任务、活动蓝图、回退版本、证据及检查点都可引用旧包。先停用新选择，再排空，确认无活动引用且满足恢复/审计保留要求后才退役或清理；UNKNOWN、原始资料和主人产物不被当作垃圾。架构规则、调试产物和文档污染继续按[健康治理](health-maintenance.md#system-health)检查。

新工程的运行规格、检查点、状态和恢复兼容均需独立实现。未知格式禁止继续执行；新数据不能被旧实现误读；失败恢复不得抹除较新的撤权、纠正或动作回执。

<a id="composition-change-recovery"></a>
### 自我改进改到哪一层，失败后具体恢复什么

本节细化上一节的 proposed 设计。Agent 发现能力缺口后，应先用可观察失败提出改进目标，再选择最小足够变更；“让自己更强”本身不能作为发布依据。完整流程复用[既有成长图](architecture-atlas.md#figure-evolution-pipeline)，角色与运行时只是新增受管对象。

| 发现的问题 | 优先修改对象 | 必须比较的结果 | 失败回退和不能回退的部分 |
|---|---|---|---|
| 现有工具够用，但步骤顺序/角色组合不好 | 蓝图或任务图 | 同输入、同预算下的任务结果、遗漏和多余动作 | 新任务恢复旧配方；在途已完成动作不重新执行，未执行部分重新核验 |
| 方法经常漏检查、讲解不清楚 | Skill 方法/样例 | 正反例、关键检查、引用准确性及方法适用边界 | 恢复旧技能版本；已保存的主人反馈保持，不能为了回退删除失败证据 |
| 缺少可调用的功能或网页接口改变 | Tool/Connector/受限脚本 | 真实效果、输入范围、身份、取消、超时、未知结果和依赖准入 | 回退执行实现；已发信/已改远端标签等按领域补偿，不能靠换代码撤销 |
| 任务使用了过多或错误的资料 | Context selector/检索策略 | 源准确性、撤销、跨域隔离、Token 和质量 | 恢复选择算法；主人新纠正和新撤权继续有效，已外发资料无法技术性追回 |
| 模型选择成本过高或质量不足 | 模型策略/模型适配器 | 同类任务的正确性、费用、时延、外发范围与本地资源 | 恢复策略指针；旧远端调用的账单和未决响应仍记录 |
| 认知循环、等待、恢复逻辑存在通用缺陷 | Agent Runtime | 单步协议、旧检查点、故障注入、前台可用性和组合回归 | 停新准入，兼容时换回旧引擎；不兼容则排空、转换或向前修复，不能强读状态 |
| 数据结构或存储布局需升级 | 领域存储/迁移器 | 备份可读性、计数/摘要、权限材料、往返或向前恢复 | 代码回退不等于数据降级；原数据留存和兼容门先行，失败不能换一个空目录冒充恢复 |
| 调度权、停止或发布门本身需要改造 | 受保护控制/恢复模块 | 原权限规定要求的独立检查、停止优先性与恢复演练 | 保留最小恢复通道；业务 Agent 不可直接修改生效门禁或自行清除锁存 |

首次试用先面对新任务，观察独立完成率、干预、重复动作、资料违规、成本及失败恢复；有效的“改进”也可能是减少调用、减少角色或退回确定性方法。没有足够语义标准的需求形成可审阅候选，不能让同一模型既写答案又把自己的答案作为唯一标准。

退役分“停止选择、停止新任务、在途排空、恢复引用核对、满足保留要求后清理”。每步记录原版本和替代去向；相同技能内容可以合并引用，但保留来源和适用差异。调试脚本是否多余按实际调用、证据和恢复用途判断，不按文件名带 debug 就删除。功能使用率低也不自动表示可以删除控制或恢复能力。

自检负责观察和报告，自愈负责在已知修复策略内恢复，进化负责改变能力及方法。三者可以共享事件和证据，但不能把“自检发现版本旧”自动解释成“允许下载并替换”，也不能把一项普通业务失败升级成整个系统自行关机；控制完整性及 G0 处理仍以安全章为准。

<a id="continuity-upgrade-protocol"></a>
## 核心可换而身份不断：实现替换与连续性验收

**proposed。** 本协议把[连续身份](architecture.md#continuity-definition)纳入原候选、独立验收、灰度、回退与退役流程；它不另建发布系统。可以更换 Personal Core、三职能实现、Agent Runtime、模型、存储及控制实现，但必须证明各自的语义和状态兼容。

![保持连续身份的核心升级、灰度与回退](diagrams/continuity-upgrade.png)

[SVG 放大](diagrams/continuity-upgrade.svg) · [唯一图源](diagrams/continuity-upgrade.mmd)。影子阶段仅重放资料和观察，不再产生外部动作；旧实现保留到排空与回退条件满足。

1. **明确变化对象与收益。** 从真实缺口提出改进，记录基线、影响范围、资源/费用和成功判据；新模型发布不自动触发全系统替换。
2. **创建隔离候选。** 保持原领域接口和数据所有者；生成实现、适配器或迁移器，继承原准入规则。候选不持有发布权或根凭据。
3. **核验兼容与连续性。** 比较身份继承、有效规则、记忆纠正/遗忘、承诺、任务回执、未知效果、模型资料用途及导入/导出结果；语法和 schema 通过只是部分证据。
4. **只读影子与新任务灰度。** 影子使用获准样本，不执行邮件发送/文件改写等副作用；新旧对比相同任务、模型用途和总预算。确定哪些新任务试用，不把运行中任务的实现悄悄替换。
5. **排空或检查点交接。** 暂停受影响入口的新受理，在安全边界固定水位并追赶增量；原维护路径切换有效运行代际。无法证明状态兼容时先排空，或明确进入局部维护窗口；旁路聊天是否可持续要实测。
6. **确认收益或回退。** 新实现接管后继续观察正确性、体验、延迟、资源与费用。回退实现时保留较新的事实、纠正、撤权、停止状态及动作回执；旧实现不认识新数据时须经过验证的反向迁移，否则进入恢复，不能强行加载旧备份。
7. **按引用退役。** 没有在途、回退或证据引用且符合保留策略后退役旧包；资料正文按其删除要求处理，不能为了退役方便删掉身份连续性映射或未决动作记录。

| 可替换对象 | 需要额外证明什么 | 不能承诺的地方 |
|---|---|---|
| 模型/提示/角色配方 | 原用途可接受、结果质量非劣、记忆与承诺场景保持、费用和工具能力明确 | 同一身份不保证新模型语气和判断完全相同；更大模型不必更适合全部任务 |
| Agent Runtime / Personal Core | 状态导出与取消可用，任务/动作编号和所有权保持，资料不跨域，原恢复入口可用 | 私有 KV 缓存及供应商隐藏状态不能假定可迁移 |
| 数据库/索引/知识结构 | 原事实、来源、删除、撤权、迁移映射及增量水位完整 | 只有备份不能证明新写入可向旧格式无损回退 |
| 控制/监督/策略实现 | 仍可信的现行路径独立核验，原控制语义不弱化，切换期间不存在无人守门的动作入口 | 原生代码、OS/驱动和控制核心升级可能需要维护窗口，不保证单机零停机 |

若所有数据和有效备份同时丢失，不能保证恢复全部经历；若所有可用实现都不兼容，不能保证无中断运行；未知未来技术也不能保证无需新适配。架构提高的是可迁移、可测量和可回退性，不是“永远领先”的证明。检验是否成长，仍按原[收益评估方法](delivery-validation.md#composition-benefit-experiment)，不能用版本号增大或 Agent 数增多替代。

<a id="autonomous-evolution-policy"></a>
### 自主追踪前沿、选择改进并采用有效结果

**持续成长是 accepted 的产品目标；下列通用策略仍 proposed。** Jarvis 应具备自己的改进闭环，外部 Codex/其他研发 Agent 只是可替换的候选生成能力，不是每次进化的必要指挥者。已有 K3—K5 的领域实现继续有效；本节使其与[主动目标循环](tasks-agents.md#proactive-goal-cycle)、SelfModel 和原发布器相连，不增加一条自动发布旁路。

| 步骤 | 自动判断及产物 | 不应做的事 |
|---|---|---|
| 发现值得改的地方 | 从重复失败、主人纠正、人工负担、性能下降、依赖停服/安全更新、已授权技术观察产生改进机会 | 为提高更新次数制造问题，或只因新闻热度重构全部核心 |
| 有界获取新知识 | 优先读取适用版本的官方资料与来源，再核对研究和复现实验；缓存、去重并登记新鲜度 | 盲目下载运行网页脚本，或把网上指令当作维护授权 |
| 比较可行替代 | 比较保持现状、修复旧实现、调整策略、换部件、编写新实现；记录获益对象、成本和不确定性 | 默认更大模型/更复杂 Agent 团队一定更好；不计迁移与维护费用 |
| 生成与实验 | 在独立候选环境组合技能、编写程序或适配新库；使用获准样本和固定基线 | 暗中改生产数据、权限、测试答案、留出集或发布判据 |
| 独立核验 | 对质量、连续性、兼容、隐私、资源和恢复做相应测试；必要时独立模型审阅只是证据之一 | 让同一生成者的自评分成为唯一放行依据，或把没有结果当作通过 |
| 按策略采用 | 现行维护策略覆盖该变更且证据满足时，自动进行原影子/灰度/观察流程；否则提交具体缺失条件 | 每次小修复都等待主人手工批准，或越过真实缺失的权限自动上线 |
| 观察、恢复、积累 | 真实收益不足或触发退化阈值时停止扩大、回退或局部维护；保留失败反例并按引用退役 | 隐藏退化、不断更换版本重试同一失败，或回退掉新的事实与撤权 |

采用策略通过[ImprovementPolicy](contracts.md#goal-opportunity-contract)表达：主人一次设定可自动维护的能力范围、预算及发布条件，之后适用的更新自行推进。原安全章规定的身份、根策略、权限扩大等变更继续走其独立控制入口；此处不放宽。没有可信判据的开放业务需求不能靠增加评委 Agent 获得确定性，先做可撤销的小范围试验，或取得必要的人类结果判断。

“最近/最新”拆成三个独立状态：**已发现、已试验、已采用**。一个新方法可以已经研究却暂不采用；也可以因成本或兼容性等待。记录未采用的原因、复查条件和适用场景，避免遗忘前沿或盲目追新。严重缺陷、支持终止和已证明的不适用性可以让旧方案失去继续使用资格；保留原方案不是无限期拖延修复的理由。

技术观察以来源更新、故障和已授权检查期限为触发；发现/检索可先用低成本规则，复杂分析才调用模型。不设所有模块共用的固定高频 LLM 心跳。每日探索额度、候选数量、实验时间、下载/磁盘限额和前台资源预留均由现行策略限定，离线时优先使用已验证本地资料与工具，无法核实新事实就标记时效缺口。

自主能力也有反馈：记录哪些更新减少主人干预、提高真实完成率、降低费用，哪些产生回退或新故障。根据证据调整普通选择策略；不能自行降低根约束和放行门槛。“一直可以进化”意味着保留发现、实验、替换和恢复的通路，不承诺每轮必然变好、所有未来技术都能兼容或资源永远足够。

<a id="growth-release-runtime"></a>
## 当前能力包发布、灰度与恢复实现

**0.2.0-dev.2 implemented；完整的是当前无状态纯文本能力包的生命周期，不是任意核心/数据库版本的通用热替换。** 代码位于 `modules/release_recovery/packages.py`；操作入口归[核心运行](core-bootstrap.md#growth-seed-control)。

| 阶段 | 持久事实与转换 | 中断/失败后 |
|---|---|---|
| CANDIDATE | 包内容摘要绑定代码、能力、配方、state_schema=0 与验收规格摘要 | 未准入的包不能绑定任务；文件存在不等于已安装 |
| VERIFIED / REJECTED | 宿主比较实际输出与冻结公开/独立用例，保存 Worker 和用例证据 | 不通过不改现役指针；研发预算允许时另生候选 |
| PREPARED | 保存目标、原指针、预期修订与操作编号，重新运行放行探针 | 宿主死亡后归 ABORTED，现役指针保持原样 |
| COMMITTED / CANARY | 在同一数据库事务中切换 active/previous、递增修订并确认操作 | 事务后死亡保留新指针，不凭进程退出猜测回滚 |
| 观察 / STABLE | 灰度调用先跑冻结回归，再执行实际输入；连续记录成功，达到 2 次后转 STABLE | 2 次仅为最小观察窗，不代表长期可靠性或业务收益已充分证明 |
| 回退/停用 | 执行故障或现役摘要损坏时，检查上一包后恢复；无可用恢复包则停用该能力 | 不换 task/action 编号重做未知动作；无关任务仍可运行 |
| RETIRED | 不再允许绑定或执行，文件作为恢复/审计材料暂留 | active、previous、未终结任务和 UNKNOWN 动作仍引用的包不得退役 |

发布及恢复只改变代码指针与包状态，不回滚身份、事实纠正、已撤权许可、调用预算或已发生动作。包只能在原 principal/scope 内使用；同一能力名不能通过另一资料域的候选覆盖。任务在受理时固定包版本，后续默认版本变化不暗改在途任务；已被拒绝、退役或停用的版本不能继续取得执行资格。

Worker 宿主死亡时由 kill-on-close Job 终止执行；租约记录只包含本工程生成的 profile/SID/stage 标识，下次在执行锁内撤去临时 ACL、删除孤儿 profile 和暂存目录。对恢复编号/路径做严格校验，不扫描或清理用户原始目录。包、回执和身份不属于暂存清理目标。

控制库由 v1 增量事务迁至 v2，只新增研发/模型调用/包/发布表，保留原表数据；新表 schema 不是可任意降级的数据格式。本版不提供整库历史回灌或旧宿主对 v2 的兼容保证。任意核心替换、有状态迁移、双运行器交接、签名发布、操作系统崩溃/断电恢复和自动旧包物理删除仍需独立实现与验收，不能把当前能力包回退当成这些项目完成。

实际收益现在可观察为：原目标是否交付、生成/修复次数、调用 token、Worker 延迟/峰值内存、失败/回退记录。自动选择更有收益的版本、长期 A/B 评估及主动发现任务尚未运行；不会因模型说“更好”而自动替换稳定能力。
